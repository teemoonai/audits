# teemoonai/teemoon-android @ v1.1.1-3919 (be4111ea46b808934e91245b3bfb6fdab58d3d77) — 1.1.1 (3919)

## verdict: QUALIFIED-PASS — no way was found for the app to pass a key or a message to anyone but the chosen provider without the user's action; the two medium-severity issues of 1.1.0 are addressed in the source (a made-up hardware proof is now rejected on the phone, and every enclave near.ai lists is checked before a sealed send); one of them stays open in a narrower form that only near.ai can close (an enclave near.ai does not list can still hold the key); one low-severity wording issue is open and accepted by the maintainer; this is a reading of the source code only: the tests, a run of the app and the check of the public tag were not part of it when it was written

## Summary

**What was checked.** The source code of teemoon for Android 1.1.1 (3919), at the version named in the title. Everything that changed in the app since 1.1.0 was read: 39 files. An earlier build of 1.1.1 was withdrawn before release; the changes made after it (four source files) were read line by line, and everything else was confirmed to be byte for byte the code already reviewed. The whole app was searched again for every place where an API key or a message could be written to storage, a log or the clipboard, or sent over the network. Each issue recorded against 1.1.0 was looked up again in the new code.

**What was found.** No way was found for the app to pass your API keys or your messages to anyone except the provider you chose, unless you take an action such as sending, sharing or copying. Of the two medium-severity issues found after 1.1.0, one is fixed in the source: a made-up hardware proof no longer passes the check on the phone. The other is fixed for every enclave near.ai lists and stays open for enclaves near.ai does not list, which the app has no way to see. The low-severity issue of 1.1.0 is fixed: a near.ai model you have used end-to-end encrypted now asks before its first message without encryption. One low-severity issue is open: four lines on the trust screen say near.ai's gateway does not have the key, which the app does not check (the maintainer accepted this wording). Two problems of the withdrawn build are fixed in this one: the screen no longer says the app "checked every enclave near.ai listed" when it could not compare the files one of them runs (it now says it couldn't finish; the send still does not ask, minor note 15), and a fault that made every later check of a near.ai model fail until the app was restarted is gone. There are fifteen minor notes; nine of them carry over from 1.1.0, where they were eleven.

The review of the withdrawn build was begun by one AI model and completed by another; the second brought it up to the released code. Both are named in the identity table below.

**What was not checked.** This page was written from the source code alone. The app's tests were not run by this review, the app was not run on a phone or an emulator, and the published app file was not compared with the source; those results are added to this page separately when they exist. Whether the public tag points at this code had not been checked when this was written. The inside of the bundled image-decoding library and of the bundled Intel-proof library was not read. The Google Play edition contains one Google library (the rating prompt) that was not reviewed.

### Is my data safe?

This review found no path by which the app itself gives your keys or your messages to anyone but the provider you choose. It is teemoon's own AI-assisted review, not an audit by an outside firm, and it cannot tell you what a provider does with a message after it arrives; only near.ai models that run in attested secure enclaves are end-to-end encrypted, and for those the app now checks every enclave near.ai lists, not every enclave that may hold the key (see the first finding).

## What was found, in plain terms

### The one to know about: an enclave near.ai does not list can still hold the key (medium severity, narrowed since 1.1.0)

- **What can happen.** near.ai runs each model on more than one secure enclave, and they share one encryption key. near.ai's key service decides which enclaves get that key. Before a sealed send, the app now asks near.ai for the list of enclaves for the model and checks each one: the hardware proof with Intel, the graphics-chip proof with NVIDIA, that the key is in the proof, and the enclave's start-up and deployment records. An enclave that near.ai's key service gives the key to, but that near.ai does not put on the list, can open your message too, and the app cannot see it. For the listed enclaves, the check does not include one thing the app does for the enclave it talks to: tracing each program image to near.ai's published builds.
- **When.** Every message to an end-to-end encrypted near.ai model. On 2026-11-20 near.ai's list for one model changed several times in a day (three enclaves, then a different three, then four). The app checks the list it got when it last verified, at most ten minutes before a send.
- **Does it affect you?** Only if you use near.ai models. Your message still goes only to near.ai and is still sealed to a key that sits in checked hardware. What you rely on near.ai for: that every holder of the key is on the list. The trust screen now says this in its own words ("near.ai's key service decides which secure enclaves get that key").
- **Planned fix.** None scheduled in the app: the app cannot close this. near.ai would have to publish what its key service admits, or give each enclave its own key. For the listed enclaves, tracing their images is proposed by this review.

### Fixed: a made-up hardware proof no longer passes the check on the phone (was medium severity in 1.1.0)

- **What could happen in 1.1.0.** When Intel's servers could not be reached, the check on the phone accepted a proof signed with a made-up key, behind a "still checking" question.
- **Now.** The check on the phone confirms that the key which signed the proof was vouched for by Intel's own quoting enclave, on a machine Intel certified. A made-up proof is rejected and the send is blocked, whether or not Intel's servers answer.
- **Does it affect you?** If you see "still checking near.ai's hardware", the app could not reach Intel's or NVIDIA's servers. The check on the phone still cannot tell whether Intel has since withdrawn its trust in a machine; only the answer from Intel's servers can. Waiting and trying again remains the careful choice for something sensitive.
- **Planned fix.** Done in this version. A test run with a made-up proof is being added to this page.

### Fixed: a near.ai model that stops being end-to-end encrypted now asks first (was low severity in 1.1.0)

- **What could happen in 1.1.0.** A near.ai model you had used end-to-end encrypted could change to "proxied", and later messages went out over an ordinary encrypted connection with a changed label and no question.
- **Now.** The app remembers which near.ai models it has sent a sealed message to. If one of them is no longer end-to-end encrypted, the next send shows "<model> isn't end-to-end encrypted anymore" and sends only if you choose "send without encryption". An earlier "send anyway" does not answer it.
- **Does it affect you?** One limit: the memory starts empty when you update. A model you used sealed only before the update asks after you have sent it one sealed message on 1.1.1 (minor note 1).
- **Planned fix.** Done in this version. Extra protection for the stored list is planned for version 1.1.2.

### Four lines say near.ai's gateway does not have the key; the app does not check that (low severity, accepted)

- **What can happen.** The trust screen says the network and near.ai's gateway "don't have" or "don't hold" the key. The app checks that the key is in the hardware proof of each listed enclave. It has no check of what near.ai's gateway holds.
- **When.** Whenever the trust screen shows the sealed step for a near.ai model.
- **Does it affect you?** It is a statement the app cannot back with evidence. Nothing about what the app sends changes.
- **Planned fix.** None scheduled. The maintainer accepted this wording on 2026-11-20.

### Traced — 1. The on-device quote check (the forged-quote finding of 2026-11-20)

All of it is `C/TdxQuote.kt`. Every caller in shipping code wraps `TdxQuoteVerifier.verify` in `runCatching` and reads a throw as "no verified quote" (`C/AttestationService.kt:285`, `:423`, `:479`; `C/ModelCandidates.kt:56`; `C/DcapService.kt:120`), so a parser exception is never a pass.

**Parser (`QuoteParser.parseSignatureData`, `:95-127`).**

| Step | Line | What is checked | What a hostile blob gets |
|---|---|---|---|
| signature section length | `:96-98` | 4 length bytes present; `sigDataSize >= 128`; the section fits the data | a negative size (high bit set) fails `< 128`; a size near 2^31 overflows the `Int` sum at `:98` and passes it, then `copyOfRange` at `:99-102` throws an unchecked exception, which every caller reads as not verified |
| outer certification data | `:105-106` | at least 6 bytes; type and size read little-endian | fewer bytes: no QE report, no chain. A size with the high bit set is negative after `toInt()` (`:106`), so `start + outerSize <= remaining.size` holds (`:107`, `:109`) and `copyOfRange` gets an end before its start and throws: not verified |
| outer type 5 (a bare certificate chain) | `:107-108` | size fits | the chain is read, `qeReport` stays null, so `attestationKeyIsBoundToChain` returns false at `:175`: not verified |
| outer type 6 | `:109-122` | size fits; QE report = bytes 0..383, its signature = 384..447 (`:115`); auth size is a u16 at 448 and must fit (`:113-114`) | an auth size that does not fit leaves all three null: not verified. The nested block's type is skipped unread (`:119`); a negative nested size makes `copyOfRange` throw: not verified |
| fallback | `:125` | if no certificate was found, the whole remainder is scanned for PEM blocks | certificates may be found, but the QE fields are still null: not verified |

**Verifier (`TdxQuoteVerifier.verify`, `:154-163`).** `isVerified` is `signatureValid && certChainValid` (`C/TdxVerificationResult.kt:40`). `signatureValid` is now the body signature under the quote's attestation key AND the new binding (`:157-160`).

`attestationKeyIsBoundToChain` (`:174-184`), compare by compare:

| Compare | Line | Bytes |
|---|---|---|
| a QE report, its signature and auth data exist | `:175-177` | null on any: false |
| the leaf key is P-256 | `:178`, `:209-215` | the first certificate of the chain; its curve order must equal P-256's (`:211`); any other key, or an unreadable certificate, is null: false |
| the QE report is signed by that leaf key | `:179`, `:218-226` | ECDSA P-256 over SHA-256 of the 384 report bytes; r and s 32 bytes each, big-endian; wrong sizes false (`:219`); any exception false (`:225`) |
| the QE report is Intel's TD Quoting Enclave's | `:180`, `:200-206` | below |
| report_data binds the attestation key | `:181-183` | report bytes 320..383; the first 32 must equal `sha256(attestation key (64 bytes) || QE auth data)`; the last 32 must all be zero |

`reportIsIntelsTdQuotingEnclave` (`:200-206`): MRSIGNER is bytes 128..159, compared whole with the pinned 32 bytes (`:202`, constant `:192`); ISVPRODID is bytes 256..257 read little-endian, must be 2 (`:203`, `:193`); MISCSELECT is bytes 16..19 under mask `FFFFFFFF`, must be zero (`:204`, `:194-195`); attributes are bytes 48..63 under mask `FB FF FF FF FF FF FF FF 00..00`, must be `11 00..00` (`:205`, `:196-197`). The masked compares work on sign-extended bytes on both sides (`.toInt()` of the report byte AND `.toInt()` of the mask byte, against `.toInt()` of the expected byte), which equals an unsigned byte compare for every value: a report byte with its high bit set under an `FF` mask stays negative and never equals `0x11` or `0`. The debug attribute (bit `0x02` of byte 48) is inside the mask and must be clear. The four pinned values equal the `TD_QE` entry of Intel's signed QE identity in the tree's conformance data (`conformance/vendor/collateral.json`, `vectors.assembledCollateralFields.qe_identity`: mrsigner `DC9E2A7C...A8C5`, isvprodid 2, miscselect `00000000` / `FFFFFFFF`, attributes `1100...` / `FBFFFFFFFFFFFFFF0000000000000000`; read and compared by this review). The comment at `:187` names the file as `conformance/collateral.json`; the file is under `conformance/vendor/`.

**Which certificate's key verifies the QE report.** `verifyCertificateChain` (`:229-241`) builds a certification path from the quote's certificates in order, minus any copy of Intel's root (same subject and same key, `:236`), and validates it with PKIX against the pinned Intel SGX Root CA only (`:237-238`), revocation off. The path's first certificate is the one being validated. The QE report is checked under the key of the chain's first certificate (`:178`). The two are the same certificate unless the first one is a copy of the root: then the QE report would have to be signed by Intel's root key. A chain whose first certificate the path does not validate fails `certChainValid`. So a QE report signature is accepted only under a key that Intel's root certifies. The identity pin is what stops a self-made enclave on a genuine machine from vouching for a key: any enclave can obtain a report signed under a genuine machine's PCK key; only Intel's signer and product id pass `:202-203`.

**The injectable `isTdQe` parameter (`:174`).** It defaults to the real check. No shipping code names the function or the parameter (grep `attestationKeyIsBoundToChain|isTdQe|reportIsIntelsTdQuotingEnclave` over `*/src/main`: `TdxQuote.kt` only). It is `internal`: only the `confidential` module and its tests can pass another.

**What the on-device check still does not check.** The QE's ISVSVN (bytes 258..259) and CPUSVN; Intel's TCB status for the platform; revocation of the PCK certificate or of the platform CA; the PCK certificate's own SGX extensions; the freshness of the pinned QE identity (a constant: if Intel rotates the TD QE signing key the check fails closed until the app is updated, as the comment at `:189-190` says); the header's attestation key type (`isEcdsa256`, `:39`, has no caller; the verify is P-256 only, so another type fails). These are what the Intel DCAP pass adds (`C/DcapService.kt`).

**What the gate does when Intel cannot be reached now.** Unreachable or unreadable collateral is `Unchecked` (`C/DcapService.kt:52-55`, `:74-87`): soft. `couldntCheckHardware` (`C/ConfidentialSession.kt:1504-1506`) turns the state to degraded (`:1266`), `degradeIsHardFailure` stays false, and the send asks "still checking near.ai's hardware" (`A/SendChoices.kt:46-47`, `:104-105`). What stands behind that ask is now a quote whose attestation key Intel's TD Quoting Enclave vouched for, on a platform whose PCK certificate chains to Intel's root. A quote with a made-up attestation key fails at `:160` for the read enclave (`modelQuoteVerification.isVerified` false: hard, `C/ConfidentialSession.kt:1287`, `:1480`) and for each listed enclave (`QUOTE_INVALID`, `C/ModelCandidates.kt:56`: hard through `candidatesBroken`, `:1255`, `:1467`). A key with no readable quote is hard (`:1479`). A compose-manager quote is never verified on the device; with Intel unreachable its log is `Unchecked`, not bound (`C/NearTrustScope.kt:156`, `:225`). What an attacker still needs for the "still checking" ask to cover a key they hold, with Intel unreachable: a genuine Intel platform whose PCK key or TD Quoting Enclave is compromised or revoked (the local check cannot see TCB status or revocation), or a genuine TDX machine of their own (Residuals: hardware proof is not software proof).

The orchestrator, 2026-11-24: not run as an experiment on the built app. The unit tests that take a forged quote through the send gate (`ForgedQuoteTest`, `ForgedSiblingQuoteTest`, `SendGateRuleTest`) go red when the report_data binding is removed (mutant M02 under Mutation checks), so the case is pinned by tests.

## Addendum 2026-11-25 — the read enclave's missing boot log

### LOW (deployed: ARMED, needs near.ai to serve the read enclave's report with no boot log) — gate: the read enclave's missing boot log neither asks nor blocks, and the read enclave need not be on near.ai's list

(`C/TrustScopeText.kt:37`, `:82`; `A/TrustLadderViews.kt:513`).

- **What the missing boot log costs.** The RTMR3 replay ties the compose-hash event, and the os-image-hash event when the log carries it, to the quote (`C/NearDeployBinding.kt:145-152`). Without it:

  - the key-provider and mr-kms events of the read enclave are not tied either; the app uses them only in the listed key-service compare.
