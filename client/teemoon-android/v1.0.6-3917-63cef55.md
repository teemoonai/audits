# teemoon Android client (1.0.6, dev build 3917) — Key and Plaintext Exfiltration Audit (delta from `328d0d4`, full read of `confidential/`)

> Client side of the teemoon plaintext question. Lineage: [`../README.md`](../README.md)
> · Map: [`../ARCHITECTURE.md`](../ARCHITECTURE.md) · Surface: [`../audit-surface.md`](../audit-surface.md)
> · Base: `dev-328d0d4.md` (3916, Google Play 1.0.5, public [`v1.0.5-3916-34e5566.md`](v1.0.5-3916-34e5566.md)) · Its bases: `dev-5c8cfa6.md`, `dev-01901e6.md`, `dev-1ccca1c.md`, `v1.0.4-3910-f869b01.md`

**Question.** Can a provider key reach anywhere but its storage and its own
provider? Can prompt or reply text reach a log, an unprotected file, the
clipboard, a notification, another app, or a network destination other than
the send path the user chose? For each, does any path need no user action or
run on adversary-controlled content? The model and the provider are assumed
hostile; the device axis only.

**Where plaintext exists at this commit (structural, not findings):** the
composer and `ChatViewModel`; the Room store `teemoon-chat.db` and its FTS
sidecar `chat-search-index.sqlite` (both with their `-wal`/`-shm`); the
transports until they seal (near.ai attested) or by definition (every other
provider); the in-process LiteRT-LM runtime and — new at 1.0.6 — the kept
`Conversation` and its `KeptConversation` transcript copy on the heap; the
transcript renderer; the in-memory debug and error records; the system
prompt in SharedPreferences.

## Audit prompt

The portable prompt in [`method.md` §3](../method.md#3-the-portable-audit-prompt)
with its delta form, and the Android surface translation
(`tools/client-context-android.txt`), applied as the brief for this cut
directs: ten numbered priority items (keys; send path and egress;
`confidential/` in full against the SDK comparison; at rest; renderers;
logs; clipboard; entry points; carried claims; the disclosures the user
asked the page to carry). Every surface is touched by this range, so each
of the ten gets an explicit answer below. Three paths are **no-user-action**
paths and are traced as such: the launch-time NVIDIA retirement heal
(`ProviderHealing.kt`), the first-send Ollama probe (`FirstSendKindProbe.kt`,
runs inside a send the user started but makes a request the user did not
aim), and the post-turn reply-signature check that now outlives the turn
(`GenerationEngine.kt:367-372`). One path is driven by **adversary content**:
the 400 effort retry reads the provider's error body (`OpenAiTransport.kt:187-188`).

  never lets a send out on an unverified model quote or a hard DCAP
  failure (`ConfidentialSession.kt:848`, `:823`, BLOCK via `:957`,
  `:986-987`; `DcapService` verifies `gpuIntelQuote` and `modelIntelQuote`,
  `DcapService.kt:72-78`), so the verdict can mis-label a reply only in a
  session that already failed closed before the send. The SDK's rule the
  comparison asks for — "ed25519 only against the quote-bound key" — is
  met for the binding; the quote's own validity is enforced one layer up.
- **Fix shape:** `AttestationRecord.kt:122` and `:136` → return `false`
  unless the verification `isVerified`; or `TeeSignature.kt:207` and
  `:194` → add the `isVerified` condition.
- **Pin:** none — `SignatureVerdictTest.record()` always builds a valid
  stub (`AttestationFixtures.verification`). A `PROVIDER_TEE` ecdsa
  signature with `gpuQuoteVerification.signatureValid = false` must not be
  `Verified`; at `add2a08` it is.
