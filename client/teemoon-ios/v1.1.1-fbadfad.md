## What was found, in plain terms

### The one to know about: an enclave that holds the key but is not on near.ai's list is not checked (medium severity, open)

- **What can happen.** near.ai runs each model on several secure enclaves, and they share one encryption key. near.ai's key service decides which enclaves get that key. Since this version the app asks near.ai for the list of enclaves and checks each one before it sends. An enclave that has the key but is not on the list is not checked, and it could open your message too. The app also does not trace the software of the listed enclaves to published source code the way it does for the first one; it only shows whether teemoon's reviews cover them.
- **When.** Every message to an end-to-end encrypted near.ai model. On 2026-11-20 near.ai's list for one model changed four times in a day: enclaves joined and left, and one machine with the same key served another model while it was not on the list. Two days later the list had changed again.
- **Does it affect you?** Only if you use near.ai models. Your message still goes only to near.ai and is still sealed. The trust screen now says this plainly: near.ai's key service decides which secure enclaves hold the key, and teemoon says whether it checked every enclave near.ai listed.
- **Planned fix.** None in the app; the app cannot check the key service. It is listed as a known issue in the release notes. near.ai would have to publish how its key service decides, or give each enclave its own key.

### Fixed: a made-up hardware proof is now rejected on the iPhone (medium severity in 1.1.0)

In 1.1.0 the check on the iPhone did not confirm that the key which signed the hardware proof belongs to Intel's hardware. It now does, so a made-up proof blocks the send whether or not Intel's servers answer. What the check on the iPhone still leaves to Intel's servers: whether that hardware is up to date and whether Intel has withdrawn it. If Intel's servers cannot be reached the app still asks before sending.

### Fixed: the app asks before a near.ai model stops being end-to-end encrypted (low severity in 1.1.0)

A near.ai model that you have sent sealed messages to now gets a question before the first message that would go out without end-to-end encryption. Only that question's own "send without encryption" answers it: a tap on a different question no longer counts. Shortcuts refuses instead of asking.

### Fixed: an encryption key with no proof behind it now blocks the send (low severity in 1.1.0)

In 1.1.0 this state asked "still checking" and offered "send anyway". It now blocks.

### Fixed before release: three problems in the earlier build of 1.1.1

- A tap on one send question could be counted as your answer to the question about a model that stopped being end-to-end encrypted. Now a tap only answers the question it was shown with.
- The trust screen could say "teemoon checked every enclave near.ai listed" while some of the software files of a listed enclave had not been compared. It now says the check could not be finished.
- Two descriptions of near.ai said the operator or host "can't read" your chats. They were reworded.

### Four lines say near.ai's gateway does not have the key, and the app does not check that (low severity, accepted)

- **What can happen.** The trust screen says the network and near.ai's gateway do not have, or do not hold, the key. The app checks that the key is in the hardware proof of the enclaves near.ai lists. It has no way to check where else near.ai's key service has sent the key.
- **When.** Whenever the trust screen is shown for an end-to-end encrypted near.ai model.
- **Does it affect you?** Only in how much you read into that sentence. Nothing is sent differently.
- **Planned fix.** None. The maintainer accepted this wording on 2026-11-20.

### Your custom system prompt is stored outside the protected chat store (low severity, known since 1.0.6)

- **What can happen.** If you edit the system prompt in settings, its text is kept in the app's ordinary settings storage, which device backups include.
- **When.** Always, if you have edited the system prompt.
- **Does it affect you?** Only if you put something private in the system prompt.
- **Planned fix.** Planned for version 1.1.2.

### Verdict

**QUALIFIED-PASS**, by source alone.

What was read supports these statements at this commit:

1. **Keys.** One key-bearing request is new since 1.1.0, the enclave list, and it goes to the near.ai gateway that already received that key, on the ephemeral session, with a size cap, a time cap and cancellation. ### LOW (deployed: ARMED, needs near.ai to serve the read enclave's report with no boot log) — gate: the read enclave's missing boot log neither asks nor blocks, and the read enclave need not be on near.ai's list

- **State.** The read enclave's trust scope (the GPU node's report, `Confidential/ConfidentialSession+Verifiers.swift:206-216`) has `boot == .absent`: no `event_log`, or no compose-hash event in it (`Confidential/ActionLogBinding.swift:148-150`), or no readable node quote (`Confidential/TrustScope.swift:139`). The one trace on screen is a caution line in the trust sheet, "boot event log missing: the compose file matches its hash, but that hash isn't tied to the quote." (`Confidential/TrustScopeText.swift:34`, `:129`).
- **The listed path covers this only while near.ai lists the read enclave.** A listed enclave with no boot log asks (`listedEvidenceAbsent`, `Confidential/TrustScope.swift:55`; `Confidential/ConfidentialSession+Verdict.swift:25`, `:180`, `:304`).   - the key-provider and mr-kms events of the read enclave are not tied either; the app uses them only in the listed key-service compare.
