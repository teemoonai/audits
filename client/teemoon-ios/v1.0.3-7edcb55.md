# teemoon iPhone client (1.0.3) — Plaintext and Key Exfiltration Audit (delta from `21d534e`)

> Client side of the teemoon plaintext question. Lineage: [`../README.md`](../README.md)
> · Map: [`../ARCHITECTURE.md`](../ARCHITECTURE.md) · Surface: [`../audit-surface.md`](../audit-surface.md)

This is the hotfix release for the one deployed finding in the client's
history: at every release from 1.0 to 1.0.2 the near.ai API key was archived
in cleartext in the shared URL cache on disk, found on 2026-09-10 by running
1.0.2. The page asks one question of the fix — does the key now stay in the
Keychain and nowhere else on disk — and re-checks that nothing else moved.

## Audit prompt

The portable prompt in [`method.md` §3](../method.md#3-the-portable-audit-prompt),
in its delta form, with:

```text

PREVIOUS teemoon-ios  tag v1.0.2  @ 21d534e6e6f70e750f5654e4b27ffc41592c4101

           ':(exclude)*.png' ':(exclude)*.xcassets*'        (150 lines, 4 files)
```

plus five questions the release has to answer: whether the fix runs before any
session exists, whether it empties the store the 1.0.2 pass read the key from,
whether any session bypasses it, whether the purge covers key removal and
replacement, and whether the LOW still holds. Two reviewers ran it in parallel
on the same checkout, each told to write a skeleton report before verifying
anything. Both returned `qualified-pass`, no new finding, the MEDIUM fixed in
source, and the same belt gap on two key-deletion paths (under *residuals*).
The runtime pass, run afterwards, is what settles the parts the source cannot.

### Traced — keys, from the Keychain to the disk the fix takes away

**Where the key went before.** Nine of the twelve authenticated request sites
ride `URLSession.shared` (through `URLSessionHTTP`, `Inference/HTTPClient.swift:19`),
whose configuration takes `URLCache.shared` — by default a disk-backed cache at
`Library/Caches/ai.teemoon.app/Cache.db` — and CFNetwork archives each cacheable
response with the request that produced it, `Authorization` header included.
The 1.0.2 page has the full account.

**What the fix does, and whether it can be too late.** The whole question is
ordering: `URLSessionConfiguration.default` captures `URLCache.shared` when it
is created and `URLSession.shared` is created on first access, so the swap must
land before either. What runs before `teemoonApp.swift:41`, in order:

- *Stored-property initializers of the `App` struct* (Swift runs these before
  the init body). `:18` `@UIApplicationDelegateAdaptor(BackgroundDownloadDelegate.self)`
  constructs an `NSObject` with no stored properties and no `init`
  (`:682-694`); its one method is UIKit's background-download relaunch
  callback, delivered after launch. `:24` `@State downloadCenter = OllamaDownloadCenter()`
  is eager (`@State`, not `@StateObject`), and the class initialises an empty
  array and an empty dictionary (`Providers/OllamaDownloadCenter.swift:33-34`);
  its network use is inside `run(ref:)`, reached only from a user's `start`.
  `:122-217` `let sharedModelContainer` is an eager instance closure — the
  comment at `:208` calling it a lazy `static let` is stale — and it builds a
  SwiftData container, hardens the store (`:205` → `:264-277`) and logs on
  failure; no `URLSession`, no `URLCache`, and no CloudKit entitlement that
  could spin up a sync client. `:20-23` have no initial value; they are
  assigned at `:116-119`, after the fix.
- *Globals and statics.* No `main.swift`, no ObjC `+load`, no
  `__attribute__((constructor))` in `teemoon/`, `Packages/*/Sources` or
  `Vendor/textual/Sources`; `Packages/` contains no `URLSession` at all. The
  only lazy statics near networking are the background-download sessions
  (`Providers/LocalModelDownloadSession.swift:37-38`, `.background`
  configurations, first touched from `teemoonApp.swift:93-94` — after the fix
  — and carrying no header) and textual's `ImageLoader.shared`, whose
  `.default` configuration (`Vendor/textual/Sources/Textual/Internal/Image/ImageLoader.swift:78`)
  is the only `.default` in the tree, is built on first use, and is never
  reached from a reply because the app installs `NoRemoteAttachmentLoader` at
  both transcript roots (`Views/Chat/ConversationView.swift:141`, `:805`).
- *Alternate entries.* The Siri intent runs in the app process
  (`App/RequestLLMIntent.swift:135`, `openAppWhenRun = false`), which SwiftUI
  starts by constructing `TeemoonApp` — the init, and so the fix, precedes any
  intent delivery. The UI-test host path is `#if DEBUG` end to end.

The first `URLSession.shared` access in the process is `teemoonApp.swift:68`
(`ConfidentialSession(providers:)` → default arguments
`Confidential/ConfidentialSession.swift:155`, `:157` → `ProvenanceService.swift:50`,
`NRASService.swift:62`), twenty-seven lines after the swap. The other two

**In source, the fix runs first.** What only a running process can show —
that no Apple framework the app links creates a default session before

**The store it empties is the right one.** `Support/SharedURLCache.swift:29`

### Runtime pass (method §4b) — 2026-09-11

The tag was built from source (`xcodebuild build-for-testing`, Xcode 26.6,
iOS 26.5 simulator — a simulator created for this pass and used for nothing
else) and measured in three states, because a hotfix has two questions to answer:
what it does to the container a 1.0.2 user brings to it, and what it writes
on its own afterwards.

**Baseline — 1.0.2 on the fresh simulator.** The 1.0.2 build (`21d534e`) was
installed and driven through the client's live near.ai suite (three tests:
the attestation sheet, two sealed turns, two sealed turns with the debug
panel open; the first two passed, the third failed a UI assertion about the
debug card's E2EE stamp — a display matter, out of scope here). Afterwards
`Cache.db` held 20 archived requests; the three model attestation-report
fetches to `glm-5-3-flash.completions.near.ai` carried an `Authorization`
header equal to the key on the developer's host file (compared, never
printed), and the key's bytes were present three times in `Cache.db-wal`.
The MEDIUM reproduces on a container the fix has never seen.

**Upgrade — 1.0.3 installed over that container, launched once.**
`xcrun simctl install` of the 1.0.3 build over the same bundle id keeps the
data container, as an App Store update does. After one twenty-second launch
with no user action: `cfurl_cache_response` and `cfurl_cache_blob_data` at 0
rows, the `fsCachedData/` directory gone, `Cache.db-wal` down from 1.5 MB to
105 KB, and the key's bytes in no file — the database, its write-ahead log,
preferences, HTTP storages, the store and its search index all read byte for
byte. The delete at `Support/SharedURLCache.swift:29` removes the bytes, not
just the rows.

**1.0.3 sessions on that container.** The live near.ai suite (same three
tests; same two passes and one display failure) and the offline product suite
(18 tests, embedded fake SSE server on loopback, no key) were run, then the
regression test `SharedURLCacheTests` (2 tests, passed) on the same build.
During both UI suites the process's sockets were polled once a second and
the unified log for the process streamed; afterwards the Keychain attributes
and the container were read. Packet capture was unavailable (BPF devices
root-only), so endpoints are remote addresses resolved forward and reverse —
and, for two CloudFront edges neither resolves, by asking each for Intel's
certificate host by name and getting the file back under a valid certificate.

### Findings

### MEDIUM (deployed: no — present 1.0 through 1.0.2, fixed at this release) — the near.ai API key was written in cleartext to the shared URL cache on disk

Closed. At 1.0–1.0.2 every authenticated fetch outside the chat request went
through `URLSession.shared` with its default disk cache, and the model
attestation-report response — served without `Cache-Control: no-store` — was
archived with its request, `Authorization: Bearer <near.ai key>` included, into
`Library/Caches/ai.teemoon.app/Cache.db`; nine copies after one session, found
by running 1.0.2, missed by two source reads. Full account on the
[1.0.2 page](v1.0.2-21d534e.md#medium-deployed-yes--since-10-fixed-in-103--the-nearai-api-key-is-written-in-cleartext-to-the-shared-url-cache-on-disk-by-the-attestation-report-fetch).

At `7edcb55` the shared cache is emptied and replaced with a zero-capacity one
as the first statement of app init (`App/teemoonApp.swift:41` →
`Support/SharedURLCache.swift:29-30`), before any session exists (traced
above), and every key write or clear through the editor purges it again
(`Providers/ProviderStore+Credentials.swift:141`). Measured on this build:
on a container brought from 1.0.2 with the key archived three times, one launch left zero rows and zero key bytes in the database, its write-ahead log and every other file; a live near.ai session and the offline suite on that build then added zero archived requests; the regression test passes on the same build. Full measurement under *Runtime pass* above.

What a user of an earlier release should know: the copies written by 1.0–1.0.2
are removed on the first launch of 1.0.3 (measured: one launch, and the bytes are gone, write-ahead log included); the key itself was
never sent anywhere but near.ai, so rotating it is a precaution against a
device that was already in someone else's hands, not a response to a
transmission.

### LOW (deployed: yes — since 1.0) — the user-edited system prompt is stored in UserDefaults, outside the protected store and inside backups

Unchanged; `Settings/AppSettings.swift` is byte-identical. Read at `:28`,
written at `:32`, edited through a `TextEditor` at
`Views/Settings/ChatsSettingsView.swift:24`, sent as the system message of
every request, and observed in `Library/Preferences/ai.teemoon.app.plist`
after this pass's sessions. Preferences carry the container's default
protection class and are included in iCloud and encrypted Finder backups. Most
users never change the default prompt. **Remediation:** keep it in the
hardened store, or write it to a file with the store's protection class and
backup exclusion. Not addressed by this release.

### Residuals — by design, stated not hidden

Carried from the 1.0 and 1.0.2 pages: opt-in web search is content-driven
egress to one fixed host; provider keys restore via encrypted backup; an
unattested provider is plaintext by definition; user-initiated copies go to the
general pasteboard; E2EE metadata is plaintext by protocol; a no-tap re-send
after backgrounding goes through the same gate; a developer-only stderr
capture ships env-gated in the release binary. New at this release:

- **The purge belt has two holes.** `SharedURLCache.purge()` runs on every key
  write or clear through the provider editor but not on provider deletion
  (`Providers/ProviderStore.swift:184-193`) or on the Brave key's setter
  (`Settings/AppSettings.swift:184-193`). Moot while the launch-time swap
  holds — nothing is cached for either path to leave behind, and this pass
  measured that — but it is the property the old MEDIUM had ("survives the
  user deleting the key"), and one line in each path, or a purge inside
  `Keychain.delete`, would close it. Hygiene, not a leak.
