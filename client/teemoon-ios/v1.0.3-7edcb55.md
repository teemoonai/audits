# teemoon iPhone client (1.0.3) — Plaintext and Key Exfiltration Audit (delta from `21d534e`)

> Client side of the teemoon plaintext question. Lineage: [`../README.md`](../README.md)
> · Map: [`../ARCHITECTURE.md`](../ARCHITECTURE.md) · Surface: [`../audit-surface.md`](../audit-surface.md)

This is the hotfix release for the one deployed finding in the client's
history: at every release from 1.0 to 1.0.2 the near.ai API key was archived
in cleartext in the shared URL cache on disk, found on 2026-09-10 by running
1.0.2. The page asks one question of the fix — does the key now stay in the
Keychain and nowhere else on disk — and re-checks that nothing else moved.

## Audit prompt

The portable prompt in [`method.md` §3](../method.md#3-the-portable-audit-prompt),
in its delta form, with:

           ':(exclude)*.png' ':(exclude)*.xcassets*'        (150 lines, 4 files)

plus five questions the release has to answer: whether the fix runs before any
session exists, whether it empties the store the 1.0.2 pass read the key from,
whether any session bypasses it, whether the purge covers key removal and
replacement, and whether the LOW still holds. Two reviewers ran it in parallel
on the same checkout, each told to write a skeleton report before verifying
anything. Both returned `qualified-pass`, no new finding, the MEDIUM fixed in
source, and the same belt gap on two key-deletion paths (under *residuals*).
The runtime pass, run afterwards, is what settles the parts the source cannot.

### Traced — keys, from the Keychain to the disk the fix takes away

**Where the key went before.** Nine of the twelve authenticated request sites
ride `URLSession.shared` (through `URLSessionHTTP`, `Inference/HTTPClient.swift:19`),
whose configuration takes `URLCache.shared` — by default a disk-backed cache at
`Library/Caches/ai.teemoon.app/Cache.db` — and CFNetwork archives each cacheable
response with the request that produced it, `Authorization` header included.
The 1.0.2 page has the full account.

**What the fix does, and whether it can be too late.** The whole question is
ordering: `URLSessionConfiguration.default` captures `URLCache.shared` when it
is created and `URLSession.shared` is created on first access, so the swap must
land before either. What runs before `teemoonApp.swift:41`, in order:

- *Stored-property initializers of the `App` struct* (Swift runs these before
  the init body). `:18` `@UIApplicationDelegateAdaptor(BackgroundDownloadDelegate.self)`
  constructs an `NSObject` with no stored properties and no `init`
  (`:682-694`); its one method is UIKit's background-download relaunch
  callback, delivered after launch. `:24` `@State downloadCenter = OllamaDownloadCenter()`
  is eager (`@State`, not `@StateObject`), and the class initialises an empty
  array and an empty dictionary (`Providers/OllamaDownloadCenter.swift:33-34`);
  its network use is inside `run(ref:)`, reached only from a user's `start`.
  `:122-217` `let sharedModelContainer` is an eager instance closure — the
  comment at `:208` calling it a lazy `static let` is stale — and it builds a
  SwiftData container, hardens the store (`:205` → `:264-277`) and logs on
  failure; no `URLSession`, no `URLCache`, and no CloudKit entitlement that
  could spin up a sync client. `:20-23` have no initial value; they are
  assigned at `:116-119`, after the fix.
- *Globals and statics.* No `main.swift`, no ObjC `+load`, no
  `__attribute__((constructor))` in `teemoon/`, `Packages/*/Sources` or
  `Vendor/textual/Sources`; `Packages/` contains no `URLSession` at all. The
  only lazy statics near networking are the background-download sessions
  (`Providers/LocalModelDownloadSession.swift:37-38`, `.background`
  configurations, first touched from `teemoonApp.swift:93-94` — after the fix
  — and carrying no header) and textual's `ImageLoader.shared`, whose
  `.default` configuration (`Vendor/textual/Sources/Textual/Internal/Image/ImageLoader.swift:78`)
  is the only `.default` in the tree, is built on first use, and is never
  reached from a reply because the app installs `NoRemoteAttachmentLoader` at
  both transcript roots (`Views/Chat/ConversationView.swift:141`, `:805`).
- *Alternate entries.* The Siri intent runs in the app process
  (`App/RequestLLMIntent.swift:135`, `openAppWhenRun = false`), which SwiftUI
  starts by constructing `TeemoonApp` — the init, and so the fix, precedes any
  intent delivery. The UI-test host path is `#if DEBUG` end to end.

The first `URLSession.shared` access in the process is `teemoonApp.swift:68`
(`ConfidentialSession(providers:)` → default arguments
`Confidential/ConfidentialSession.swift:155`, `:157` → `ProvenanceService.swift:50`,
`NRASService.swift:62`), twenty-seven lines after the swap. The other two
session constructors in the tree are `.ephemeral` — the chat request

TLS-attestation probe (`Confidential/TLSAttestationVerifier.swift:85`).
**In source, the fix runs first.** What only a running process can show —
that no Apple framework the app links creates a default session before

### Runtime pass (method §4b) — 2026-09-11

The tag was built from source (`xcodebuild build-for-testing`, Xcode 26.6,
iOS 26.5 simulator — a simulator created for this pass and used for nothing
else) and measured in three states, because a hotfix has two questions to answer:
what it does to the container a 1.0.2 user brings to it, and what it writes
on its own afterwards.

**Baseline — 1.0.2 on the fresh simulator.** The 1.0.2 build (`21d534e`) was
installed and driven through the client's live near.ai suite (three tests:
the attestation sheet, two sealed turns, two sealed turns with the debug
panel open; the first two passed, the third failed a UI assertion about the
debug card's E2EE stamp — a display matter, out of scope here). Afterwards
`Cache.db` held 20 archived requests; the three model attestation-report
fetches to `glm-5-3-flash.completions.near.ai` carried an `Authorization`
header equal to the key on the developer's host file (compared, never
printed), and the key's bytes were present three times in `Cache.db-wal`.
The MEDIUM reproduces on a container the fix has never seen.

**Upgrade — 1.0.3 installed over that container, launched once.**
`xcrun simctl install` of the 1.0.3 build over the same bundle id keeps the
data container, as an App Store update does. After one twenty-second launch
with no user action: `cfurl_cache_response` and `cfurl_cache_blob_data` at 0
rows, the `fsCachedData/` directory gone, `Cache.db-wal` down from 1.5 MB to
105 KB, and the key's bytes in no file — the database, its write-ahead log,
preferences, HTTP storages, the store and its search index all read byte for
byte. The delete at `Support/SharedURLCache.swift:29` removes the bytes, not
just the rows.

**1.0.3 sessions on that container.** The live near.ai suite (same three
tests; same two passes and one display failure) and the offline product suite
(18 tests, embedded fake SSE server on loopback, no key) were run, then the
regression test `SharedURLCacheTests` (2 tests, passed) on the same build.
During both UI suites the process's sockets were polled once a second and
the unified log for the process streamed; afterwards the Keychain attributes
and the container were read. Packet capture was unavailable (BPF devices
root-only), so endpoints are remote addresses resolved forward and reverse —
and, for two CloudFront edges neither resolves, by asking each for Intel's
certificate host by name and getting the file back under a valid certificate.

### Findings

### MEDIUM (deployed: no — present 1.0 through 1.0.2, fixed at this release) — the near.ai API key was written in cleartext to the shared URL cache on disk

Closed. At 1.0–1.0.2 every authenticated fetch outside the chat request went
through `URLSession.shared` with its default disk cache, and the model
attestation-report response — served without `Cache-Control: no-store` — was
archived with its request, `Authorization: Bearer <near.ai key>` included, into
`Library/Caches/ai.teemoon.app/Cache.db`; nine copies after one session, found
by running 1.0.2, missed by two source reads. Full account on the
[1.0.2 page](v1.0.2-21d534e.md#medium-deployed-yes--since-10-fixed-in-103--the-nearai-api-key-is-written-in-cleartext-to-the-shared-url-cache-on-disk-by-the-attestation-report-fetch).

At `7edcb55` the shared cache is emptied and replaced with a zero-capacity one
as the first statement of app init (`App/teemoonApp.swift:41` →
`Support/SharedURLCache.swift:29-30`), before any session exists (traced
above), and every key write or clear through the editor purges it again
(`Providers/ProviderStore+Credentials.swift:141`). Measured on this build:
on a container brought from 1.0.2 with the key archived three times, one launch left zero rows and zero key bytes in the database, its write-ahead log and every other file; a live near.ai session and the offline suite on that build then added zero archived requests; the regression test passes on the same build. Full measurement under *Runtime pass* above.

What a user of an earlier release should know: the copies written by 1.0–1.0.2
are removed on the first launch of 1.0.3 (measured: one launch, and the bytes are gone, write-ahead log included); the key itself was
never sent anywhere but near.ai, so rotating it is a precaution against a
device that was already in someone else's hands, not a response to a
transmission.

### LOW (deployed: yes — since 1.0; back-applied 2026-09-19 from the 1.0.4 page) — reply text and model-written tool arguments are interpolated into unfenced log statements

Present at this commit and not seen by this page's review: `Inference/ChatGeneration.swift:358` logs the first 120
characters of each finished reply and `Inference/GenerationEngine.swift:392` each tool call's arguments, both at debug
level; `Inference/GenerationEngine.swift:307` logs stripped reply fragments at warning level. None is `#if DEBUG`-fenced
or carries an explicit privacy level, so on a phone the text is redacted by the platform's default and the debug lines
are not persisted — the platform's protection, not the app's. **This corrects any statement on this page that the
inference path's log lines never carry a body, and any runtime-pass count of zero app-originated lines with message
text:** those passes streamed the log at the default level, which drops debug lines. Found by the 1.0.4 runtime pass
streaming at debug level; full account and remediation on the
[1.0.4 page](v1.0.4-3abe3e2.md#low-deployed-yes--since-10--reply-text-and-model-written-tool-arguments-are-interpolated-into-unfenced-log-statements).

### LOW (deployed: yes — since 1.0) — the user-edited system prompt is stored in UserDefaults, outside the protected store and inside backups

Unchanged; `Settings/AppSettings.swift` is byte-identical. Read at `:28`,
written at `:32`, edited through a `TextEditor` at
`Views/Settings/ChatsSettingsView.swift:24`, sent as the system message of
every request, and observed in `Library/Preferences/ai.teemoon.app.plist`
after this pass's sessions. Preferences carry the container's default
protection class and are included in iCloud and encrypted Finder backups. Most
users never change the default prompt. **Remediation:** keep it in the
hardened store, or write it to a file with the store's protection class and
backup exclusion. Not addressed by this release.

### Residuals — by design, stated not hidden

Carried from the 1.0 and 1.0.2 pages: opt-in web search is content-driven
egress to one fixed host; provider keys restore via encrypted backup; an
unattested provider is plaintext by definition; user-initiated copies go to the
general pasteboard; E2EE metadata is plaintext by protocol; a no-tap re-send
after backgrounding goes through the same gate; a developer-only stderr
capture ships env-gated in the release binary. New at this release:

- **The purge belt has two holes.** `SharedURLCache.purge()` runs on every key
  write or clear through the provider editor but not on provider deletion
  (`Providers/ProviderStore.swift:184-193`) or on the Brave key's setter
  (`Settings/AppSettings.swift:184-193`). Moot while the launch-time swap
  holds — nothing is cached for either path to leave behind, and this pass
  measured that — but it is the property the old MEDIUM had ("survives the
  user deleting the key"), and one line in each path, or a purge inside
  `Keychain.delete`, would close it. Hygiene, not a leak.

### Controls that would change the verdict

- Any session created before `TeemoonApp.init` runs, or any configuration in
  the tree that sets its own `urlCache` — either reopens the disk cache for
  whatever rides it.
- Any code that assigns `URLCache.shared` after launch.
- A renderer capability that fetches on render (previews, embeds, a web view).
- A second derivation of send authorization anywhere a message can start.
- A model-callable tool that fetches a model-chosen URL or reads other threads.
- `captureNativeLogIfAsked` becoming a user-facing setting.
- A dependency added to `Package.resolved` with its own network client.

### Verdict: QUALIFIED-PASS

Keys: at `7edcb55` a provider key lives in the Keychain and nowhere else on
disk — the claim every earlier page made and running 1.0.2 broke now holds, in
source (the swap runs before any session exists and nothing bypasses it) and
at runtime (a 1.0.2 container's copies removed on first launch; zero archived
requests after live and offline sessions); every request that carries a key
still reaches only the key's own provider. Messages: private, as at 1.0.2 —
the delta touches nothing on the plaintext path, a live session opened no
endpoint the map does not name, and every property the 1.0 verdict rests on
holds. One LOW remains: the user-edited system prompt is in UserDefaults and
backed up. The purge belt has two holes that the launch-time swap makes moot.
The on-device runtime's egress remains unobserved on a phone.

## Addendum 2026-11-25 — a near.ai lookalike host got the encrypted treatment

### LOW (deployed: ARMED, needs the user to add a custom provider whose URL contains "near.ai") — gate: a provider counts as near.ai when its URL contains the text "near.ai" anywhere, so a lookalike host gets the attested, end-to-end-encrypted treatment

Traced at 7edcb55 (v1.0.3); every line number below was checked at this tag. Paths are under `teemoon/`. A source read: nothing here was run.

- **Precondition.** The user adds a custom provider by hand whose URL contains `near.ai` somewhere: a host such as `near.ai.example.com` or `api.linear.ai`, or a path such as `/near.ai/v1`. No preset does this. The user's own key and messages going to the host they typed is not a leak and is not the finding. The finding is what the app claims about that host, and whose key it seals to.
- **Gate.** The capabilities getter grants `.attestation` and `.endToEndEncryption` when `endpoint.contains("near.ai")` and the model's tier is `.teeOwn` (`Providers/Provider.swift:278-280`). That is a substring test on the whole URL, not a host rule. The tier does not narrow it much: `classify` returns `.teeOwn` for every id it does not recognise (`Providers/NearAIModelCatalog.swift:114-131`, the default at `:131`), and the catalog cache is read only after it (`:90-91`). An id that names a closed vendor (claude, gpt-, gemini, o3, o4, -max) or a known third-party id does not qualify; any other id does.
- **What the capability shows before any check.** The provider's row reads "<provider name> · end-to-end encrypted" (`Presentation/WhereProviderPresentation.swift:154-155`).
- **A model id near.ai does not list: nothing is sent.** The refresh looks the model up in near.ai's own directory, `https://completions.near.ai/endpoints` (`Providers/EndpointDirectory.swift:29`, `:47-53`; `Confidential/ConfidentialSession+Refresh.swift:87-88`). With no host for the id there is no record (`:96-118`), so no seal context (`Confidential/ConfidentialSession.swift:183-190`), and the send is refused with "End-to-end encryption could not be established, so nothing was sent." (`Chat/ChatViewModel.swift:94-95`, `:238`). The row's claim is wrong and the provider cannot be used; no message leaves.
- **A model id near.ai lists: where each request goes.**
  - The plain attestation report: `GET <custom host>/attestation/report`, with the user's key (`Confidential/AttestationService.swift:44-64`, `:99`); the host may answer it or refuse it, and either way the record is built (`Confidential/AttestationService.swift:99`, `:110-117`).
  - The model report, the one that supplies the sealing key: a race between near.ai's direct host for that model and `<custom host>/attestation/report?model=…&signing_algo=ed25519` (`Confidential/AttestationService+Model.swift:40-54`). The first source to return a key wins (`:179-191`); nothing prefers near.ai's answer. The custom host's answer needs a 32-byte key, and a matching `model_name` only if it sends one (`:132-143`).
  - The GPU-node report: near.ai's direct host (`Confidential/AttestationService.swift:92-94`; `Confidential/AttestationService+GPU.swift:52-59`).
  - The TLS check: near.ai's direct host, with no credential (`Confidential/ConfidentialSession+Verifiers.swift:167-185`).
  - The chat request: `POST <custom host>/chat/completions` with the user's key (`Inference/HTTPTransport.swift:59-67`, `:77-81`), its body sealed to the record's `modelEd25519PubKey` (`Inference/ConfidentialLanguageModel.swift:46-52`; `Inference/HTTPTransport.swift:68`, `:92-96`; `Confidential/AttestationService.swift:147`).
- **Whose key the message is sealed to.** Whichever source won the race. If the custom host answers first, the message is sealed to a key that host chose and is posted to that host, which can open it. If near.ai's host wins, the message is sealed to near.ai's enclave key and posted to the custom host, which cannot open it.
- **A key with no quote asked; it did not block.** The state is degraded (`Confidential/ConfidentialSession+Verdict.swift:98-106`), and the break is not a hard one, because that needs a quote that is present and fails (`:211-238`). The send policy is therefore the ask (`:246-261`; `Confidential/TrustVerdict.swift:87-90`), with the reason "The model's hardware attestation is unavailable." (`Confidential/ConfidentialSession+Verdict.swift:162`) and the caption "not end-to-end encrypted" (`Confidential/AttestationState.swift:28`). If the user confirms, the message goes out sealed to that key. A made-up quote fails Intel's check and blocks (`Confidential/DCAPService.swift:100`).
- **A key with a genuine quote reads as verified.** The model quote is checked for three things: it chains to Intel (`Confidential/AttestationService+Model.swift:145-147`; `Confidential/DCAPService.swift:100`), the key sits in its report data (`Confidential/AttestationRecord.swift:128-134`), and it echoes the app's nonce (`:170-186`). Its measurements are compared with no reference. A quote from any genuine TDX guest the host's operator runs, carrying that operator's key and the app's nonce, passes all three. No other degrade condition (`Confidential/ConfidentialSession+Verdict.swift:50-91`) has to fire: the custom host controls the plain report, and the GPU-node report and the TLS check go to near.ai's real host for that model, so whatever genuine evidence that host returns sits on the same screen as the operator's key (whether near.ai answers a request carrying another host's key was not tested). The state is `.ok` (`:103`) and the send is allowed with no ask.
- **What the app then shows.** The caption "end-to-end encrypted" (`Confidential/AttestationState.swift:27`), the hero "encrypted to <model> — only it can read this" with "only you and <model>'s sealed hardware can read this chat." (`Confidential/TrustVerdict.swift:153`, `:177`), and the chain line that says not the provider, not the network, nobody else can open it (`:190-191`). For this provider that is false: the host's operator holds the key. The app shows the provider under the name the user gave it, not as near.ai.
- **The user's key for the custom host also reaches near.ai's hosts.** The credential stored for the custom provider (`Confidential/ConfidentialSession+Refresh.swift:71`, `:121-124`) is sent as a bearer token to near.ai's direct host for that model, on the GPU-node report and on the direct model report (`Confidential/AttestationService.swift:44-64`, `:92-94`, `:95-97`; `Confidential/AttestationService+GPU.swift:59`; `Confidential/AttestationService+Model.swift:40-46`, `:109`). This needs no hostile party, only the precondition and a model id near.ai lists. For such a provider this page's statement that a key leaves the device only to its own provider does not hold: near.ai receives a key the user stored for another host.
- **Severity and state.** LOW, ARMED. Not INFO: under the precondition the app's central sentence is false, the verified state can be reached by a host that is not near.ai with a key it chose, and a key goes to a host the user did not configure. Not MEDIUM: nothing happens until the user types such a URL into a custom provider and picks a model id near.ai lists; the message reaches only the host the user typed, which is where a custom provider's messages go with no claim at all, so no third party gains a message; the verified state needs a host built for the purpose that also runs real TDX hardware, and without a genuine quote the app asks or blocks; the key that strays goes to near.ai and nowhere else. What is lost is the assurance: a user who believed the screen could send that host what they would not have sent it in the clear. No report of a provider configured this way is known to this review.
- **Fixed in v1.0.4.** At 3abe3e2 the getter tests `isNearAI` (`Providers/Provider.swift:285`), which is the host rule `host == "near.ai" || host.hasSuffix(".near.ai")` (`Providers/WhereLocality.swift:85-90`; `Providers/EndpointModelCatalog.swift:149`). No `contains("near.ai")` and no `hasSuffix("near.ai")` is left in the app's Swift source at that tag. A lookalike host gets neither capability and is an ordinary custom provider with no encryption claim.
