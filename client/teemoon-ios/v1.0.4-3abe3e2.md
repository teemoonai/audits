### Traced — keys

**The rewritten cache fix.** At 1.0.3 `disable()` called
`URLCache.shared.removeAllCachedResponses()` and then swapped the cache; that
call instantiated the default store it was about to discard, which is why the
1.0.3 pass saw an empty 4 KB `Cache.db` reappear. At `3abe3e2`
`Support/SharedURLCache.swift:20-23` first removes `Cache.db`, `Cache.db-shm`,
`Cache.db-wal` and `fsCachedData` under `Library/Caches/<bundle id>/` with
`FileManager` (`:27-32`, `:34-38`) — never touching `URLCache` — and then
assigns the zero-capacity cache (`:22`), still the only assignment of
`URLCache.shared` in the tree. It is still the first statement of
`TeemoonApp.init` (`App/teemoonApp.swift:40`). What runs before it is what ran
before it at 1.0.3: the delegate adaptor (`:18`), the eager
`OllamaDownloadCenter()` (`:24`, file not in the diff) and the eager
`sharedModelContainer` closure (`:136`); the delta adds no stored property,
static or entry point ahead of the init. The first `URLSession.shared` access
is `ConfidentialSession(providers:)` at `:74`. No session sets its own
`urlCache` and no request a `cachePolicy` — the grep hits are the fix, the two
`.ephemeral` sessions (`Inference/ConfidentialLanguageModel.swift:111-113`,
`Confidential/TLSAttestationVerifier.swift:85`), the header-less `.background`
download configuration and textual's unreachable image loader. All five new
authenticated sites ride `URLSession.shared`, so they ride the zero cache.

Two things are weaker than at 1.0.3, and neither is a finding. The delete is
`try?` (`:36`): if it failed, a 1.0.2-era store would survive silently until
the next launch retried it — nothing would be *added* to it, because the swap
is unconditional. And `purge()` is gone, so the swap is now the only
mechanism; the 1.0.3 page's "belt with two holes" is a belt removed. Deleting
whole files is a stronger erase than the SQL delete it replaces. Whether it
works on a container that actually holds the key is measured below.

The 1.0.2 page's check stood on the v0.14.0 binary; these are different

60.5 MB, sha256
`892798555f337315aa89f2f405e3e3b41d68de9d977b15c7d4a4fd3fa637684c`, from the

- **Linked:** AVFoundation, AudioToolbox, AVFAudio, CoreVideo, IOSurface,
  QuartzCore, MetalKit, Metal, OpenGLES, Foundation, CoreFoundation, libc++,
  libobjc, libSystem. **No** CFNetwork, Network.framework, libcurl, gRPC or

- **Socket imports:** `socket`, `connect`, `bind`, `listen`, `accept`, `send`,
  `sendto`, `recv`, `recvfrom`, `getaddrinfo`, `socketpair`.
- **Who calls them:** the full disassembly (6.9 million instructions, 117,074

  then 11, then 4, then none — every one inside the Rust standard library's
  `std::net` / `std::os::unix::net`. No LiteRT, Dawn or TensorFlow function
  calls into it. The walk follows direct calls; a call through a function
  pointer would not appear, and no address of these functions was looked for.
- **Embedded URLs:** documentation and bug-tracker links only

  v0.17 binary links Dawn/WebGPU, new since v0.14.
- **File writes:** imported, not traced. `MTLCaptureManager` is imported (a
  GPU capture writes a file when something starts one); nothing in the
  wrapper or the app does.

**Conclusion:** as built, the new runtime has no code path to the network —
the same static result as v0.14.0, on the shipped bytes. The upstream source
at v0.17.1 was **not** read for this page; the 1.0.2 page's source-side notes

### Runtime pass (method §4b) — 2026-09-19

Both tags were built from source (`xcodebuild build-for-testing`, Xcode 26.6,
iOS 26.5 simulator created for this pass). The 1.0.4 app binary's hash was
taken before and after the test-target changes described at the end of this
section and did not move.

**Baseline — 1.0.2 on the fresh simulator.** The 1.0.2 live near.ai suite
(two passes and the known display failure) left 23 archived requests in
`Cache.db`, two with an `Authorization` header, and the near.ai key's bytes
eight times in `Cache.db-wal`. The old MEDIUM reproduces.

**Upgrade — 1.0.4 installed over that container, launched once, no user
action.** `Library/Caches/ai.teemoon.app/` was **empty**: `Cache.db`, `-shm`,
the 1.7 MB `-wal` and `fsCachedData/` all gone, and none recreated. Every
remaining file was read byte for byte for seven provider keys held on the
developer's host (UTF-8 and UTF-16, compared, never printed): no hit. The
rewritten fix cleans a 1.0.2 container.

**1.0.4 sessions on that container.** near.ai live suite (3 tests: 2 passed,
the same display failure); one live send each through xAI (passed), NVIDIA
(passed), Fireworks (the harness's pinned model is no longer deployed — HTTP
404 from `api.fireworks.ai`, error card shown) and OpenRouter (HTTP 429 from
the free model's upstream, error card shown) — each keyed request went out,
which is what the measurements need; the offline product suite (21 tests,
passed); the cache regression suite (3 tests, passed). Sockets polled once a
second, unified log streamed **at debug level**, Keychain attributes and the
container read afterwards. Packet capture unavailable (BPF root-only);
endpoints are remote addresses matched against forward resolution of the
hosts the source names.

the app binary is byte-identical before and after. The 1.0.2 baseline needed
the same one-constant model patch as the 1.0.3 pass.

### Findings

### LOW (deployed: yes — since 1.0) — reply text and model-written tool arguments are interpolated into unfenced log statements

Three `os.Logger` statements, none inside `#if DEBUG`, none with an explicit
privacy level, all present at every release since 1.0:

- `Inference/ChatGeneration.swift:358` — debug level — the first 120
  characters of every finished reply;
- `Inference/GenerationEngine.swift:392` — debug level — the JSON arguments of
  every tool call, which for web search is a query the model wrote from the
  user's prompt;
- `Inference/GenerationEngine.swift:307` — **warning** level — up to four
  fragments of reply text stripped as residual tool markup (did not fire in
  this pass).

Observed in this pass's log stream with the text in clear. On a user's phone
two platform defaults stand between these lines and a reader: a Swift
`Logger` interpolation of a dynamic string is private unless marked otherwise,
and is rendered `<private>` unless a debugger is attached or a logging
profile enabling private data is installed; and debug-level messages are kept
in memory only, not persisted (the warning-level one is persisted, redacted).
So the reachable reader is someone streaming the log from a trusted, unlocked,
profile-configured device — but that protection is the platform's default,
not the app's decision, and the method counts a log line that can carry a
body as a finding at any privacy level. Neither of this release's reviewers,
nor either of the two before them, read these lines, because no delta has
touched them; earlier runtime passes streamed at the default level, which
excludes debug. **Remediation:** log counts and lengths, not content — or
fence the two debug lines with `#if DEBUG` and drop the fragment from the
warning. The 1.0–1.0.3 pages' log claims are corrected by this page.

### LOW (deployed: yes — since 1.0) — the user-edited system prompt is stored in UserDefaults, outside the protected store and inside backups

Unchanged. Read at `Settings/AppSettings.swift:28`, written at `:32`, observed
in `Library/Preferences/ai.teemoon.app.plist` after this pass's sessions.
**Remediation:** keep it in the hardened store, or in a file with the store's
protection class and backup exclusion. Not addressed by this release.

### INFO (deployed: yes — new at 1.0.4) — a truncated hash of a keyed provider's API key is written to a catalogue file and is never removed

For xAI, Fireworks and custom cloud endpoints the saved model list is scoped
by `key-` plus the first 16 hex digits of an unsalted SHA-256 of the key
(`Providers/LiveCatalogStore.swift:208-212`), stored as the `scope` field of a
backup-excluded JSON file under `Application Support/ModelLists/`. The method
that would delete a server's lists, `forget(endpoint:)` (`:171-178`), has no
caller, and provider deletion (`Providers/ProviderStore.swift`) does not touch
the directory; a list is replaced only when another key fetches for the same
endpoint (`:280-286`). Sixty-four bits of a hash of a high-entropy key cannot
be turned back into the key, which is why this is not a LOW; what it lets a
reader of the container do is confirm that a key they already hold was used
on this device, after the user has deleted it. Found independently by both
reviewers; the file's other content was confirmed by reading one.
**Remediation:** call `forget(endpoint:)` from key removal and provider
deletion; salt the scope with a per-install random value.

### Residuals — by design, stated not hidden

Carried: opt-in web search is content-driven egress to one fixed host;
provider keys restore via encrypted backup; an unattested provider —
OpenRouter and NVIDIA now among them — reads plaintext by definition, and
OpenRouter forwards it to whichever upstream serves the model; user-initiated
copies go to the general pasteboard; E2EE metadata is plaintext by protocol;
a no-tap re-send after backgrounding goes through the gate; a developer-only
stderr capture ships env-gated in the release binary. Changed at this
release:

- **The cache fix is one mechanism, and its cleanup is silent.** The swap is
  unconditional; the deletion of an old store is `try?` with no log and no
  second path since `purge()` was removed. Measured working here; a failure
  would be invisible.
- **`Keychain.deleteAll()` ships compiled**, callable only from code that the
  release configuration compiles out.

### Controls that would change the verdict

- Any session created before `TeemoonApp.init` runs, any configuration that
  sets its own `urlCache`, or any later assignment of `URLCache.shared`.
- A markdown or image view placed in the tail-card root
  (`TranscriptCollectionView.swift:1240`) without the non-fetching loader.
- An adapter that builds a request from anything but the provider's own base
  URL, or a background catalogue refresh that starts passing a key.
- Any of the three log statements gaining `privacy: .public`, or moving to a
  persisted level with content.
- A caller for `Keychain.deleteAll()` outside `#if DEBUG`.
- A second derivation of send authorization anywhere a message can start.
- A model-callable tool that fetches a model-chosen URL or reads other threads.
- A future runtime binary that links a network stack; a dependency added to
  `Package.resolved` with its own network client.

### Verdict: QUALIFIED-PASS

Keys: at `3abe3e2` a provider key lives in the Keychain and nowhere else on
disk, and leaves only in a request to the endpoint it was saved with —
seventeen sites, five new, each read and each exercised live; the rewritten
cache fix was measured on a container that held the key and left no cache
file behind, and sessions against five providers left the key in no file and
no log line. One INFO: a truncated hash of a keyed provider's key outlives the
key in a catalogue file. Messages: the send gate is tighter than at 1.0.3, the
renderer fetches nothing, no unlisted endpoint was opened. Two LOWs, both
since 1.0: reply text and tool arguments reach log statements that only the
platform's defaults redact — found at this release by raising the log level,
and a correction to every earlier page — and the user-edited system prompt is
in UserDefaults and backed up. The new on-device runtime binary has no code
path to the network; its file writes, and the app on a phone, remain
unobserved.
