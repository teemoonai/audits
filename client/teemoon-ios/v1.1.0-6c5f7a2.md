#### H1a — the 1.0.6 MEDIUM (ARMED) gate finding: FIXED

The 1.0.6 defect was `requiresE2EEConfirmation` returning false on `unpublishedOnlyButE2EEIntact` before the state was read, with `e2eeBindingIntact` blind to the recipe-hash mismatch. At `6c5f7a2`:

| …and is a hard failure | `Verdict.swift:321`, `:323` | `degradeIsHardFailure`: `guard state == .degraded`, then `modelComposeIntegrityFailed` → true |
| guard 1 — the exemption refuses every hard failure | `Verdict.swift:287` | `guard !degradeIsHardFailure else { return false }` inside `unpublishedOnlyButE2EEIntact` |

*Each guard alone.* With `:287` deleted, a hash mismatch under unpublished-only provenance still fails `:288` (`!modelComposeIntegrityFailed` is false) → exemption false → `requiresE2EEConfirmation` true (`:366`) → `hardFailure` true (`:323`) → `.block` (`TrustVerdict.swift:196`). With the `:288-289` list deleted, `:287` returns false for the same state. The two guards are redundant for every cause that `degradeIsHardFailure` lists; the `:288-289` list additionally covers the non-hard causes (`couldntCheckHardware`, stale-and-unrefreshable, `tierGaveUp`) that must ask rather than block, which `:287` does not.

*Which test fails per single-guard removal.* For the hash-mismatch pair, none can: each guard alone preserves the outcome, so the single-guard mutation is behaviour-preserving for that state. A test can only go red when both are removed, or (for the non-hard causes) when the `:288-289` term for that cause is removed. The tests that exercise the pair are the vector-table tests in `teemoonTests/SendGateRuleTests.swift` (`:135`, `:147`, `:157`, `:172`), which read `conformance/sendgate.json` relative to the source file (`:36-41`). **That file is not in the public tree** (`git ls-tree -r HEAD | grep -i "conformance\|sendgate"` lists only test Swift files; `ls src/conformance` fails), and `TestFixture.sourceTreeAvailable` (`teemoonTests/TestFixture.swift:63-65`) checks only that the test source exists. So at the audited public commit the kit-vector tests cannot load their table. The in-tree literal tests do not combine the two conditions: `AppStateTests.swift:722-742` (mismatch, no unpublished), `:787-800` (unpublished, no mismatch), `E2EESecurityExploitTests.swift:405-411` (mismatch alone → `.block`). ### LOW (deployed: ARMED, mechanism carried from 1.0.6) — gate: near.ai's model list can move a model the user was sending sealed to plain TLS with no ask

`NearAIModelCatalog.confidentiality(forID:)` returns the cached tier from near.ai's own model list ahead of the id rule (`Providers/NearAIModelCatalog.swift:116`), and the comment at `:112-113` states that the list may move an own-fleet guess down. The tier comes from the `owned_by` field (`:129-134`): any value that is not a near.ai or third-party-attested marker reads as proxied. `Provider.capabilities` grants attestation and end-to-end encryption only for the own-fleet and unknown tiers (`Providers/Provider.swift:300-301`). A model that is not attestable is outside the send gate (`Confidential/ConfidentialSession+Verdict.swift:362` returns false when the capability is absent), so its next turn goes to `cloud-api.near.ai` over platform TLS, with the key, unsealed and without a question. The list is fetched from that same gateway (`Providers/NearAIModelCatalog.swift:300-303`, recorded `:320`; saved lists replayed at `Providers/LiveCatalogStore.swift:197`). So the party the sealing is meant to keep out, the gateway, can turn the sealing off for a model by changing one field of an unauthenticated list. The screens do stop claiming encryption (`Providers/Provider.swift:310-313`; the row caption reads "not end-to-end encrypted", `Presentation/WhereGetPolicy.swift:279`), so the display is honest; what is missing is an ask when a chat that was sealed on its last turn is about to go unsealed. A turn that began attestable is not affected (`Chat/ChatViewModel.swift:743`, `:768`). Released state: not observed; it needs near.ai to list an own-fleet model with a different owner. The lookup order is the same at 1.0.6 (`git show v1.0.6:teemoon/Providers/NearAIModelCatalog.swift`, `:96-100`) and the 1.0.6 page did not record it; 1.1.0 adds the keyless refresh that fetches the list before a send (`Confidential/VerdictDeadline.swift:47-49`). Not traced: whether any composer notice appears when a chat's model changes tier between turns. The Shortcuts entry has the same shape: each request is a new turn that reads the policy once after `prepareTurn` (`App/RequestLLMIntent.swift:79-83`), so a demoted model is sent in plain TLS there too. Remediation: when the previous turn of a chat was sealed and the tier for the same model id now reads proxied, ask before sending, as for a soft failure.

Status: known and accepted for 1.1.0 by the maintainer, fix planned for 1.1.1 ("Accept for 1.1.0, fix 1.1.1", 2026-11-15, relayed to the audit by the project's coordinating session, not typed to the auditor). The Android 1.1.0 candidate has the same finding. The class stands until the fix is read.

### LOW (deployed: ARMED, mechanism carried from 1.0.6; second reviewer) — gate: a model key with no quote behind it gets the "still checking" ask with send anyway, and the turn is sealed to that key

The model attestation fetch accepts a report that carries a 32-byte key and no quote the parser can read: the quote check is skipped, not failed (`Confidential/AttestationService+Model.swift:147`, `:152-154`, `:166`). `e2eeKeyBoundToModelTEE` is then nil, not false (`Confidential/AttestationRecord.swift:180-182`), so no term of `degradeIsHardFailure` fires and it returns false at its last line (`Confidential/ConfidentialSession+Verdict.swift:317-345`, `:344`); the state is degraded (`:185`), the policy is confirm, and the alert is the transient one, "still checking", with a send-anyway button (`Presentation/SendChoices.swift:90-93`). On send anyway the peer is built from that key (`Inference/ConfidentialLanguageModel.swift:76`) and the turn is sealed to it. Whoever answered the attestation request chose the key, so that party can read the turn: the same exposure as plain TLS to near.ai, behind an ask whose words describe a wait and not a missing proof. The user must tap send anyway; nothing is sent without the ask, and the reply is marked as sent before confirmation (`Confidential/SentBeforeConfirmed.swift:33-38`). Trigger: a hostile or broken attestation endpoint that returns a key and omits the quote; not seen on the fleet. The same lines are at 1.0.6 (`git show ab64f15:teemoon/Confidential/ConfidentialSession+Verdict.swift`, `:217-244`) and the 1.0.6 page did not record it. The published send-gate vectors cover the neighbouring case (quote present, NVIDIA evidence absent: confirm, still checking) and have no vector for a key with no quote. Remediation: treat a key with no verified model quote as a hard failure, or give it its own ask that says the key is unproven.

Status: accepted for 1.1.0 by the maintainer, fix planned for 1.1.1 (relayed to the audit by the release session with the build-62 request, 2026-11-16; not typed to the auditor). The class stands until the fix is read.

### INFO (deployed: ON; second reviewer) — egress: the launcher lookup can make about 400 Docker Hub requests on the shared session, and Docker's token host sets a cookie
