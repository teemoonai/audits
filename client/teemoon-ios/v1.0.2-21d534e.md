### The native runtime binary — capability check (added 2026-09-10)

The one item every client page carried as *not traced* was `CLiteRTLM`, the
compiled LiteRT-LM runtime the on-device model runs in. Source cannot be read,
but the shipped bytes can be asked what they are able to do. The device slice
of the xcframework pinned by `Packages/LiteRTLM/Package.swift` (LiteRT-LM
v0.14.0, `CLiteRTLM.xcframework.zip`, SwiftPM checksum `dddac2f6…`; the
`ios-arm64` Mach-O is 43.2 MB, sha256 `32c2576cddd50542934289b850ce2061115f90f63de2857ff6f7c5f8f2425607`)
was inspected with `otool -L`, `nm -u`, `strings`, and a full `otool -tv`
disassembly. In plain terms: the binary was disassembled end to end (5.2
million instructions); every instruction that calls a socket or
name-resolution function was located and attributed to the function that
contains it; then every call *to* those functions was located and attributed
in turn, and so on outward, until no caller remained that was not part of the
Rust standard library itself. If any LiteRT code could reach the network,
this walk would have found the function that does it.

- **Linked frameworks:** AVFoundation, AudioToolbox, CoreVideo, MetalKit,
  OpenGLES, Metal, CoreFoundation, Foundation, libc++, libobjc, libSystem.
  **No** CFNetwork, Network.framework, NSURLSession, libcurl, gRPC, or TLS
  library.
- **Imported socket primitives:** `socket`, `connect`, `bind`, `listen`,
  `accept`, `sendto`, `recvfrom`, `getaddrinfo`, `socketpair` are imported
  — the binary *could* open a connection.
- **Who calls them:** every one of those calls sits inside the Rust standard
  library's own `std::net` / `std::os::unix::net` implementation, which is
  linked wholesale because parts of LiteRT-LM are Rust. Walking one hop up:
  **no function in the binary calls** `TcpStream::connect`,
  `TcpStream::connect_timeout`, `UdpSocket::connect` / `bind`,
  `TcpListener::bind`, `UnixStream::connect`, or `UnixDatagram::connect`, and
  the hostname-resolution path (`lookup_host` ← `to_socket_addrs`) has **no
  caller outside the standard library either**. The socket layer is present
  but unreachable from any LiteRT code path.
- **Embedded URLs:** documentation links only (tensorflow.org, json-schema.org,
  winimage.com/zLibDll). No hostnames.
- **File writes:** `open`, `fopen`, `fwrite`, `write`, `mkdir`, `rename`,
  `unlink` are imported (model loading, caches); what it writes was not
  traced.

**Conclusion:** as built, the native runtime cannot make a network connection
— the "not traced" item is closed as a *static* capability result on the
exact shipped bytes. What remains open is dynamic confirmation on a phone,
which needs a packet capture this pass could not obtain, and the runtime's
own file writes.

**Source side (added 2026-09-10, one Fable reviewer, citations re-read).**
Upstream `google-ai-edge/LiteRT-LM` at tag `v0.14.0` (`f73637c5`; the vendored
wrapper's `VENDORING.md` records `80f301ff`, one commit earlier — the tag moved
by a checksum-only commit on 2026-07-10; the release with the xcframework was
published 2026-07-08 from a release branch, and nothing records which commit
built it). What the source shows, consistent with the bytes:

- **No network path.** Zero socket, resolver or URL-loading call sites in the
  shipped C++ and Swift (`runtime/`, `c/`, `src/`, `swift/`); no `http(s)://`
  literal outside comments and license headers. `Cargo.lock` carries no HTTP
  or TLS crate; the `tokenizers` crate is pinned with `default-features = false`
  (`Cargo.toml:22`), which turns its Hugging Face download feature off. The Rust
  parts are linked as a `staticlib` (`Cargo.toml:35`), which is why libstd —
  and its unreferenced `std::net` — is in the binary at all; no first-party
  Rust file mentions `std::net`. No telemetry, crash-reporting, model-download
  or remote-config feature exists, behind a flag or otherwise.
- **Logging cannot carry text.** The runtime logs through abseil; its only
  verbosity control is `litert_lm_set_min_log_level` (`c/engine.h:306` →
  `runtime/util/logging.cc:67-78`), which nothing in the shipped library or
  the Swift wrapper calls, so abseil defaults apply. No log statement streams
  prompt, token or generated text; the two `ABSL_VLOG` sites are dead and there
  is no `ABSL_DLOG`. Logit printing is off by default
  (`runtime/executor/llm_executor_settings.h:182`, `= 0`) and CLI-only.
- **Disk.** Run-time writes are model-derived caches beside the model file —
  `*.xnnpack_cache`, `*_mldrift_program_cache.bin`, `*_mldrift_weight_cache.bin`
  (`runtime/executor/executor_settings_base.h:183-187`) — written by the LiteRT
  core; KV-cache serialisation is unimplemented with no caller; no temp files.
- **Not reviewable as source:** four prebuilt dylibs shipped inside the repo
  (`prebuilt/ios_arm64/`: LiteRT core, the Metal accelerator, the top-k Metal
  sampler — loaded by name at `runtime/components/sampler_factory.cc:292`,
  `:513` — and the Gemma constraint provider) and the external LiteRT archive
  pinned in `WORKSPACE:6-8`. The audio frameworks the binary links come from
  that external archive's audio preprocessor, not this tree.

**Two things a reader should understand about this component.**

*Why a C++ runtime carries Rust.* LiteRT-LM bridges in a few components that
exist only as Rust crates — the tokenizer (`tokenizers`), the chat-template
engine (`minijinja`), grammar-constrained decoding (`llguidance`), and the
tool-call parsers (generated with a Rust ANTLR runtime) — compiles them into
one static library and links it into the C++ binary. Linking any Rust static
library brings the whole Rust standard library along, and the standard
library includes TCP and UDP sockets whether or not anything uses them. That
is the entire explanation for the socket imports found in the bytes: language
runtime baggage with no caller, which is what both the disassembly walk and
the source read independently showed.

*What "prebuilt" means here.* LiteRT, the inference engine underneath
LiteRT-LM, is its own open-source project (the successor to TensorFlow Lite).
LiteRT-LM does not build it from source in its tree: it pins one LiteRT commit
and checksum in `WORKSPACE` and ships Google's compiled iOS dylibs in
`prebuilt/`. So the core's source is public and pinned, but the bytes on the
phone were compiled by Google, and nothing ties those bytes to that commit —
the same binary-to-source gap this method names for the app's own App Store
binary (§5), one layer down. A source review of the LiteRT core at the pinned
commit is possible and has not been done; for the Metal top-k sampler and the
Gemma constraint provider dylibs it was not checked whether public source
exists at all. The bytes check covers all of them in one respect only: the
combined binary they are linked into reaches no networking code.

### Findings

### MEDIUM (deployed: yes — since 1.0; fixed in 1.0.3) — the near.ai API key is written in cleartext to the shared URL cache on disk by the attestation-report fetch

Every authenticated fetch outside the chat request goes through `URLSessionHTTP`,
whose default is `URLSession.shared` (`Inference/HTTPClient.swift:19`), and no
code anywhere configures `URLCache` or a cache policy. The model
attestation-report request sets `Authorization: Bearer <near.ai key>`
(`Confidential/AttestationService+Model.swift:109`; `:104` at 1.0) and near.ai
serves that report without `Cache-Control: no-store`, so CFNetwork archives the
whole request — header value included — into
`Library/Caches/ai.teemoon.app/Cache.db`. After one live session the database
held nine `glm-5-2.completions.near.ai/v1/attestation/report` entries whose
archived `Authorization` header equals the key on the developer's host file
(compared, never printed). The same session default sits behind the gateway
report, the key checks, the signature fetch, the catalogs, the endpoint
probes, the adapters and the Brave search (`X-Subscription-Token`); which of
those also land on disk depends only on each server's cache headers.

**Leak scenario.** The key exists on disk outside the Keychain, under the
container's default protection (readable after the first unlock) and outside
the Keychain's access control, and it survives the user deleting the key from
the app until the cache evicts it. Anyone with file access to the container —
a forensic extraction of a once-unlocked device, a jailbroken device, a
backup tool that ignores the Caches exclusion — reads it. `Library/Caches` is
excluded from iCloud and Finder backups by the system, which bounds this to
device access. It is a key at rest, not a network exfiltration, so it is
MEDIUM rather than HIGH; but the page's "Keychain and nowhere else on disk"
claim is false at every shipped release, and neither source read caught it.

**Fixed in 1.0.3 (35):** the shared URL cache is replaced with a zero-capacity
one before any session exists and the on-disk store is emptied at launch;
key removal or replacement purges it as well; a regression test pins it. The
[1.0.3 page](v1.0.3-7edcb55.md) records the runtime re-measurement: zero
archived requests after live and offline simulator sessions, and this
release's copies removed from a 1.0.2 container on the first launch of 1.0.3
(simulator only; a phone run has not been done). The remediation as it was
recommended:

**Remediation (client repo).** Give every authenticated request a session
whose configuration has `urlCache = nil` (or `.ephemeral`), or set
`cachePolicy = .reloadIgnoringLocalCacheData` per request; call
`URLCache.shared.removeAllCachedResponses()` when a key is removed or
changed, and once on first launch of the fixed build to purge existing
copies. A regression test that fetches through the production `HTTPClient`
with a marker header and asserts the marker is absent from
`URLCache.shared` would pin it.

text:** those passes streamed the log at the default level, which drops debug lines. Found by the 1.0.4 runtime pass
streaming at debug level; full account and remediation on the
[1.0.4 page](v1.0.4-3abe3e2.md#low-deployed-yes--since-10--reply-text-and-model-written-tool-arguments-are-interpolated-into-unfenced-log-statements).

### LOW (deployed: yes — since 1.0) — the user-edited system prompt is stored in UserDefaults, outside the protected store and inside backups

`AppSettings.systemPrompt` reads and writes `UserDefaults`
(`Settings/AppSettings.swift:28`, `:32`), edited in Settings → Chats through
a `TextEditor` (`Views/Settings/ChatsSettingsView.swift:24`), and lands in
`Library/Preferences/ai.teemoon.app.plist` — observed in the container after
the sessions. That text is sent as the system message of every request, so
it is prompt plaintext the user wrote, and it can carry exactly what the
store's hardening exists to protect (who they are, what they are working on).
Preferences carry the container's default protection class and are included
in iCloud and encrypted Finder backups. Most users never change the default
prompt, which is why this is LOW. **Remediation:** keep it in the hardened
store, or write it to a file with the store's protection class and backup
exclusion.

### Residuals — by design, stated not hidden

Carried from the 1.0 page: opt-in web search is content-driven egress to one
fixed host; provider keys restore via encrypted backup; an unattested provider
is plaintext by definition; user-initiated copies go to the general pasteboard;
E2EE metadata is plaintext by protocol. New at this release:

- **A no-tap re-send exists.** An on-device turn cut off by backgrounding is
  re-sent once on return (`Views/Chat/ChatView.swift:676`), through the same
  gate as a tap, to the provider already chosen, carrying only the user's own
  last message. Not a new destination; recorded because it needs no user
  action.
- **A developer-only stderr capture ships in the release binary.**
  `captureNativeLogIfAsked` (`App/teemoonApp.swift:30-39`) redirects stderr —
  where the LiteRT runtime logs — to `Documents/native.log` when
  `TEEMOON_NATIVE_LOG=1` is in the launch environment. It is env-gated, not
  `#if DEBUG`-fenced, so the code is present in the App Store build; an App
  Store launch has no environment, `Documents` is not exposed via file sharing,
  and reaching it needs Xcode or `devicectl` on a Developer-Mode device the
  user already controls. The app's own stderr lines carry no message text; what
  the native binary prints is the standing *not traced* item above. Hygiene,
  not a leak; a `DEBUG` fence would remove the question.

### Controls that would change the verdict

- A renderer capability that fetches on render (previews, embeds, a web view).
- A second derivation of send authorization anywhere a message can start.
- A model-callable tool that fetches a model-chosen URL or reads other threads.
- `captureNativeLogIfAsked` becoming a user-facing setting.
- A dependency added to `Package.resolved` with its own network client.
- Any new authenticated fetch through `URLSession.shared` while the URL cache
  is still enabled — it will land on disk if the server allows caching.

### Verdict: QUALIFIED-PASS

Messages: private at `21d534e`. The delta adds one network sink (model
downloads) that carries nothing from the conversation, one no-tap send that
goes through the existing gate, and diagnostics that carry no content; a live
session opened no endpoint the map does not name; every property the 1.0
verdict rests on holds and the renderer defence is stronger. Keys: they leave
the device only to their own provider, but the runtime pass found the near.ai
key at rest in the shared URL cache on disk (MEDIUM, since 1.0), so "Keychain
and nowhere else" does not hold until the client stops caching authenticated
requests. One LOW: the user-edited system prompt is in UserDefaults and
backed up. The on-device runtime's egress remains unobserved.

## Addendum 2026-11-25 — a near.ai lookalike host got the encrypted treatment

### LOW (deployed: ARMED, needs the user to add a custom provider whose URL contains "near.ai") — gate: a provider counts as near.ai when its URL contains the text "near.ai" anywhere, so a lookalike host gets the attested, end-to-end-encrypted treatment

Traced at 21d534e (v1.0.2); every line number below was checked at this tag. Paths are under `teemoon/`. A source read: nothing here was run.

- **Precondition.** The user adds a custom provider by hand whose URL contains `near.ai` somewhere: a host such as `near.ai.example.com` or `api.linear.ai`, or a path such as `/near.ai/v1`. No preset does this. The user's own key and messages going to the host they typed is not a leak and is not the finding. The finding is what the app claims about that host, and whose key it seals to.
- **Gate.** The capabilities getter grants `.attestation` and `.endToEndEncryption` when `endpoint.contains("near.ai")` and the model's tier is `.teeOwn` (`Providers/Provider.swift:278-280`). That is a substring test on the whole URL, not a host rule. The tier does not narrow it much: `classify` returns `.teeOwn` for every id it does not recognise (`Providers/NearAIModelCatalog.swift:114-131`, the default at `:131`), and the catalog cache is read only after it (`:90-91`). An id that names a closed vendor (claude, gpt-, gemini, o3, o4, -max) or a known third-party id does not qualify; any other id does.
- **What the capability shows before any check.** The provider's row reads "<provider name> · end-to-end encrypted" (`Presentation/WhereProviderPresentation.swift:154-155`).
- **A model id near.ai does not list: nothing is sent.** The refresh looks the model up in near.ai's own directory, `https://completions.near.ai/endpoints` (`Providers/EndpointDirectory.swift:29`, `:47-53`; `Confidential/ConfidentialSession+Refresh.swift:87-88`). With no host for the id there is no record (`:96-118`), so no seal context (`Confidential/ConfidentialSession.swift:183-190`), and the send is refused with "End-to-end encryption could not be established, so nothing was sent." (`Chat/ChatViewModel.swift:94-95`, `:238`). The row's claim is wrong and the provider cannot be used; no message leaves.
- **A model id near.ai lists: where each request goes.**
  - The plain attestation report: `GET <custom host>/attestation/report`, with the user's key (`Confidential/AttestationService.swift:44-64`, `:99`); the host may answer it or refuse it, and either way the record is built (`Confidential/AttestationService.swift:99`, `:110-117`).
  - The model report, the one that supplies the sealing key: a race between near.ai's direct host for that model and `<custom host>/attestation/report?model=…&signing_algo=ed25519` (`Confidential/AttestationService+Model.swift:40-54`). The first source to return a key wins (`:179-191`); nothing prefers near.ai's answer. The custom host's answer needs a 32-byte key, and a matching `model_name` only if it sends one (`:132-143`).
  - The GPU-node report: near.ai's direct host (`Confidential/AttestationService.swift:92-94`; `Confidential/AttestationService+GPU.swift:52-59`).
  - The TLS check: near.ai's direct host, with no credential (`Confidential/ConfidentialSession+Verifiers.swift:167-185`).
  - The chat request: `POST <custom host>/chat/completions` with the user's key (`Inference/HTTPTransport.swift:59-67`, `:77-81`), its body sealed to the record's `modelEd25519PubKey` (`Inference/ConfidentialLanguageModel.swift:46-52`; `Inference/HTTPTransport.swift:68`, `:92-96`; `Confidential/AttestationService.swift:147`).
- **Whose key the message is sealed to.** Whichever source won the race. If the custom host answers first, the message is sealed to a key that host chose and is posted to that host, which can open it. If near.ai's host wins, the message is sealed to near.ai's enclave key and posted to the custom host, which cannot open it.
- **A key with no quote asked; it did not block.** The state is degraded (`Confidential/ConfidentialSession+Verdict.swift:98-106`), and the break is not a hard one, because that needs a quote that is present and fails (`:211-238`). The send policy is therefore the ask (`:246-261`; `Confidential/TrustVerdict.swift:87-90`), with the reason "The model's hardware attestation is unavailable." (`Confidential/ConfidentialSession+Verdict.swift:162`) and the caption "not end-to-end encrypted" (`Confidential/AttestationState.swift:28`). If the user confirms, the message goes out sealed to that key. A made-up quote fails Intel's check and blocks (`Confidential/DCAPService.swift:100`).
- **A key with a genuine quote reads as verified.** The model quote is checked for three things: it chains to Intel (`Confidential/AttestationService+Model.swift:145-147`; `Confidential/DCAPService.swift:100`), the key sits in its report data (`Confidential/AttestationRecord.swift:128-134`), and it echoes the app's nonce (`:170-186`). Its measurements are compared with no reference. A quote from any genuine TDX guest the host's operator runs, carrying that operator's key and the app's nonce, passes all three. No other degrade condition (`Confidential/ConfidentialSession+Verdict.swift:50-91`) has to fire: the custom host controls the plain report, and the GPU-node report and the TLS check go to near.ai's real host for that model, so whatever genuine evidence that host returns sits on the same screen as the operator's key (whether near.ai answers a request carrying another host's key was not tested). The state is `.ok` (`:103`) and the send is allowed with no ask.
- **What the app then shows.** The caption "end-to-end encrypted" (`Confidential/AttestationState.swift:27`), the hero "encrypted to <model> — only it can read this" with "only you and <model>'s sealed hardware can read this chat." (`Confidential/TrustVerdict.swift:153`, `:177`), and the chain line that says not the provider, not the network, nobody else can open it (`:190-191`). For this provider that is false: the host's operator holds the key. The app shows the provider under the name the user gave it, not as near.ai.
- **The user's key for the custom host also reaches near.ai's hosts.** The credential stored for the custom provider (`Confidential/ConfidentialSession+Refresh.swift:71`, `:121-124`) is sent as a bearer token to near.ai's direct host for that model, on the GPU-node report and on the direct model report (`Confidential/AttestationService.swift:44-64`, `:92-94`, `:95-97`; `Confidential/AttestationService+GPU.swift:59`; `Confidential/AttestationService+Model.swift:40-46`, `:109`). This needs no hostile party, only the precondition and a model id near.ai lists. For such a provider this page's statement that a key leaves the device only to its own provider does not hold: near.ai receives a key the user stored for another host.
- **Severity and state.** LOW, ARMED. Not INFO: under the precondition the app's central sentence is false, the verified state can be reached by a host that is not near.ai with a key it chose, and a key goes to a host the user did not configure. Not MEDIUM: nothing happens until the user types such a URL into a custom provider and picks a model id near.ai lists; the message reaches only the host the user typed, which is where a custom provider's messages go with no claim at all, so no third party gains a message; the verified state needs a host built for the purpose that also runs real TDX hardware, and without a genuine quote the app asks or blocks; the key that strays goes to near.ai and nowhere else. What is lost is the assurance: a user who believed the screen could send that host what they would not have sent it in the clear. No report of a provider configured this way is known to this review.
- **Fixed in v1.0.4.** At 3abe3e2 the getter tests `isNearAI` (`Providers/Provider.swift:285`), which is the host rule `host == "near.ai" || host.hasSuffix(".near.ai")` (`Providers/WhereLocality.swift:85-90`; `Providers/EndpointModelCatalog.swift:149`). No `contains("near.ai")` and no `hasSuffix("near.ai")` is left in the app's Swift source at that tag. A lookalike host gets neither capability and is an ordinary custom provider with no encryption claim.
