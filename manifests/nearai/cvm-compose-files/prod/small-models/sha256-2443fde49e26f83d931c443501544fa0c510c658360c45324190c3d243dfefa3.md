## Findings

### CRITICAL (deployed: ON) — FLUX logs every user prompt at INFO to stdout, and this file's otelcol pipeline ships it off-box (log + egress)

The base page listed the FLUX base image `lmsysorg/sglang@sha256:8ece90ad…` as "observed, not audited". Its review has since published with a **LEAKS** verdict ([image page](/images/docker.io/lmsysorg/sglang/sha256-8ece90ad52faa8b56149f0117227d9009db34513213e35990da468aeb6fe0b75.md)): the diffusion server's `SamplingBatch.log()` interpolates the prompt and negative prompt verbatim into a `logger.info` on the generation path of every request, and the deployed `--log-requests-level 0` (line 177) is **silently discarded** by the diffusion entrypoint's `parse_known_args` — it was never the control, and no deployed flag or env suppresses the line (`environment: *sglang-env`, 184 → anchor 53-61 sets no `SGLANG_DIFFUSION_LOGGING_LEVEL`; the command sets no `--log-level`).

This file completes the egress: the container logs via `json-file` (anchor 1-6, merged via `x-flux-common` ← `x-vllm-common` `logging: *logging-conf`, 27), otelcol-contrib tails `/var/lib/docker/containers/*/*-json.log` (1478-1479), `filter/app_logs` drops only management containers (2036-2045) — the FLUX container passes — and `otlphttp/gateway` exports to the literal `https://telemetry.infra.near.ai` (2072-2073) via the `logs` pipeline (2088-2091). **No processor redacts content.** Under the threat model, an image-generation prompt is user plaintext, and it reaches a telemetry backend on every request: plaintext leaves the trust boundary. Severity is CRITICAL at this layer because the manifest is what wires the confirmed log line to the egress; the image page carries the HIGH for the log line itself.

At the deployed flags nothing in this file can turn this off; the only in-recipe fix is changing the FLUX service (log level env, or an engine without the hot-path print).
