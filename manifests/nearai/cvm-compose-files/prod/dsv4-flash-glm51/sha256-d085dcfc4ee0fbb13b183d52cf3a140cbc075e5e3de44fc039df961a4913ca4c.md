The checks the brief asks for, answered against both:

- **`--log-requests-level 0` on every sglang service — yes: line 80 (DeepSeek anchor, both replicas) and line 147 (GLM-5.1).** Level 0 is the minimum and is *below* the code default of 2 (at which prompt and output text first appear). Per the engine reviews it is also inert on its own, because `--log-requests` is absent so `log_requests` defaults `False` and every logger early-returns. Deliberate defence in depth; **not** a mitigation for the CRITICAL, since `/configure_logging` overrides both the level and the boolean in one call.
- **`--log-requests` — absent** from both commands. No per-request logging entry point is enabled at boot on any of the three engines.
- **`--api-key` / `--admin-api-key` — absent everywhere in the file.** Grepped the whole document for `api.key`: the only hits are `WEB_CONTEXT_SEARCH_API_KEY` on the three proxies (271, 314, 359). **[HIGH — omission]** Setting `--admin-api-key` would install SGLang's auth middleware and convert `/configure_logging`, `/start_profile`, the weight-update routes and ~30 other administrative endpoints from open to bearer-gated on all three engines. It is one flag per engine, already implemented upstream, and it is the single highest-value change available to this document. Its absence is what keeps the engines' CRITICAL live at this deployment.
- **`--revision` on every model — yes, and it is complete.** DeepSeek `553034d7…` (line 58) and GLM-5.1 `8f60817a…` (line 139), with the `model-downloader` pre-fetching **the same two revisions** (188, 190). **Both engines run `--trust-remote-code` (56, 160) and both are revision-pinned**, so upstream HF-head drift cannot inject code into either plaintext process. This is the gap that was found open on `small-models.yaml` (FLUX running `--trust-remote-code` with **no** `--revision`) and on the dsv4-qwen36-gemma4 node; **it is closed here on both engines.** Positive.
- **`--watchdog-timeout 1800` on all three** (68, 155) — the trigger for the engine HIGH. No `--soft-watchdog-timeout`. Blast radius per fire: up to 64 in-flight requests per DeepSeek replica, 128 on GLM-5.1.

**[MEDIUM — and this is the finding unique to this recipe] One `${VAR}` interpolation sits inside an engine command: `${DSV4_RETURN_HIDDEN_STATES:+--enable-return-hidden-states}` (line 82).** Every other recipe reviewed in this repo has **zero** interpolation in its engine commands — the GLM-5.2 pages state that explicitly as a positive ("no operator env, measured or spliced, can alter an engine flag"). Here, an operator-supplied environment variable appends a flag to a plaintext process's argv, on both DeepSeek replicas. Assessed precisely:

- **This page answers a question the engine review left open.** The [`6bb5fee3` page](/images/docker.io/lmsysorg/sglang/sha256-6bb5fee34b6c4537c09a4775e2292ac40350d5ad1218fcc835b2692142f443b1.md) records the `allowed_envs` membership of `DSV4_RETURN_HIDDEN_STATES` as *"a manifest question, not answerable from this source tree; INCONCLUSIVE here."* **Answer: it is NOT in the node's 22-entry `allowed_envs`** ([measured page](/manifests/measured/sha256-d98a2568546afce9ab53f7eb4d4b2058e5497e1efd05a8ad0934793043240ed7.md), Check 1). So the measured dstack env channel **cannot** set it; the only remaining route is compose-manager's `POST /compose/up` env overlay (not covered by this `file_sha256`, not recorded in the signed action log at the audited compose-manager builds).
- **Impact if flipped is bounded, per the traced source.** With the flag on, a client that also sets `return_hidden_states=true` receives **only the last token's** hidden state, attached to **its own** response, over the **same** HTTP channel to the **same** caller. The engine review's trace conclusion is explicit: *"enabling it creates no new data path and no new actor… It is not a plaintext leak even when on."* Deferred to that page; not re-derived.
- **The residual is compositional, and it is why this is MEDIUM rather than INFO.** Hidden states live in `out["meta_info"]["hidden_states"]` and are **not** in the finished-request logger's `out_skip_names`, so they *would* appear in request logs at any level — but only if `--log-requests` is already on, which is itself the engine HIGH. The real finding at this layer is structural: **the file establishes the precedent that an engine's argv is env-shaped.** A future variable spliced the same way need not be as benign, and nothing in this document constrains the pattern.

### Check 3 — Telemetry pipeline: the full stdout chain, and whether anything scrubs **[priority]**

**Result: a fixed, hash-pinned, entirely unscrubbed path from all three engines' stdout to an off-box endpoint.**

1. **Retention on the CVM disk first.** Every service uses `x-logging-conf` (18-23): `driver: json-file`, `max-size: 100m`, `max-file: 10` — **up to ~1 GB of retained stdout per container**, before anything ships it. If the CRITICAL is ever triggered, that is 1 GB of prompt and completion text at rest per engine, times three engines.
2. **`otelcol-contrib`'s `filelog` receiver tails all of it**: `include: [/var/lib/docker/containers/*/*-json.log]` (655-656), mounted `/var/lib/docker/containers:ro` (615), running `user: "0:0"` (602).
3. **A long chain of `regex_parser` operators (684-747)** lifts `model`, `served_model`, `deployment`, `ip`, `port`, `env`, `host`, `instance`, `gpu_pair`, `ppcie`, `config_variant`, `quantization`, `eagle`, `eagle_prefill_fairness`, `sglang_revision`, `engine_image` out of the `com.datadoghq.ad.logs` label. These parse the **label**, never the log body.
4. **`transform/docker_metadata` (985-995)** resolves `service.name` / `log.source` from the Docker labels.
5. **`filter/app_logs` (997-1006) is the *inverse* of the measured harness's filter** — it drops any record with neither `model` nor `deployment` attribute, plus `compose-manager`, `compose-manager-launcher`, `otelcol-management`, `otelcol-contrib`, `datadog-agent`, and **keeps the app containers: all three sglang engines, all three proxies, nginx, both dcgm exporters, the registrar, the downloader.**
6. **Export:** `otlphttp/gateway` -> `endpoint: https://telemetry.infra.near.ai` (1039-1040), literal, `Authorization: Bearer ${MONITORING_INGEST_TOKEN}` (1042), with a **disk-backed sending queue** (1043-1045) written to `/var/lib/otelcol-contrib/storage` (1049) — so log bodies also transit a named volume (`otelcol_app_storage`, 616, 636) on their way out.

**[HIGH — systemic] No scrubbing exists at any hop.** The processor chain for `logs/app` is `memory_limiter, resource, transform/docker_metadata, filter/app_logs, groupbyattrs/docker_service, batch` (1057). Not one of them redacts, hashes, truncates or pattern-matches a log body. The `com.datadoghq.ad.logs` and `nearai.otel.*` labels are routing metadata — they *tag* streams, they never select or scrub content. **So the complete chain is: anything any of the three engines prints -> json-file (~1 GB retained) -> filelog -> [no scrubbing] -> `https://telemetry.infra.near.ai`.** Both engine residuals terminate exactly here.

- **On this node specifically, that is the *only* measured off-box log destination**, because the measured harness [`d98a2568…`](/manifests/measured/sha256-d98a2568546afce9ab53f7eb4d4b2058e5497e1efd05a8ad0934793043240ed7.md) starts **no Datadog agent**. The `com.datadoghq.ad.*` labels this file attaches to every service (197, 223, 249, 273, 316, 361, 397-398, 444-445, 502-503, 545, 578, 628) are consumed here only by the OTel regex parsers; with no agent present they ship nothing to `us3.datadoghq.com`. **If this same recipe ran on the sibling harness [`0fccab4e…`](/manifests/measured/sha256-0fccab4eb7ffc4c9ec1be8e2851e7b820efef0485cfd21ac027bf1408dc836b0.md), `DD_LOGS_CONFIG_CONTAINER_COLLECT_ALL=true` would additionally route every engine log line to Datadog.** The labels are written for a fan-out this node does not have.
- **[MEDIUM] Two open OTLP receivers with no scrubbing**: `otlp` on `0.0.0.0:4317` (grpc) and `0.0.0.0:4318` (http), lines 648-653. They are `expose`d only (611-613), not published to the host — but the network is the shared `external: true` bridge (Check 4), so **any container on `dstack_default` can push arbitrary telemetry into near.ai's pipeline through them.** Precisely scoped: at this config the `otlp` receiver feeds only `metrics/otlp` and `traces` (1063-1074), **not** the logs pipeline — so it is a *span* content risk, not a log-injection one. Per-request and user-attributable, but not message content. It rides the same pipeline off-box.

## Cross-check synthesis

- **[X1 / CRITICAL — exposure, not capture] Three unauthenticated `/configure_logging` endpoints are reachable, and this document is why.** `external: true` shared network (630-633) + six bare `location /` blocks + no `--admin-api-key` + a downstream pipeline that ships stdout verbatim off-box. Nothing here *captures* content; everything here declines to *contain* the mechanism that would. A single unauthenticated POST from any co-resident container, or an authenticated one from any caller with an accepted bearer, flips an engine from logging nothing to logging every prompt and completion — with no restart, no measurement change, and no action-log entry.
- **[X2 / HIGH] The watchdog dump has a fixed, unscrubbed exit path, on three engines.** `--watchdog-timeout 1800` (68, 155) is deployed on all of them; the dump is undisableable by configuration; the log pipeline in Check 3 carries whatever it prints to `telemetry.infra.near.ai`. Up to 64 in-flight requests per DeepSeek replica, 128 on GLM-5.1.
- **[X3 / HIGH — systemic] Global app-stdout shipping is a fixed feature of this file.** `filter/app_logs` keeps precisely the plaintext-handling containers. The manifest proves no content is collected **only if no service prints content** — for two model families and two proxy builds simultaneously.
- **[X4 / HIGH] Two content-egress switches on the E2EE terminators sit outside `allowed_envs` but inside reach of the non-measured `/compose/up` env overlay** (`WEB_CONTEXT_SEARCH_*`, `FUSION_*`), on all three proxies.
- **[X5 / MEDIUM] The engine argv is env-shaped here.** `${DSV4_RETURN_HIDDEN_STATES:+--enable-return-hidden-states}` (82) is bounded and benign per the engine trace, and the variable is **not** in `allowed_envs` — but it is the only engine-command interpolation in this repo's manifest set, and the pattern it establishes is not self-limiting.
- **[X6 / MEDIUM] Co-tenancy concentrates everything.** Two customer-facing models, three engines, three privileged proxies, one flat bridge, one IPC namespace, one log pipeline, one root-equivalent control plane on the harness. Nothing here is a leak; the observation is that any single containment failure on this node reaches two models' users.

## Verdict

**Qualified PASS — clean on what it configures, with the same containment gaps as its siblings and two structural aggravations of its own.**

- **What this file configures:** clean. Every logging flag is literal and minimal; `--log-requests-level 0` is set explicitly on all three engines and `--log-requests` is absent; no dump, crash, profile or trace flag exists; **both** `--trust-remote-code` engines are revision-pinned and the downloader pins the same revisions; `OHTTP_ENABLED=true` is literal on all three proxies; telemetry destinations are literal; there is **no KV or prompt disk cache**; the two proxy builds' privacy-relevant env is identical; dcgm is digest-pinned, GPU-scoped and unpublished; and no tag-only image appears anywhere. On the configured path, **no plaintext copy is written to any log, file, cache or network destination.**
- **What this file fails to contain:** the engines' own live paths. It leaves `/configure_logging` reachable on three engines by two independent routes, declines the one flag (`--admin-api-key`) that would gate them, and guarantees that anything any engine prints leaves the CVM unscrubbed. **The invariant this layer delivers is "content capture is not configured", not "content capture cannot be enabled".**
- **Its own two aggravations:** an engine command that reads an operator-supplied env var, and two model families sharing one unsegmented network, one IPC namespace and one log pipeline.
- **Recommended, in order:** (1) pass `--admin-api-key` to all three engines; (2) put the engines on a project-private network instead of `external: true dstack_default`, or add a path allowlist to the inlined nginx config (which is in this very file, 1252-1327, and therefore covered by `file_sha256`); (3) add a scrubbing/deny processor to `filter/app_logs` for engine-sourced records; (4) make `--enable-return-hidden-states` a literal (present or absent) rather than an interpolation.

**Unverifiable at this layer (hand-offs):** whether the action log currently pins this `file_sha256` and which commit/tag it names (I verified the file's own hash, not its provenance — the material supplied carried no commit); whether the deployed `b183677a` and `b0c5cd07` trees apply any path filtering (inherited from the `b0c5cd07` review, not re-derived, and not re-derived for `b183677a` at all); how `WEB_CONTEXT_SEARCH_*` / `FUSION_*` / `MODEL_PROXY_TOKEN` / `CLOUD_API_USAGE_TOKEN` / `HF_HUB_OFFLINE` / `DSV4_RETURN_HIDDEN_STATES` / `TLS_PORT*` obtain their values and whether empty is fail-closed (proxy source — if so, the Check 4 HIGH downgrades); the effective log level of either proxy build, since no `RUST_LOG`/`LOG_LEVEL` is set (source leg); whether nginx actually spills bodies to `client_body_temp` on this image, and what the OS does with that file afterwards; whether any of the six published ports is reachable from outside the CVM (dstack guest port handling); the bytes behind `dcgm-exporter@sha256:ed594cf5…` (digest-pinned but not yet reviewed in [`images/`](/images/)); whether the three engines, the proxies or nginx ever *print* request content at the configured levels (source legs — load-bearing given X3); the guest OS's swap and core-dump policy ([`os/`](/os/)).
