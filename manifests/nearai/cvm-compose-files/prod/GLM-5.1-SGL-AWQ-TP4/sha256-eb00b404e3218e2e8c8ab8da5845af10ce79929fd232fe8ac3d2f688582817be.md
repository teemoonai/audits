- **[HIGH] Gateway `MODEL_DISCOVERY_SERVER_URL` + `MODEL_DISCOVERY_API_KEY`** — the operator can repoint cloud-api's endpoint discovery at an arbitrary server with no measurement change. On the non-OHTTP path this is a plaintext-routing primitive; OHTTP payloads stay sealed to the model node's attested key regardless. Needs cloud-api source confirmation of routing precedence.
- **[HIGH] Gateway `ENABLE_CHUTES` / `CHUTES_MODELS` / `CHUTES_API_KEY`** — an entire third-party provider path is enabled and handed an arbitrary model list purely via env (defaults are hard-off). If `CHUTES_MODELS` can shadow TEE-served model ids, non-OHTTP plaintext for those models leaves the attested path. The source leg must confirm shadowing is impossible.
- **[MEDIUM] Gateway `OHTTP_ENABLED`** (default `false`) — the operator can silently disable the OHTTP gateway. This fails *visible* (the feature is off), not as capture, but it is an E2EE kill-switch outside the measurement. (The model-node proxy's `OHTTP_ENABLED=true` is literal — good.)
- **[MEDIUM] Gateway `OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `GEMINI_API_KEY` / `BRAVE_*` keys** — external plaintext-egress providers keyed by operator env; harmless to the GLM TEE path only if routing can't cross over.

### Check 4 — Telemetry pipelines **[HIGH — systemic]**

The Datadog agent on **both** CVMs runs `DD_LOGS_CONFIG_CONTAINER_COLLECT_ALL=true` and mounts `/var/lib/docker/containers:ro` — the **full stdout/stderr of every container** (sglang, vllm-proxy, nginx, cloud-api, ingress) ships to `us3.datadoghq.com`. `DD_PROCESS_AGENT_ENABLED=true` additionally ships process cmdlines. Three OTel collectors (digest-pinned) tail the same container logs and export to `https://telemetry.infra.near.ai`; metrics are Prometheus scrapes (counters only).

No receiver ingests request bodies *by configuration*, and all destinations are literal — but the consequence is that the manifest layer does not contain content capture; it *guarantees* that anything a plaintext-handling service ever prints leaves the TEE to a third-party US SaaS. The privacy property degenerates to "the engine/proxy/api never print content" — a source-discipline question this layer cannot answer (see C3).

**[MEDIUM]** The OTLP receivers on `0.0.0.0:4317/4318` forward verbatim with **no content-scrubbing processor** — if any service ever emits prompt-bearing spans, these ship them.

### Cross-check synthesis — architectural findings

- **[C1 / HIGH] The hardware measurement does not cover the engine's configuration.** The measured model-CVM manifest contains only the management harness; the engine compose — sglang flags included — is fetched at runtime by compose-manager from GitHub at an operator-chosen tag/commit. An operator with repo push access + `BEARER_TOKEN` could deploy an inner compose with `--log-requests` (or a hostile image) with no measurement change. **Compensating control:** every action is disclosed in the attestation report's `compose_manager_attestation` log with `file`/`commit`/`file_sha256` (verified live: the latest entry matches the audited file), so clients that pin and verify the inner-compose hash — as teemoon's verifier does — detect it. The guarantee is *transparency + client verification*, not measurement.
- **[C2 / HIGH] The enforcement point is root-equivalent and self-updating.** compose-manager can ptrace sglang and read plaintext memory; the launcher swaps its image to any build cosign-signed by the nearai CI workflow on the (measured) `LAUNCHER_CHANNEL`. Confirmed live: the running image `@6e035c8f…` ≠ the manifest-pinned `@b487f391…`. Content-capture capability inside the measured TCB is one signed CI build away; the trust anchor is nearai's GitHub org + CI, mitigated by the action log's `compose_manager_started` disclosure.
- **[C3 / HIGH] Global stdout exfiltration is a fixed feature** (Check 4): all container logs on both CVMs ship to Datadog + near.ai by measured config. The manifest layer proves *no content is collected only if no service prints content*.

### Verdict

**Qualified PASS.**

- **Within hardware-measured config + `allowed_envs`:** upheld. No allowed env is a debug/log/telemetry-content switch; every engine flag and telemetry destination is literal; the operator cannot flip on content capture by env alone.
- **As an end-to-end claim:** the two measured-in escape hatches — the runtime-fetched inner compose (C1) and the cosign-gated, ptrace-capable, self-updating compose-manager (C2) — let a repo/CI-authorized operator change plaintext-handling behavior with an unchanged measurement, *but both leave a signed, client-verifiable trace in the attestation action log.* So the real invariant is **"content capture cannot be enabled without either changing the measurement or leaving a signed, client-verifiable trace."** Plus (C3): the manifests permanently ship all container stdout off-box, so the no-content-leaves guarantee is only as strong as every service's discipline about what it prints.

**Unverifiable at this layer (hand-offs):** TDX quote/signature verification of the attestation report itself; how the non-`allowed_envs` interpolated vars (`WEB_CONTEXT_SEARCH_*`, `FUSION_*`, `MODEL_PROXY_TOKEN`) get their values — if empty means fail-closed, the Check 6 HIGH downgrades (source leg); whether SGLang/vllm-proxy/cloud-api ever *print* request content (source legs — load-bearing given C3); whether `CHUTES_MODELS` / `MODEL_DISCOVERY_SERVER_URL` can reroute TEE-served model ids (cloud-api source); the dstack OS image hash + disk-encryption posture.
