## Check 3 — The otelcol-management log pipeline: is the filter fail-closed? **[the load-bearing question]**

**Result: fail-CLOSED, by two independent mechanisms — verified against this document's config, not carried over on trust.**

The chain: every container using the `json-file` driver — per the recipe's shared anchor (recipe `:95-100`) that is the engine, the proxy, nginx, the registrar and dcgm — writes `/var/lib/docker/containers/<id>/<id>-json.log`; this collector's `filelog/docker_containers` receiver tails exactly that glob (`:223`, `start_at: end`, `:224`). **The receiver ingests the flagship engine's stdout.** Between it and `https://telemetry.infra.near.ai` (`:341`) stands the `logs/cvm` processor chain (`:358`): `memory_limiter, resource, transform/docker_metadata, filter/management_logs, groupbyattrs/docker_service, batch`.

Record by record:

1. **Receiver operators** (`:227-253`, in order): `json_parser` (`on_error: send_quiet`, `:235` — malformed lines pass on unparsed, not dropped); `move` of text to body; container-id regex from the path (`on_error: send_quiet`, `:250`); then, **last and unconditional**:

   ```
   - type: add
     field: attributes["service.name"]
     value: cvm-docker
   ```

   (`:251-253`). No `if` clause — it runs for every record, including ones whose parse failed. **Every record leaves the receiver with `service.name = "cvm-docker"`; the nil case cannot occur in this document.**

2. **`transform/docker_metadata`** (`:311-319`, `error_mode: ignore`) overwrites `service.name` from the container's exported log labels (`com.docker.compose.service`, then the `service` field of `com.datadoghq.ad.logs`), each statement nil-guarded. Management containers (labels at `:54`, `:85`, `:138`, `:186`, exported via `:60`, `:91`, `:144`, `:192`) become `compose-manager` / `compose-manager-launcher` / `dns-cloudflare`; recipe containers become their own names (`sglang`, `vllm-proxy`, `nginx`, …, recipe `:239`, `:278`); a failed statement leaves `cvm-docker`.

3. **`filter/management_logs`** (`:321-325`): one condition — `service.name` not equal to any of the three management names → **dropped** (the filterprocessor drops when a condition is met). Every engine record — named or defaulted — satisfies it.

4. **The hypothetical nil case:** OTTL map indexing returns nil (not an error) for a missing key, so the one genuinely fail-open door — `error_mode: ignore` skipping an *erroring* condition and passing the record — is not reachable via a missing attribute; and nil compared to a string is "not equal", so the condition is true and the record drops anyway. Semantics per the collector-contrib `pkg/ottl`/filterprocessor documentation for the deployed line; the image is the digest-pinned, [separately audited](/images/docker.io/otel/opentelemetry-collector-contrib/sha256-85ac41c2db88d0df9bd6145e608a3cb023f5d8443868adbfbbf66efb51087917.md) `85ac41c2…` (`:5`).

So: label resolves → non-management name → dropped; label missing → `cvm-docker` → dropped; parse error → `cvm-docker` → dropped; attribute hypothetically absent → nil → dropped. Only records whose labels *claim* a management identity are exported. This matches the sibling-node mechanism exactly, confirmed here line by line.
