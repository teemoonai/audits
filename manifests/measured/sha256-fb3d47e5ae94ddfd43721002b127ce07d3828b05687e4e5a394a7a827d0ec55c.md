## Check 2 — The compose-manager image: a default, not a pin — and measured-in drift persistence **[HIGH — architectural, = C2]**

The known fleet lead, confirmed here in its strongest form:

1. **The image reference is env-overridable:** `image: ${COMPOSE_MANAGER_IMAGE:-nearaidev/compose-manager@sha256:5165400d9eb43ab5da36986a85de0ba55f3fb4d05211c4397ecc4bde3ef0113b}` (line 125). The digest is a *fallback*, not a pin. `COMPOSE_MANAGER_IMAGE` is not in `allowed_envs`, so the measured env channel cannot set it —
2. — but this node's **`pre_launch_script` (part of the measured `app_compose`) sets it at every boot**: it reads `/var/lib/docker/volumes/dstack_work/_data/.env.launcher` — a file the *launcher* persists on a docker volume — and `export`s any `COMPOSE_MANAGER_IMAGE` line found there ("Restore the launcher's last-known-good image override so a CVM reboot doesn't revert compose-manager to the Ansible-baked fallback digest"). The script parses the file as data, not source (the comment itself notes sourcing "is a root-RCE path"), and a forced-repin branch is compiled out at this measurement (`if [ "false" = "true" ]`).
3. The launcher swaps that image to any build cosign-signed by `LAUNCHER_COSIGN_IDENTITY_REGEXP=https://github.com/nearai/compose-manager/.github/workflows/.*` (line 205) on the operator-chosen channel, then writes the new digest to `LAUNCHER_ENV_FILE=/app/work/.env.launcher` (line 198) — the same file step 2 replays at boot.

**Consequence:** the digest in the measured manifest is only the *first-boot* value. Afterward, the measured boot path itself re-installs whatever digest the launcher last wrote, indefinitely, across reboots — post-attestation mutability of the root-equivalent deployer is not an accident here but a *measured-in mechanism*. Compensating controls are unchanged from the fleet pattern: the swap target must be nearai-CI-cosign-signed, and swaps are disclosed in the attestation action log (`compose_manager_started`). The fallback digest itself is audited: [`compose-manager@5165400d`](/images/docker.io/nearaidev/compose-manager/sha256-5165400d9eb43ab5da36986a85de0ba55f3fb4d05211c4397ecc4bde3ef0113b.md) — verdict *COMPROMISABLE by credentialed operator (control-plane; no data-plane role)*, with a **signed GitHub build attestation** resolving it to source commit `69c363ea`. Whether the digest *running right now* equals the fallback is runtime state this layer cannot see — verify against the live action log.

## Check 3 — Privileges and mounts

## Check 4 — Telemetry pipeline **[HIGH — systemic, = C3]**

- **datadog-agent** (digest-pinned, [audited](/images/docker.io/datadog/agent/sha256-5556fb80b952832719a76b016f905616c76ee0989a239c4680c6220148e865d6.md)): `DD_LOGS_ENABLED=true` + `DD_LOGS_CONFIG_CONTAINER_COLLECT_ALL=true` (lines 10-12) with the container-log mount — the **full stdout/stderr of every container in the CVM**, including all nine plaintext-handling engines and proxies of the inner stack, ships to `us3.datadoghq.com`. The only exclusion is itself (`DD_CONTAINER_EXCLUDE_LOGS=name:datadog-agent`, line 13). `DD_PROCESS_AGENT_ENABLED=true` (line 14) additionally ships process cmdlines; the journald config collects container journal logs with an in-manifest `TODO: Add filters to reduce log volume` (line 247). The agent also runs an **OTLP receiver on `0.0.0.0:4317` with `DD_OTLP_CONFIG_LOGS_ENABLED=true`** (lines 11, 20) — any service on the shared network can push OTLP logs that forward to Datadog verbatim.
- **otelcol-management** (digest-pinned, [audited](/images/docker.io/otel/opentelemetry-collector-contrib/sha256-85ac41c2db88d0df9bd6145e608a3cb023f5d8443868adbfbbf66efb51087917.md)): tails the same JSON logs but `filter/management_logs` **drops every record not from `compose-manager` / `compose-manager-launcher` / `dns-cloudflare`** (lines 330-334) before exporting to the literal `https://telemetry.infra.near.ai` (line 350). Management-filtered — the app-side shipping is done by the inner stack's otelcol-contrib instead (recipe page, Check 4).
- **No redaction stage exists anywhere in either pipeline.** The chain from a plaintext-handling container's stdout to an off-box endpoint is: process prints → json-file log driver → (a) datadog-agent collect-all → Datadog US SaaS, and (b) filelog receiver → filter (routing only, no content scrubbing) → near.ai telemetry gateway. The manifest guarantees anything those services ever print leaves the TEE; "no content leaves" therefore rests entirely on source-level print discipline — the load-bearing reason the per-engine source audits exist.

## Check 5 — Network topology and egress

- The harness creates the shared bridge `dstack_default` (lines 221-226); the inner compose joins it as `external: true`. The in-manifest comment says the point is that app-side telemetry can reach management services without a CVM restart. **No `internal: true`, no egress restriction** — combined with the inner stack, one flat network spans management and all plaintext services **[MEDIUM]**.
- Published ports: compose-manager's control API on `8080:8080` (line 129) — reachable on the guest host interface; auth is `BEARER_TOKEN`. The launcher is on the host network outright.
- Named outbound destinations, all literal except the flagged env: `us3.datadoghq.com` (datadog), `https://telemetry.infra.near.ai` (otelcol-management), `https://github.com/nearai/cvm-compose-files` (compose-manager `GITHUB_REPO`, line 157), Docker registries (image pulls; `DOCKER_REGISTRY_USER/TOKEN`), Let's Encrypt + Cloudflare DNS (certbot), S3 (`AWS_*`), and the operator-set `SLACK_WEBHOOK_URL`.
- `pre_launch_script` also sets `vm.swappiness=0` ("prevent KV cache swap-out") — privacy-positive: prompt-derived KV pages stay out of swap.

## Cross-check synthesis

- **[C1 / HIGH]** The hardware measurement does not cover the plaintext stack's configuration: every engine flag, proxy env, telemetry filter, and nginx rule lives in the runtime-fetched `prod/small-models.yaml`, pinned only by the signed action log. Guarantee = transparency + client verification, not measurement. This node's literal `MIN_TAG_AGE_HOURS=2` narrows (does not close) the deploy-latency lever.
- **[C2 / HIGH]** The enforcement point is root-equivalent and self-updating (Checks 2-3), the swap-executor's image is provenance-INCONCLUSIVE, and — new in this measurement — drift persistence across reboots is itself measured in.
- **[C3 / HIGH]** Global stdout exfiltration is a fixed feature (Check 4), with zero redaction stages.

## Verdict

**Qualified PASS.** Within hardware-measured config + `allowed_envs`, the invariant holds: the 21-entry list contains no debug/log/telemetry-content switch, all telemetry destinations are literal, and this node uniquely hard-codes the tag-age floor. As an end-to-end claim, the fleet invariant applies unchanged: **content capture cannot be enabled without either changing the measurement or leaving a signed, client-verifiable trace** — via C1 (log-pinned inner compose) and C2 (cosign-gated, action-log-disclosed compose-manager swaps, now with measured-in persistence), with C3 making everything conditional on source-level print discipline for the nine plaintext services next door.

**Unverifiable at this layer (hand-offs):** which compose-manager digest is *currently* running (persisted override state + action log, not config); whether `/compose/up` env splices are recorded in the signed action log (compose-manager source pages); TDX quote/signature verification of the attestation report itself; the content of `/dstack/.host-shared/.decrypted-env` (operator secrets — the measured channel constrains the *names* via `allowed_envs`, the splice channel does not); launcher behavior in detail (its image is provenance-INCONCLUSIVE, so unlike compose-manager there is no source page to defer to); everything inside the inner compose — see the [recipe review](/manifests/nearai/cvm-compose-files/prod/small-models/sha256-a385f19a51054767b8be49a64ebc3111e0e62f721a861e54c78984b186904599.md).
