# Deployment Manifests & Configuration — Privacy Audit

> Method: [`/notes/method.md`](/notes/method.md) (§4 Manifest-only checks)

**Role:** the layer that makes the plaintext-handling processes trustworthy. An operator can change only the env vars in `allowed_envs` without a new hardware measurement — so the questions are what the fixed config does, and what the allowed envs could do.

**Why this node matters:** it is a *shared* node. Two different customer-facing models — `deepseek-ai/DeepSeek-V4-Flash` and `zai-org/GLM-5.1-FP8` — run their engines and their E2EE-terminating proxies inside this one CVM, on this one flat network, under this one compose-manager. The engine pages for both builds deployed here ([`sglang@6bb5fee3`](/images/docker.io/lmsysorg/sglang/sha256-6bb5fee34b6c4537c09a4775e2292ac40350d5ad1218fcc835b2692142f443b1.md) and [`sglang@aac6b242`](/images/docker.io/lmsysorg/sglang/sha256-aac6b242680daeb74d2ab1d85f70575357552d7d165d2e5d30eb362797db54a1.md)) return **PRIVATE at deployed flags** with the same **CRITICAL** residual — an unauthenticated `/configure_logging` that turns on full prompt+output logging and arbitrary-path request dumping at runtime, with no restart and no attestation-visible change — plus the watchdog **HIGH** (prompt and output token ids dumped to stdout on a 30-minute hang). Neither is a finding *about* this document. But **how exposed they are is decided here and in the recipe**: the network topology says who can reach port 8000, and the telemetry pipeline says where the engines' stdout goes if the switch is ever flipped. Those two are the priority of this page.

### Check 2 — Privileges and mounts

- **[HIGH — architectural] `compose-manager` is root-equivalent and can read engine memory.** `pid: host` (`:117`), `cap_add: [SYS_ADMIN, SYS_PTRACE]` (`:118-120`), read-write `/var/run/docker.sock` (`:122`), `/var/run/dstack.sock` (`:123`), the decrypted CVM env at `/dstack/.host-shared/.decrypted-env:/app/.env:ro` (`:124`). The manifest's own comment (`:100-116`) spells out the rationale: the caps exist so it can `nsenter -t 1 -m -u -i -n -p` into PID 1's namespaces, and it records that dstack-OS ships no AppArmor (*"verified 2026-05-19 — no apparmor binaries/profiles in the rootfs, no AppArmor strings in bzImage"*), so no `security_opt` line is needed. With `SYS_PTRACE` plus host PID namespace it can attach to **any process in the CVM — here that is three plaintext-handling proxies and three inference engines**, i.e. prompt plaintext in process memory for *both* models at once. This is capability, not configured behavior: the [compose-manager source review](/images/docker.io/nearaidev/compose-manager/sha256-6e035c8fb99c1d31f41760d25af178683a658cca4afd73cd0d366fbb5bf884be.md) traced the binary exhaustively and found **no code path that uses it** to read another process's memory. The finding is that the capability sits inside the measured TCB, that the image carrying it is swappable (Check 5), and that on this node one such container straddles two models' plaintext.
- **[HIGH — architectural] `compose-manager-launcher` runs `network_mode: host` (`:156`) with read-write `docker.sock` (`:158`)** and the decrypted env read-only (`:162`). Anything that can drive that socket can start a container with any privilege on this host.
- **[MEDIUM] `otelcol-management` mounts the entire guest root filesystem read-only** — `/:/hostfs:ro` (`:22`) — plus `docker.sock:ro` (`:18`) and `/var/lib/docker/containers:ro` (`:23`), running as `user: "0:0"` (`:8`). The mount exists for `hostmetrics` root-path parity (`:19-21`, and `root_path: $${env:CVM_HOSTMETRICS_ROOT_PATH}` at `:257`, fed by `CVM_HOSTMETRICS_ROOT_PATH=/hostfs` at `:16`). Consequence: the collector process can *read* every file in the guest, including any file an engine writes — which is exactly where a runtime-enabled `dump_requests_folder` would land. At this configuration nothing exports arbitrary file content (Check 3); the capability is unused, not absent. **This mount is present here and absent on the sibling `0fccab4e…`**, which mounts container logs only.
- **[INFO] `certbot` / `certbot-init`** hold the `*.completions.near.ai` private key in the `certs` volume (`:45`, `:66`) — note `certbot-init` also requests `$HOSTNAME.hosts.near.ai` (`:83`). TLS terminates inside the enclave and the key never leaves the CVM. PASS for the privacy model.
- **No `privileged: true` anywhere in this document.** The privileged, `ipc: host`, root proxies — three of them on this node — live in the inner recipe, not here.
- `work` is a shared named volume between compose-manager and the launcher (`:125`, `:163`) — it carries `.env.launcher` and `launcher-state.json`, the state that makes an image swap survive reboot (Checks 5 and 6).

### Check 3 — Telemetry pipeline: the full stdout chain, and whether anything scrubs **[the priority check]**

**Result at this measurement: the measured layer ships management logs only, to one literal destination — and there is no Datadog agent on this node.**

The chain, end to end:

1. **Every container writes stdout/stderr to the Docker `json-file` driver**, retained on the CVM disk at `max-size: 100m` x `max-file: 10` for the four management containers (`:55-59`, `:86-91`, `:139-144`, `:187-192`) — up to ~1 GB per container — and `local` at 20m x 3 for the collector itself (`:33-37`, deliberately, to avoid a tail-your-own-log feedback loop, `:30-32`).
2. **`otelcol-management`'s `filelog` receiver tails ALL of them**: `include: [/var/lib/docker/containers/*/*-json.log]` (`:222-223`). This is not scoped to management containers — the receiver ingests the JSON logs of **every container in the CVM, both models' engines and all three proxies included**.
3. **`transform/docker_metadata` (`:311-319`) resolves `service.name`** from the Docker compose labels / `com.datadoghq.ad.logs` label.
4. **`filter/management_logs` (`:321-325`) drops everything that is not management**: `'attributes["service.name"] != "compose-manager" and attributes["service.name"] != "compose-manager-launcher" and attributes["service.name"] != "dns-cloudflare"'`. A record whose `service.name` failed to resolve is `nil`, satisfies all three inequalities, and is therefore **dropped** — the filter is **fail-closed**, which is the right direction.
5. **Export:** `otlphttp/gateway` -> `endpoint: https://telemetry.infra.near.ai` (`:341`), literal, `Authorization: Bearer ${MONITORING_INGEST_TOKEN}` (`:343`), with a disk-backed sending queue at `/var/lib/otelcol-management/storage` (`:344-351`).

Pipelines (`:355-367`): `logs/cvm` (the filtered chain above), `metrics/cvm_system` (`hostmetrics` cpu/memory/load/paging/network/disk/filesystem `:255-268` + `docker_stats` container metrics `:270-277`), `metrics/self`. All three export to the same literal gateway.

Findings:

- **[MEDIUM] Both models' engine stdout is ingested by a measured collector and dropped by a *processor*, not by scoping.** Isolation between "an engine printed something" and "it left the box via this collector" is one OTTL condition wide. The condition is measured — changing it changes `compose_hash`, which is the real strength of this design — but the receiver is deliberately CVM-wide, so this is "OFF at this configuration", not "cannot happen".
- **[HIGH — systemic, C3] Nothing in the chain scrubs.** The processor list is `memory_limiter, resource, transform/docker_metadata, filter/management_logs, groupbyattrs/docker_service, batch` (`:358`). None redacts, hashes, or truncates a log body. Whatever a service prints, its full body is exported verbatim for any service the filter admits. The privacy property degenerates to *"no service prints content"* — a source-discipline question this layer cannot answer, which is why the per-engine source reviews are load-bearing. Here that discipline must hold for **two model families and two proxy builds simultaneously**.
- **[MEDIUM] The `com.datadoghq.ad.logs` labels carried by the inner recipe are inert here.** They are consumed by the OTel regex parsers and, where an agent runs, by Datadog autodiscovery. This measured config starts **no Datadog agent**, so nothing on this node ships container logs to `us3.datadoghq.com` *by the measured configuration*. That is a genuine, material privacy advantage over the sibling node — and it is not a property of the model, the recipe, or the client's request. It is a property of which physical host answered.
- **The engines' stdout still leaves this CVM** — via the **inner** recipe's own `otelcol-contrib`, whose `filter/app_logs` is the inverse filter (it *keeps* app containers) and which exports to the same `https://telemetry.infra.near.ai`. That path is measured by the recipe's `file_sha256`, not by this hash; see the [recipe page](/manifests/nearai/cvm-compose-files/prod/dsv4-flash-glm51/sha256-d085dcfc4ee0fbb13b183d52cf3a140cbc075e5e3de44fc039df961a4913ca4c.md), Check 3. So the correct statement for this node is **one measured off-box log destination (near.ai), not two** — not "none".
- **[INFO] `public_logs: false`** — the dstack host-facing log endpoint is off, so the *host* operator cannot read container logs through dstack itself. Good, and worth naming because it removes one obvious sink.
- **[INFO] No OTLP receiver in this document.** Unlike the sibling (which runs the Datadog agent's `DD_OTLP_CONFIG_RECEIVER_PROTOCOLS_GRPC_ENDPOINT=0.0.0.0:4317` with `DD_OTLP_CONFIG_LOGS_ENABLED=true`), the measured layer here exposes no ingestion surface; the recipe's `otelcol-contrib` does (`expose: 4317/4318`), and that is assessed on the recipe page.

### Check 4 — Network topology and egress **[the other priority check]**

**[HIGH — this is the document that creates the shared network.]**

```
networks:
  default:
    name: dstack_default
```

(`:195-200`, with the comment at `:196-198`: *"Model compose files attach to this shared network so app-side telemetry can reach management services without restarting the compose-manager CVM for model scrape/log/trace changes."*). There is **no `internal: true` and no egress restriction anywhere in this document**. The inner recipe joins this same bridge with `external: true` — so **three engines, three proxies**, nginx, two dcgm exporters, the registrar, both collectors, compose-manager and the launcher all share **one flat L2 domain**.

Why that matters here rather than only in the recipe: each engine's `/configure_logging` is unauthenticated (see both sglang pages), and **any container on `dstack_default` can reach any engine's port 8000 directly**, bypassing nginx and the E2EE-terminating proxies entirely. This measured document is what defines that network and puts a `pid: host` + `SYS_PTRACE` + `docker.sock` container on it. **On this node the flat domain also means the two models are not isolated from each other**: a container serving DeepSeek-V4-Flash traffic and a container serving GLM-5.1 traffic are one `curl` apart, with no authentication between them. Moving the engines to project-private networks, or setting `internal: true` on a segment, are both changes to *this* layer.

### Check 6 — dstack settings and the `pre_launch_script` **[where this node differs from every other measured document here]**

`kms_enabled: true`, `gateway_enabled: true`, `local_key_provider_enabled: false`, `no_instance_id: false`, `secure_time: false`, **`public_logs: false`** (good), `public_sysinfo: true` (metadata only).

Unlike the two-line scripts on the GLM-5.2 nodes and on this node's own sibling, the measured `pre_launch_script` here is a **31-line program**. Verbatim, in three parts:

```
#!/bin/bash
export ENCRYPTION_KEY=$(cat /dstack/.host-shared/.appkeys.json | jq -r .k256_key)

# Tune kernel for inference workloads
echo 0 > /proc/sys/vm/swappiness            # prevent KV cache swap-out
echo 5 > /proc/sys/vm/dirty_ratio            # reduce write-back cache pressure
echo 1 > /proc/sys/vm/dirty_background_ratio # flush dirty pages sooner
```

- **[INFO]** the CVM's k256 app key is exported into the compose environment namespace. No service in this document references `${ENCRYPTION_KEY}`; the inner recipe does not either. In-CVM key handling, no egress path configured.
- **[INFO — positive] `vm.swappiness=0` with the in-manifest rationale *"prevent KV cache swap-out"*.** This is a deliberate, measured control keeping prompt-derived KV pages out of swap — the same control the GLM-5.2/gpu04 node was found *lacking*. Whether the dstack guest has any swap device at all is a guest-OS property I did **not** trace ([`os/`](/os/)); if it has none the setting is moot, but as a measured intention it is the right one.

Then the part that has no counterpart anywhere else in this repo's measured set:

```
OVERRIDES="/var/lib/docker/volumes/dstack_work/_data/.env.launcher"
if [ "false" = "true" ]; then
  mkdir -p "$(dirname "$OVERRIDES")"
  printf 'COMPOSE_MANAGER_IMAGE=%s\n' 'nearaidev/compose-manager@sha256:6e035c8f...' > "$OVERRIDES"
  ...
fi
if [ -f "$OVERRIDES" ]; then
  while IFS='=' read -r k v; do

fi
```

- **[HIGH] The measured boot script itself replays the launcher's persisted image override.** The fleet fact established from source on the [`compose-manager@5165400d`](/images/docker.io/nearaidev/compose-manager/sha256-5165400d9eb43ab5da36986a85de0ba55f3fb4d05211c4397ecc4bde3ef0113b.md) page — that the launcher writes `COMPOSE_MANAGER_IMAGE=<swapped digest>` into `work/.env.launcher` and the swap therefore survives reboot with `compose_hash` unchanged — is not merely *implied* by the `${…:-default}` at `:95` on this node. It is **written into the hardware-measured document**, which reads that file off the `dstack_work` volume at every boot and exports the value before compose starts. The measurement thus attests, in its own text, that the digest at `:95` is a fallback and that the running control-plane image is whatever the last successful swap persisted. Same end state as the fleet, stated explicitly rather than inferred; the honest reading is that this node's manifest is *more transparent* about the mechanism, not that it is more exposed.
- **[INFO — positive, credit where due] The script parses the override file as data, not by sourcing it**, with the in-manifest reason: *"sourcing would execute any shell metacharacters in the value, which is a root-RCE path if the launcher ever wrote an unvalidated digest."* The `case` arm also restricts the replay to exactly `COMPOSE_MANAGER_IMAGE` — no other key in that file can reach the compose environment. That is a correctly-reasoned defensive control inside the measurement.
- **[INFO] The forced re-pin branch is OFF at this measurement** — `if [ "false" = "true" ]` is a dead branch (the template's `repin_launcher_override` rendered false), so this boot does **not** overwrite the persisted override with `6e035c8f…`. Flipping it to `true` would change `compose_hash`, which is the correct place for that decision to be visible.
- **[MEDIUM] The path is assumed, not discovered:** `"/var/lib/docker/volumes/dstack_work/_data/.env.launcher"` with the comment *"Path assumes default Docker data-root; dstack CVMs always use this."* If a future guest OS moves the Docker data-root, the replay silently no-ops and the node boots the fallback digest instead of the promoted one. That is a fail-safe direction (it reverts to the measured default), so it is noted, not faulted.

## Cross-check synthesis — architectural findings

- **[C1 / HIGH] The measurement does not cover the plaintext stack's configuration.** This hash measures the management harness only. Every engine flag, proxy env, nginx rule and app-telemetry filter that governs plaintext — for **both** models on this node — lives in the runtime-fetched inner recipe, pinned by the compose-manager action log (`file` / `commit` / `file_sha256`), not by the hardware. With `MIN_TAG_AGE_HOURS` defaulting to 0, an operator with repo push access plus `BEARER_TOKEN` can deploy a recipe carrying `--log-requests --log-requests-level 3` with **no measurement change**. The compensating control is disclosure: the action log entry is signed and client-verifiable, so a client that pins and checks the inner-compose hash — as teemoon's verifier does — detects it. **Transparency plus client verification, not measurement.**
- **[C2 / HIGH] The enforcement point is root-equivalent and self-updating, and this document says so out loud.** compose-manager can `nsenter`/ptrace any process in the CVM — three engines and three proxies here — and the launcher can swap its image to any build cosign-signed by a `nearai/compose-manager` CI workflow on the operator-chosen `LAUNCHER_CHANNEL`. The digest at `:95` is a `${…:-default}`, and the measured `pre_launch_script` re-exports the persisted override at every boot. Content-capture capability inside the measured TCB is one signed CI build away; the anchor is nearai's GitHub org and CI.
- **[C3 / HIGH] Off-box stdout shipping is a fixed feature — but narrower here than on the sibling.** The measured collector reads every container's log and exports only management records to one literal near.ai endpoint. Both models' engine stdout leaves via the recipe's collector. No scrubbing exists at any hop of either pipeline.
- **[C4 / HIGH — topology] This document creates the shared, unrestricted `dstack_default` network** on which three unauthenticated engine admin surfaces sit, **and on which two different models' plaintext-handling containers are mutually reachable**. Containment is available at this layer (private segments, or `internal: true`) and is not taken.
- **[C5 / MEDIUM — co-tenancy] Multi-model co-residency concentrates every capability finding.** One `pid: host` + `SYS_PTRACE` container, one flat network, one log pipeline, one root-equivalent control plane — covering DeepSeek-V4-Flash *and* GLM-5.1 traffic at once. Nothing here is a leak; the observation is that a single compromise of the enforcement point on this node reaches two models' users rather than one.

## Verdict

**Qualified PASS.**

- **Within hardware-measured config + `allowed_envs`:** upheld. None of the 22 allowed envs is a debug, log-level, log-bodies or telemetry-content switch; the collector's level, filter and destination are literals; the fail-closed management filter means a name-resolution failure drops rather than exports. An operator cannot flip on content capture through the measured env channel alone.
- **As an end-to-end claim:** the invariant this layer delivers is the fleet's — **"content capture cannot be enabled without either changing the measurement or leaving a signed, client-verifiable trace"** — via C1 (log-pinned inner recipe) and C2 (cosign-gated, disclosed compose-manager swaps), with C3 making the guarantee conditional on every plaintext service's print discipline, C4 leaving three unauthenticated engine admin surfaces reachable from a shared network this document defines, and C5 noting that all of it covers two models at once.
- **Better than its sibling in the respect that matters most:** with no Datadog agent measured in, this node does not ship container stdout to a third-party US SaaS. It also pins `vm.swappiness=0` against KV swap-out. Both are accidents of which host answered, not guarantees of the service — and both are partly offset by the `/hostfs` mount the sibling does not have.

**Unverifiable at this layer (hand-offs):** TDX quote/signature verification, and whether a fresh attestation still reports this `compose_hash` (I reviewed a local capture and did not fetch); whether the action log currently pins `d085dcfc…` as this node's inner recipe (the gpu02 association rests on the recipe's own header text plus the supplied capture); whether compose-manager's `/compose/up` env overlays are recorded in the signed action log (compose-manager source — the [`5165400d` page](/images/docker.io/nearaidev/compose-manager/sha256-5165400d9eb43ab5da36986a85de0ba55f3fb4d05211c4397ecc4bde3ef0113b.md) says they are not, at that build); whether compose-manager's published `8080` is reachable from outside the CVM (dstack guest port handling); whether the guest has a swap device at all, and whether its Docker data-root matches the override path assumed by the `pre_launch_script` (guest-OS leg, [`os/`](/os/)); whether the two sglang builds, the two vllm-proxy-rs builds or nginx ever *print* request content at their configured levels (source legs — load-bearing given C3); the `os_image_hash` and disk-encryption posture of this specific node.
