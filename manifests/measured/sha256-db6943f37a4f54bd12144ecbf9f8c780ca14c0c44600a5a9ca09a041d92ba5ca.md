# Deployment Manifests & Configuration — Privacy Audit

> Part of the near.ai inference-path privacy re-audit (Fable-only, 2026-07-22).
> Method: [`../PRIVACY_AUDIT.md`](/notes/method.md) · Architecture: [`ARCHITECTURE.md`](/notes/ARCHITECTURE.md) · Index: [`README.md`](README.md)

**Config source:** outer dstack `app_compose` extracted from live attestation — sha256 verified locally `db6943f3…` = the attested `tcb_info.compose_hash` (fresh nonce, 2026-07-22); inner compose [`cvm-compose-files/prod/dsv4-qwen36-gemma4.yaml`](https://github.com/nearai/cvm-compose-files/blob/main/prod/dsv4-qwen36-gemma4.yaml), obtained via the `compose_manager_attestation` action log and hash-checked against its `file_sha256`.
**Role:** the layer that makes the plaintext-handling processes trustworthy. An operator can change only the env vars in `allowed_envs` without a new hardware measurement — so the questions are what the fixed config does, and what the allowed envs could do. This node multiplies the stakes: one measurement covers the harness under **four** plaintext-serving endpoints (DeepSeek-V4-Flash, Qwen3.6-27B, Qwen3.6-35B-A3B, Gemma-4-31B).
**Verdict:** Qualified PASS — the strict manifest invariant holds (no allowed env is a content-logging switch; every engine logging flag and telemetry destination is literal), but the same measured-in escape hatches as the GLM node (runtime-fetched inner compose; root-capable self-updating compose-manager; global stdout shipping) mean the end-to-end claim holds only as "…without changing the measurement OR leaving a signed, client-verifiable trace." Two findings are new relative to the GLM node: both Qwen engines run `--trust-remote-code` with **no `--revision` pin**, and the DeepSeek service documents an env-splice channel (`DSV4_RETURN_HIDDEN_STATES` via compose-manager `/compose/up`) that bypasses `allowed_envs` entirely.

### Check 4 — Telemetry pipelines **[HIGH — systemic]**

The measured datadog-agent runs `DD_LOGS_ENABLED=true` + `DD_LOGS_CONFIG_CONTAINER_COLLECT_ALL=true` and mounts `/var/lib/docker/containers:ro` and `/var/run/docker.sock:ro` — the **full stdout/stderr of every container in the CVM** — all three engines, all four proxies, nginx, registrar — ships to `us3.datadoghq.com` (literal). `DD_PROCESS_AGENT_ENABLED=true` additionally ships process cmdlines; the journald config collects container journal logs with an in-manifest `TODO: Add filters to reduce log volume`. In parallel, two digest-pinned OTel collectors tail the same JSON logs: **otelcol-management** (measured) filters to compose-manager/launcher/certbot only; **otelcol-contrib** (inner) does the inverse — its `filter/app_logs` drops management/telemetry containers and ships the **app** containers' logs (sglang, vllm, vllm-proxy, nginx, dcgm, registrar, tagged with model/deployment) to `https://telemetry.infra.near.ai` (literal). So every plaintext-handling service's stdout leaves the TEE **twice**, to two different backends, by measured/pinned config.

The `com.datadoghq.ad.logs` and `nearai.otel.*` labels carry routing metadata only (model, deployment, env, host, ip, port) — they tag streams, they do not select or scrub content. All metrics paths are Prometheus scrapes of `/metrics` (sglang `sglang:*`, vllm, dcgm, proxy) — counters and histograms only.

No receiver ingests request bodies *by configuration*, and every destination is literal — but as on the GLM node, the manifest does not *contain* content capture; it **guarantees that anything a plaintext-handling service ever prints leaves the TEE** to a third-party US SaaS and to near.ai. The privacy property degenerates to "the engines/proxies never print content" — a source-discipline question (the load-bearing reason the sglang/vllm/proxy source audits exist). See C3.

**[MEDIUM]** Two open OTLP ingestion surfaces forward verbatim with **no content-scrubbing processor**: otelcol-contrib's `otlp` receiver on `0.0.0.0:4317/4318` (pipelines `metrics/otlp` and `traces` → `telemetry.infra.near.ai`) and the datadog-agent's own OTLP receiver (`DD_OTLP_CONFIG_RECEIVER_PROTOCOLS_GRPC_ENDPOINT=0.0.0.0:4317` with `DD_OTLP_CONFIG_LOGS_ENABLED=true`). If any service on the flat network ever emits prompt-bearing spans or OTLP logs, both pipes ship them unexamined.

**[INFO]** nginx's `json_combined` access log records `$uri` (not `$request` — no query strings, no bodies) plus `request_id`/`org_id`/`workspace_id` headers — identity/usage metadata, shipped to both sinks via the global log collection. Metadata, not message content; noted because it is per-request and user-attributable.

### Check 5 — Volumes / mounts

- **Engines:** `hugginface_cache` (weights), `kernel_cache` (`/root/.cache/deep_gemm`, compiled kernels), Gemma adds `vllm_cache` (`VLLM_CACHE_ROOT=/root/.cache/vllm/gemma4-31b-qat-vllm`, compile artifacts). **No KV/prompt disk cache; KV stays in GPU memory**, and the measured `pre_launch_script` sets `swappiness=0` specifically to keep KV out of swap. PASS.
- **Proxies [INFO — excessive privilege]:** all four run `privileged: true`, `user: root`, and (via the `x-nvidia` anchor) `ipc: host`, mounting `dstack.sock` and `certs:ro`. A privileged root proxy is root-equivalent inside the guest.
- **[MEDIUM] `ipc: host` on every engine and proxy** — all four engines and four proxies share one IPC namespace: cross-container (and cross-*model*) SysV/POSIX shared-memory visibility. Combined with privileged proxies, any one proxy has the capability surface to inspect another model's engine shm. Nothing configures such access; the manifest merely permits it.
- **Cross-container visibility:** `/var/lib/docker/containers:ro` into datadog-agent, otelcol-management, otelcol-contrib **[MEDIUM]**; `docker.sock` into datadog-agent (`:ro`), compose-manager (rw), launcher (rw) **[MEDIUM]**; `dstack.sock` into compose-manager and all proxies (attestation/key operations); the shared `certs` volume exposes the `*.completions.near.ai` private key to nginx and (ro) to the proxies — in-CVM only, PASS for the privacy model.
- **[HIGH — architectural, = C2]** compose-manager — which **is in this measured compose** — runs `pid: host` + `SYS_ADMIN` + `SYS_PTRACE` + rw `docker.sock` + nsenter-into-PID-1 (the manifest's own comment spells out the capability rationale). It can read any process's memory in the CVM — **the plaintext of all three model families at once**. On this combined node the blast radius of C2 is 4x the single-engine node's.

Plaintext confinement relies on engine behavior, not network policy. Sanctioned engine egress that this permits by design: HF weight fetches (`HF_HUB_OFFLINE=0` always, Check 2) and Gemma's request-driven media fetches (allowlisted to one literal S3 domain, redirects off).

Same class, lower severity: `FUSION_ENABLED`/`FUSION_INTERNAL_BEARER_TOKEN` (all four proxies), `CLOUD_API_USAGE_TOKEN`, `MODEL_PROXY_TOKEN`.

### Cross-check synthesis — architectural findings

- **[C1 / HIGH] The hardware measurement does not cover the plaintext stack's configuration.** This measured compose contains only the management harness; every engine flag, proxy env, telemetry filter, and nginx rule audited above lives in `dsv4-qwen36-gemma4.yaml`, fetched at runtime by compose-manager from GitHub at an operator-chosen tag (`MIN_TAG_AGE_HOURS` default 0). An operator with repo push access + `BEARER_TOKEN` could deploy an inner compose with `--log-requests` — for **four models at once** — with no measurement change. **Compensating control:** each action is disclosed in the attestation report's `compose_manager_attestation` log (`file`/`commit`/`file_sha256`; verified live 2026-07-22 — the latest entry matches the audited file), so clients that pin and verify the inner-compose hash detect it. The guarantee is *transparency + client verification*, not measurement. New on this node: the inner compose's own comments document **env splicing at `/compose/up`** (`DSV4_RETURN_HIDDEN_STATES`, "like GPT_OSS_CACHE_SUBPATH") — behavior-relevant env can change without either the measurement or (verifiably, at this layer) the file hash moving.
