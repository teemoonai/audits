## Check 3 — The otelcol-management log pipeline: is the filter fail-closed? **[the load-bearing question]**

**Result: fail-CLOSED, by two independent mechanisms — verified against this document's config and the documented OTel semantics, not assumed.**

The chain: every container on the box using the `json-file` driver — which per the recipe's shared `logging-conf` anchor (recipe `:1-6`) is all nine model endpoints, their proxies, and nginx — writes `/var/lib/docker/containers/<id>/<id>-json.log`; the measured collector's `filelog/docker_containers` receiver tails exactly that glob (`include: [/var/lib/docker/containers/*/*-json.log]`, `:223`, from `start_at: end`, `:224`). **The receiver ingests every engine's stdout.** What stands between that and `https://telemetry.infra.near.ai` (`:341`) is the processor chain of `logs/cvm` (`:358`): `memory_limiter, resource, transform/docker_metadata, filter/management_logs, groupbyattrs/docker_service, batch`.

Trace, record by record:

1. **Receiver operators** (`:227-253`, in order): `json_parser` explodes the Docker JSON line into attributes (`on_error: send_quiet`, `:234` — a malformed line is passed on unparsed, not dropped); `move` puts the log text into body; the container id is regexed from the file path (`on_error: send_quiet`, `:250`); and **last, an unconditional `add`**:

   ```
   - type: add
     field: attributes["service.name"]
     value: cvm-docker
   ```

   (`:251-253`). No `if` clause — it runs for every record, including ones whose `json_parser` failed. **Every record leaves the receiver with `service.name = "cvm-docker"`. The nil case cannot occur in this document.**

2. **`transform/docker_metadata`** (`:311-319`, `error_mode: ignore`) *overwrites* `service.name` from the container's log labels — `com.docker.compose.service`, then the `service` field of `com.datadoghq.ad.logs` — each statement guarded `where attributes["attrs"] != nil and …`. For the four management containers, whose `json-file` options export those labels (`labels: "com.datadoghq.ad.logs,com.docker.compose.service"`, `:60`, `:91`, `:144`, `:192`), this yields `compose-manager` / `compose-manager-launcher` / `dns-cloudflare`. For inner-stack containers — which export the same labels via the recipe's anchor — it yields their own names (`vllm`, `sglang`, `vllm-proxy`, `nginx`, …). If a statement errors (e.g. `ParseJSON` on a malformed label), `error_mode: ignore` skips that statement and the record keeps `cvm-docker`.

3. **`filter/management_logs`** (`:321-325`) has one `log_record` condition: `'attributes["service.name"] != "compose-manager" and attributes["service.name"] != "compose-manager-launcher" and attributes["service.name"] != "dns-cloudflare"'`. Per the filterprocessor's contract, *"If any condition is met, the telemetry is dropped."* Every engine record — named `vllm`/`sglang`/etc. or defaulted `cvm-docker` — satisfies all three inequalities and is **dropped**.

4. **The hypothetical nil case, since it is the fail-open question:** were a record somehow to reach the filter with no `service.name` at all, OTTL's map indexing *"if the given key does not exist, nil will be returned"* — it returns nil rather than erroring, so the filter's `error_mode: ignore` escape (an *erroring* condition is skipped, leaving the record in the pipeline — the one genuinely fail-open path in this processor) **is not reachable via a missing attribute**. The comparison then follows OTTL's comparison table, where nil against a string is *"not equal"*, defined as: the `!=` operator returns true and every other operator returns false. `nil != "compose-manager"` → true, three times, condition true → **dropped**. (Both semantics per the collector-contrib `pkg/ottl/LANGUAGE.md` and `processor/filterprocessor/README.md` for the deployed collector line; the image is the digest-pinned, [separately audited](/images/docker.io/otel/opentelemetry-collector-contrib/sha256-85ac41c2db88d0df9bd6145e608a3cb023f5d8443868adbfbbf66efb51087917.md) `85ac41c2…`, verdict "management-logs only by configuration".)

So: label resolves → non-management name → dropped; label missing → `cvm-docker` → dropped; parser errors → `cvm-docker` → dropped; attribute hypothetically absent → nil → still dropped. The only records exported are those whose labels *claim* one of the three management identities.

### MEDIUM (deployed: OFF, one condition wide) — every engine's stdout is ingested by the measured collector and excluded by filter expression, not by scoping (telemetry)

The isolation between "an engine printed plaintext" and "it left the box via this collector" is one measured OTTL condition (`:325`) plus one measured `add` default (`:251-253`). Both are inside the hash — changing either changes `compose_hash`, which is the strength of the design — but the receiver is deliberately CVM-wide, so this is "OFF at the measured config", not "cannot happen". Two residuals, both outside this document's control: (a) the filter admits by **spoofable label** — any container whose labels declare `service: compose-manager` (or a compose service literally so named) gets its stdout exported; containers are defined by the log-pinned inner recipe and by whatever the root-equivalent compose-manager is instructed to run, so this collapses into the C1/C2 trust chain rather than adding a new one; (b) no redaction stage exists for the *admitted* streams — processors are route-and-batch only (`:358`) — so anything the three management services ever print (none of which handles message plaintext; compose-manager does hold every Check-2 secret) ships verbatim to `telemetry.infra.near.ai`.
