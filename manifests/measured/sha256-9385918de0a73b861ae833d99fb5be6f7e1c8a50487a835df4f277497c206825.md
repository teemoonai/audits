# Deployment Manifests & Configuration — Privacy Audit

> Method: [`/notes/method.md`](/notes/method.md) (§4 Manifest-only checks) · Architecture: [`/notes/ARCHITECTURE.md`](/notes/ARCHITECTURE.md)

**Role:** the layer that makes the plaintext-handling processes trustworthy. An operator can change only the env vars in `allowed_envs` without a new hardware measurement — so the questions are what the fixed config does, and what the allowed envs could do.

**Why this node matters:** the engine pages for [`sglang@5027e95b`](/images/docker.io/lmsysorg/sglang/sha256-5027e95bf6ec536856b1b52a91d1f35ff5c564ab83e8a94758a169ff09bb8df3.md) (the build this host runs) found a **CRITICAL** — an unauthenticated `/configure_logging` that turns on full prompt+output logging and arbitrary-path request dumping at runtime, with no restart and no attestation-visible change — and a **HIGH**: a watchdog debug dump of prompt and output token ids on any 30-minute hang, undisableable. ### Check 2 — Privileges and mounts

- **[HIGH — architectural] `compose-manager` is root-equivalent and can read engine memory.** `pid: host` (`:117`), `cap_add: [SYS_ADMIN, SYS_PTRACE]` (`:118-120`), read-write `/var/run/docker.sock` (`:122`), `/var/run/dstack.sock` (`:123`), the decrypted CVM env at `/dstack/.host-shared/.decrypted-env:/app/.env:ro` (`:124`). The manifest's own comment (`:100-116`) spells out the rationale: the caps exist so it can `nsenter -t 1 -m -u -i -n -p` into PID 1's namespaces. With `SYS_PTRACE` plus host PID namespace it can attach to **any process in the CVM, including sglang** — i.e. prompt plaintext in process memory. This is capability, not configured behavior: the [compose-manager source review](/images/docker.io/nearaidev/compose-manager/sha256-6e035c8fb99c1d31f41760d25af178683a658cca4afd73cd0d366fbb5bf884be.md) traced the binary exhaustively and found **no code path that uses it** to read another process's memory. The finding is that the capability sits inside the measured TCB and the image that carries it is swappable (Check 5).
- **[HIGH — architectural] `compose-manager-launcher` runs `network_mode: host` (`:156`) with read-write `docker.sock` (`:158`)** and the decrypted env read-only (`:162`). Anything that can drive that socket can start a container with any privilege on this host.
- **[MEDIUM] `otelcol-management` mounts the entire guest root filesystem read-only** — `/:/hostfs:ro` (`:22`) — plus `docker.sock:ro` (`:18`) and `/var/lib/docker/containers:ro` (`:23`), running as `user: "0:0"` (`:8`). The mount exists for `hostmetrics` root-path parity (`:19-21`, `:255-257`). Consequence: the collector process can *read* every file in the guest, including any file the engine writes — which is exactly where a runtime-enabled `dump_requests_folder` would land. At this configuration nothing exports arbitrary file content (Check 3); the capability is unused, not absent. **This mount is unique to this measured config** — the sibling `002b406e…` collector has neither `/hostfs` nor `docker.sock`.
- **[INFO] `certbot` / `certbot-init`** hold the `*.completions.near.ai` private key in the `certs` volume (`:45`, `:66`). TLS terminates inside the enclave and the key never leaves the CVM. PASS for the privacy model.
- **No `privileged: true` anywhere in this document.** The privileged, `ipc: host`, root proxies live in the inner recipe, not here.
- `work` is a shared named volume between compose-manager and the launcher (`:125`, `:163`) — it carries `.env.launcher` and `launcher-state.json`, the state that makes an image swap survive reboot (Check 5).

### Check 3 — Telemetry pipeline: the full stdout chain, and whether anything scrubs **[the priority check]**

**Result at this measurement: the measured layer ships management logs only, to one literal destination — and there is no Datadog agent on this node.**

The chain, end to end:

1. **Every container writes stdout/stderr to the Docker `json-file` driver**, retained on the CVM disk at `max-size: 100m` x `max-file: 10` for the four management containers (`:56-59`, `:87-90`, `:139-143`, `:187-192`) — up to ~1 GB per container — and `local` at 20m x 3 for the collector itself (`:33-37`, deliberately, to avoid a tail-your-own-log feedback loop, `:30-32`).
2. **`otelcol-management`'s `filelog` receiver tails ALL of them**: `include: [/var/lib/docker/containers/*/*-json.log]` (`:222-223`). This is not scoped to management containers — the receiver ingests the JSON logs of **every container in the CVM, the inner recipe's engines and proxy included**.
3. **`transform/docker_metadata` (`:311-319`) resolves `service.name`** from the Docker compose labels / `com.datadoghq.ad.logs` label.
4. **`filter/management_logs` (`:321-325`) drops everything that is not management**: `'attributes["service.name"] != "compose-manager" and attributes["service.name"] != "compose-manager-launcher" and attributes["service.name"] != "dns-cloudflare"'`. A record whose `service.name` failed to resolve is `nil`, satisfies all three inequalities, and is therefore **dropped** — the filter is **fail-closed**, which is the right direction.
5. **Export:** `otlphttp/gateway` -> `endpoint: https://telemetry.infra.near.ai` (`:341`), literal, `Authorization: Bearer ${MONITORING_INGEST_TOKEN}`, with a disk-backed sending queue at `/var/lib/otelcol-management/storage` (`:344-351`).

Pipelines (`:355-367`): `logs/cvm` (the filtered chain above), `metrics/cvm_system` (`hostmetrics` cpu/memory/load/paging/network/disk/filesystem `:255-268` + `docker_stats` container metrics `:270-277`), `metrics/self`. All three export to the same literal gateway.

Findings:

- **[MEDIUM] Engine stdout is ingested by a measured collector and dropped by a *processor*, not by scoping.** Isolation between "the engine printed something" and "it left the box via this collector" is one OTTL condition wide. The condition is measured — changing it changes `compose_hash`, which is the real strength of this design — but the receiver is deliberately CVM-wide, so this is "OFF at this configuration", not "cannot happen".
- **[HIGH — systemic, C3] Nothing in the chain scrubs.** The processor list is `memory_limiter, resource, transform/docker_metadata, filter/management_logs, groupbyattrs/docker_service, batch` (`:358`). None redacts, hashes, or truncates a log body. Whatever a service prints, its full body is exported verbatim for any service the filter admits. The privacy property degenerates to *"no service prints content"* — a source-discipline question this layer cannot answer, which is why the per-engine source reviews are load-bearing.
- **[MEDIUM] The `com.datadoghq.ad.logs` labels carried by the inner recipe are inert here.** They are consumed by the OTel regex parsers and, where an agent runs, by Datadog autodiscovery. This measured config starts **no Datadog agent**, so nothing on this node ships container logs to `us3.datadoghq.com` *by the measured configuration*. That is a genuine, material privacy advantage over the sibling node — and it is not a property of the model, the recipe, or the client's request. It is a property of which physical host answered.
- **The engine's stdout still leaves this CVM** — via the **inner** recipe's own `otelcol-contrib`, whose `filter/app_logs` is the inverse filter (it *keeps* app containers) and which exports to the same `https://telemetry.infra.near.ai`. That path is measured by the recipe's `file_sha256`, not by this hash; see the [2xTP4 recipe page](/manifests/nearai/cvm-compose-files/prod/GLM-5.2-W4AFP8-SGL-2xTP4/sha256-f408de5c89d7e7f8b4715b1f62409f67cadf52e232cfdce663f94482a134bba2.md), Check 3. So the correct statement for this node is **one measured off-box log destination (near.ai), not two** — not "none".
- **[INFO] `public_logs: false`** — the dstack host-facing log endpoint is off, so the *host* operator cannot read container logs through dstack itself. Good, and worth naming because it removes one obvious sink.
- **[INFO] No OTLP receiver in this document.** Unlike the sibling (which runs the Datadog agent's `DD_OTLP_CONFIG_RECEIVER_PROTOCOLS_GRPC_ENDPOINT=0.0.0.0:4317` with `DD_OTLP_CONFIG_LOGS_ENABLED=true`), the measured layer here exposes no ingestion surface; the recipe's `otelcol-contrib` does (`expose: 4317/4318`), and that is assessed on the recipe page.

### Check 4 — Network topology and egress **[the other priority check]**

**[HIGH — this is the document that creates the shared network.]**

```
networks:
  default:
    name: dstack_default
```

(`:195-200`, with the comment at `:196-198`: *"Model compose files attach to this shared network so app-side telemetry can reach management services…"*). There is **no `internal: true` and no egress restriction anywhere in this document**. The inner recipe joins this same bridge with `external: true` — so the engine, the proxy, nginx, dcgm, the collectors, compose-manager and the launcher all share **one flat L2 domain**.

Why that matters here rather than only in the recipe: the engine's `/configure_logging` is unauthenticated ([`sglang@5027e95b`](/images/docker.io/lmsysorg/sglang/sha256-5027e95bf6ec536856b1b52a91d1f35ff5c564ab83e8a94758a169ff09bb8df3.md), CRITICAL), and **any container on `dstack_default` can reach engine port 8000 directly**, bypassing nginx and the E2EE-terminating proxy entirely. This measured document is what defines that network and puts a `pid: host` + `SYS_PTRACE` + `docker.sock` container on it. Moving the engine to a project-private network, or setting `internal: true` on a segment, are both changes to *this* layer.

- No other ports are published by this document. nginx's `8000`/`8444` and dcgm's `9400` come from the recipe.

**What actually differs, in privacy terms — three things:**

1. **[HIGH] Whether your prompts, if the engine is ever made to print them, reach a third-party US SaaS is decided by the node lottery.** On `002b406e…` a measured Datadog agent collects **all** container stdout and ships it to `us3.datadoghq.com`; on this node no such agent exists and the measured collector drops app logs.
