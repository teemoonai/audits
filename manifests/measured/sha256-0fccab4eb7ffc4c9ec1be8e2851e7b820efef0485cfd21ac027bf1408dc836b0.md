# Deployment Manifests & Configuration — Privacy Audit

> Method: [`/notes/method.md`](/notes/method.md) (§4 Manifest-only checks)

**Role:** the layer that makes the plaintext-handling processes trustworthy. An operator can change only the env vars in `allowed_envs` without a new hardware measurement — so the questions are what the fixed config does, and what the allowed envs could do.

**Why this document exists as a separate page:** it is a *second* measured harness answering for the same models as `d98a2568…`. Two co-existing node configs behind one model endpoint is a node lottery — which CVM answers your request decides your posture, and the client cannot choose. This page's job is to state exactly what is different, and the difference is telemetry.

```text
MANIFEST leg of a defensive privacy audit (authorized). Others audit source; you audit
what the attested deployment manifests permit and configure. This document is hardware-
measured: an operator can change ONLY vars in allowed_envs without a new measurement.
MATERIAL: the dstack app_compose whose compose_hash is 0fccab4e... (management harness,
gpu11), the second config serving the dsv4-flash / glm-5-1 host set.
CHECKS: (1) allowed_envs verbatim - flag anything that could flip a content-logging or
debug switch. (2) privileges and mounts - pid: host, SYS_PTRACE, SYS_ADMIN, privileged,
docker socket, container-log mounts, /hostfs; what plaintext each could reach.
(3) telemetry pipeline - the full stdout -> off-box chain, EVERY destination, and whether
ANY scrubbing exists. (4) network topology and egress. (5) image pinning. (6) pre_launch
script. (7) the diff against the sibling measured config serving the same hosts.
OUTPUT: per-check results with exact evidence; findings CRITICAL/HIGH/MEDIUM/INFO; the
allowed_envs list verbatim; a verdict; unverifiable items.
```

### Check 2 — Privileges and mounts

- **[HIGH — architectural] `compose-manager` is root-equivalent and can read engine memory.** `pid: host` (`:147`), `cap_add: [SYS_ADMIN, SYS_PTRACE]` (`:148-150`), read-write `/var/run/docker.sock` (`:152`), `/var/run/dstack.sock` (`:153`), the decrypted CVM env at `/dstack/.host-shared/.decrypted-env:/app/.env:ro` (`:154`). The manifest's own comment (`:130-146`) is identical to the sibling's: the caps exist for `nsenter -t 1 -m -u -i -n -p` into PID 1's namespaces, and dstack-OS ships no AppArmor. With `SYS_PTRACE` plus host PID namespace it can attach to **any process in the CVM, including every inference engine** — prompt plaintext in process memory. Capability, not configured behavior: the [compose-manager source review](/images/docker.io/nearaidev/compose-manager/sha256-b487f39160e9a53c3d98943a9c709d28e12babef75e0bb5a6cd5692abc8b2db6.md) found **no code path that uses it** to read another process's memory.
- **[HIGH — architectural] `compose-manager-launcher` runs `network_mode: host` (`:186`) with read-write `docker.sock` (`:188`)** and the decrypted env read-only (`:192`). Anything that can drive that socket can start a container with any privilege on this host.
- **[MEDIUM] `datadog-agent`'s mount set is the broadest read surface in this document** (`:21-27`): `/var/run/docker.sock:ro`, **`/proc/:/host/proc/:ro`**, `/sys/fs/cgroup/:ro`, **`/var/lib/docker/containers:ro`**, `/run/log/journal:ro`, `/run/systemd/:ro`. Concretely: it reads **every container's JSON log file** (that is the collection path, Check 3) and the guest's whole `/proc` tree. What that reaches:
  - **Container logs — yes, in full, by configuration** (`DD_LOGS_CONFIG_CONTAINER_COLLECT_ALL=true`). If any plaintext service ever prints request content, this agent is configured to collect it.
  - **Process metadata — yes, by configuration** (`DD_PROCESS_AGENT_ENABLED=true`, `:14`; `HOST_PROC=/proc`, `:19`): process names, command lines, resource usage. Engine command lines contain launch *flags*, not messages — but they do disclose the deployed configuration to Datadog.
  - **Another process's memory — not configured, and additionally gated.** The agent has **no `pid: host` and no `SYS_PTRACE`**; reading `/host/proc/<pid>/mem` would require ptrace permission against targets launched with a full cap set. I did **not** verify the guest's `yama/ptrace_scope` or the effective permission, so I state this as *not configured and additionally constrained*, **not** as "cannot happen".
  - It does **not** mount `/` — unlike the sibling's collector, which mounts `/:/hostfs:ro`. So on this node the file-read surface is container logs + `/proc` + cgroups + journal, not the whole guest root.
- **[MEDIUM] `DD_DOGSTATSD_NON_LOCAL_TRAFFIC=true`** (`:15`) — the agent accepts StatsD from other containers on the shared bridge. Metrics only by protocol shape, but it is an ingestion surface open to every co-resident container, and whatever is pushed into it leaves for `us3.datadoghq.com`.
- **[INFO] `otelcol-management` runs `user: "0:0"` (`:44`) but mounts only `/var/lib/docker/containers:ro` (`:53`)** plus its own storage volume. **No `docker.sock`, no `/hostfs`** — materially narrower than the sibling's collector.
- **[INFO] `certbot` / `certbot-init`** hold the `*.completions.near.ai` private key in the `certs` volume (`:75`, `:96`); `certbot-init` also requests `$HOSTNAME.hosts.near.ai` (`:113`). TLS terminates inside the enclave. PASS for the privacy model.
- **No `privileged: true` anywhere in this document.**
- `work` is a shared named volume between compose-manager and the launcher (`:155`, `:193`) — it carries `.env.launcher` and `launcher-state.json`, the state that makes an image swap survive reboot (Check 5).

### Check 3 — Telemetry pipeline: the full stdout chain, and whether anything scrubs **[the priority check, and the reason this page exists]**

**Result: TWO measured off-box log destinations. Every container's stdout is collected twice — once by an OTel collector that filters it down to management records, and once by a Datadog agent that filters nothing. No scrubbing stage exists on either path.**

**Path A — `otelcol-management` -> near.ai (filtered, fail-closed):**

1. Containers write stdout/stderr to the Docker `json-file` driver at 100m x 10 (`:85-90`, `:116-121`, `:169-174`, `:217-222`); the agent and the collector themselves use `local` at 20m x 3 (`:33-37`, `:63-67`).
2. `filelog/docker_containers` tails **every** container log: `include: [/var/lib/docker/containers/*/*-json.log]` (`:259-260`).
3. `transform/docker_metadata` (`:324-332`) resolves `service.name` from compose labels / the `com.datadoghq.ad.logs` label.
4. `filter/management_logs` (`:334-338`) drops everything that is not management: `'attributes["service.name"] != "compose-manager" and attributes["service.name"] != "compose-manager-launcher" and attributes["service.name"] != "dns-cloudflare"'`. A record whose `service.name` failed to resolve is `nil`, satisfies all three inequalities, and is **dropped** — **fail-closed**, the right direction. Identical to the sibling's.
5. Export: `otlphttp/gateway` -> `endpoint: https://telemetry.infra.near.ai` (`:354`), literal, `Authorization: Bearer ${MONITORING_INGEST_TOKEN}` (`:356`), disk-backed sending queue at `/var/lib/otelcol-management/storage` (`:357-364`).

Pipelines (`:368-376`): `logs/cvm` and `metrics/self` only. **No `hostmetrics`, no `docker_stats`** — the sibling has both; here the agent covers host and container metrics instead.

**Path B — `datadog-agent` -> `us3.datadoghq.com` (unfiltered):**

```
DD_LOGS_ENABLED=true
DD_OTLP_CONFIG_LOGS_ENABLED=true
DD_LOGS_CONFIG_CONTAINER_COLLECT_ALL=true
DD_CONTAINER_EXCLUDE_LOGS=name:datadog-agent
DD_PROCESS_AGENT_ENABLED=true
DD_DOGSTATSD_NON_LOCAL_TRAFFIC=true
DD_OTLP_CONFIG_RECEIVER_PROTOCOLS_GRPC_ENDPOINT=0.0.0.0:4317
DD_SITE=us3.datadoghq.com
```

(`:6-20`, verbatim from the `environment` block.) Plus journald: the `journald_config_file` config (`:246-251`) mounts `conf.d/journald.d/conf.yaml` with `type: journald`, `container_mode: true`, and the in-manifest note **`# TODO: Add filters to reduce log volume`**.

Findings:

- **[HIGH] `DD_LOGS_CONFIG_CONTAINER_COLLECT_ALL=true` is the widest content path measured on this node.** It means *collect the stdout of every container*, with exactly one exclusion — `DD_CONTAINER_EXCLUDE_LOGS=name:datadog-agent` (`:13`), which exists to prevent a feedback loop, not to protect content. There is **no allowlist, no filter processor, and no redaction anywhere in this path.** Where Path A admits three management services and drops the rest, Path B admits everything the inner recipe runs — engines, proxies, nginx, dcgm, registrar. **If a plaintext service ever prints request content, this is the configuration that carries it verbatim to a third-party SaaS in the United States.** This is "OFF at this configuration" in the sense that nothing is *known to print* content; it is emphatically **not** "cannot happen", and it is the single clearest privacy difference between the two nodes serving these models. The agent build itself is audited — [`datadog/agent@5556fb80`](/images/docker.io/datadog/agent/sha256-5556fb80b952832719a76b016f905616c76ee0989a239c4680c6220148e865d6.md), *metadata-only exposure at audited config* — and that verdict is exactly config-conditional in the way this finding describes.
- **[HIGH] An open OTLP *logs* receiver sits on the shared network.** `DD_OTLP_CONFIG_RECEIVER_PROTOCOLS_GRPC_ENDPOINT=0.0.0.0:4317` (`:20`) **together with** `DD_OTLP_CONFIG_LOGS_ENABLED=true` (`:11`) means any container on `dstack_default` can push arbitrary **log records** — not just metrics/spans — into Datadog through this agent, unauthenticated at the network layer. Note the precise contrast with the inner recipe's `otelcol-contrib`, whose OTLP receiver (per the sibling recipe review) feeds only `metrics/otlp` and `traces`: **that one cannot inject logs; this one can.** The endpoint binds `0.0.0.0` and no `ports:` entry publishes it, so reachability is bridge-wide, not host-wide.
- **[MEDIUM] journald collection is unfiltered by the manifest's own admission.** `container_mode: true` with `# TODO: Add filters to reduce log volume` (`:251`) ships guest journal records for containers to the same destination. Journal content is systemd/kernel-sourced rather than application stdout, but no filter is applied and the TODO is measured into the hash.
- **[HIGH — systemic] No scrubbing exists on either path.** Path A's processor list is `memory_limiter, resource, transform/docker_metadata, filter/management_logs, groupbyattrs/docker_service, batch` (`:371`); Path B has no processing stage at all. Nothing redacts, hashes, or truncates a log body anywhere in this document. The privacy property degenerates to *"no service prints content"* — a source-discipline question this layer cannot answer.
- **[INFO] `public_logs: false`** — the dstack host-facing log endpoint is off, so the *host* operator cannot read container logs through dstack itself.
- **[INFO] The `com.datadoghq.ad.logs` labels the inner recipes attach to every service are *live* here.** On gpu02 they are inert routing metadata consumed only by OTel regex parsers. On this node they are consumed by Datadog autodiscovery as designed — the labels were written for exactly this fan-out.

**What actually differs, in privacy terms — three things:**

1. **[HIGH] Whether your prompts, if an engine is ever made to print them, reach a third-party US SaaS is decided by the node lottery — and this is the node where they would.** `CONTAINER_COLLECT_ALL=true` collects every container's stdout with no filter and ships it to `us3.datadoghq.com`; gpu02 has no such agent and its collector drops app logs. Same models, same domains, same client request, two different sets of readers. Neither is a leak today — both rest on "the engines print nothing" — but the *blast radius of the engines' CRITICAL* is strictly larger here.
2. **[HIGH] This node adds ingestion surfaces the sibling does not have.** An OTLP **logs** receiver and a non-local DogStatsD listener, both bound for any container on the shared bridge, both terminating at Datadog. gpu02's measured layer accepts nothing.
3. **[MEDIUM] The reads and the kernel discipline trade the other way.** This node's collector cannot read the guest root filesystem (no `/hostfs`) where gpu02's can; but the Datadog agent reads all container logs and `/proc` here, and this node's boot script does **not** set `vm.swappiness=0` against KV swap-out where gpu02's does.

## Cross-check synthesis — architectural findings

- **[C1 / HIGH] The measurement does not cover the plaintext stack's configuration.** This hash measures the management harness only. Every engine flag, proxy env, nginx rule and app-telemetry filter that governs plaintext lives in the runtime-fetched inner recipe — **not supplied for this review at all on this node** — pinned by the compose-manager action log, not by the hardware. With `MIN_TAG_AGE_HOURS` defaulting to 0, an operator with repo push access plus `BEARER_TOKEN` can deploy a recipe carrying `--log-requests --log-requests-level 3` with no measurement change. Compensating control: the signed, client-verifiable action log.
- **[C2 / HIGH] The enforcement point is root-equivalent and self-updating.** compose-manager can `nsenter`/ptrace any process in the CVM, and the launcher can swap its image to any build cosign-signed by a `nearai/compose-manager` CI workflow on the operator-chosen `LAUNCHER_CHANNEL`; the measured digest at `:125` is a `${…:-default}` and the swap persists via `work/.env.launcher`. Content-capture capability inside the measured TCB is one signed CI build away.
- **[C3 / HIGH] Off-box stdout shipping is a fixed feature — and on this node it is doubled and half-unfiltered.** Two collectors read every container's log. One exports three management services to near.ai. The other exports **everything** to `us3.datadoghq.com`. No scrubbing at any hop of either.
- **[C4 / HIGH — topology] This document creates the shared, unrestricted `dstack_default` network** on which the engines' unauthenticated admin surfaces sit **and** on which this node's Datadog OTLP-logs / DogStatsD receivers listen. Containment is available at this layer (`internal: true`, private segments) and is not taken in either direction.

## Verdict

**Qualified PASS — the weaker half of the pair.**

- **Within hardware-measured config + `allowed_envs`:** upheld. None of the 22 allowed envs is a debug, log-level, log-bodies or telemetry-content switch; the Datadog site, the near.ai endpoint, the collector's level and its filter are all literals; the management filter is fail-closed. An operator cannot flip on content capture through the measured env channel alone — though `DD_API_KEY` does let one redirect the Datadog stream to a different *account* without a measurement change.
- **As an end-to-end claim:** the fleet invariant holds — **"content capture cannot be enabled without either changing the measurement or leaving a signed, client-verifiable trace"** — but the *consequence* if any plaintext service ever prints content is materially worse here than on gpu02: an unfiltered copy of every container's stdout is already configured to leave the enclave for a third-party SaaS in another jurisdiction. Nothing in this document captures content. Everything in it is arranged to forward whatever is printed.
- **The honest summary of the lottery:** for these models, the difference between the two attested nodes is not the model, the recipe, or your request — it is whether a Datadog agent was measured into the harness that answered you. teemoon clients can tell the two apart only by comparing the `compose_hash` in the attestation report against this repo.

**Unverifiable at this layer (hand-offs):** TDX quote/signature verification, and whether a fresh attestation still reports this `compose_hash` (I reviewed a local capture and did not fetch); **which inner recipe this node runs** (not supplied — so no statement here about engine flags, proxy builds, nginx routing or the app-telemetry filter on this node); whether Datadog's agent, at this digest and config, applies any server-side scrubbing (the [image page](/images/docker.io/datadog/agent/sha256-5556fb80b952832719a76b016f905616c76ee0989a239c4680c6220148e865d6.md) is the authority, and its verdict is config-conditional); whether the agent could in practice read another process's memory via `/host/proc` given the guest's ptrace policy (guest-OS leg); whether compose-manager's `/compose/up` env overlays are recorded in the signed action log (compose-manager source); whether compose-manager's published `8080` is reachable from outside the CVM (dstack guest port handling); whether the guest has a swap device at all ([`os/`](/os/)); whether any plaintext service ever *prints* request content (source legs — load-bearing given C3); the `os_image_hash` and disk-encryption posture of this specific node.
