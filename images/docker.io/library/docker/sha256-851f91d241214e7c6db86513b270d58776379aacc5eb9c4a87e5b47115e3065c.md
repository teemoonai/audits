## What the image contains (from the config and the Dockerfile at the provenance commit)

- **Base:** Alpine 3.21.3 minirootfs — busybox `sh`, `awk`, `cp`, `mv`, `date`, `stat`, `chmod`, `grep`, `base64`, `printf` (the userland the recipe's outer script uses; the inner script runs in the launcher, not here).
- **Packages:** `ca-certificates`, `openssh-client` (for `DOCKER_HOST=ssh://`), `git` (Dockerfile `:9-14`).
- **`docker` 27.5.1**, static CLI from `download.docker.com/linux/static/stable/x86_64/docker-27.5.1.tgz` (`:33`, `:47-58`) — **downloaded with no checksum in the Dockerfile**; the image digest is what pins the resulting bytes.
- **Plugins:** buildx 0.20.1 (`:60-104`, sha256-checked `:97`) and compose 2.33.0 (`:106-152`, sha256-checked `:143`, also symlinked as `docker-compose` `:150`) under `/usr/local/libexec/docker/cli-plugins/`. The recipe's comment says "no compose plugin needed here" (`:105-109` of the recipe); it is present and unused — the recipe's `docker compose` runs inside the launcher.
- **`docker-entrypoint.sh`** (`:155`, `:166`): if `DOCKER_HOST` is unset and `/var/run/docker.sock` exists, exports it (`entrypoint:23-24`); otherwise falls back to `tcp://docker:2375|2376` (`:29-36`); sets TLS vars when `/certs/client/*.pem` exist (`:15-20`, `:37-44`). **Bypassed by the recipe** (`entrypoint: ["sh", "-c"]`, recipe `:133`); the CLI's own default is the same unix socket, so nothing changes.
- **Config:** `Entrypoint ["docker-entrypoint.sh"]`, `Cmd ["sh"]`, `WorkingDir /`, no `User` (root), no `ExposedPorts`, no `Volumes`, no `Labels`; `Env`: `PATH`, `DOCKER_VERSION=27.5.1`, `DOCKER_BUILDX_VERSION=0.20.1`, `DOCKER_COMPOSE_VERSION=2.33.0`, `DOCKER_TLS_CERTDIR=/certs`. 10 layers; `created 2025-02-12T12:04:16Z` (SOURCE_DATE_EPOCH, not build time).

Nothing in the image runs on its own: no daemon, no agent, no telemetry, no background process. What it does is whatever `sh -c` is given.

## The one in-scope use

`rotate-token` (recipe `:104-269`): `entrypoint: ["sh", "-c"]` with the outer script as the command; `network_mode: none`; `read_only`, `cap_drop: [ALL]`, `no-new-privileges`, `user: "0:0"`; **`/var/run/docker.sock` read-write** as its only mount; `NEW_BEARER_TOKEN` from the unattested env overlay. From this image the script uses `awk` (validation, value via `ENVIRON`), `date`, `echo`, `printf`, `base64 -d`, and `docker` twice — `docker exec compose-manager-launcher sh -c 'true'` (`:167`) and `docker exec -i -e NEW_BEARER_TOKEN compose-manager-launcher sh -s` (`:259`), the second carrying the decoded inner script on stdin and the token by bare `-e` forward (docker/cli v27.5.1 `opts/env.go:18-31`: a bare key is read from the CLI's own environment and sent in the exec-create request over the socket, never in argv). `git`, `ssh`, `ca-certificates`, buildx and compose are never invoked, and with no network namespace they could reach nothing if they were. The socket is the recipe's capability, not the image's: the image is the conduit. Everything the socket could do, what the script actually does with it, what the signed log records and what is left behind is the [recipe page's](/manifests/nearai/cvm-compose-files/prod/rotate-compose-manager-token/sha256-0d1263e5169ebacdb1da157857aafff9a5bb5645aabbd921b3bd7e18d60a8ee2.md) subject; its class and findings are the ones that apply to this image's deployment.

## Findings

### INFO (deployed: ON, by the recipe) — the image is a docker CLI and a busybox shell; at the deployed invocation it runs a hash-pinned script that uses the socket for two exec calls into the launcher and nothing else; no plaintext reach of its own (sink: none; the socket's reach is the recipe page's ARMED residual)

Read from the recipe page. The container has no network (`:124`), no model volume, no engine; the hardening on the service bounds the process, not the socket. The image adds no sink: no logging of its own, no persistence (read-only rootfs plus a `/tmp` tmpfs), no egress path (no namespace to use one).

### INFO (deployed: ON, supply chain) — identity rests on a digest pin plus builder-declared provenance; the docker binary inside was fetched by the upstream Dockerfile without a checksum (sink: none)

The recipe pins the index by digest (`:110`) and the validator at the same commit refuses an unpinned image (`validate_rotate_compose_manager_token.rb:35`), so the bytes that ran are these. What binds those bytes to a source is the buildkit provenance in the index — the builder's own unsigned statement — and the tag history; both agree on `docker-library/docker@2738fa1f`. Inside that build, `docker-27.5.1.tgz` is `wget` and untarred with no hash check (Dockerfile `:47-58`), unlike the two plugins (`:97`, `:143`): the Docker Inc. download server was trusted at build time on 2025-02-14. Residual trust in a third-party binary, as `method.md` §6 already names for every sidecar; relevant here only because this binary is the one that speaks to the root-equivalent socket.

### INFO (deployed: OFF, bypassed) — the image's entrypoint would select a TCP daemon when no socket is present; the recipe replaces the entrypoint and mounts the socket, so the CLI's default unix socket is used (sink: egress, not reachable)

`docker-entrypoint.sh:29-36`; recipe `:133`, `:130`. With `network_mode: none` a TCP fallback could not connect anyway.

## Not traced

- **The `docker-library/official-images` commit** that published this build and the signed (Docker Official Images) side of the chain, if any — not found without the GitHub API; the identity claim above does not depend on it.
- **The compose and buildx plugin binaries** — checksummed by the Dockerfile, never invoked under the recipe; not reviewed.
- **The image layers themselves** were not pulled; contents are stated from the Dockerfile and the config history, which the provenance binds to the same commit.
- **The arm/arm64 children** — the CVMs are amd64; only the amd64 child, config and attestation were fetched.

## Verdict

**QUALIFIED PASS** — the image is a conduit: a shell and a docker client that, at the one place it is deployed, executes a script pinned by the recipe's hash and reviewed line by line on the recipe page, using the socket for two exec calls into the launcher and nothing else, with no network namespace, no plaintext reach and no sink of its own. Its identity is a digest the recipe pins and a registry re-fetch confirms, bound to `docker-library/docker@2738fa1f` by the builder's own provenance statement and by the tag history rather than by a signature; the docker binary inside is Docker Inc.'s static release, taken on trust at the upstream build and not source-reviewed here. The findings that matter for this deployment — the root-equivalent socket as ARMED capability, the credential the run leaves behind, and what the signed log does not record — are the recipe page's, and this image only executes them.
