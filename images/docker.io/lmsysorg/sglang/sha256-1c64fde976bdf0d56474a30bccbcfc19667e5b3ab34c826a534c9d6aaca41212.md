# analysis

## Why INCONCLUSIVE

The review method ([/notes/method.md](/notes/method.md) §5) resolves an engine build in three lookups. All three were unavailable to this run — the environment had no registry, network, or source-tree access, and each attempt was refused rather than returning data:

| # | Lookup | Purpose | Status |
|---|---|---|---|
| 1 | `GET https://glm-5-2-long.completions.near.ai/v1/attestation/report?signing_algo=ecdsa&nonce=<hex>` | the model node's `app_compose` → the inner compose (`file` + `commit` + `file_sha256` from the `compose_manager_attestation` action log) → **the deployed sglang launch command, env, and pinned image reference** | not fetched |
| 2 | Docker Hub registry: manifest for `sha256:1c64fde9…`, then the amd64 image config → `ENV SGLANG_BUILD_COMMIT`, `LABEL org.opencontainers.image.revision`, `SGLANG_IMAGE_TAG` | the **source commit** to audit, and whether the tag/label pair is self-consistent (the pin check done on the `9e02c8e1` build) | not fetched |
| 3 | `git clone github.com/sgl-project/sglang && git checkout <commit from #2>` | the tree every file:line citation must be pinned to | not possible (blocked on #2) |

Without #1 there are **no deployed flags**, and every conclusion in this repo's engine pages is explicitly *relative to* the deployed flags — the SGLang code can log full prompts and pickle requests to disk, and whether it does is entirely a launch-configuration question. Without #2/#3 there is **no source to cite**. A verdict of "PRIVATE at deployed flags" here would rest on assuming both the flags and the code, which is exactly the overclaim the fail-closed rule exists to prevent.

## What *is* established

### INFO (structural) — the engine sees plaintext by role
`lmsysorg/sglang` on the model node is the inference engine: it necessarily holds the decrypted prompt and generates the response in process memory. Per [/notes/method.md](/notes/method.md) §1 this is legitimate plaintext, and structural exposure alone is INFO, never a finding. The finding question — does *this build*, at *its* launch flags, log / persist / egress that content — is the one this review could not answer.

### INFO — this is a fourth, distinct build of this ref
`1c64fde976bd…` does not match any digest previously reviewed for this ref (`aac6b242…`, `9e02c8e1…`, `6bb5fee3…`), nor the `5027e95bf6ec…` build recorded as *observed, not audited* for the GLM-5.2 stack in the [lineage README](README.md). Whether it is run directly from the public tag (as the Qwen3.6 and DeepSeek builds are) or rebuilt in-enclave with a patch layer (as the GLM-5.1 build is, `glm51-sgl-awq-tp4-patched:local`) is itself unknown here, and materially changes what "this digest" covers.

## What is deliberately *not* carried over

The three reviewed sibling builds of this ref all landed on **PRIVATE at deployed flags** with the same finding set — a CRITICAL unauthenticated `/configure_logging` runtime switch, a HIGH `--log-requests` path that is off at deployment, all disk-persistence features off, content-free pull-based metrics, and `--trust-remote-code` on. It is a reasonable *prior* that this build shares the upstream code shape, and the endpoint has persisted across `8805f4cf`, `127b9e32`, and `7de33ce8`.

**A prior is not evidence, and this page claims none of it for `1c64fde9…`.** Specifically, none of the following is verified for this build: that `--log-requests` is absent; that `--log-requests-level` is inert; that no dump / crash-dump / tensor-dump / metrics-file folder is set; that the KV/prefix cache has no disk tier; that no `--enable-trace` or content-bearing exporter is active; that the checkpoint is `--revision`-pinned; or that `/configure_logging` is unauthenticated *and* unreached. Two of those varied across the siblings already — the GLM-5.1 build pins `--revision` and the Qwen3.6 build does not; the DeepSeek build adds `--enable-return-hidden-states` and EAGLE spec-decode that the others lack — so per-build launch configuration demonstrably differs on this ref and cannot be assumed. A long-context deployment in particular is the profile most likely to enable a hierarchical / offloaded KV tier (`--enable-hierarchical-cache`, HiCache storage dirs), which is precisely a disk-persistence question and precisely what was not readable here.
