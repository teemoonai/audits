# SGLang inference engine (GLM-5.2) — Privacy Audit

> Part of the near.ai inference-path privacy audit. Method: [/notes/method.md](/notes/method.md).

**Image:** `lmsysorg/sglang@sha256:5027e95bf6ec536856b1b52a91d1f35ff5c564ab83e8a94758a169ff09bb8df3` (v0.5.14, 2026-06-26)
**Source:** `sgl-project/sglang` @ `49e384ce9d304648e9959666ecb8ce8cd98d0deb`
**Location:** two co-resident TP4 replicas inside the CVM, behind `nearaidev/vllm-proxy-rs` (the E2EE/OHTTP terminator) behind nginx. Engine port 8000 is **not** published to the host — reachable only on the Docker network `dstack_default`, which is declared `external: true`.
**Role:** the inference engine. It is the one process legitimately entitled to see message plaintext.
**Verdict:** At the deployed launch flags, no plaintext copy is written to any log, file, cache, or network destination in steady-state operation. Two paths keep this short of "cannot happen": an **unauthenticated `/configure_logging` endpoint** that turns on full prompt+output logging *and* arbitrary-path request dumping with no restart, and a **watchdog debug dump** that writes the full prompt and output token IDs of the in-flight batch to stdout on any engine hang, with no flag to disable it. Both feed a log pipeline that ships container stdout verbatim off-box.

### HIGH (deployed: ON) — a watchdog timeout writes the full prompt and output token IDs of every in-flight request to stdout, with no flag to disable it

This one needs no attacker and no configuration change. It is on right now.

The scheduler watchdog is constructed with a `dump_info` callback ([`invariant_checker.py:350`](https://github.com/sgl-project/sglang/blob/49e384ce9d304648e9959666ecb8ce8cd98d0deb/python/sglang/srt/managers/scheduler_components/invariant_checker.py#L350) — `dump_info=dump_info`) whose body returns:

That is the complete prompt token sequence and the complete generated token sequence, for every request in the batch. Token IDs are not a redaction — the tokenizer for `z-ai/glm-5.2` is public, so this is plaintext with one `decode()` call.

It is emitted at ERROR level to the process's log stream:

[`watchdog.py:149-150`](https://github.com/sgl-project/sglang/blob/49e384ce9d304648e9959666ecb8ce8cd98d0deb/python/sglang/srt/utils/watchdog.py#L149) — `if self.dump_info is not None and (info_msg := self.dump_info()):` / `logger.error(f"{self.debug_name} debug info:\n{info_msg}")`

There is no server flag, no env var, and no verbosity level that suppresses this. `--log-requests` is irrelevant to it. The trigger is `--watchdog-timeout 1800` (deployed, compose line 140): the forward counter failing to advance for 1800s while a batch is in flight. The soft watchdog, which would fire far sooner, is off — `soft_watchdog_timeout` defaults to `None` ([`server_args.py:813-816`](https://github.com/sgl-project/sglang/blob/49e384ce9d304648e9959666ecb8ce8cd98d0deb/python/sglang/srt/server_args.py#L813)) and is only auto-set in CI ([`server_args.py:6252-6254`](https://github.com/sgl-project/sglang/blob/49e384ce9d304648e9959666ecb8ce8cd98d0deb/python/sglang/srt/server_args.py#L6252)). So the trigger requires a genuine 30-minute engine hang.

I want to be precise about how likely that is rather than hand-wave it as theoretical: the deployment file's own header documents this fleet hitting deterministic boot-loops, an IMA crash combo, D-state driver hangs that wedge the GPU for ~15 minutes, and NVML/NVSwitch state corruption requiring a host VM restart (compose lines 51–57, 101–113). A hang on this hardware is an operational reality, not a hypothetical. When one happens, the prompts of whoever was mid-request get written out.

Severity is HIGH rather than CRITICAL because the trigger is an availability incident rather than something a remote party can induce on demand, and the blast radius is the in-flight batch (bounded by `--max-running-requests 96`) rather than all traffic. It is not LOW, because it is unconditional, undisableable, lands in a stream that leaves the machine, and requires no misconfiguration whatsoever.

### MEDIUM (deployed: ON) — engine stdout is shipped verbatim off-box, with no redaction anywhere in the pipeline

This is the amplifier that converts either finding above from "a local file" into "egress". It lives in the compose file, which *is* attested, so it is in scope.

The `otelcol-contrib` sidecar mounts the host's Docker log directory read-only (compose line 409):

```
- /var/lib/docker/containers:/var/lib/docker/containers:ro
```

and tails every container's JSON log file (compose lines 449–453):

```yaml
filelog/docker_containers:
  include: [/var/lib/docker/containers/*/*-json.log]
```

The raw log line is moved into the record body unmodified (compose lines 463–466: `type: move`, `from: attributes.log`, `to: body`). The `logs/app` pipeline then exports to a remote gateway (compose lines 676–679, 692–695):

```yaml
otlphttp/gateway:
  endpoint: https://telemetry.infra.near.ai
  headers:
    Authorization: "Bearer $${env:MONITORING_INGEST_TOKEN}"
```

The only filter is `filter/app_logs` (compose lines 640–649), which drops records with no `model`/`deployment` attribute and drops a handful of infrastructure services by name. The sglang containers carry `com.datadoghq.ad.logs` labels with `model:` and `deployment:` tags (compose lines 293, 336), so their logs match and are **kept**. There is no `transform` that scrubs, hashes, truncates, or pattern-matches the body. The Datadog autodiscovery labels on the same containers point a second collector at the same stream.

So the full chain is: *anything the engine prints to stdout or stderr* → Docker `json-file` driver (compose lines 64–69) → otel filelog receiver → `https://telemetry.infra.near.ai`. Both the CRITICAL and HIGH findings terminate here.

Note also that the scheduler ranks are subprocesses of the container's main process and inherit its stdout/stderr, so scheduler-side output — including the watchdog dump above — travels the same path.

At deployed flags nothing prompt-derived is written to that stream, which is why this is MEDIUM and not higher. But the absence of any redaction stage means the pipeline provides zero defence in depth: it is a straight pipe from the engine's log calls to an off-box collector.

[`serving_base.py:89`](https://github.com/sgl-project/sglang/blob/49e384ce9d304648e9959666ecb8ce8cd98d0deb/python/sglang/srt/entrypoints/openai/serving_base.py#L89) — `if request_logger.log_requests and request_logger.log_requests_level >= 2:`

And the deployed `--log-requests-level 0` is genuinely the safest of the four levels: at level 0 the skip list strips `text`, `input_ids`, `input_embeds`, all media fields and `sampling_params` from the request, and `text`/`output_ids`/`embedding` from the response ([`request_logger.py:200-213`](https://github.com/sgl-project/sglang/blob/49e384ce9d304648e9959666ecb8ce8cd98d0deb/python/sglang/srt/utils/request_logger.py#L200)). Level 2 is where prompt and output text first appear (truncated to 2048), level 3 is unbounded. The reason it is listed rather than simply praised: `--log-requests-level 0` offers **no protection against the CRITICAL finding**, because `/configure_logging` overrides the level and the boolean in the same call. It should not be read as a mitigation for that path.

### Verdict: private at the deployed flags — with two live paths that stop it short of "cannot happen"

At the flags actually deployed, I found no path by which message plaintext reaches a log, file, cache, database, or network destination during normal operation. Request logging is off and set to its safest verbosity, request dumping and crash dumping are off, the engine emits no telemetry of its own, Prometheus labels are content-free, no media fetch path exists for this text-only architecture, `--trust-remote-code` has nothing to execute at the pinned revision, and nothing request-derived is written to the persisted volumes. The operator's choice of `--log-requests-level 0` is a deliberate, correct piece of defence in depth.

That is a real result, and it is the state the engine is in right now. But "off" is not "cannot happen", and two things keep this from being a clean bill of health.

The first is the **unauthenticated `/configure_logging` endpoint**. The earlier finding in this repo holds at `49e384ce` — I checked it from source rather than assuming, and it is if anything broader than before, now also accepting `crash_dump_folder`. One unauthenticated HTTP POST, for which SGLang ships a ready-made client script with prompt-logging defaults, flips this engine from logging nothing to logging every prompt and every completion verbatim — and can additionally begin pickling full request/response pairs to any path on the filesystem. No restart, no config change, no attestation-visible event. The one nearby control the project *did* get right — the explicit `admin_api_key` check on the HiCache storage endpoints — shows this is an omission rather than a design position.

The second is the **watchdog debug dump**, which is not conditional on anything. On any 30-minute engine hang, the full prompt and output token IDs of every in-flight request are written to stdout by design, at ERROR level, with no flag to turn it off. The deployment file's own header documents this exact hardware hanging, boot-looping and wedging repeatedly. This is not a hypothetical.

Both terminate in the same place: container stdout is tailed by an otel sidecar mounting the host Docker log directory and exported verbatim to `https://telemetry.infra.near.ai`, with no redaction stage anywhere in the pipeline.

The single change that would most improve this posture is passing `--admin-api-key` to the engine. It costs one flag, it is already fully implemented upstream, and it converts `/configure_logging` — along with ~30 other currently-open administrative routes — from open to authenticated.

### Residuals

1. **`/configure_logging` is unauthenticated and can enable full prompt/output logging and arbitrary-path request dumping at runtime.** No restart, no attestation change, no operator-visible artifact other than the log volume itself. Confirmed present at this exact commit.
2. **Whether that endpoint is reachable from outside the CVM depends entirely on `nearaidev/vllm-proxy-rs`,** which is a different image. nginx applies no path filter (`location /` → proxy, compose lines 899–900, 924–925). **This is a residual, not a mitigation** — and it is worth noting that a path allowlist in an unattested proxy is a strictly weaker control than an API key inside the attested engine. *(See the [`vllm-proxy-rs@b0c5cd07` review](/images/docker.io/nearaidev/vllm-proxy-rs/sha256-b0c5cd0786b19dfa46144107be15e340b7a338b1c341d02ffa994c9f1ea77dfd.md), published the same day, which establishes from source that the proxy has **no** path allowlist at all — its catch-all forwards any authenticated request to any engine path.)*
3. **`dstack_default` is an `external: true` shared Docker network.** Any container on that network on the same host — including ones from other compose projects, which are outside this file's attestation — can reach engine port 8000 directly, bypassing both nginx and the proxy entirely.
4. **The watchdog prompt dump cannot be disabled by configuration.** It requires an upstream source change to `create_scheduler_watchdog`.
5. **Container stdout leaves the machine with no redaction.** Every finding above that writes to a log is therefore an egress finding, not a local-disk finding.
6. **CUDA core dumping is enabled in code by default** and blocked only by the absence of `CUDA_ENABLE_USER_TRIGGERED_COREDUMP=1`. A debugging session that adds that variable would begin writing GPU memory — KV cache and activations — to disk on crash.
7. **Image identity is self-asserted.** No signed provenance attestation ties this digest to commit `49e384ce`; the OCI labels are builder-supplied. Everything in this review inherits that assumption.
8. **The image filesystem was not inspected.** The `sglang.private.*` metrics-exporter hook and the external multimodal-processor hook are silent plugin points that a modified image could populate without any change to the OSS source reviewed here.
