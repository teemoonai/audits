## identity — established, and byte-proved

The brief for this page said identity was not given and that INCONCLUSIVE was an acceptable outcome. It is not needed. Identity is **established**, and not by inference: by extracting the build's own git metadata from inside the image and then diffing the entire source tree against upstream.

**The "unpinned clone" lead is true — and it was still recoverable.** sglang's `docker/Dockerfile` does clone `main` unpinned when `USE_LATEST_SGLANG=1`, confirmed at the matching upstream commit ([`docker/Dockerfile:185`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/docker/Dockerfile#L185)):

```
git clone --depth=1 https://github.com/sgl-project/sglang.git /sgl-workspace/sglang;
```

No branch, no tag, no commit — so the *Dockerfile* records nothing about which commit was taken. That is why no label carries a revision, and the earlier conclusion that "no commit can ever be recovered from the image" follows naturally. It is nevertheless **wrong**, for one reason: `git clone` leaves `.git/` in the layer, and the layer is a public blob.

The recovery, reproducible by anyone with `curl` and an anonymous Docker Hub pull token:

1. **Index → amd64 manifest → config blob.** `sha256:8ece90ad…` is an OCI index; the `linux/amd64` manifest is `sha256:938a6d4cc9d93d93e3541396c72d79fd254f3448a1967f9ee938129cacbe1be7`, whose config blob is `sha256:74e89401be4ce9c1fa77c720cfe6e60f7107cfaf16f83a7a8771a0e0a5dac499`. `created` = **2026-01-21T00:56:13Z**, and `history` has 139 entries.
2. **Locate the clone step in `history`.** Entry `[115]`, timestamped `2026-01-21T00:31:27Z`, is the `RUN` above, carrying the full ARG fingerprint: `BRANCH_TYPE=remote USE_LATEST_SGLANG=1 SGL_VERSION= SGL_KERNEL_VERSION=0.3.21 DEEPEP_COMMIT=9af0e0d0… FLASHINFER_VERSION=0.6.1 CUDA_VERSION=12.9.1 GDRCOPY_VERSION=2.5.1`. Note `USE_LATEST_SGLANG=1` — the upstream Dockerfile's default is `0` ([`docker/Dockerfile:16`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/docker/Dockerfile#L16)), so this was an explicit unpinned-nightly build.
3. **Map that history entry to its layer.** Counting non-empty entries, `[115]` is layer index 21: `sha256:b1b903f3800d6bfbb2552c91caec6fffa6449b8580c8fd6944443c3429d434c9`, 18.8 MB.
4. **Read the git metadata out of it.** That layer contains `sgl-workspace/sglang/.git/`:

```
.git/shallow                    1e309030e309bec523513a01a68e2128963cfb4e
.git/refs/heads/main            1e309030e309bec523513a01a68e2128963cfb4e
.git/packed-refs                1e309030e309bec523513a01a68e2128963cfb4e refs/remotes/origin/main
```

   A `--depth=1` clone writes the cloned tip into `.git/shallow`. **That is the commit.**

5. **Confirm it, don't just trust it.** `1e309030e309bec523513a01a68e2128963cfb4e` is *"update urllib3 and gpgv Dockerfile (#17439)"*, committed **2026-01-20T22:47:20Z** — the last commit on `main` before the clone ran at `00:31:27Z`, with the next commit landing at `01:40:05Z`, after. Consistent. Then, decisively: `diff -rq` of the extracted tree against the GitHub tarball for that exact commit — **3604 files on each side, zero differences**. The source in the image *is* upstream at that commit, byte for byte.

The corroborating fingerprint holds too: the image's `[137]` step is `pip install --upgrade "urllib3>=2.6.3"`, which is [`docker/Dockerfile:427`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/docker/Dockerfile#L427) — a line introduced by that very commit, whose subject is *"update urllib3"*. The Dockerfile in the image and the commit in `.git/shallow` describe the same build.

### a structural fact that shapes everything below: `sglang serve` runs a *different program* for diffusion models

`sglang serve` dispatches on the model: if the path is a diffusers model it builds a **separate** argument parser and launches the `multimodal_gen` server rather than the LLM server ([`python/sglang/cli/serve.py:46-62`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/python/sglang/cli/serve.py#L46-L62)). FLUX is a diffusers model, so the reviewed code path is `python/sglang/multimodal_gen/`, **not** `python/sglang/srt/`.

Two consequences, both material:

1. **Every finding published about the LLM engine's flags is irrelevant here.** `--log-requests`, `--log-requests-level`, `/configure_logging`, `--crash-dump-folder`, `AuthLevel` — none of it exists in `multimodal_gen`. Reasoning from the sibling sglang pages to this service would be wrong in both directions.
2. **Four of the eight deployed flags are silently discarded.** Line 61 is `parser.parse_known_args(extra_argv)` — unknown flags are dropped without error. The diffusion parser defines `--enable-torch-compile` and `--trust-remote-code`, but **not** `--log-requests-level`, `--mem-fraction-static`, `--enable-metrics`, or `--tensor-parallel-size`. So `--log-requests-level 0` is inert — and, importantly, it was never the control anyone might assume: the prompt disclosure below is a plain `logger.info`, not a request logger, so even a working `--log-requests-level 0` would not have suppressed it.

## findings

### HIGH (deployed: **ON**, unconditional) — the full user prompt is logged at INFO on every generation

`SamplingBatch.log()` builds a multi-line "Sampling params" string that interpolates the user's prompt and negative prompt verbatim, and emits it at INFO — [`schedule_batch.py:259-290`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/python/sglang/multimodal_gen/runtime/pipelines_core/schedule_batch.py#L259-L290):

```
    def log(self, server_args: ServerArgs):
        if self.is_warmup:
            return
        ...
        debug_str = f"""Sampling params:
                      prompt: {self.prompt}
                  neg_prompt: {self.negative_prompt}
                        seed: {self.seed}
            output_file_path: {self.output_file_path()}
        """
        logger.info(debug_str)
```

It is called from the pipeline's `forward()` — [`composed_pipeline_base.py:330`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/python/sglang/multimodal_gen/runtime/pipelines_core/composed_pipeline_base.py#L330), `batch.log(server_args=server_args)` — i.e. on the **generation path of every request**, not on an error path. The only early return is `is_warmup`.

**Is INFO actually emitted?** Yes. `configure_logger` calls `logging.basicConfig(level=getattr(logging, server_args.log_level.upper()), …, force=True)` ([`logging_utils.py:372-380`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/python/sglang/multimodal_gen/runtime/utils/logging_utils.py#L372-L380)) with `log_level: str = "info"` ([`server_args.py:352`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/python/sglang/multimodal_gen/runtime/server_args.py#L352)); the module default is `SGLANG_DIFFUSION_LOGGING_LEVEL = "INFO"` to `ext://sys.stdout` ([`envs.py:23`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/python/sglang/multimodal_gen/envs.py#L23), [`logging_utils.py:39-56`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/python/sglang/multimodal_gen/runtime/utils/logging_utils.py#L39-L56)). The deployed command sets no `--log-level` and the deployed env sets no `SGLANG_DIFFUSION_LOGGING_LEVEL`. **INFO is in force.**

**Where the line goes.** Container stdio → the compose's `json-file` driver → the node's log shippers. This is not speculative for this service: it carries `com.datadoghq.ad.logs: '[{"source":"sglang","service":"sglang", …}]'` ([`prod/small-models.yaml:879`](https://github.com/nearai/cvm-compose-files/blob/main/prod/small-models.yaml#L879)) and `nearai.otel.source: "sglang"` ([`:884`](https://github.com/nearai/cvm-compose-files/blob/main/prod/small-models.yaml#L884)) — it is explicitly enrolled for log collection. The user's prompt therefore reaches a telemetry backend, unredacted. **Under this repo's threat model that is precisely a FINDING: a copy of plaintext reaching a log and a telemetry exporter.**

- **Deployed status: ON.** Nothing in the attested config turns it off.
- **Activates on:** every non-warmup generation.
- **Disabling it** requires `--log-level warning` or `SGLANG_DIFFUSION_LOGGING_LEVEL=WARNING` — neither deployed, and both blunt (they would silence all INFO logging). There is no prompt-specific control, because upstream did not intend this string as a request log; it is a debug print left at INFO on the hot path.

An image-generation prompt is user plaintext in exactly the sense the [scope rule](/README.md#scope-rule) means: it is the message the user typed, sealed to the model's key by OHTTP, and unsealed by the proxy for this engine alone. Its appearance in a shipped log line is the same class of disclosure as a chat prompt in an LLM engine's request log.

### HIGH (deployed: **ON**, unconditional) — every generated image is written to disk and, at the deployed config, never deleted

`save_output=True` is **hardcoded**, not a request parameter — [`image_api.py:83,85`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/python/sglang/multimodal_gen/runtime/entrypoints/openai/image_api.py#L83-L85):

```
        num_outputs_per_prompt=max(1, min(int(n or 1), 10)),
        save_output=True,
        server_args=server_args,
        output_file_name=f"{request_id}.{ext}",
```

The path is `output_path` + `output_file_name` ([`schedule_batch.py:221-231`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/python/sglang/multimodal_gen/runtime/pipelines_core/schedule_batch.py#L221-L231)), with `output_path: str | None = "outputs/"` ([`server_args.py:331`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/python/sglang/multimodal_gen/runtime/server_args.py#L331)) — a **relative** path, and the image's final `WORKDIR` is `/sgl-workspace/sglang`, so files land at `/sgl-workspace/sglang/outputs/<uuid4>.<ext>`. The write itself is `imageio.imwrite(save_file_path, frames[0], quality=quality)` ([`entrypoints/utils.py:75-100`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/python/sglang/multimodal_gen/runtime/entrypoints/utils.py#L75-L100)), gated only on `save_output`.

**The cleanup does not run.** The only deletion path is `cloud_storage.upload_and_cleanup(save_file_path)` ([`image_api.py:149`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/python/sglang/multimodal_gen/runtime/entrypoints/openai/image_api.py#L149)), and its very first act is to return early when cloud storage is disabled — [`storage.py:89-103`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/python/sglang/multimodal_gen/runtime/entrypoints/openai/storage.py#L89-L103): `if not self.is_enabled(): return None`, with the `os.remove(file_path)` reachable only *after* a successful upload. Cloud storage is off here (next finding). **So the file is written and left there.** The default response format is `b64_json` ([`image_api.py:140`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/python/sglang/multimodal_gen/runtime/entrypoints/openai/image_api.py#L140)), which reads the file back and base64-encodes it into the response — and still does not delete it.

So the container accumulates, indefinitely and without bound, a directory of every image every user generated — content derived directly from user plaintext, at rest inside the enclave, readable by anything with filesystem access to that container. There is **no** `outputs/` volume in the compose (`:173-175` mounts only the two caches), so this lands on the container's writable layer: it does not survive container recreation, but it persists for the container's entire lifetime, which for `restart: unless-stopped` is indefinite.

- **Deployed status: ON.** No flag disables the write; `save_output=True` is a literal.
- **Note the asymmetry with the LLM engine.** There, every disk-dump feature is opt-in and off (`--crash-dump-folder`, `--dump-requests-folder`, …). Here, persistence is the **default and only** behavior.

### MEDIUM (deployed: **OFF**) — S3 upload path would egress generated images to a non-model destination

`CloudStorage.__init__` enables itself only when `SGLANG_CLOUD_STORAGE_TYPE` equals `s3` ([`storage.py:12`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/python/sglang/multimodal_gen/runtime/entrypoints/openai/storage.py#L12)), then reads `SGLANG_S3_BUCKET_NAME`, `SGLANG_S3_ENDPOINT_URL`, `SGLANG_S3_REGION_NAME`, `SGLANG_S3_ACCESS_KEY_ID`, `SGLANG_S3_SECRET_ACCESS_KEY` ([`storage.py:25-39`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/python/sglang/multimodal_gen/runtime/entrypoints/openai/storage.py#L25-L39)) and uploads each generated file via `boto3` ([`storage.py:62-67`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/python/sglang/multimodal_gen/runtime/entrypoints/openai/storage.py#L62-L67)). None of those names appears in the deployed environment, so **it is off**, and `is_enabled()` short-circuits every call.

If it were ever switched on, this is a **CRITICAL-class** path: user-derived content leaving the enclave to an arbitrary, operator-chosen S3 endpoint — with `SGLANG_S3_ENDPOINT_URL` the destination need not even be AWS. Whether these variable names are in the node's measured `allowed_envs` — i.e. whether an operator could set them without changing the hardware measurement — is a **manifest question this source tree cannot answer: INCONCLUSIVE here, and worth checking against the measured harness.** Note the interaction with the previous finding: enabling S3 would be the *only* thing that ever cleans up `outputs/`, trading a local at-rest copy for an off-box one.

### LOW — `GET /v1/images/{image_id}/content` serves stored images back, bounded by an unguessable id

[`image_api.py:337-364`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/python/sglang/multimodal_gen/runtime/entrypoints/openai/image_api.py#L337-L364) returns a `FileResponse` for the on-disk file recorded in `IMAGE_STORE` under `image_id`, with no auth. Given the previous findings — the file exists and is never deleted, and the store is populated for every request ([`image_api.py:152-159`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/python/sglang/multimodal_gen/runtime/entrypoints/openai/image_api.py#L152-L159)) — this is a standing, unauthenticated read-back endpoint for other users' generated images.

What bounds it is the identifier: `generate_request_id()` is `str(uuid.uuid4())` ([`sampling_params.py:41-42`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/python/sglang/multimodal_gen/configs/sample/sampling_params.py#L41-L42)) — 122 bits of randomness, not enumerable. Only the requesting client learns its own id. Rated LOW for that reason alone; note that the bound is secret-URL security, and it is defeated by anything that discloses request ids — including the **prompt log line above, which prints `output_file_path` containing the uuid** into the shipped logs. The two findings compose: whoever reads the telemetry logs learns both the prompt and the id needed to fetch the image.

### INFO — `--trust-remote-code` with **no** `--revision`, the only such service on this node

The deployed command passes `--trust-remote-code` and pins no revision, so arbitrary Python from `black-forest-labs/FLUX.2-klein-4B` executes in-process at whatever `main` HuggingFace serves when the container starts. That code runs inside the container that holds the plaintext prompts, and nothing in sglang constrains it. The recipe page already flags this as the only such service on the node; this review confirms it from the image side and adds the consequence: the two HIGH findings above are *sglang's own* behavior, but a `--trust-remote-code` checkpoint could add arbitrary further sinks that no review of this digest would ever see. `HF_HUB_OFFLINE=${HF_HUB_OFFLINE:-0}` (`:55`) means the fetch is live unless an operator sets it.

### INFO — `--enable-metrics` is discarded, and there is no `/metrics` endpoint to scrape

Following from the `parse_known_args` behavior above: `--enable-metrics` is dropped, and a sweep of `multimodal_gen/runtime/` for `prometheus`, `opentelemetry`, `otel`, `sentry`, or a `/metrics` route returns **nothing** — the diffusion server registers only `/health`, `/health_generate`, `/models` on its health router, plus the routers listed above ([`http_server.py:52-91,199-206`](https://github.com/sgl-project/sglang/blob/1e309030e309bec523513a01a68e2128963cfb4e/python/sglang/multimodal_gen/runtime/entrypoints/http_server.py#L52-L91)). The compose nevertheless configures a datadog openmetrics check against `http://model-sg-flux2-klein-4b-tp1:8000/metrics` ([`prod/small-models.yaml:880`](https://github.com/nearai/cvm-compose-files/blob/main/prod/small-models.yaml#L880)). That scrape can only be 404ing. **Privacy-positive, and a configuration-reality mismatch worth reporting**: there is no metrics exporter in this service at all, therefore no metric labels to leak — but the manifest reads as though there were, which is exactly the sort of drift a reviewer relying on manifests alone would get wrong.

### INFO — this is a *development* image, and it shows

The base carries, from its `history`: `gdb`, `py-spy`, `nsight-systems-cli`, `openssh-server` (installed twice, `[93]` and `[122]`), `zsh` + oh-my-zsh with two plugin clones from GitHub `[131]`, `clangd`, `cmake`, `vim`, `tmux`, `htop`, and a `rustup` toolchain used to build `sglang-router` then deleted `[120]`. It also curls binaries at build time from `raw.githubusercontent.com`, `just.systems`, `sh.rustup.rs`, and several GitHub release URLs. That is a normal dev-image inventory and an abnormal production-enclave inventory: it enlarges both the supply-chain surface (many unpinned network fetches at build time, `completeness.materials: false`) and the post-compromise toolkit inside a container that holds plaintext. Not a leak path on its own — no finding — but it is the direct consequence of pinning a rolling `dev-x86` tag instead of a release, and it is the cost side of the CUDA-compatibility reason the compose comment gives for doing so.

## verdict: LEAKS — the FLUX diffusion server logs every user prompt at INFO and writes every generated image to disk, both unconditionally at deployed flags

This is not a flag-dependent verdict and not a hypothetical. At the attested launch command and environment, two copies of user content leave the "plaintext only in the model process" boundary on **every single request**:

1. the **prompt text**, into a stdout log line the compose explicitly enrolls for datadog/otel collection — i.e. off-box, unredacted, to a telemetry backend;
2. the **generated image**, into `/sgl-workspace/sglang/outputs/`, where the deployed configuration never deletes it.

Neither has an off switch short of raising the whole log level, and the disk write has none at all. Both are properties of `multimodal_gen`, the diffusion server this digest actually runs — a code path with no request logger, no authentication and no dump-folder gating, and to which none of the safe-by-default reasoning from this fleet's LLM-engine reviews applies.

Alongside them sit an **operator-flippable S3 egress path** for generated images (off, and its `allowed_envs` reachability unverified), a server with **no authentication mechanism at all** exposing model-mutation and image-read-back endpoints, and `--trust-remote-code` against an **unpinned** checkpoint — the only such service on its node.

**Identity, by contrast, is settled**: `sgl-project/sglang@1e309030e309bec523513a01a68e2128963cfb4e`, recovered from `.git/shallow` inside the clone layer and confirmed by a zero-difference diff of all 3604 files against upstream. The untagged digest was a rolling `dev-x86` push that has since 404'd. Everything above is read from that exact source — but the *running* container is a derived build whose `RUN` layers, and their unpinned PyPI resolution, remain unreviewed.
