# vLLM inference engine (gpt-oss-120b) — Privacy Audit

> Part of the near.ai inference-path privacy audit. Method: [/notes/method.md](/notes/method.md).

- **Image:** `vllm/vllm-openai@sha256:6766ce0c...` (= `v0.12.0`)
- **Source:** https://github.com/vllm-project/vllm/tree/v0.12.0
- **Location:** near.ai model-node CVM, `prod/small-models.yaml`, 3 replicas behind `proxy-gptoss-120b` (`vllm-proxy-rs`); container stdout is collected by a Datadog agent in the same enclave (`com.datadoghq.ad.logs` label), and `:8000/metrics` is scraped by both Datadog (`ad.instances` openmetrics check) and an OTel collector (`nearai.otel.*` labels)
- **Role:** the inference engine — one of the two parties allowed to see plaintext
- **Verdict:** no plaintext reaches any log, disk, or non-model network destination in normal operation at the deployed flags; one **crash-path** defect can put full prompt+output **token IDs** (plaintext-equivalent) on stdout → Datadog; usage-stats phone-home to `stats.vllm.ai` is ON (metadata only, no message content)

No `--api-key`, no `VLLM_API_KEY`, no usage-stats opt-out, no `VLLM_SERVER_DEV_MODE`, no profiler dir, no OTLP endpoint, no kv-transfer/offload config.

**Traced:** request/response logging path (`cli_args.py`, `arg_utils.py`, `api_server.py`, `entrypoints/logger.py`, `serving_engine.py`, `serving_chat.py`); env-gated response-body middleware; dev-mode/profiler endpoint gating and auth middleware wiring; usage-stats reporter (`usage/usage_lib.py`); OTLP tracing (`tracing.py`, `v1/engine/output_processor.py`, `config/observability.py`); Prometheus labels (`v1/metrics/loggers.py`); engine-crash dump (`logging_utils/dump_input.py`, `v1/engine/core.py`, `v1/core/sched/output.py`, `v1/core/sched/scheduler.py`, `v1/request.py`); Responses-API store (`serving_responses.py`); runai streamer loader (`model_executor/model_loader/runai_streamer_loader.py`); the `openai` tool parser and its `harmony_utils` call path; uvicorn access-log wiring.

Absence of findings in untraced code is not evidence of absence.

### MEDIUM (deployed: ARMED — fires only on engine-step crash) — crash dump can write full prompt+output token IDs of resumed requests to stdout, which Datadog ships out of the enclave

When `execute_model` raises, the engine unconditionally dumps the failing step's `SchedulerOutput` at ERROR level — there is no flag to disable it: [`core.py:316`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/v1/engine/core.py#L316) `dump_engine_exception(self.vllm_config, scheduler_output, ...)` → [`dump_input.py:79`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/logging_utils/dump_input.py#L79) `logger.error("Dumping scheduler output for model execution: %s", dump_obj)`. ERROR passes the deployed `VLLM_LOGGING_LEVEL=INFO`, and the compose `com.datadoghq.ad.logs: '[{"source":"vllm",...}]'` label ships this container's stdout to Datadog.

The dumper scrubs *new* requests: `NewRequestData.anon_repr` replaces token IDs with a length ([`output.py:89-99`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/v1/core/sched/output.py#L89), `"prompt_token_ids_len={prompt_token_ids_len}"`), and tensors print shape-only ([`dump_input.py:37`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/logging_utils/dump_input.py#L37) "*We only print the 'draft' of the tensor to not expose sensitive data*"). **But** `CachedRequestData` has no `anon_repr`, so it falls through to the `__dict__` serializer ([`dump_input.py:42-47`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/logging_utils/dump_input.py#L42)) — and it carries [`output.py:123`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/v1/core/sched/output.py#L123) `all_token_ids: dict[str, list[int]]`, populated with `req.all_token_ids.copy()` for every running/resumed request not scheduled in the immediately previous step ([`scheduler.py:842`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/v1/core/sched/scheduler.py#L842)). `Request.all_token_ids` is prompt tokens plus generated tokens ([`request.py:91-95`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/v1/request.py#L91), `self.prompt_token_ids.copy()`). Token IDs under the public gpt-oss tokenizer are plaintext-equivalent.

Exposure window: a crash must coincide with a request resuming after preemption (or otherwise skipping the prior step) — narrow, but preemption at `--max-num-seqs 64` / 128K contexts / 0.90 GPU utilization is routine under load, and crashes correlate with exactly that pressure. In steady state this path emits nothing. (`new_token_ids` stays empty here — populated only under pipeline parallelism, and this is TP1/PP1.)

### MEDIUM (deployed: OFF — one env var away) — response-body logging middleware

[`api_server.py:1427`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/entrypoints/openai/api_server.py#L1427) `if envs.VLLM_DEBUG_LOG_API_SERVER_RESPONSE:` installs middleware that logs full API response bodies (the code itself warns "*can include sensitive information*"). Default false ([`envs.py:28`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/envs.py#L28)), not set in the compose env. If ever set, model outputs would land on stdout → Datadog. The attested compose is the only thing keeping this off.

### LOW (deployed: ON) — usage-stats phone-home to `stats.vllm.ai` (metadata only, no message content)

Enabled by default: [`usage_lib.py:70`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/usage/usage_lib.py#L70) `_USAGE_STATS_ENABLED = not (do_not_track or no_usage_stats or do_not_track_file)`, opt-outs `VLLM_DO_NOT_TRACK` / `DO_NOT_TRACK` / `VLLM_NO_USAGE_STATS` ([`usage_lib.py:58-60`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/usage/usage_lib.py#L58)) — **none set in the compose**. Destination `https://stats.vllm.ai` ([`envs.py:35`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/envs.py#L35)), POSTed at startup and then every 10 minutes ([`usage_lib.py:268`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/usage/usage_lib.py#L268) `time.sleep(600)`, [`usage_lib.py:281`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/usage/usage_lib.py#L281) `global_http_client.post(_USAGE_STATS_SERVER, json=data)`). I read the full payload construction ([`usage_lib.py:203-259`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/usage/usage_lib.py#L203)): GPU/CPU/platform info, model *architecture*, vLLM version, a fixed allowlist of env-var values, uptime counters — no prompts, no request data. Finding is unexpected non-model egress from inside the enclave (fingerprintable deployment metadata), not plaintext. Whether the CVM firewall actually lets this out was not verifiable from source. It also writes `~/.config/vllm/usage_stats.json` in-container.

### LOW (deployed: OFF) — request/prompt logging: default-off, and the deprecated-flag polarity resolves safely

The only consumed switch is `enable_log_requests`, default `False`: [`arg_utils.py:2029`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/engine/arg_utils.py#L2029) `enable_log_requests: bool = False`. The deprecated `--disable-log-requests` still exists ([`arg_utils.py:2048-2052`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/engine/arg_utils.py#L2048), default `not AsyncEngineArgs.enable_log_requests` = `True`) but a whole-tree grep shows its dest is **never read anywhere** — it is a pure no-op alias, so there is no polarity trap: absent both flags, logging is OFF. The `RequestLogger` is only constructed when enabled: [`api_server.py:1506-1507`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/entrypoints/openai/api_server.py#L1506) `if args.enable_log_requests: request_logger = RequestLogger(...)`; otherwise `None`, and `_log_inputs` returns immediately ([`serving_engine.py:1314`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/entrypoints/openai/serving_engine.py#L1314) `if self.request_logger is None: return`).

Defense-in-depth detail worth recording: even if `--enable-log-requests` were added, at this version the prompt text/token IDs are emitted at **DEBUG** ([`logger.py:37-45`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/entrypoints/logger.py#L37) `"Request %s details: prompt: %r, ..."`), which `VLLM_LOGGING_LEVEL=INFO` suppresses; the INFO line carries only request id + sampling params ([`logger.py:47-52`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/entrypoints/logger.py#L47)). Output logging additionally requires `--enable-log-outputs` ([`cli_args.py:181`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/entrypoints/openai/cli_args.py#L181), default `False`; enforced pairing at [`cli_args.py:294`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/entrypoints/openai/cli_args.py#L294)) and *does* log generations at INFO ([`logger.py:76-84`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/entrypoints/logger.py#L76) `"Generated response %s%s: output: %r"`), gated at every call site by both flags (e.g. [`serving_chat.py:1081`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/entrypoints/openai/serving_chat.py#L1081) `if self.enable_log_outputs and self.request_logger:`). `--max-log-len` unset means **unlimited** when logging is on ([`cli_args.py:167-169`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/entrypoints/openai/cli_args.py#L167) "*The default of None means unlimited*") — it never activates logging by itself.

### LOW (deployed: ON) — HTTP surface is unauthenticated inside the enclave network; but no runtime switch can turn content logging on

Auth exists only via `--api-key` or `VLLM_API_KEY` ([`api_server.py:1418`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/entrypoints/openai/api_server.py#L1418) `if tokens := [key for key in (args.api_key or [envs.VLLM_API_KEY]) if key]:`; [`envs.py:27`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/envs.py#L27) default `None`) — neither is deployed, so any process with network reach in the compose network (proxy, nginx, Datadog agent, OTel collector, registrar) can call `/v1/chat/completions` etc. on the vLLM replicas directly. Mitigations verified: the replicas are not port-published to the host (only nginx/proxy are); and — the sglang contrast the audit brief asks about — **vLLM v0.12.0 has no `/configure_logging` analog**: I enumerated the mutable-state endpoints and they are all gated at process start by envs that are unset here: dev-mode block [`api_server.py:857`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/entrypoints/openai/api_server.py#L857) `if envs.VLLM_SERVER_DEV_MODE:` (default 0, [`envs.py:133`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/envs.py#L133)) guarding `/server_info`, `/sleep`, and notably `/collective_rpc` ([`api_server.py:928`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/entrypoints/openai/api_server.py#L928) — arbitrary RPC into workers, would be a serious hole if dev mode were ever set); profiler endpoints [`api_server.py:1070-1072`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/entrypoints/openai/api_server.py#L1070) `if envs.VLLM_TORCH_PROFILER_DIR or envs.VLLM_TORCH_CUDA_PROFILE:` (both unset, [`envs.py:92`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/envs.py#L92)). Logging posture is therefore fixed at container start by the attested compose. Residual: an unauthenticated neighbor can still *submit* requests or read `/metrics`.

### INFO (deployed: OFF/none) — disk persistence: nothing content-bearing lands on the volumes

`VLLM_CACHE_ROOT` ([`envs.py:33`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/envs.py#L33)) consumers in-tree are torch.compile/artifact caches (`vllm/compilation/backends.py`), model registry, and kernel-tuning caches — model-derived, never request-derived. The HF volume holds weights. KV/prefix cache: blocks live in GPU HBM; prefix-cache keys are opaque digests in process RAM ([`kv_cache_utils.py:34`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/v1/core/kv_cache_utils.py#L34) `BlockHash = NewType("BlockHash", bytes)`); no `--kv-transfer-config` / CPU-offload flags are deployed, so no disk tier exists. Responses-API store: gated by `VLLM_ENABLE_RESPONSES_API_STORE` (default false, [`envs.py:205`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/envs.py#L205); [`serving_responses.py:205`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/entrypoints/openai/serving_responses.py#L205)) and even when enabled is an in-memory dict, not disk ([`serving_responses.py:235`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/entrypoints/openai/serving_responses.py#L235) `self.response_store: dict[str, ResponsesResponse] = {}`). Profiler output requires the unset `VLLM_TORCH_PROFILER_DIR`.

### INFO — `--tool-call-parser openai` does not log model output; `--load-format runai_streamer` reaches only HF Hub here

The gpt-oss tool parser's only log statement is a static message with no content ([`openai_tool_parser.py:61-63`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/entrypoints/openai/tool_parsers/openai_tool_parser.py#L61) `logger.exception("Error decoding JSON tool call from response.")`); parsing delegates to `openai_harmony` via [`harmony_utils.py:509`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/entrypoints/harmony_utils.py#L509), which contains no logger calls in vLLM's wrapper (the external library itself: untraced). The runai streamer loader, given an HF model id (not an object-store URI), downloads weights from HF Hub then streams from local disk ([`runai_streamer_loader.py:71-81`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/model_executor/model_loader/runai_streamer_loader.py#L71), `download_weights_from_hf(...)` at [`L74`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/model_executor/model_loader/runai_streamer_loader.py#L74)); S3 egress would require `RUNAI_STREAMER_S3_ENDPOINT` / `AWS_ENDPOINT_URL` ([`runai_streamer_loader.py:54-57`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/model_executor/model_loader/runai_streamer_loader.py#L54)), which are not deployed. Weight ingress from `huggingface.co` (with `HF_TOKEN`, since `HF_HUB_OFFLINE` defaults to 0) is expected egress, carries no user data outbound beyond the token/model name. `--enable-prompt-tokens-details` only adds token *counts* to usage objects ([`cli_args.py:172`](https://github.com/vllm-project/vllm/blob/v0.12.0/vllm/entrypoints/openai/cli_args.py#L172)).

### Controls that would change the verdict

| Control | Effect |
|---|---|
| Set `VLLM_NO_USAGE_STATS=1` (or `VLLM_DO_NOT_TRACK=1`) in the service env | Removes the only steady-state non-model egress (`stats.vllm.ai`); cheap, no downside |
| Patch/upstream an `anon_repr` for `CachedRequestData` (or scrub `all_token_ids` in `prepare_object_to_dump`) | Closes the crash-path token-ID leak at the source |
| Drop/scrub `source:vllm` ERROR "Dumping scheduler output" lines in the Datadog pipeline | Containment for the same leak without touching the image |
| Add `--api-key` / `VLLM_API_KEY` (proxy holds the secret) | Closes the unauthenticated intra-enclave HTTP surface |
| Keep `VLLM_DEBUG_LOG_API_SERVER_RESPONSE`, `VLLM_SERVER_DEV_MODE`, `VLLM_TORCH_PROFILER_DIR`, OTLP endpoint, and both log flags **absent** (attested compose already does) | Any one appearing would create a plaintext path — treat their absence as a monitored invariant |
| Adding `--enable-log-requests --enable-log-outputs`, or `VLLM_LOGGING_LEVEL=DEBUG` together with `--enable-log-requests` | Would put full prompts and/or generations on stdout → Datadog — verdict flips to RED |

### Verdict: no exfiltration path for chat plaintext at the deployed flags in normal operation

Request/response logging is off by default with the deprecated-flag polarity independently confirmed harmless; tracing/profiling/dev endpoints are container-start gated and off; disk artifacts are model-derived only; metrics are aggregate-only. Two real findings: (1) an unconditional engine-crash dump that, when a crash coincides with a preemption-resume, writes full prompt+output token IDs — plaintext-equivalent — to stdout that Datadog exports from the enclave; (2) default-on usage telemetry to `stats.vllm.ai` (deployment metadata, no content).

**Residuals.** Image↔source correspondence rests on the digest→tag reverse lookup plus Docker Hub publication integrity, not a reproducible build — everything above assumes the image binaries match the v0.12.0 tree. Native/binary components (`runai_model_streamer`, `openai_harmony`, torch, NCCL, CUDA) and the co-resident Datadog agent, OTel collector, `vllm-proxy-rs`, and nginx were not audited here; the proxy in particular sees plaintext by design and carries several outbound URLs (`cloud-api.near.ai`, web-context search) that need their own review. Whether enclave egress policy actually blocks `stats.vllm.ai`, and what the Datadog pipeline retains from this container's stdout, could not be established from source. Sampling params echoed in crash dumps and INFO logs can contain user-supplied `stop` strings — a small content fragment not counted above. Absence of evidence in the untraced components is not proof.
