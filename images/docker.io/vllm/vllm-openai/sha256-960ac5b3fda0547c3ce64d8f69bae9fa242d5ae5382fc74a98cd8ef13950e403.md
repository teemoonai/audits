# vLLM inference engine — Privacy Audit

> Part of the near.ai inference-path privacy audit. Method: [/notes/method.md](/notes/method.md).

**Image:** `docker.io/vllm/vllm-openai@sha256:960ac5b3…` (vLLM v0.23.1rc1 per compose comment, FA4 gemma-4 attention)
**Source:** [`github.com/vllm-project/vllm`](https://github.com/vllm-project/vllm/tree/b4c80ec0fd19c13a53d89623bb5957cd5cd631bb) @ `b4c80ec0fd19` (the image's declared build commit); reviewed against [`e3e3cd54589c`](https://github.com/vllm-project/vllm/tree/e3e3cd54589cee689b785aab5bda81b3e4203191), verified equivalent for every citation — see correction above
**Location:** Model node CVM — the deepest point of the path.
**Role:** **the model.** It *must* see your plaintext to run inference. The question is whether, at the deployed launch flags, it logs / persists / egresses that content.
**Verdict:** **PRIVATE at the deployed flags** — request logging is opt-in-and-off, there is no runtime toggle, disk tiers are off, and the one on-by-default egress (usage-stats phone-home) is content-free.

### Verdict: PRIVATE at deployed flags
On the deployed launch command/env, the engine does **not** log, persist, or egress user plaintext: request logging is opt-in and absent (this vLLM's default — the polarity is the opposite of legacy `--disable-log-requests` versions, verified at source); prompt text would additionally require DEBUG level; there is **no runtime endpoint** that can enable logging without a restart; KV/prefix cache is GPU-RAM-only; `VLLM_CACHE_ROOT` holds compile artifacts, not request data; tracing is off and content-free by construction; metrics are pull-based counts. Prompt/response content stays in process memory for the request's duration.

**Residuals (why not unconditional):** (1) **Build trust, not version drift** — the source commit is now pinned to the image's declared `b4c80ec0` and every citation was verified to hold there, so the earlier "unknown commits of drift" residual is retired. What remains is weaker but real: the OCI label is *self-asserted by the builder*, not a signed provenance attestation, and nothing reproducibly ties the shipped layers to that tree — a malicious or compromised build could label itself anything. (2) **Usage-stats egress ON** — content-free but unsolicited, every 10 min to `stats.vllm.ai`; should be disabled via `VLLM_NO_USAGE_STATS` or blocked by CVM egress policy (unverified here). (3) **Crash-dump residue** — client `stop`/`bad_words`/guided-decoding schemas reach stdout on an engine crash (prompts are redacted to lengths). (4) Unauthenticated HTTP surface — no content switch exists, but co-resident containers can use the model and hit ops endpoints; env-flip risks (`VLLM_DEBUG_LOG_API_SERVER_RESPONSE`, `VLLM_SERVER_DEV_MODE`) hinge on the dstack `allowed_envs` list, outside this tree. (5) `patch_tile80.py` and the image build itself were not source-audited; `--trust-remote-code` is on though inert for in-tree Gemma-4, and remote *code* revision would not be pinned by `--revision` if it ever activated.
