## Findings

### MEDIUM (deployed: ARMED, fires on the Qwen3-VL service when a chat request names media by http(s) URL in a content part written without a type field, which the deployed proxy forwards unchanged) — media-fetch retry warning writes the request's media URL and the fetch error to the stdout log, which the collector ships out of the enclave

Not on the lineage pages. The engine's HTTP helper wraps its fetches in a retry decorator ([`connections.py:469`](https://github.com/vllm-project/vllm/blob/4ba787ec9959e566d3b587a796dff07673324da5/vllm/connections.py#L469) `@_async_retry` on `async_get_bytes`; `:449` on the sync twin) that, when an attempt fails with a retryable error and attempts remain ([`:350-354`](https://github.com/vllm-project/vllm/blob/4ba787ec9959e566d3b587a796dff07673324da5/vllm/connections.py#L350)), calls `_log_retry`:

```text
    url = args[1] if len(args) > 1 else kwargs.get("url")
    ...
    logger.warning(
        "HTTP fetch failed for %s (attempt %d/%d, %s): %s -- retrying in %.3fs%s",
        url,
```

([`:258`](https://github.com/vllm-project/vllm/blob/4ba787ec9959e566d3b587a796dff07673324da5/vllm/connections.py#L258), [`:267-276`](https://github.com/vllm-project/vllm/blob/4ba787ec9959e566d3b587a796dff07673324da5/vllm/connections.py#L267)). No flag, no level guard beyond WARNING, no truncation. The URL is the one in the request the engine receives: an image part goes `content_parser.py:386` `self._connector.fetch_image_async(image_url)` → [`connector.py:563`](https://github.com/vllm-project/vllm/blob/4ba787ec9959e566d3b587a796dff07673324da5/vllm/multimodal/media/connector.py#L563) → `load_from_url_async` → [`:467-468`](https://github.com/vllm-project/vllm/blob/4ba787ec9959e566d3b587a796dff07673324da5/vllm/multimodal/media/connector.py#L467) `await connection.async_get_bytes(url_spec.url, ...)` — the URL is the first positional argument, i.e. `args[1]`. `audio_url` and `video_url` parts take the same path (`content_parser.py:478`, `:506`). Once the engine holds an http(s) URL the line fires readily: `VLLM_MEDIA_FETCH_MAX_RETRIES` is unset, default 3 ([`envs.py:76`](https://github.com/vllm-project/vllm/blob/4ba787ec9959e566d3b587a796dff07673324da5/vllm/envs.py#L76); `connections.py:339`), so the first two failed attempts each log; retryable means timeouts, connection-level failures including DNS, and 5xx ([`:201-244`](https://github.com/vllm-project/vllm/blob/4ba787ec9959e566d3b587a796dff07673324da5/vllm/connections.py#L201)); and this engine's network is `internal: true`, which the recipe's `engine-egress-probe` (`:2272-2319` in `bbc809427267`) asserts has no default route and resolves no outside name — every external fetch fails in exactly the retryable class.

**Does an http(s) URL reach the engine? Not in the standard shape; yes in one the proxy does not recognise.** The proxy in front (`c57cd9ea`, source `3f7e9798`) runs `inline_remote_media` on the chat route (`src/routes/chat.rs:218`) with inlining on by the recipe's default. For a content part whose `type` is `image_url` or `audio_url` it downloads the URL itself and rewrites it to a `data:` URL, and if the download fails the request is refused with a 400 (`src/media_inline.rs:134-290`; "Fail closed", `:8-11`) — so on that shape the engine receives bytes or nothing, and the warning cannot fire. But that build selects parts by their `type` string alone (`:152-170`: `let ty = part.get("type")...unwrap_or(""); match ty { "image_url" => ..., "audio_url" => ..., "input_audio" => ..., _ => continue }`); its image check does the same (`src/image_validation.rs:195`), its content-part policy matches `type` (`src/content_policy.rs:33-36`), and its request guard only refuses non-http(s)/data schemes on media keys (`src/request_guard.rs:570-632`). vLLM, however, takes a part's media from its keys when `type` is missing ([`chat_message.py:255-263`](https://github.com/vllm-project/vllm/blob/4ba787ec9959e566d3b587a796dff07673324da5/vllm/renderers/chat_utils/chat_message.py#L255): `if part_type is None or uuid is not None: if "image_url" in part: ... return "image_url", image_url`; audio at `:297-306` of the same function) and then fetches it (`:498-500` `mm_parser.parse_image`). I ran the tree's message types under pydantic 2.12.5 on the untyped forms:

```text
role user   {"image_url": "https://host/a.png?sig=..."}   -> accepted, engine sees the part unchanged
role user   {"audio_url": "https://host/a.wav"}           -> accepted, engine sees the part unchanged
role user   {"image_url": {"url": "https://..."}}         -> ValidationError (no fetch)
role user   {"type":"image_url","image_url":{...}}        -> accepted (this is the shape the proxy inlines)
```

So a chat request with `{"image_url": "<http(s) URL>"}` (bare string, no `type`) under an ordinary `user` role passes the proxy's guard, is skipped by its inliner and image check, reaches the engine as written, and the engine tries the fetch on a network with no route: two WARNING lines carrying the URL and the exception text, then the request fails. A part typed `input_image` is likewise outside the inliner's match and inside vLLM's image branch (`:498`); I read that path but did not execute it. This is a request shape vLLM accepts but no standard OpenAI client emits — hence ARMED and MEDIUM, not ON. The newer proxy build `e3a4fbca` (`3b47be98`) finds media by key and refuses anything left un-inlined; it does not front this engine.

**Other ways to hand the engine a URL.** `VLLM_PROXY_INLINE_MEDIA=0` in the proxy's environment turns the inliner into a no-op (`src/media_inline.rs:138-140`) and every URL request then logs; the recipe writes the variable as a `${...:-1}` default, and whether an operator can change it without changing a measurement is a manifest-page question (the name does not appear in the measured documents I was given). A caller that reaches `:8000` without the proxy would also do it; on `engine-qwen3vl` the only other containers are the collector and the exited probe, neither of which sends chat requests. In the two `small-models.yaml` revisions the engine would sit on the shared `dstack_default`.

What does not trigger it: `data:` URLs never reach the network ([`connector.py:439`](https://github.com/vllm-project/vllm/blob/4ba787ec9959e566d3b587a796dff07673324da5/vllm/multimodal/media/connector.py#L439)); a 4xx is not retried. I verified the retry classification by reading `_is_retryable`; that aiohttp reports DNS and connect failures as `ClientConnectorError` (a `ClientConnectionError`) is from aiohttp's class hierarchy and was **not executed** here. The proxy's behaviour was read in its source, not run. **Fix (restart-time):** `VLLM_MEDIA_FETCH_MAX_RETRIES=1` on the engine removes the retry and with it the log line; moving this proxy to the `e3a4fbca` build closes the untyped shape; upstream should log the host at most.

**Can it execute?** A text part without a `text` key must first pass request validation. I ran the tree's own types (`ChatCompletionMessageParam`, `types.py:264-320`) under a model with `extra="allow"` (as `OpenAIBaseModel`, `serve/engine/protocol.py:37-39`), pydantic 2.12.5 (the tree requires `>= 2.12.0`, `requirements/common.txt:22`):

```text
custom role          {"type":"text","content":"MY SECRET MESSAGE"}   -> part={'type': 'text', 'content': 'MY SECRET MESSAGE'}  WARNING
custom role          {"type":"text","text":null,"note":"..."}        -> part kept whole                                       WARNING
custom role          {"type":"refusal","text":"MY SECRET MESSAGE"}   -> part kept whole                                       WARNING
```

So with the standard OpenAI roles the lazily validated content list raises before the parser sees the part; with any other role string the message matches `CustomChatCompletionMessageParam` (`role: Required[str]`, `types.py:284-287`), the malformed part survives with its extra keys, and the warning prints it. The request-level validators (`chat_completion/protocol.py:587-619`) touch only `tool_calls` and `reasoning_content`. **Through the proxy?** Yes. The deployed proxy source (`3f7e9798`) has no role allowlist: its request guard reads content parts only for the `uuid` cap and media URL schemes (`src/request_guard.rs:570-596`), and its system-message merge touches `role == "system"` messages only and leaves every other role unchanged (`src/system_messages.rs:79`; test `other_roles_are_never_merged_moved_past_each_other_or_changed`, `:344`). Nothing in it refuses a text part that lacks `text`. So both halves of the trigger pass through to the engine. The trigger is a client bug (wrong key name on a text part) combined with a non-standard role, not ordinary traffic — hence MEDIUM and ARMED rather than ON — but what it prints is the user's text, at WARNING, with the level and flags as deployed. I did not run the engine or the proxy; the pydantic version inside the image was not checked.

### Verdict

**QUALIFIED PASS.** The class call, stated so a reader can disagree: following this repo's precedent for the crash dump, a sink that only a malformed or non-standard client request, or a crash, can trigger is ARMED and does not set LEAKS; LEAKS is kept for content that reaches a sink in the course of requests a standard client makes or output the model itself produces. By that rule the two content sinks below are qualifications; a reader who counts any client-reachable trigger would call this page LEAKS, conditionally. At the deployed flags a request in the standard shapes leaves no copy of its content in any log, file or non-model destination: request logging is passed off, the response-body middleware, dev routes, tracing and profiler are gated by values the recipe leaves unset, there is no runtime logging switch, disk artifacts are config-keyed, the token-id history stays out of the crash dump, and the proxy in front of Qwen3-VL fetches media itself so the engine is handed bytes, not URLs. What qualifies the pass is that two content sinks remain reachable **through the deployed proxy** by a request the client chooses to write: (1) a media part with no `type` field, which this proxy build forwards unchanged and vLLM accepts, makes the no-egress engine print the URL in its retry warning; (2) a text part without its `text` field under a non-standard role, which the proxy also forwards, is printed whole by the chat parser. Both are one bounded piece on a stated trigger, in a deployment that ships WARNING lines out of the enclave with no redaction. Neither is reached by a standard OpenAI-shaped client, which is why they qualify the pass rather than set LEAKS.

**Residuals.** Image↔source correspondence rests on a builder-asserted label. Native components were not read.
