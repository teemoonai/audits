# vLLM inference engine (Qwen3-VL-30B) — Privacy Audit

> Part of the near.ai inference-path privacy audit. Method: [/notes/method.md](/notes/method.md).

**Image:** `docker.io/vllm/vllm-openai@sha256:ccd6a6db…` (untagged; bracketed to vLLM main between `12b38c0f` and `v0.17.0`)
**Source:** [`github.com/vllm-project/vllm`](https://github.com/vllm-project/vllm/tree/v0.17.0) reviewed at `v0.17.0` (`b31e9326a7d9`); drift across the bracket measured file-by-file — see coverage
**Location:** near.ai model-node CVM, GPU 7 (shared with FLUX, embedding, reranker, whisper, privacy-filter), behind `proxy-qwen3vl-30b-a3b` on port 8003.
**Role:** **the model.** It must see your plaintext to run inference. The question is whether, at the deployed launch flags, it logs / persists / egresses that content — and, because this one is a **vision** model, whether the request can steer it to fetch from arbitrary places.
**Verdict:** **PRIVATE for message plaintext at the deployed flags** — request logging is opt-in and absent, no runtime toggle exists, disk tiers are off. **But** the multimodal fetch path is deployed with *no* domain allowlist and redirect-following left at its permissive default, while the sibling multimodal service in the same compose file locks both down. That is a hardening gap, not a plaintext leak, and it is the reason this page is not an unqualified PRIVATE.

### MEDIUM (deployed: ACTIVE) — Media fetch has no domain allowlist and follows redirects; the allowlist guard is a truthiness test, so "unset" means "no enforcement"

For every `image_url` in a chat request, the async content parser builds a `MediaConnector` with the model config's value: [`chat_utils.py:886-891`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/entrypoints/chat_utils.py#L886-L891) `MEDIA_CONNECTOR_REGISTRY.load(envs.VLLM_MEDIA_CONNECTOR, …, allowed_media_domains=tracker.allowed_media_domains)` (sync twin at [`:773-778`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/entrypoints/chat_utils.py#L773-L778)), reading [`chat_utils.py:495-496`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/entrypoints/chat_utils.py#L495-L496) `return self._model_config.allowed_media_domains`. With `--allowed-media-domains` absent that is `None` ([`config/model.py:160`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/config/model.py#L160) `allowed_media_domains: list[str] | None = None`; CLI flag registered at [`arg_utils.py:681-683`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/engine/arg_utils.py#L681-L683), default at [`:378`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/engine/arg_utils.py#L378)), which the connector normalises to an empty list: [`connector.py:81-83`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/multimodal/media/connector.py#L81-L83) `if allowed_media_domains is None: allowed_media_domains = []`.

The enforcement is then a **truthiness test on that list**, not a presence test on the flag — [`connector.py:124-133`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/multimodal/media/connector.py#L124-L133):

```python
def _assert_url_in_allowed_media_domains(self, url_spec: Url) -> None:
    if (
        self.allowed_media_domains
        and url_spec.hostname not in self.allowed_media_domains
    ):
        raise ValueError(...)
```

An empty list is falsy, so the `and` short-circuits and **the function returns without checking anything**. The docstring at [`connector.py:53-55`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/multimodal/media/connector.py#L53-L55) ("If set, only media URLs that belong to this domain can be used") describes the enabled case only; the disabled case is silent, unlogged, and total. At the deployed flags, `_assert_url_in_allowed_media_domains` is a no-op on every request.

The fetch that follows is unconditioned — [`connector.py:174-184`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/multimodal/media/connector.py#L174-L184):

```python
if url_spec.scheme and url_spec.scheme.startswith("http"):
    self._assert_url_in_allowed_media_domains(url_spec)
    connection = self.connection
    data = await connection.async_get_bytes(
        url_spec.url,
        timeout=fetch_timeout,
        allow_redirects=envs.VLLM_MEDIA_URL_ALLOW_REDIRECTS,
    )
```

and redirect-following defaults to **on** — [`envs.py:68`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/envs.py#L68) `VLLM_MEDIA_URL_ALLOW_REDIRECTS: bool = True`, resolved at [`envs.py:765-767`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/envs.py#L765-L767) `bool(int(os.getenv("VLLM_MEDIA_URL_ALLOW_REDIRECTS", "1")))`. The gemma sibling sets it to `0`; this service does not set it at all.

**What this is and is not.** It is *not* a copy of message plaintext to a third party: nothing in vLLM sends the conversation anywhere. It *is* a request-steered outbound HTTP GET issued by the plaintext-handling process inside the CVM, to any host the requester names, with redirects followed — so the URL string itself (attacker-chosen, and in practice carried inside the user's message payload), the fetch timing, and the CVM's egress identity reach an arbitrary destination, and the engine can be used as an SSRF pivot into the `dstack_default` docker network — where, per the next finding, every model container's `:8000` is unauthenticated. Redirects matter independently: they are the standard way an allowlist gets walked out of, which is presumably why the gemma service disables them.

**What bounds it, verified:** schemes are limited — non-`http(s)`/`data`/`file` URLs are rejected at [`connector.py:194-195`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/multimodal/media/connector.py#L194-L195) `msg = "The URL must be either a HTTP, data or file URL."`, and the HTTP client re-validates at [`connections.py:38-44`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/connections.py#L38-L44) `if parsed_url.scheme not in ("http", "https"): raise ValueError(...)`. `file:` URLs are refused outright because `--allowed-local-media-path` is absent — [`connector.py:104-109`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/multimodal/media/connector.py#L104-L109) `if allowed_local_media_path is None: raise RuntimeError("Cannot load local files without --allowed-local-media-path.")`, so the engine cannot be made to read the enclave's filesystem. `data:` URLs (the path a normal mobile client uses — base64 inline) never touch the network at all, and only base64 is accepted ([`connector.py:93-95`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/multimodal/media/connector.py#L93-L95)). Fetched bytes stay in RAM — there is no media-cache-to-disk env in this tree. Timeouts are short ([`envs.py:65`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/envs.py#L65) `VLLM_IMAGE_FETCH_TIMEOUT: int = 5`).

**Fix:** add `--allowed-media-domains …` and `VLLM_MEDIA_URL_ALLOW_REDIRECTS=0` to this service, matching the gemma sibling. Both are restart-time. Note that `--allowed-media-domains` compares `url_spec.hostname` by exact membership ([`connector.py:127`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/multimodal/media/connector.py#L127)) — no suffix matching, so it is a strict host list, which is the right shape.

### HIGH (deployed: OFF) — Prompt and response logging exist, are opt-in, and are absent — but the outputs path is INFO-level, contradicting its own flag docs

No `--enable-log-requests` is deployed and the default is off: [`arg_utils.py:2174`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/engine/arg_utils.py#L2174) `enable_log_requests: bool = False` (flag registered [`:2186-2194`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/engine/arg_utils.py#L2186-L2194)). Without it the logger object is never constructed — [`api_server.py:313-316`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/entrypoints/openai/api_server.py#L313-L316) `if args.enable_log_requests: request_logger = RequestLogger(max_log_len=args.max_log_len) else: request_logger = None` — and the chat path's call at [`chat_completion/serving.py:409-414`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/entrypoints/openai/chat_completion/serving.py#L409-L414) dead-ends immediately at [`engine/serving.py:1131-1132`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/entrypoints/openai/engine/serving.py#L1131-L1132) `if self.request_logger is None: return`. So at the deployed flags no prompt or response text is written by this path at any log level.

Two properties matter for the "what if someone flips it" case, and they differ from the flag's documentation.

*Inputs are DEBUG-gated.* [`logger.py:44-61`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/entrypoints/logger.py#L44-L61) wraps the prompt emission in `if logger.isEnabledFor(logging.DEBUG):` before `logger.debug("Request %s details: prompt: %r, prompt_token_ids: %s, …")`. Under the deployed `VLLM_LOGGING_LEVEL=INFO` that branch is inert even if the flag were set; the unconditional INFO line at [`logger.py:63-68`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/entrypoints/logger.py#L63-L68) carries only request id, sampling params and LoRA request. Enabling prompt logging therefore takes **two** changes (flag + level), which is a genuinely good design.

*Outputs are not.* [`logger.py:92-99`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/entrypoints/logger.py#L92-L99) emits `logger.info("Generated response %s%s: output: %r, output_token_ids: %s, finish_reason: %s", …)` with **no level guard at all** — the complete generated text, at INFO. The flag's own docstring says otherwise: [`cli_args.py:144-147`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/entrypoints/openai/cli_args.py#L144-L147) `enable_log_outputs: bool = False` / *"Requires `--enable-log-requests`. As with `--enable-log-requests`, information is only logged at INFO level at maximum."* Read against the code, "at INFO at maximum" means model responses land in the log at the **deployed** level, not a debug-only one. Streaming deltas too, since [`cli_args.py:148-151`](https://github.com/vllm-project/vllm/blob/v0.17.0/vllm/entrypoints/openai/cli_args.py#L148-L151) `enable_log_deltas: bool = True`. ### Verdict: PRIVATE for message plaintext at the deployed flags, with one unhardened egress path

For the question this repo asks — can anything exfiltrate the user's plaintext chat messages — the answer at these flags is **no, on every path I traced**. Request logging is opt-in and the flag is absent, so the logger object is never constructed and the call sites no-op; prompt text would additionally require DEBUG, which is not the deployed level; response logging needs a second flag on top. There is **no runtime endpoint** that can enable any of it — every escalation is restart-time, which on this platform means a new container and a new measurement. Prefix/KV cache lives in GPU memory with no disk tier configured; the processed-media cache is in-process RAM; `VLLM_CACHE_ROOT` holds compile artifacts keyed by config hash, not request data; the responses store is off and would be in-memory anyway. Tracing is off and content-free by construction; metrics are pull-based counts labelled only by model and engine. The one on-by-default network egress carries hardware and config facts and no message content, verified field by field. Message plaintext stays in process memory for the life of the request.

The verdict is **not unqualified**, for a reason specific to this service being the vision one. Its multimodal fetcher will retrieve `image_url`s from any host, following redirects, because `--allowed-media-domains` is absent and the guard that would enforce it is a truthiness test on an empty list — and because `VLLM_MEDIA_URL_ALLOW_REDIRECTS` was left at its permissive default. That moves no chat plaintext to a third party, and the schemes are constrained enough that the enclave's filesystem is not exposed. But it is a request-steered outbound channel from the plaintext-handling process, and the sibling multimodal service in the same attested compose file closes both halves of it. Two lines of YAML, matching a configuration this operator has already written once, would remove the qualification.

**Residuals (why not unconditional):**

1. **Identity, not just drift.** This image is untagged and label-less: unlike every sibling page here, nothing in the registry asserts a source commit. The bracket is inferred from build ARGs, and although I confirmed that 16 of 18 cited files had zero commits in the 3-day window (and checked the other two individually, one of which shifts a cited line by exactly one), the whole exercise assumes the image was built from vLLM main at all. There is no build attestation and no reproducible build, so nothing ties the shipped layers to any tree.
2. **Media-fetch egress unrestricted** — the MEDIUM above. Its real-world blast radius depends on two things outside this tree that I did not verify and will not assume: whether `vllm-proxy-rs` validates or rewrites `image_url` before forwarding, and whether the CVM has an egress firewall.
3. **Unauthenticated engine port on the shared network** — any co-resident container can use the model directly, bypassing the proxy, and can drive the fetcher in (2). No content-logging switch is reachable that way, which is what bounds it.
4. **Usage-stats egress ON** — content-free but unsolicited, every 10 minutes to `stats.vllm.ai`, plus an appended local JSON file. One env var stops it.
5. **Crash-dump residue** — client `stop`/`bad_words`/structured-output schemas reach stdout on an engine crash; prompts and outputs are redacted. The `mm_features` field is redacted *by virtue of* its leaves being tensors, which I verified as a mechanism but did not exhaustively confirm for every Qwen3-VL processor field.
6. **Shared prefix cache** — no `cache_salt` is applied, so cross-caller prefix reuse is observable by timing. No plaintext copy; the mitigation belongs to the caller.
7. **Scope** — this covers `model-vllm-qwen3vl-30b-a3b-fp8-tp1` only. The embedding and reranker services share the digest but not the multimodal surface. The whisper service `FROM`s this digest and then `pip install`s `vllm[audio]` from PyPI at build time, which can replace the audited engine entirely inside the enclave; it needs its own page.
