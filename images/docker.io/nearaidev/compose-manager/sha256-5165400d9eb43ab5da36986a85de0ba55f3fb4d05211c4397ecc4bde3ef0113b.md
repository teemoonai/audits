## Results

### CRITICAL (mechanism) / HIGH (effective) — the caller-supplied `env` map is applied after the attested hash and is recorded nowhere a verifier can see

Unchanged from the base page, re-verified at this commit's line numbers.

`POST /compose/up` accepts a free-form map — `env: HashMap<String, String>,` ([`main.rs:359`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L359)). The only validation is key charset and a newline ban: `validate_env_vars` ([`:418-428`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L418-L428)) — **no allow-list, any name and value is accepted.** The attested hash covers the compose text only: `let file_sha256 = hex::encode(sha2::Sha256::digest(content.as_bytes()));` ([`:1051`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L1051)). The map is then written to a temp file (`write_temp_env_file` [`:430-442`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L430-L442)) and appended as the **last** `--env-file` — `cmd.args(["--env-file", tef.to_str().unwrap()]);` ([`:932`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L932)), i.e. after `state.env_files`, so it **overrides** the sealed CVM secrets.

What gets committed to the quote is the action log and nothing else: `DeploymentAction` is `{timestamp, action, tag, commit, file, file_sha256, services, container, image}` ([`:163-185`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L163-L185)) — **there is no `env` field** — and `attestation_report` hashes exactly that list into TDX `report_data`: `report_data[..32].copy_from_slice(&actions_hash);` ([`:1392`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L1392)). A remote verifier therefore sees which compose file was deployed and its SHA-256, and has **zero visibility into the values substituted into that file's `${VAR}`s**.

**Effective.** Reachability is unchanged from the base page and is bounded by the *inner* compose's parameterization, not by anything on this page; the mitigating facts there still hold (engine image digests and the sglang launch command including `--log-requests-level 0` are literals covered by `file_sha256`). Caller access requires `BEARER_TOKEN`, which **is** in `allowed_envs` on every manifest read here — so the operator is the reachable adversary, which is precisely the confidential-computing threat actor.

### HIGH (mechanism and effective) — the measured manifest pins this digest only as a *fallback*; the running manager image is restored from an unmeasured file across reboots

This is the sharpest answer to "can an operator change what runs after the enclave is measured", and it is visible in the measured manifest itself, not only in source.

The measured compose does not pin the manager image outright. It reads:

```
image: ${COMPOSE_MANAGER_IMAGE:-nearaidev/compose-manager@sha256:5165400d9eb43ab5da36986a85de0ba55f3fb4d05211c4397ecc4bde3ef0113b}
```

(measured `compose_hash` `fb3d47e5…`, `docker_compose_file:125`; identically at `002b406e…:125`). The digest on this page is the **default**, taken only when `COMPOSE_MANAGER_IMAGE` is unset.

The same manifest's `pre_launch_script` sets it from a persistent file inside the CVM's docker volume, outside the measurement:

```
OVERRIDES="/var/lib/docker/volumes/dstack_work/_data/.env.launcher"
if [ -f "$OVERRIDES" ]; then
  while IFS='=' read -r k v; do
    case "$k" in COMPOSE_MANAGER_IMAGE) export "$k=$v" ;; esac
  done < "$OVERRIDES"
```

`.env.launcher` is written by the launcher on every successful swap — `write_env_var "COMPOSE_MANAGER_IMAGE" "$image_ref"` ([`launcher.sh:324`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/launcher/launcher.sh#L324)), path `LAUNCHER_ENV_FILE=/app/work/.env.launcher` (measured `fb3d47e5…:198`). The launcher polls Docker Hub for `LAUNCHER_CHANNEL` every 300s and resolves whatever digest that **mutable tag** currently points at (`CHANNEL="${LAUNCHER_CHANNEL:-latest}"` [`launcher.sh:7`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/launcher/launcher.sh#L7); `fetch_remote_digest` [`:103-127`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/launcher/launcher.sh#L103-L127)), then hot-swaps the container ([`:327`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/launcher/launcher.sh#L327)).

**`LAUNCHER_CHANNEL` is in `allowed_envs`** on every manifest read here — so an operator can redirect the channel, and both the swap and its survival across reboot happen **with no change to `compose_hash` and no change to any RTMR**. The measurement pins a default, not the running image.

**What bounds it.** The swap is gated by cosign: `verify_attestation` runs `cosign verify --certificate-identity-regexp="$COSIGN_IDENTITY" --certificate-oidc-issuer="$COSIGN_ISSUER"` ([`launcher.sh:151-154`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/launcher/launcher.sh#L151-L154)) and refuses the update on failure ([`:319-322`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/launcher/launcher.sh#L319-L322)). The identity is a **measured literal** — `LAUNCHER_COSIGN_IDENTITY_REGEXP=https://github.com/nearai/compose-manager/.github/workflows/.*` (measured `fb3d47e5…:205`, `002b406e…:205`) — and the issuer defaults to GitHub's OIDC issuer ([`launcher.sh:28`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/launcher/launcher.sh#L28)).

**Improvement on the base page, verified here:** the kill-switch `LAUNCHER_SKIP_VERIFY` ([`launcher.sh:140-143`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/launcher/launcher.sh#L140-L143)) and `LAUNCHER_COSIGN_IDENTITY_REGEXP` are **absent from `allowed_envs`** on all seven measured manifests examined. The base page recorded this as INCONCLUSIVE; at these measured configs the cosign gate is **not** operator-disableable without breaking the measurement. So the residual is bounded to: *any image signed by any workflow under `nearai/compose-manager`*, which the operator can install and make persistent, invisibly to `compose_hash`. A client verifier still catches it only if it pins the expected manager digest itself.

### MEDIUM (mechanism) — after a launcher swap, compose-manager's service definition comes from the launcher image, not from the measured manifest

`bootstrap` unconditionally copies the compose file bundled inside the launcher image over the working copy — `cp /app/docker-compose.yml "$COMPOSE_FILE"` ([`launcher.sh:229`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/launcher/launcher.sh#L229)) — and every swap runs `docker compose -p "$COMPOSE_PROJECT" -f "$COMPOSE_FILE" … up` ([`:185`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/launcher/launcher.sh#L185)) with `LAUNCHER_COMPOSE_PROJECT=dstack` (measured `fb3d47e5…:197`). The privilege set in the bundled file is identical to the measured one (`pid: host`, `SYS_ADMIN`, `SYS_PTRACE`, `/var/run/docker.sock`, `/var/run/dstack.sock`, `.decrypted-env`, `work` volume — [`launcher/docker-compose.yml:14-22`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/launcher/docker-compose.yml#L14-L22) vs measured `fb3d47e5…:147-155`), so this is not a privilege escalation. But the **env differs**: the bundled file uses `GITHUB_REPO=${CM_GITHUB_REPO:-https://github.com/nearai/cvm-compose-files}` ([`:24`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/launcher/docker-compose.yml#L24)) and `MIN_TAG_AGE_HOURS=${CM_MIN_TAG_AGE_HOURS:-2}` ([`:27`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/launcher/docker-compose.yml#L27)) where the measured file uses literals (`fb3d47e5…:157`, `:160`), and it drops `SLACK_WEBHOOK_URL`/`INSTANCE_LABEL`. **Checked:** neither `CM_GITHUB_REPO` nor `CM_MIN_TAG_AGE_HOURS` is in `allowed_envs` on the two manifests that run this build, so the compose-source repo cannot be redirected by an operator here. The structural point stands: **after any swap, the bytes governing compose-manager's own configuration are the launcher image's, and those bytes are only as trustworthy as the launcher build that shipped them** — see the launcher pages, one of which ([`sha256:d652f92b…`](../compose-manager-launcher/sha256-d652f92b64f57ef8aa086bd77a4cf932c1976965b3cea2814a7ee82fe73aa993.md)) has no build attestation at all and runs alongside this image on both hosts read here.

### MEDIUM (mechanism) — the attested `actions_hash` is not canonically encoded at this build

`attestation_report` hashes `let actions_json = serde_json::to_string(&actions).unwrap();` ([`main.rs:1387`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L1387)) — serde's struct **declaration order**, not sorted keys. An independent verifier re-deriving `actions_hash` from the returned `actions` array must reproduce Rust's field order exactly; the obvious `json.dumps(..., sort_keys=True)` gives a different hash. This is a *verifiability* defect, not a leak: the hash is still bound into the quote. Later commits fix it (`canonicalize_actions`, introduced after this build and present in `f91a204`), which is a concrete argument for preferring the newer manager build. The log itself is a rewritable file — `persist_actions_to_disk` writes a whole new `actions.json` via temp-file-plus-rename ([`:154-161`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L154-L161)) — **not append-only, not tamper-evident**; integrity holds only because the quote hashes it at read time and the CVM boundary denies the host operator write access.

### MEDIUM (mechanism) — tag-to-content TOCTOU; the running image is self-reported

`validate_tag` resolves the ref through the GitHub API and records `commit_sha` ([`:491-510`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L491-L510)), but `fetch_github_file` re-fetches by the **mutable ref**: `"https://raw.githubusercontent.com/{}/{}/{}/{}"` ([`:513-516`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L513-L516)). A tag moved between the two calls yields content that does not match the recorded commit. Impact is low because `file_sha256` is computed on the bytes actually fetched and *is* attested. The age gate is `MIN_TAG_AGE_HOURS` with a source default of 48 ([`:1900-1903`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L1900-L1903)); **at this deployment it is the measured literal `MIN_TAG_AGE_HOURS=2`** (`fb3d47e5…:160`, `002b406e…:160`) and `CM_MIN_TAG_AGE_HOURS` is **not** in these manifests' `allowed_envs`, so the operator cannot lower it further without changing the measurement. (Contrast the newer manifests, where it is 0 and operator-tunable — see the [`6e035c8f…`](sha256-6e035c8fb99c1d31f41760d25af178683a658cca4afd73cd0d366fbb5bf884be.md) page.)

Separately, `compose_manager_started` records the manager's own digest by asking Docker about itself — `current_image_digest` ([`:1751-1768`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L1751-L1768)), recorded at ([`:2003-2010`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L2003-L2010)). It is **self-reported by the possibly-swapped process**; a malicious image could write a known-good string. Whether the dstack TDX event log independently measures the container image is not verifiable from this repo.

### INFO — plaintext reach: the capability exists, no code path uses it (traced exhaustively)

Structurally this container can read any other container's memory and logs: `pid: host` plus `SYS_PTRACE` plus `SYS_ADMIN` plus a read-write docker socket (measured `fb3d47e5…:147-152`) is full control-plane privilege on the node, and the inference engine's plaintext lives in a sibling container's memory. That is why this image is in scope.

Traced, at this commit, with a grep of every subprocess invocation in the 2522-line file:

- **No `docker exec`, `attach`, `cp`, `top`, `stats`, `diff`, `export` or `commit` anywhere.** The only log path is `POST /compose/logs`, which runs `docker compose logs --tail N` ([`:1221`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L1221)) against the compose file in `WORK_DIR` — i.e. the model stack's own container stdout, not memory. Whether that stdout ever contains prompts is a property of the engine's launch flags, which live in the inner compose and are covered by `file_sha256`, not here.
- **`nsenter` into PID 1 is used exactly twice, both with compile-time-constant payloads:** `systemctl <action> dstack-guest-agent.service` ([`:1822-1823`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L1822-L1823)) with the unit as a `const` ([`:1437`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L1437)) and the action checked against a fixed list ([`:1439`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L1439)); and the algif-blacklist script, also a `const` ([`:1472-1482`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L1472-L1482)). Neither interpolates caller input.
- **No memory-reading path at all** — no `/proc/<pid>/mem`, no `ptrace`, no core-dump handling. `SYS_PTRACE` is present only because `ptrace_may_access` gates opening `/proc/1/ns/*` for the nsenter calls, which the manifest comments at `fb3d47e5…:130-138`.

So: **can it read plaintext? Structurally yes; in this code, no implemented path does.** The honest statement is "not implemented at this build", not "cannot happen" — the privilege remains, and a swapped image (see the HIGH above) would carry it.

### INFO — logging, persistence, egress

Logs are `tracing` at `info` by default, level settable only through the standard `RUST_LOG`-style `EnvFilter` ([`:1886-1892`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L1886-L1892)); **`RUST_LOG` is not in `allowed_envs` on any manifest read here**, and in any case no log statement in this file takes a request or response body — the logged fields are compose file names, tags, service names, exit codes and container names. Persistence is `actions.json` and the fetched compose file, both under `WORK_DIR=/app/work` (measured `fb3d47e5…:159`), plus short-lived `.env.tmp.*` files deleted on stream drop ([`:910-915`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L910-L915)). Egress is exactly four destinations: `api.github.com` ([`:468-471`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L468-L471)), `raw.githubusercontent.com` ([`:513-516`](https://github.com/nearai/compose-manager/blob/69c363ea0f0d313a5324b207b2905072656e8c40/src/main.rs#L513-L516)), the local docker and dstack sockets, and an optional Slack webhook. The Slack body is rendered by `format_message`, which emits only the action name, host label, file, tag, service list and actor — **no env values and no message content** — and `send` posts `{"text": …}` and nothing else. `SLACK_WEBHOOK_URL` **is** in `allowed_envs`, so an operator can redirect those notifications; they carry deployment metadata only.

Note for completeness: the node's telemetry sidecars ship this container's stdout off-node — `otelcol-management` tails `/var/lib/docker/containers/*/*-json.log` and exports to `https://telemetry.infra.near.ai` (measured `fb3d47e5…:255-256`, `:349-352`), with a filter that keeps only `compose-manager`, `compose-manager-launcher` and `dns-cloudflare` (`:330-334`); `datadog-agent` on this manifest has `DD_LOGS_CONFIG_CONTAINER_COLLECT_ALL=true` (`:12`). Those sidecars are separately in scope and are not audited on this page.

### Verdict: COMPROMISABLE by credentialed operator (bounded)

**(a) Can it read plaintext?** It holds the privilege to, and no code path at this commit does. Structural exposure, no implemented leak.

**(b) Can an operator change what runs after the enclave is measured?** **Yes.** Two independent, verified paths: the unattested per-request `env` overlay on the deployed stack (CRITICAL/mechanism), and the `LAUNCHER_CHANNEL`-driven, reboot-persistent swap of the manager image itself, where the measured digest is only a `${COMPOSE_MANAGER_IMAGE:-…}` fallback (HIGH). The second is bounded to images signed by a `nearai/compose-manager` CI workflow, because the cosign identity regexp is a measured literal and `LAUNCHER_SKIP_VERIFY` is not in `allowed_envs`.

**(c) Logging/persistence/egress:** nothing sensitive. Four destinations, all justified; no body, prompt or env value reaches any of them.

**(d) `allowed_envs`:** 21 names on `fb3d47e5…` / `002b406e…`. None flips a content-logging or debug switch in this source. The two that matter for supply chain are `BEARER_TOKEN` (full control-plane API access, hence the `env`-overlay finding) and `LAUNCHER_CHANNEL` (post-measurement image swap). `RUST_LOG`, `LAUNCHER_SKIP_VERIFY`, `CM_GITHUB_REPO` and `CM_MIN_TAG_AGE_HOURS` are all **absent** — checked name by name.

**What the signed action log actually commits to:** `{timestamp, action, tag, commit, file, file_sha256, services, container, image}` per action, SHA-256'd into `report_data[..32]`. It commits to *which compose file text* was deployed and *which git commit* it was said to come from. It does **not** commit to the env overlay applied to that text, nor — except as a self-report — to which manager image produced the log.

**Recommended fix:** hash the resolved env overlay (keys plus per-value SHA-256) into the `compose_up` action so it enters `actions_hash`; adopt the later `canonicalize_actions` so third parties can re-derive the hash; and pin `COMPOSE_MANAGER_IMAGE` by digest in the measured compose instead of treating the measured digest as a defaultable fallback.

**Unverified / untraced, stated explicitly:** whether the dstack TDX RTMR/event log independently measures the compose-manager container image (not determinable from this repo); the behavior of the inner stack this manager deploys (separate manifest pages); the contents of the telemetry sidecars' pipelines beyond the measured config quoted above; and the *fleet-wide* deployment count of 11 of 17 hosts, which comes from the orchestrating census — this review directly read two of those manifests (`fb3d47e5…`, `002b406e…`) and confirms only that this digest is the pinned default in both.
