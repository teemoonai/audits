### MEDIUM (deployed: ON) — new: disk/exec: the TLS loader copies the CVM's certificate **and private key** out of the certbot container with `docker cp -L`, at startup and every six hours — the first implemented read of another container's filesystem in this binary

This build adds the first code path in which compose-manager reads a file out of a container it did not spawn. `copy_from_container` ([`tls.rs:174-207`](https://github.com/nearai/compose-manager/blob/be649f8808429317c9a3006115c6d2d7cf001317/src/tls.rs#L174-L207)) finds the target by compose labels — `docker ps -aq --filter label=com.docker.compose.project={project} --filter label=com.docker.compose.service={service}` (`:179-187`), **first id wins** (`first_container_id` `:209-215`) — then runs

```
docker cp -L <id>:<dir>/fullchain.pem <tmp>/fullchain.pem
docker cp -L <id>:<dir>/privkey.pem   <tmp>/privkey.pem
```

(`:194-199`), reads both into memory (`:198`), builds a rustls `ServerConfig` (`:111-131`) and removes the scratch directory (`:205`). The scratch directory is `std::env::temp_dir()/compose-manager-tls-<pid>-<rand>` created 0700 (`:218-230`), inside this container's own filesystem. Runs once at startup (`start` `:256-264`) and then every `RELOAD_INTERVAL` = 6 h (`:47`, `:268-274`), or every 60 s until the first success (`:50`). Failure never aborts the server (`:14-15`, `:261-263`); it falls back to plain HTTP.

**Deployed state.** `TLS_MODE` is unset at this harness, so the source is `container` with the defaults `DEFAULT_CERT_SERVICE = "dstack/certbot"` and `DEFAULT_CERT_DIR = "/etc/letsencrypt/live/completions.near.ai"` (`:52-53`, `:76-95`). The dstack app-compose project is `dstack` (`main.rs:1702`, `LAUNCHER_COMPOSE_PROJECT=dstack` `:171`), and the measured `certbot` service holds the `certs` volume at `/etc/letsencrypt` (`:45`). So on this CVM the process holds, in memory, the private key of the certificate the CVM maintains for `completions.near.ai` — the key the measured file says other containers may reuse (`:206`). **ON.**

**Why MEDIUM and not HIGH.** (1) No plaintext: the copied bytes are a certificate chain and a key, not messages, and the key material goes nowhere — not logged (the only log lines are `"TLS certificate loaded"` `:259`, `:279` and errors formatted from `anyhow` contexts that name paths and container ids, `:189`, `:239-243`), not sent anywhere, not persisted beyond the removed scratch dir. (2) The capability is not new: a process with the read-write docker socket (`:122`) could always have mounted `certs:` into a spawned container, and with `pid: host` + `SYS_PTRACE` could read any process; the base page's INFO already says so. What is new is that an *implemented, always-on* path now exercises it. (3) The target is **not caller-selectable**: `TLS_CERT_SERVICE`/`TLS_CERT_DIR` come from the process environment (`:72`, `:79`, `:90`), which here is the measured compose (hash-bound), none of the five `TLS_*` names is in `allowed_envs`, and the launcher's bundled compose that would govern after a swap sets none either (checked at `8e07c358` and `be649f88`). Re-pointing `docker cp` at, say, the engine's container and a directory under it requires a new measurement, a new launcher bundle, or a swapped manager image with different defaults — the last being the existing swap residual, not a new one. So the engine-targeted variant is **not ARMED through any operator-settable env**; it is reachable only through changes this repo would see.

**What the key enables, stated for the plaintext question.** TLS 1.2/1.3 with the rustls safe defaults (`:126`) is forward-secret, so holding the key does not decrypt captured traffic; it permits *impersonating* `completions.near.ai` to a client that trusts the certificate alone. Clients that bind the TLS endpoint to an attestation quote (as the teemoon clients do, per their pages) are not fooled by a correct certificate on the wrong code. That residual belongs to the client pages and is noted, not rated, here.

**Compounding, stated plainly:** the copy produces **no action-log entry** (background task, no `record_action`), and because it is on by default with no flag in the measured compose, nothing in the attested document says this manager holds the key.

### IMPROVEMENTS over the base build

1. **The deploy API's bearer token no longer has to cross the wire in the clear.** At `f91a2045` port 8080 was plain HTTP; remote callers (the dashboard, automation) sent `Authorization: Bearer <BEARER_TOKEN>` unencrypted to a port published on the guest host. At `be649f88` the same port accepts TLS with the CVM's own certificate, plain-HTTP authenticated requests are flagged in the log (`tls.rs:330-332`), and the README directs remote clients to `https://`. Not enforced — plain HTTP still authenticates — so this is an available improvement, not a closed exposure.
2. **Constant-time token comparison and rotation without a hard cutover** (`token_eq`/`token_matches_any` [`:905-915`](https://github.com/nearai/compose-manager/blob/be649f8808429317c9a3006115c6d2d7cf001317/src/main.rs#L905-L915), `parse_bearer_tokens` `:889-900`). This changes nothing about *where* the token value comes from — still `BEARER_TOKEN` through `allowed_envs`, the decrypted env, or the override file — so the measured page's MEDIUM on the 2026-09-29 rotation-through-the-overlay carries unchanged; it only removes the reason to do a rotation in one step.
3. **Compose project pinned on every invocation**, including logs (`docker_compose_command` `:3533-3547`; comment `:1706-1710`): a `COMPOSE_PROJECT_NAME` leaked through an env file can no longer redirect `--remove-orphans` at the `dstack` project.

## Verdict: COMPROMISABLE by credentialed operator (bounded); no data-plane role; no plaintext exposure

**(a) Can it read plaintext?** Privilege yes; implemented path no. Three implemented reads of other containers now exist — `docker compose logs` (wider than before: any non-reserved project), `docker inspect` incl. `Config.Env` (unchanged), and **new** `docker cp -L` of the certbot container's certificate and private key (fixed target at the deployed env). None touches message content; none is recorded in the attested log.

**(b) Can an operator change what runs after measurement?** Yes, by the same three routes as the base — the unattested `env` overlay; the `LAUNCHER_CHANNEL`-driven, reboot-persistent manager swap (now with a dedicated promotion workflow); the unpinned `alpine` executions — with the age gate at 0.

**(c) Logging/persistence/egress:** nothing sensitive leaves. No new outbound destination. New inbound TLS.

**(d) `allowed_envs`:** 22 names, byte-identical to the base harnesses. None flips a content-logging or debug switch; none reaches the new TLS variables. `BEARER_TOKEN`, `LAUNCHER_CHANNEL`, `CM_MIN_TAG_AGE_HOURS` remain the three that matter.

**What the signed action log commits to at `be649f88`:** `{timestamp, action, tag, commit, file, file_sha256, services, container, image}` per action, canonically encoded (`canonicalize_actions` `:371`, contract `:361`) and SHA-256'd into `report_data[..32]` (`:2706`). It does **not** commit to the env overlay, **not** to the compose project, **not** to the manager image except as a self-report, **not** to `/host/gpu`, `/host/cache` or the TLS key copy. The one thing it says about this CVM today: this digest started at 23:48:24Z and deployed `prod/qwen38-27b-abliterated-cc-1gpu.yaml` @ `91214155…` twice.

**Recommended fix:** add `project` and a hash of the resolved env overlay to the `compose_up`/`compose_down` action; read the certificate through a read-only `certs:` mount instead of `docker cp` of the private key, or at least record a `tls_cert_loaded` action naming the source container; pin `alpine` by digest and record `/host/cache`; raise `CM_MIN_TAG_AGE_HOURS` above 0 and remove it from `allowed_envs`; make plain-HTTP `Authorization` a rejection rather than a warning once callers have moved.
