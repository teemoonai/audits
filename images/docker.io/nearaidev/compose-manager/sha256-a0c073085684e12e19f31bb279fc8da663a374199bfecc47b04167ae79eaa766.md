### IMPROVEMENTS over the base build

1. **The pinned-repo property is enforced, not assumed.** At `be649f88` a credentialed caller could fetch a compose file from any GitHub repository by traversal in `file` (or re-point the commit lookup by traversal in `tag`) while the attested entry recorded a legitimate `cvm-compose-files` `tag` and `commit`. At `c7fbaaf5` both URLs are segment-built from validated parts (`:822-829`, `:942-962`) and the fetch is by the resolved commit (`:1057-1066`). This closes a route by which the signed action log could have **misattributed** a deployment — material to the client audit, which reads `commit` + `file` + `file_sha256` from this log.
2. **The work directory is a boundary.** `safe_target_path` + `prepare_target_dir` + `write_target_file` (`:965-1034`) refuse absolute paths, `..`, symlinked parents and symlinked targets, and write atomically. At the base, `work_dir.join(&file)` with an absolute `file` wrote anywhere in the container.
3. **Caller-named services cannot become flags.** `--` before every service list (`:1534-1536`, `:2028-2030`, `:3756-3758`) plus the name grammar (`:909-920`); the project pin that was improvement 3 on the base page can no longer be undone by a `--project-name=` "service".
4. **Bad input fails before the lock and before any network call** (`:2131-2137`, `:2385-2391`, `:2507-2512`, `:2566-2568`), with 400s.

None of these touches `env`, the attested fields, the manager swap, the alpine pulls, the TLS key copy or the age gate.

## Verdict: **COMPROMISABLE** by credentialed operator (bounded); no data-plane role; no plaintext exposure; running undeclared on six CVMs

**(a) Can it read plaintext?** Privilege yes; implemented path no. The three implemented reads of other containers are the base's — `docker compose logs` (any non-reserved project), `docker inspect` incl. `Config.Env`, `docker cp -L` of the certbot certificate and key (fixed target at the deployed env). None touches message content; none is recorded in the attested log. The delta adds no read.

**(b) Can an operator change what runs after measurement?** Yes, by the same three routes — the unattested `env` overlay (literally after the sealed env on all six CVMs, `:131`); the `LAUNCHER_CHANNEL`-driven, reboot-persistent manager swap, which **this very build demonstrates** (six CVMs, 2026-11-04T04:13-04:16Z, declared by no measurement); the unpinned `alpine` executions — with the age gate at 0. The delta removes a fourth, quieter route: deploying a compose file from outside the pinned repository under a legitimate-looking attested entry.

**(c) Logging/persistence/egress:** nothing sensitive leaves. No new log line, no new destination, one new transient file holding compose text.

**(d) `allowed_envs`:** 22 names, unchanged. None flips a content-logging switch; none reaches `TLS_*`, `ENV_FILES`, `RUST_LOG`. `BEARER_TOKEN`, `LAUNCHER_CHANNEL`, `CM_MIN_TAG_AGE_HOURS` remain the three that matter.

**What the signed action log commits to at `c7fbaaf5`:** `{timestamp, action, tag, commit, file, file_sha256, services, container, image}` per action (`DeploymentAction` `:404-425`), canonically encoded (`canonicalize_actions` `:371-375`, sorted keys, compact, nulls and empty arrays omitted — contract `:361-370` unchanged) and SHA-256'd into `report_data[..32]` (`:2915-2921`). **Nothing new is recorded and nothing stops being recorded**; the post-swap entries on three CVMs confirm the shape empirically. It does **not** commit to the env overlay, **not** to the compose project, **not** to the manager image except as a self-report, **not** to `/host/gpu`, `/host/cache` or the TLS key copy. What it now says more truthfully: `commit` is the tree the `file_sha256` bytes were fetched from.

**For the client audit:** no change to the hashing contract, the field set or the `compose_manager_started` self-report; the apps' `report_data = SHA256(canonical actions) || nonce` check and per-service running table read the same shape from this build. The one behavioural change a client could observe is that `commit` and `file_sha256` are now consistent by construction.

**Recommended fix:** add `project` and a hash of the resolved env overlay to the `compose_up`/`compose_down` action; record the manager image in the measured document (pin `COMPOSE_MANAGER_IMAGE` rather than default it) or at least name the running digest in `/version` from the launcher's verified pull rather than self-inspection; read the certificate through a read-only `certs:` mount instead of `docker cp` of the private key; pin `alpine` by digest and record `/host/cache`; raise `CM_MIN_TAG_AGE_HOURS` above 0, remove it from `allowed_envs`, and gate on the tag's push time rather than the committer date.
