### INFO (deployed: ARMED, fires on an exception a request handler does not catch) — uvicorn prints "Exception in ASGI application" with a full traceback to stdout, which the collector ships; at these bytes every reachable raiser's message is fixed text (log, telemetry)

The router installs an `Exception` handler (`:562-565`) that logs the class and returns a generic 500; Starlette's server-error middleware calls it and then re-raises, so uvicorn also logs the exception at ERROR with a traceback (observed). A traceback prints code lines and the exception's message, not local variables. Raisers reachable from a request at these bytes, found by reading `handle` (`:341-487`) for statements outside a `try`:

1. `jdumps(pre)` (`:375`) with `orjson`: a body that `orjson.loads` accepts but `orjson.dumps` refuses — executed with messages nested 1,020 deep: `TypeError: Recursion limit reached`. Without `orjson`, the stdlib path raises `RecursionError` with a fixed message, or `json.loads` refuses first (`:345`, caught, 400). `jdumps(body)` (`:420`) is the same body plus engine parameters.
2. `affinity` (`:279-283`): `json.dumps(..., sort_keys=True)` of the first two messages — keys are strings and values are JSON types, so only the recursion limit applies.
3. The decode stream (`:469-480`): a broken upstream is re-raised as `StreamAborted` `from None` (`:478`), which suppresses the aiohttp exception and its text; observed as a bare `StreamAborted`.

None carries request content. This is ARMED rather than OFF because nothing gates the traceback: a future edit that raises an exception whose message embeds a value would put that value on stdout and in telemetry. **Fix (cheap):** run uvicorn with a log config that drops `uvicorn.error` tracebacks, or catch at the route level and do not re-raise.

### INFO (deployed: ON) — every outbound connection goes to the four engine addresses on the command line, on an internal network with no route out; redirects are followed, but only an engine can issue one (egress)

The router opens connections in three places: the prefill POST (`:326`), the decode POST (`:332`) and the health/metrics/passthrough GET (`:490-497`); each URL is `http://` + an address from `--prefill` / `--decode` (`:599-600`) + a fixed path (the request path, which the routes fix to `/v1/chat/completions` or `/v1/completions`, `:567-573`; `/health`, `/metrics`, `/v1/models`, `/version`). There is no other client, no DNS lookup of a request-derived name, no proxy (the `ClientSession`, `:263-265`, is built without `trust_env`, so proxy variables are not read). No retry: each leg is one POST; a failure becomes a 502/504 to the caller (`:384-394`, `:440-458`). Copies of the body exist in memory only — the parsed dict, the prefill dict, and the two serialised bodies — for the life of the request; no zeroisation.

aiohttp follows redirects by default and the session does not turn it off: in the execution, a prefill engine's 307 to `127.0.0.1:1` made the router connect there (then 502). For a 307/308 aiohttp re-sends the method and body. Only the engine can send a redirect, the vLLM routes the router calls do not redirect a POST to the exact path, and the router's only network is `internal: true` (`b293e27a1100:1324-1326`, `c9c477286e51:1226-1228`) with the egress probe asserting no default route — a deployment control outside this image, so a residual. **Fix:** `allow_redirects=False` on the two POSTs.

### INFO (deployed: ON) — the KV handoff: the router passes only engine-produced kv_transfer_params to the decode leg and drops any a client sends, so a client cannot steer a decode engine's pull; the KV bytes move engine to engine, outside this image (no sink in this image)

What the router does: leg 1 posts the request with `max_tokens=1`, `stream=false` and `kv_transfer_params={"do_remote_decode": true}` and without sampling extras and structured-output fields (`:368-372`, lists `:65-68`); it reads `kv_transfer_params` from the prefill engine's JSON (`:403-410`), discards the rest of that response including the one generated token (`:411`), and posts the client's body plus those parameters to a decode engine (`:419-420`). Before either leg it deletes `kv_transfer_params` from the body and from `vllm_xargs` (`:363-366`). That matters: in upstream v0.34.0 a chat or completion request's `kv_transfer_params` and `vllm_xargs` both end up in `sampling_params.extra_args` (`entrypoints/openai/chat_completion/protocol.py:785-788`; `completion/protocol.py:400-403`), which the engine reads as the request's transfer parameters (`v1/request.py:123-126`), and those name the host, engine id, request id and block ids a decode engine pulls from (`nixl/pull_scheduler.py:281-296`). A client able to set them could direct a decode engine at another request's KV blocks on the prefill engine — another user's prompt state. Through this router it cannot, on either path (executed: the canary sent in both places did not reach the decode body; the recipe's own test `test_client_transfer_params_never_reach_decode_on_any_path` passes). The router re-serialises the body, so a duplicated key cannot survive. Any other caller on `engine_glm53_a` that posts to an engine port directly is not subject to this — an engine-page question.

`ec_transfer_params` (encoder-cache transfer) is **not** stripped and passes to both legs; no engine in either recipe has an EC connector configured, and upstream then logs a static warning and ignores it (`v1/engine/core.py:595-602`).

**The transport, from the recipe text and upstream defaults, not from the engine images:** NIXL over UCX with `UCX_TLS=cuda_ipc,cuda_copy,tcp`, `UCX_ZCOPY_THRESH=inf` on `b293e27a1100` (the recipe comments: KV data over `cuda_ipc`, GPU to GPU on the same host; `tcp` only for UCX wire-up; notifications by copy); the handshake side channel is a ZeroMQ socket on `VLLM_NIXL_SIDE_CHANNEL_HOST`, default `localhost` (`envs.py:1821-1822`), not set in either file, with per-pair ports 5600-5900, inside the pair's shared network namespace; the address handed to the decode side is that same host (`pull_scheduler.py:287`). So by configuration the KV state stays within one CVM and one pair namespace; ZeroMQ and UCX here are neither authenticated nor encrypted, which matters only to whoever shares that namespace or network. Whether `cuda_copy` stages KV through host memory, which interfaces the UCX TCP wire-up listens on, and whether any transfer path logs or persists, are engine-image questions: see *Not traced*.

### Verdict

**PRIVATE at the deployed flags.** This image is a router, not an engine: one Python file on the stock vLLM image. It necessarily holds every request and every answer of its pair in plaintext, in memory, for the life of the request, and it is the only component between the E2EE proxy and the engines; by reading every line and running it against hostile inputs, I find that it writes none of that content to a log, a file or a metric, sends it nowhere but the four engines named on its command line, retries nothing, and keeps nothing. Its log is ten fixed-format lines of indexes, status codes, class names and counters, plus a framework traceback whose reachable messages are fixed text. It also does one thing that protects other users: it drops client-supplied `kv_transfer_params`, which would otherwise let a caller aim a decode engine at another request's KV blocks.

What qualifies it is where its stdout goes and what was not read. Stdout is shipped unredacted to `telemetry.infra.near.ai`, so the absence of content in these log lines is load-bearing, and the one unconditional output that is not a fixed-format line (the uvicorn traceback) is a place a future change could leak. The libraries it runs on were exercised, at other versions, and not read; `.pth` start-up hooks in the base were not checked. The redirect-following client and the unauthenticated port are harmless because the router's only network is internal and its only peers are the proxy, the pair's engines and the collector — a deployment property, not an image property.

**Residuals.** The internal network and the egress probe are outside this image; the engines' KV transport and their own sinks are on their pages; telemetry retention is outside source.
