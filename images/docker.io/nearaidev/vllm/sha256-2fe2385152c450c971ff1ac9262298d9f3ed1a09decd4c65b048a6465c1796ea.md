## Findings

### MEDIUM (deployed: OFF, unreachable through the proxy and armed by VLLM_PROXY_INLINE_MEDIA=0 on the proxy or by a caller that reaches the engine port without the proxy) — media-fetch retry warning writes a request's media URL and the fetch error to the stdout log, which the collector ships out of the enclave

Upstream code, kept by patches 14 and 15 (they rewrite the same file around it). Patched `connections.py:350-379`: `_log_retry` takes the URL from `args[1]` (`:361`) and calls `logger.warning("HTTP fetch failed for %s (attempt %d/%d, %s): %s -- retrying in %.3fs%s", url, ..., exc, ...)` (`:370-379`) — the only log call in the file. It is reached from the `@_async_retry` wrapper on `async_get_bytes` (`:819`; wrapper `:453-457`) whenever an attempt fails with a retryable error and attempts remain; `VLLM_MEDIA_FETCH_MAX_RETRIES` is unset, default 3 (patched `envs.py:76`; `:442`), so up to two lines per fetch. The URL is the one in the request the engine receives: `content_parser.py:386` `fetch_image_async(image_url)` → patched `connector.py:565` → `:468-469` `await connection.async_get_bytes(url_spec.url, ...)`. If the engine is handed an http(s) URL, the line fires on the retryable classes (`_is_retryable`, patched `:304-347`): a timeout (`VLLM_IMAGE_FETCH_TIMEOUT` is 5 s), a refused or reset connection, a 5xx — dead links and slow image hosts are ordinary. Patch 14 narrows that in one respect: an unresolvable name and a non-public address now raise `ValueError` (patched `:155-161`, `:204-212`, `:635-652`), which is not retryable, so those are refused without a log line.

**Does an http(s) URL reach these engines? Not through the deployed proxy.** The proxy in front is `e3a4fbca` (source `3b47be98`) with inlining on by the recipe's default. At that commit `inline_remote_media` (`src/media_inline.rs:146`; chat route `src/routes/chat.rs:220`, and per the proxy's page every JSON route that forwards a body) finds media **by key, not by a part's `type`** — `media_refs` (`src/media_refs.rs:152`) walks `messages` and the other input fields for `image_url`, `input_image`, `image`, `image_pil`, `audio_url`, `video_url`, `video` (`:42-50`), precisely so that vLLM's untyped and `uuid`-carrying parts are seen — downloads each http(s) item itself and rewrites it to a `data:` URL, refuses a request whose download fails (400) or that names a remote video (`unsupported_kind`, `:211`), and after rewriting re-walks the body and refuses it if anything other than a `data:` URL is left (`:298-303`, `reject("not_inlined")`). So with inlining on, what the engine receives is a `data:` URL or nothing, the engine never performs the fetch, and the warning cannot fire. I read this in the proxy source; I did not run it.

**An earlier window behind the older proxy.** That is today's state. Per the two signed action logs (entries read), these engines first ran behind the older proxy build `c57cd9ea` (`3f7e9798`), which matches media parts by `type` and forwards an untyped one unchanged (see the [base page](/images/docker.io/vllm/vllm-openai/sha256-d825baf9ce4b1b6bfc5ecc7b79880c7e6748c65a72d697ce3d47607aafa84c6e.md)): on the `bd0a5446` CVM from the `compose_up` of 2026-11-17T08:09Z until the `e3a4fbca` proxies were created at 2026-11-18T10:56Z, and on the `08f91377` CVM from 2026-11-17T18:12Z until 2026-11-18T12:35Z. During that window the base page's untyped-part path applied to this patched engine too: the untyped branch of the parser (patched `chat_message.py:263-271`) and the message types are untouched by the patch stack, so `{"image_url": "<http(s) URL>"}` under a `user` role reached the engine and was fetched. What it could log differs from the base page, because this engine has a route out and carries patch 14: a fetch that succeeded logged nothing; an unresolvable host or a non-public address was refused with a non-retryable `ValueError` and logged nothing; the retry warning printed the URL only when a public host timed out, refused or reset the connection, or answered 5xx. That was an ARMED state reached by a non-standard request shape, not by a standard one; it ended when the `e3a4fbca` proxies came up, and the state today is OFF.

**What re-arms it.** (1) `VLLM_PROXY_INLINE_MEDIA=0` in a proxy's environment makes the inliner a no-op (`src/media_inline.rs:150`); the recipe writes the variable as a `${...:-1}` default, and whether an operator can change it without changing a measurement is a manifest-page question (the name does not appear in the measured documents I was given). (2) A caller that reaches `:9100-9107` without the proxy: the ports are unauthenticated and bound on every interface of the CVM's host network, so any process in that namespace or any container on `dstack_default` can post a chat request with a URL. No container in this recipe is known to do so (the collector scrapes `/metrics`); it is an in-CVM caller, not an outside one. In either case what is printed is message content — a URL with whatever path, signed query string or token it carries — at WARNING, to `telemetry.infra.near.ai`. ### Verdict

**QUALIFIED PASS.** The class call, stated so a reader can disagree: following the lineage pages' treatment of the crash dump, a sink that only a malformed or non-standard client request, or a crash, can trigger is ARMED and does not set LEAKS; LEAKS is kept for content that reaches a sink in the course of requests a standard client makes or output the model itself produces. A reader who counts any client-reachable trigger would call this page LEAKS, conditionally. The seventeen patches are what their README says: LoRA and Engram arithmetic, copy-path changes for confidential computing, request bounds, and a media-fetch hardening that removes loopback, private and link-local destinations, proxies and cookies from the engine's request-driven fetch.
