## Why this page exists rather than a review

The method (§5) resolves an image to source by querying GitHub's build-attestation API for its digest and reading `predicate.buildDefinition.resolvedDependencies[0].digest.gitCommit` out of the signed DSSE payload. For this digest that query returns nothing. Without it there is no commit to audit, and auditing "whatever is on the branch today" would be reviewing bytes that are not these bytes. The method's rule is to fail closed, so this page records what was proven and stops.

## Absence of provenance: the evidence

Everything below was executed in a single unauthenticated run on 2026-08-03 and is reproducible verbatim.

**1. The attestation query returns 404, and the quota was healthy.**

```
GET https://api.github.com/rate_limit
  -> core: remaining 55 of 60

GET https://api.github.com/repos/nearai/compose-manager/attestations/sha256:d652f92b64f57ef8aa086bd77a4cf932c1976965b3cea2814a7ee82fe73aa993
  -> HTTP 404   body: {"message": "Not Found", "status": "404"}
                (no "attestations" key present)
```

A 404 from this endpoint under an exhausted quota would be meaningless. It was not exhausted: 55 of 60 requests remained before the call, 53 after the call and the positive control below. **This is a real absence, not throttling.**

**2. A positive control in the same run, same repo, same code path, returns 200.**

```
GET https://api.github.com/repos/nearai/compose-manager/attestations/sha256:78afb82330137c2fd90a9c8c6e452f8f178c15d863f87c079a11c13e92216e00
  -> HTTP 200   attestations: 1
```

`78afb823…` is the *other* audited build of this same image ([its page](sha256-78afb82330137c2fd90a9c8c6e452f8f178c15d863f87c079a11c13e92216e00.md)), queried against the same repository through the same unauthenticated path seconds later. It resolves. **So the repository name is right, the endpoint is right, the unauthenticated path works, and the alias `compose-manager-launcher -> compose-manager` documented in the method is right.** The 404 is specific to this digest, not a wrong-repo guess.

**3. The image exists — the 404 is about provenance, not about the artifact.**

```
GET https://registry-1.docker.io/v2/nearaidev/compose-manager-launcher/manifests/sha256:d652f92b64f57ef8aa086bd77a4cf932c1976965b3cea2814a7ee82fe73aa993
  -> HTTP 200
```

The manifest resolves on Docker Hub. So this is not a stale or deleted reference; it is a real, pullable, currently-deployed image with no published build provenance.

**4. Registry-side confirmation: the object carries no attached provenance either.**

The manifest for this digest is a bare `application/vnd.oci.image.manifest.v1+json` — a single-platform image, with **no sibling `attestation-manifest`**. The signed build [`sha256:91fdff3c…`](sha256-91fdff3cfa3543d72656b2368c7d8a0a83d95a0f1087378c897aa1537acdba56.md) of the same image, by contrast, is an `application/vnd.oci.image.index.v1+json` carrying a child annotated `vnd.docker.reference.type: attestation-manifest` next to its `linux/amd64` image. Two independent systems — GitHub's attestation API and the registry's own referrer graph — agree that nothing was published for these bytes.

**5. No OCI labels either, so the weaker fallback is unavailable too.**

The image's config blob (`sha256:1d31ccb8…`) has `config.Labels` = `null`. There is no `org.opencontainers.image.revision` and no `org.opencontainers.image.source`. Some third-party images in this repo are resolved to source through those labels — a weaker binding, since a label is a self-asserted string the image author typed and anyone who can push the image can forge, whereas a build attestation is a Sigstore-signed, transparency-logged statement from GitHub's OIDC-authenticated builder. **Here neither is available.** Not the strong binding, not the weak one.

**Conclusion of the identity investigation: the source commit for these bytes cannot be established. No source review is possible, and none was attempted.**

## What *can* be stated, and what it does not amount to

Two further checks were run. Both are recorded because an honest INCONCLUSIVE should say what was looked at, and **neither changes the verdict.**

**Timing.** The image's config records `created: 2026-06-04T12:40:35Z`. Commit `69c363ea0f0d313a5324b207b2905072656e8c40` — the commit that the *manager* image [`sha256:5165400d…`](../compose-manager/sha256-5165400d9eb43ab5da36986a85de0ba55f3fb4d05211c4397ecc4bde3ef0113b.md) is signed-attested to, and which is the manager pinned alongside this launcher on both manifests read here — is dated `2026-06-04T12:40:03Z`. Thirty-two seconds apart. That is consistent with both images having been produced by one CI run, which is how the repo's `build.yml` works for the signed pairs. **It is consistent with; it proves nothing.** No signature ties this digest to that run.

**Payload bytes.** Pulling this digest's layers and extracting the two files the launcher actually consists of gives:

```
262f07bbb9735721d43744160caf846db488a75f42267983529dc8eec3a31785  /app/launcher.sh
7b06fd981e3f4d1a913f33d87d78f67711a77a9612b8e5c2008e9d230e924cb9  /app/docker-compose.yml
```

Those are exactly the SHA-256s of `launcher/launcher.sh` and `launcher/docker-compose.yml` in the public repository — identical at `69c363ea`, `9a035b2f`, `3d64349a`, `8e07c358` and `f91a2045`, and identical to the files extracted from the signed build `91fdff3c…`.

**This is unsigned circumstantial evidence and it does not substitute for provenance.** Three reasons it cannot carry a verdict:

- It is a check *this reviewer* performed on bytes pulled today. Nothing binds it into the attestation chain a client verifier can follow, and the repo's model is that a page claims only what the attested identity supports.
- **The rest of the image was not verified.** The base Alpine layer, the `apk` package set, and — critically — the statically downloaded `cosign` binary are unchecked. The Dockerfile fetches cosign from a release URL with **no hash check** (`curl -fsSL …/cosign-linux-amd64 -o /usr/local/bin/cosign && chmod +x`), so "the shell script matches" says nothing about the binary that script delegates its only security decision to.
- That delegation is the whole risk. Per the signed sibling's review, `launcher.sh`'s sole gate on what gets installed into the enclave is `cosign verify --certificate-identity-regexp … --certificate-oidc-issuer …`. **A launcher image whose cosign binary is not what it claims to be would satisfy every byte-level check above and still accept an arbitrary image** — silently, on 10 of 17 hosts, with the swap persisting across reboot via `.env.launcher`. Verifying the caller and not the verifier is not verification.

## Deployed context (from the measured manifests, which are attested)

Stated for completeness. These facts come from the hardware-measured `app_compose`, not from any review of this image's code.

- Pinned by digest in the harness: `image: nearaidev/compose-manager-launcher@sha256:d652f92b…` (measured `compose_hash` `fb3d47e5…` `docker_compose_file:178`, `002b406e…:178`). The measurement fixes *which digest* is started — it cannot say what that digest does.
- Privilege: `network_mode: host` (`fb3d47e5…:186`) and a read-write docker socket, `- /var/run/docker.sock:/var/run/docker.sock` (`:188`). Plus the decrypted CVM env mounted read-only, `- /dstack/.host-shared/.decrypted-env:/dstack-env:ro` (`:192`), and the shared `work` volume (`:193`). **That is container-control privilege on the model node** — the reason this image is in scope at all.
- Its inputs: `LAUNCHER_CHANNEL=${LAUNCHER_CHANNEL:-latest}` (`:196`), `LAUNCHER_COSIGN_IDENTITY_REGEXP=https://github.com/nearai/compose-manager/.github/workflows/.*` (`:205`), `COMPOSE_MANAGER_IMAGE_REPO=nearaidev/compose-manager` (`:195`), `LAUNCHER_STATE_FILE=/app/work/launcher-state.json` (`:208`).
- `LAUNCHER_CHANNEL` **is** in these manifests' `allowed_envs`; `LAUNCHER_SKIP_VERIFY` and `LAUNCHER_COSIGN_IDENTITY_REGEXP` are **not** (checked name by name on both).
- The manager image it is positioned to replace is not hard-pinned either: `image: ${COMPOSE_MANAGER_IMAGE:-nearaidev/compose-manager@sha256:5165400d…}` (`fb3d47e5…:125`), with the manifest's own `pre_launch_script` restoring `COMPOSE_MANAGER_IMAGE` on every boot from `/var/lib/docker/volumes/dstack_work/_data/.env.launcher` — a file no measurement covers.

**Read together, that is why the absence matters here more than it would elsewhere.** The measured configuration hands this unattested image the docker socket and positions it as the thing that decides which control-plane binary runs, with a persistence path that survives reboot and leaves no entry in any attested log. Whether it in fact enforces the cosign gate the manifest configures is **not determinable** from published evidence.

## Verdict: INCONCLUSIVE

- **Can it read plaintext?** **Not determinable.** No source. It holds the capability by configuration; nothing more can be said.
- **Can an operator use it to change what runs after measurement?** **Not determinable for these bytes.** The measured configuration provides every input such a path would need, and the signed sibling built from the same repository does exactly that — but no signed evidence connects this digest to that behavior, in either direction.
- **Does it log, persist, or egress anything sensitive?** **Not determinable.**

**No privacy claim is made on this page, and the teemoon app shows no audit link for this digest.**

This is the fail-closed outcome the repo's audit policy describes, and it is a legitimate result rather than a gap in the review: the honest answer to "what does this run" is "the published record does not say."

**What would resolve it, in order of strength:** (1) publish a GitHub build attestation for `sha256:d652f92b…` — the same `build.yml` workflow already produces them for the sibling digests, so this is a rebuild-and-attest, not new machinery; (2) failing that, add `org.opencontainers.image.revision` and `.source` labels, accepting that they are self-asserted; (3) failing both, redeploy the 10 affected hosts onto the attested launcher build [`sha256:91fdff3c…`](sha256-91fdff3cfa3543d72656b2368c7d8a0a83d95a0f1087378c897aa1537acdba56.md) or [`sha256:78afb823…`](sha256-78afb82330137c2fd90a9c8c6e452f8f178c15d863f87c079a11c13e92216e00.md), whose payloads are byte-identical to this one and whose provenance is signed.

**Unverified / untraced, stated explicitly:** everything about this image's behavior. Also unverified: whether an attestation exists under a different repository or organization endpoint not covered by the documented alias (the org-wide endpoint requires authentication and was deliberately not used, since the app's runtime path is the unauthenticated repo-level one); whether dstack's RTMR/event log independently measures container images; and the fleet-wide count of 10 of 17 hosts, which comes from the orchestrating census — this review directly read two of those manifests (`fb3d47e5…`, `002b406e…`) and confirms only that this digest is pinned in both.
