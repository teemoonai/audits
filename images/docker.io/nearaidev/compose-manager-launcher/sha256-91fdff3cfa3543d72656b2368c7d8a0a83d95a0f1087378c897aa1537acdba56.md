## Results

### HIGH (mechanism and effective) — this is the post-attestation mutation engine, and its channel input is operator-settable without changing the measurement

The launcher polls Docker Hub every 300 seconds for a **mutable tag** and replaces the compose-manager container with whatever that tag currently resolves to:

```
CHANNEL="${LAUNCHER_CHANNEL:-latest}"
```

([`launcher.sh:7`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L7)); the digest comes from a `HEAD` on the registry manifest for that tag (`fetch_remote_digest` [`:103-127`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L103-L127)), is format-checked ([`valid_digest` :131-133](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L131-L133)), pulled ([`:314`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L314)), verified, then applied with `compose_up -d --no-deps compose-manager` ([`:327`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L327)). Poll interval `LAUNCHER_POLL_INTERVAL` defaults to 300 ([`:8`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L8)).

**`LAUNCHER_CHANNEL` is in `allowed_envs`** on both measured manifests that run this build, and the compose passes it straight through — `LAUNCHER_CHANNEL=${LAUNCHER_CHANNEL:-latest}` (`d98a2568…` `docker_compose_file:170`, `9385918d…:170`). So an operator selects which tag this watchdog follows **without changing `compose_hash` and without changing any RTMR**.

The swap also **persists across reboot**, outside the measurement. On success the launcher writes the new reference to its env file — `write_env_var "COMPOSE_MANAGER_IMAGE" "$image_ref"` ([`:324`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L324)), path `LAUNCHER_ENV_FILE=/app/work/.env.launcher` (`d98a2568…:172`) on the shared `dstack_work` volume — and the measured manifest's own `pre_launch_script` reads that file back on every boot:

```
OVERRIDES="/var/lib/docker/volumes/dstack_work/_data/.env.launcher"
if [ -f "$OVERRIDES" ]; then
  while IFS='=' read -r k v; do
    case "$k" in COMPOSE_MANAGER_IMAGE) export "$k=$v" ;; esac
  done < "$OVERRIDES"
```

while the compose reads `image: ${COMPOSE_MANAGER_IMAGE:-nearaidev/compose-manager@sha256:6e035c8f…}` (`d98a2568…:95`). **The digest in the measured manifest is a fallback, not a pin.** A remote verifier reading `compose_hash` learns the default, not what is running.

**What bounds it — and this is stronger than the base page could establish.** Every swap is gated by cosign:

```
if cosign verify \
    --certificate-identity-regexp="$COSIGN_IDENTITY" \
    --certificate-oidc-issuer="$COSIGN_ISSUER" \
    "$image_ref" > /dev/null 2>&1; then
```

([`:151-154`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L151-L154)), and a failure aborts the update: `log_error "Attestation failed — skipping update"; return 1` ([`:319-322`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L319-L322)). The identity regexp is a **measured literal** — `LAUNCHER_COSIGN_IDENTITY_REGEXP=https://github.com/nearai/compose-manager/.github/workflows/.*` (`d98a2568…:179`, `9385918d…:179`) — and the issuer defaults to GitHub's OIDC issuer ([`:28`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L28)). The kill-switch `LAUNCHER_SKIP_VERIFY` ([`:140-143`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L140-L143)) is **absent from `allowed_envs`** on both manifests, as is `LAUNCHER_COSIGN_IDENTITY_REGEXP` — checked name by name. The base page recorded this as INCONCLUSIVE; at the deployed config it resolves: **the gate cannot be disabled or widened by an operator without breaking the measurement.**

**Residual, exactly:** the operator can install and make persistent **any image signed by any workflow under `nearai/compose-manager`**, invisibly to `compose_hash`. That is a real reduction of the enclave's meaning — the measurement no longer determines the control-plane binary — bounded by control of that CI identity. Note also that the gate checks only the *signer identity pattern*, not that the image is the one the manifest intended: an old, superseded, or experimental branch build signed by the same workflow passes.

### HIGH (mechanism) — after any swap, the replaced container's mounts, privileges and environment come from a compose file inside this image, not from the measured manifest

`bootstrap` unconditionally overwrites the working compose file with the one baked into the image — `cp /app/docker-compose.yml "$COMPOSE_FILE"` ([`:229`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L229)) — and every apply runs `docker compose -p "$COMPOSE_PROJECT" -f "$COMPOSE_FILE" … up` ([`:185`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L185)) with `LAUNCHER_COMPOSE_PROJECT=dstack` (`d98a2568…:171`) — the same project the measured harness created. So from the first swap onward, compose-manager's service definition is governed by these 36 lines shipped in the launcher image.

**Verified: the privilege set is identical, so this is not an escalation.** [`launcher/docker-compose.yml:14-22`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/docker-compose.yml#L14-L22) declares `pid: host`, `cap_add: [SYS_ADMIN, SYS_PTRACE]`, `/var/run/docker.sock`, `/var/run/dstack.sock`, `/dstack/.host-shared/.decrypted-env:/app/.env:ro` and the `work` volume — the same set as the measured manifest at `d98a2568…:117-125`.

**The environment differs, and that is the substantive part.** The bundled file uses `GITHUB_REPO=${CM_GITHUB_REPO:-https://github.com/nearai/cvm-compose-files}` ([`:24`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/docker-compose.yml#L24)) where the measured manifest has a literal (`d98a2568…:127`), and `MIN_TAG_AGE_HOURS=${CM_MIN_TAG_AGE_HOURS:-2}` ([`:27`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/docker-compose.yml#L27)) against the manifest's `${CM_MIN_TAG_AGE_HOURS:-0}` (`d98a2568…:130`). **Checked:** `CM_GITHUB_REPO` is **not** in `allowed_envs` on either manifest, so the repository compose files are fetched from cannot be redirected by an operator; `CM_MIN_TAG_AGE_HOURS` **is**, and the launcher explicitly forwards it (`d98a2568…:169`) so the bundled file's stricter default of 2 is overridden to 0 by the measured configuration.

The general point stands and is the reason this page exists: **the bytes that define how the enclave's control plane is configured live inside a launcher image.** For this digest that image is signed and its payload was verified against published source. For the sibling digest [`sha256:d652f92b…`](sha256-d652f92b64f57ef8aa086bd77a4cf932c1976965b3cea2814a7ee82fe73aa993.md), which runs on 10 of 17 hosts, no build attestation exists at all.

### MEDIUM (mechanism) — the swap leaves no entry in any attested log

Nothing the launcher does is recorded in compose-manager's `actions.json`, which is the only structure hashed into the TDX quote. The launcher writes its own `launcher-state.json` (`LAUNCHER_STATE_FILE=/app/work/launcher-state.json`, `d98a2568…:182`; `write_state` [`:53-56`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L53-L56)) and logs to stdout, neither of which any remote verifier reads. The *indirect* trace is that a swapped manager restarts and appends its own `compose_manager_started` action carrying `docker inspect`'s view of its image — which is self-reported by the new process, as the manager pages record. A client verifier catches a swap only if it independently pins the expected manager digest.

Related, and worth stating plainly: the health-gated rollback path is honest engineering, not a security control. A failed swap rolls back to the previous reference and enters a 30-minute backoff (`rollback` [`:205-222`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L205-L222)), gated on `curl` of `LAUNCHER_HEALTH_URL` ([`:164-177`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L164-L177), configured to `http://127.0.0.1:8080/version`, `d98a2568…:174`). It protects availability; a malicious-but-healthy image passes it.

### INFO — no plaintext reach: the docker socket is used for six verbs, none of which reads another container

Structurally the launcher holds a read-write docker socket and host networking — `- /var/run/docker.sock:/var/run/docker.sock` (`d98a2568…` `docker_compose_file:158`) and `network_mode: host` (`d98a2568…:156`) — which is full control-plane privilege on the node. It does **not** hold `pid: host` or `SYS_PTRACE`, unlike compose-manager.

Every docker invocation in the 368-line program was enumerated:

- `docker login -u … --password-stdin` ([`:196`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L196))
- `docker inspect compose-manager --format '{{.Config.Image}}'` ([`:247`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L247)) — its own container only
- `docker image inspect … {{range .RepoDigests}}` ([`:250-252`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L250-L252))

- `docker compose … up` ([`:185`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L185))

**No `docker exec`, `logs`, `attach`, `cp`, `top`, `stats`, `export` or `commit` anywhere.** No `/proc` access, no ptrace, no file read outside its own three config files. It never reads the inference stack's stdout, memory or environment. The one secret it touches is the decrypted CVM env, mounted read-only and passed straight to `docker compose --env-file` without being read into its own environment — `[ -f "$BASE_ENV_FILE" ] && env_file_args+=(--env-file "$BASE_ENV_FILE")` ([`:182-185`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L182-L185)), which the manifest comments deliberately (`d98a2568…:159-161`).

So on question (a): **no reach, mechanism or effective.** The privilege to obtain reach exists, as it does for anything with the socket; this program does not exercise it.

### INFO — logging, persistence, egress

Logging is `echo` to stdout with a UTC timestamp ([`:34-35`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L34-L35)); the logged values are image references, digests, epochs and health-check outcomes. **Nothing sensitive is logged — with one caveat worth naming:** `set -euo pipefail` at [`:2`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L2) does not enable tracing, and no `set -x` appears anywhere, so the `docker login` password on [`:196`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L196) (piped via stdin, never an argv) does not surface. Persistence: `launcher-state.json` and `.env.launcher`, both on the shared `dstack_work` volume, both containing only digests and timestamps. Egress: `auth.docker.io` and `registry-1.docker.io` ([`:98`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L98), [`:110-123`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L110-L123)), Sigstore's Fulcio/Rekor via `cosign verify`, `127.0.0.1:8080` for the health check, and the docker socket. `DOCKER_REGISTRY_USER` / `DOCKER_REGISTRY_TOKEN` are in `allowed_envs` and are read at [`:97`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L97) / [`:191`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/launcher.sh#L191) — an operator can substitute registry credentials, but the digest resolution and cosign gate still apply afterward.

The launcher's stdout is shipped off-node: `otelcol-management` tails `/var/lib/docker/containers/*/*-json.log` and its filter explicitly keeps `compose-manager-launcher` (`d98a2568…` `otelcol_management_config`), exporting to `https://telemetry.infra.near.ai`. That sidecar is separately in scope and not audited here.

### Verdict: COMPROMISABLE by credentialed operator (bounded); no plaintext exposure

**(a) Can it read plaintext?** No implemented path, and unlike compose-manager it lacks `pid: host` and `SYS_PTRACE`. Six docker verbs, none of which touches another container's memory, logs or environment.

**(b) Can an operator use it to change what runs after the enclave is measured?** **Yes — that is its function.** `LAUNCHER_CHANNEL` is in `allowed_envs`, the tag is mutable, the resulting digest overrides the manifest's `${COMPOSE_MANAGER_IMAGE:-…}` default, and `.env.launcher` makes the override survive reboot. The swap is bounded — and, newly established at this deployed config, *reliably* bounded — to images signed by a workflow under `nearai/compose-manager`, because the cosign identity is a measured literal and `LAUNCHER_SKIP_VERIFY` is not operator-settable. The swap leaves no entry in the attested action log.

**(c) Logging/persistence/egress:** nothing sensitive. Four destinations, all justified.

**What the signed action log commits to:** nothing about the launcher. Its actions are outside the attested structure entirely.

**Recommended fix:** pin `COMPOSE_MANAGER_IMAGE` by digest in the measured compose rather than treating the manifest digest as a defaultable fallback; have the launcher record its swaps somewhere the manager folds into `actions.json`; and tighten the cosign gate from a workflow-identity regexp to an expected-digest allow-list.

**Unverified / untraced, stated explicitly:** whether the cosign binary and Alpine packages baked into *this* image behave as their upstream versions — only the two payload files were byte-verified against source; the Dockerfile pins cosign to a `v3.0.6` release URL ([`Dockerfile:16-17`](https://github.com/nearai/compose-manager/blob/8e07c3583909c9ab9da94d883e87add1ae90832d/launcher/Dockerfile#L16-L17)) but that download is not hash-checked at build time. Also unverified: whether dstack's RTMR/event log independently measures container images; and the fleet-wide count of 4 of 17 hosts, which comes from the orchestrating census — this review directly read two of those manifests (`d98a2568…`, `9385918d…`).
