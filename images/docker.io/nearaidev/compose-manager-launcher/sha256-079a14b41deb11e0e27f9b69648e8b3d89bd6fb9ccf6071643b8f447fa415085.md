## What the child-digest pin means for a verifier

The attested compose text on all 11 hosts now says `@sha256:079a14b4…`. Three consequences for anyone matching that text against the registry, none of which changes the bytes that run:

1. **`docker pull`/`docker image inspect` and the Hub `prod`/`latest` tags agree with the compose text**; the `prod-20260702-8e07c35` tag and the base page's digest `91fdff3c…` do not, because they name the index. A verifier comparing the pinned digest to the audited one gets a mismatch for the same image unless it resolves the index's `manifests[]`.
2. **The GitHub attestations API cannot be queried by the pinned digest** — it 404s — so the base page's one-call identity check no longer works verbatim. The working chain is: pinned digest → find the index that lists it (here `91fdff3c…`, via the `prod-20260702-8e07c35` tag or the base page) → `GET …/attestations/sha256:91fdff3c…` → confirm the index body names the child. The registry-attached statement on `c3e4bbb1…` corroborates the same commit and run but is **not signed**; it is a plain layer that Docker Hub serves, and `buildkit_completeness.resolvedDependencies` is `false` in it.
3. **A tool that resolves identity by tag reverse-lookup will stop at `prod` / `latest` / `staging-20260624-8e07c35` and recover no commit by itself** (that is what happened to this repo's resolver). The commit is recoverable only through the index or through the attestation layer's `vcs.revision`.

A future re-pin to a digest that is *not* a child of a signed index — for example a child of `8af4d5cf…` if `aa9de34` were promoted again — would need its own page; `aa9de34`'s index does carry a GitHub attestation, so that path is open.
