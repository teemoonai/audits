### Patch A — `chunked-prefill-admission-reserve.patch` (scheduling; privacy-neutral)

Touches `schedule_policy.py` and `scheduler.py`. It reads `SGLANG_CHUNKED_PREFILL_ADMISSION_RESERVE` (deployed `=4096`, compose env line 152 — this is the "near-patch symbol" from the brief; it exists **only** in this patch), and reserves a slice of the chunk budget so waiting requests are not starved by an in-flight long prefill. The only request-derived value it reads is an **integer length**:

```
first_waiting_req_tokens=( self.waiting_queue[0].seqlen if self.waiting_queue else None )
```

`seqlen` is `len(origin_input_ids) + len(output_ids)` ([`schedule_batch.py:1091`](https://github.com/sgl-project/sglang/blob/fdebc938f7f4d16fe6b9f55dcd9a767cf0899ea1/python/sglang/srt/managers/schedule_batch.py#L1091)) — a count, not content. No logging, no I/O, no egress. It changes *which* request is admitted this pass, nothing about *what* is copied.

### Patch B — `dsv4-0731-runtime.patch` (the plaintext serving path; privacy-neutral)

This is the patch that mattered to check, because it touches the exact files that handle the prompt: `chat_encoding.py`, `encoding_dsv4.py`, `serving_base.py`, `serving_chat.py`, `serving_completions.py`. I read all 397 lines of it. Two behaviours:

1. **DSV4 reasoning-effort profile selection.** Adds a `"preview"`/`"official"` mapping of reasoning-effort levels to **constant prompt-prefix strings** (`REASONING_EFFORT_PROFILES` in `encoding_dsv4.py`), resolved once at server init in `OpenAIServingChat.__init__` and threaded through `render_message`/`encode_messages`. It only *prepends a fixed string* to the prompt based on the effort level; it never reads, logs, stores or transmits message content. The deployed `--json-model-override-args '{"dsv4_reasoning_effort_profile":"official"}'` supplies the profile directly (via `hf_config.to_dict().get("dsv4_reasoning_effort_profile")`), so `resolve_dsv4_reasoning_effort_profile` returns the validated override and the fallback detection branch — which could otherwise `hf_hub_download` the checkpoint's *own* `encoding/encoding_dsv4.py` (a **model** file, not user content; and `HF_HUB_OFFLINE` is respected) — is never reached. The one added log call is `logger.debug(... encoder_path, error)`: a filesystem path and an exception, no request content.

2. **Streaming-abort-before-first-chunk.** Adds a `StreamingAbortBeforeFirstChunk` exception (`serving_base.py`) so that when the scheduler aborts a request *before* the first SSE chunk is emitted, the handler can return the scheduler's real HTTP status code instead of an in-band SSE error. The exception carries `finish_reason.get("message", "Generation aborted.")` — a scheduler-generated status string — back to `create_error_response`, i.e. to **the same requesting client**, not to any log or sink. No new logging, disk, or egress of request content.

**Neither patch adds a server arg, HTTP route, `ConfigureLoggingReq` field, file write, socket, or serializer of request content.** The engine's privacy surface is therefore the upstream `fdebc938` surface, evaluated below at the deployed flags.

### MEDIUM (deployed: ON) — engine stdout ships off-box unredacted (telemetry/egress sink), so any line the two findings above can print leaves the machine

The engine's `com.datadoghq.ad.logs` label carries `model` and `deployment` tags (compose lines 419/467), so its stdout is **kept** by the otel pipeline, not dropped. In the attested inner compose:

The bytes are upstream `sgl-project/sglang @ fdebc938` (v0.5.16) built from source, plus two local patches I recovered from the image and verified by hash against the labels: a chunked-prefill admission-reserve scheduling patch (integer lengths only) and a DSV4 reasoning-effort-profile + streaming-abort patch that touches the prompt-encoding path but only prepends constant strings and returns a status message to the same client.
