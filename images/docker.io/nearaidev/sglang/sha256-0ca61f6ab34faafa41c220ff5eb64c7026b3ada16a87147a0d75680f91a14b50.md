- **35 (caller media hashes).** A caller could supply `mm_hashes`, or a `hash` on a preprocessed item, which became that item's prefix-cache identity. ### What the redaction change does

The removed `tests/test_customer_data_log_redaction.py` (207 lines) and the added `tests/test_request_content_log_redaction.py` (390 lines) test the same module under a new name, with more sites. Read as evidence of intent, the change is a tightening, and the bytes agree. In `utils/log_redaction.py`:

- `fingerprint` (`<len=N sha256=8 hex>`) is replaced by `redact_value` (`:80`): `<len=N>` for strings and bytes, the type name for anything else. The short digest is gone, so two log lines about the same value can no longer be matched, and a guessed value can no longer be confirmed against the log.
- `redact_url` (`:91`) returns `<url len=N>`; the host is no longer kept.
- `redact_text` (`:135`) additionally replaces the host names urllib3 quotes. It still passes ordinary words through; it is now used for **error responses to the client**, not for log lines.
- `redacted_traceback` (`:175`) and `opaque_traceback` (`:193`) return stack frames and exception **type names only**, for the exception and its cause chain. Executed here with a marker in the messages of a two-exception chain: no message text in the output.
- new `summarize_grammar_error` (`:198`): fixed texts pass, the unsupported-schema text keeps its reason with the JSON pointer replaced, anything else becomes `<len=N>`. Executed with a marker: not present in the output.

### MEDIUM (deployed: ARMED; no reachable trigger found) — when the grammar matcher rejects a committed token the engine logs at ERROR the output token ids accepted so far and the client's schema verbatim — sink: log (egress to near.ai)

**New on this page; not new in the bytes.** The three files involved are untouched by both series, and the lines are present in the base image at `batch_result_processor.py:744-746` and `:889-891` (one line lower there). The base page's sweep did not open them.

- `constrained/xgrammar_backend.py:98-110` — `XGrammarGrammar.accept_token`: if the matcher does not accept the token, `raise ValueError(f"Tokens not accepted: {token}\nAccepted tokens: {self.accepted_tokens}\nKey string: {self.key_string}")` (`:104-108`). `accepted_tokens` is every output token id accepted under this grammar so far (appended at `:110`); `key_string` is the client's JSON schema, regex, EBNF or structural tag, verbatim.
- `managers/scheduler_components/batch_result_processor.py:738-745` — the first sampled token after prefill: `req.grammar.accept_token(next_token_id)` inside `try`, `except ValueError as e:` (`:739`), `logger.error(f"Grammar accept_token failed for req {req.rid} with token {next_token_id}: {e}")` (`:743-745`).
- `managers/scheduler_components/batch_result_processor.py:879-890` — every decode step, including the verified run of a speculative step: the loop calls `req.grammar.accept_token(token_id)` (`:881`), `except ValueError as e:` (`:885`), `logger.error(f"Grammar accept_token failed for req {req.rid} with token {tokens}: {e}")` (`:888-890`).
- Under `--enable-strict-thinking` the request's grammar is a `ReasonerGrammarObject` whose `accept_token` forwards to the inner grammar once the answer has started (`constrained/reasoner_grammar_backend.py:184-194`), so the inner `ValueError` propagates to these handlers unchanged.

**What is written.** Executed here: the lifted `accept_token` with a stub matcher, three accepted ids and a schema, then the log call as written. Output:

```
ERROR Grammar accept_token failed for req RID with token [44, 999]: Tokens not accepted: 999
Accepted tokens: [11, 22, 33]
Key string: {"type":"object","properties":{"ssn":{"type":"string"}}}
```

Token ids decode to text with the public tokenizer, so this is the constrained part of the reply (a structured answer, or tool-call arguments under a forced tool choice) up to the rejected token, plus the constraint the client sent. None of the redaction patches reaches it: patch 26 redacted this same key string in `XGrammarGrammar.__repr__` and in the compile-failure lines, and left the exception text at `:104-108` and the two `{e}` lines alone.

**Who can reach it.** A request gets an inner grammar only when one of `json_schema`, `regex`, `ebnf` or `structural_tag` is set on its sampling params (`constrained/grammar_manager.py:153-158`). At the deployed flags that is: `response_format` of type `json_schema`, `json_object` or `structural_tag`; the native `regex` and `ebnf` fields; tools with `tool_choice` `required` or a named function (`function_call/function_call_parser.py:341`); and tools under `auto` when a tool sets `strict: true` (`:342-344`; `SGLANG_TOOL_STRICT_LEVEL` is `OFF` and unset, so non-strict `auto` tool use is not constrained by this route). `serving_chat.py:1948` can also attach a template-level structural tag for some detectors; I did not establish whether glm47 is one. Every other request under `--enable-strict-thinking` gets a `ReasonerGrammarObject` with no inner grammar, which has nothing that can raise this error. Plain chat without tools or a response format cannot reach the line.

**Reachability: what I ruled out, and what I could not.** The line needs the matcher to reject a token the engine has already committed. Sampling is masked by the same grammar, so I read the code between the mask and `accept_token` for a way around it:

- *Mask not applied while the grammar advances.* Ruled out for the cases read. Mask construction and FSM advance are keyed on the same predicate: `batch.has_grammar` is `any(req.grammar for req in reqs)` (`managers/schedule_batch.py:2699`, recomputed at `:3913`), it gates the verify mask (`speculative/eagle_worker_common.py:664-671`) and the advance (`batch_result_processor.py:913`), and the per-request skip is `req.grammar is None` in both. A compile failure or timeout aborts the request before it decodes (`grammar_manager.py:337-345`). The extend-stage token (`:738`, or `:920-937` through the barrier) is sampled through `ModelRunner._preprocess_logits`, which fills and applies the mask first (`model_executor/model_runner.py:2085-2093`; `sampling/sampling_batch_info.py:382-407`).
- *Sampling picks a masked token through a later transform.* Ruled out for `logit_bias`. The mask writes `-inf` (`kernels/ops/grammar/bitmask_ops.py:79`). On the non-speculative path the bias is added after the mask (`sampling_batch_info.py:439-448`), but patch 27 bounds it to finite values, and a finite bias leaves `-inf` at `-inf`; on the EAGLE verify path the bias is added before the mask (`speculative/eagle_utils.py:579-588`). **Not ruled out:** a row in which every token is masked (the strict-thinking filters narrow a grammar row without widening it, `reasoner_grammar_backend.py:246-260`), where the sampler's behaviour on an all-`-inf` row decides the token; I did not read the sampler for that case.
- *A terminated grammar that keeps receiving tokens.* Ruled out. `accept_token` is a no-op once the matcher has terminated (`xgrammar_backend.py:99`), the commit loop stops at termination (`batch_result_processor.py:883-884`), and the draft-tree walk does not descend below a terminated node (`speculative/spec_utils.py:633`).
- *Rollback divergence between the wrapper and the matcher.* Not found in the cases traced by hand: the token that completes the think-end sequence is not forwarded to the inner grammar and its rollback forwards zero steps (`reasoner_grammar_backend.py:184-194`, `:211-218`); one answer token forwards one accept and one rollback. I did not trace multi-token think-end sequences, the `reasoning_in_grammar` mode, the 200-token rollback limit (`xgrammar_backend.py:64`) or jump-forward.
- *The matcher and its own mask disagreeing.* **Not ruled out, and the only path I can state.** Patch 30 (upstream PR 48117 per the recipe README) exists for exactly this: its test describes "a mask/matcher desync", a draft token whose bit is set in the parent row and which `accept_token` then rejects. The patch clears the bit for the token the draft proposed (`spec_utils.py:625-631`). The same row is the mask the target model's token is sampled under, and a desynced token the draft did not propose keeps its bit; if the target samples it, it is committed and reaches `:881`. Neither the patch nor its test says what causes the desync, the test uses a mock grammar, and I did not find the cause.

**So, exactly:** the lines exist, their `try` can raise, the raise is explicit, and upstream's own comment (`batch_result_processor.py:736`) and a patch in this series say the precondition happens. I found no request that produces it and no code path that makes it certain. Rated MEDIUM for that reason, not for what the line would carry: if it fires, it writes reply token ids and a client schema to a log that leaves the CVM, which is what the base page rated HIGH for the watchdog. It does not set the class.

## Verdict

**PRIVATE at the deployed flags** — for two running engines on the pack CVM, and declared on two more recipes — with the qualifier this repo attaches to every sglang engine page: *at the deployed flags, and not "cannot happen"*.

Identity is the strongest class here: a signed attestation, and beneath it every file the 38 patches touch compared byte for byte with a replay of the hash-pinned series. What is not verified is upstream's own base image, and upstream v0.5.23 was swept for log sinks, not read.

Against the base image this build is a real improvement on the logging surface. The watchdog dump, which was the one armed path that would have put a whole batch's prompts in the log, now prints lengths. Local file reads through media inputs are refused. The redaction module stopped keeping hosts and digests and stopped printing exception messages at the sites it covers, and it covers more sites. None of the new patches adds a place for content to go.

What it did not change is the posture around the engine. `/configure_logging` is still one unauthenticated POST away from verbatim prompt logging and request pickling, and the patch that used to be named as if it fixed that is now named for what it does. Engine stdout still leaves the CVM unredacted. The ghost cache still hands keyed digests of every request to a second container.

And one thing was there all along: a grammar rejection logs the reply's token ids and the client's schema. I could show what the line prints, that its `try` can raise, and that only requests carrying a schema, regex, grammar or forced tool choice can reach it; I ruled out four ways a rejected token could be committed and could not rule out the mask/matcher disagreement that a patch in this very series was written for. I found no request that makes it fire. It is recorded as MEDIUM and armed, it applies to two other audited images, and the fix is three lines in the style of patch 26.

Not LEAKS: no sink receives plaintext or token ids at the deployed flags in normal operation, and the one line that would was not shown to execute. That the image now runs does not change this: the rule this repo has applied to every running sglang engine with the same unauthenticated `/configure_logging` (the `050b1adf` base page among them) is PRIVATE at the deployed flags with the route recorded as CRITICAL and its reachability as a residual, and I apply it the same way here. Not COMPROMISABLE: an unauthenticated engine route has consistently been recorded as a residual under PRIVATE on this ref. Not QUALIFIED PASS, which this repo has used for proxies, management services and one engine image reviewed without a tree read; here the patched tree was replayed and the delta read in full.
