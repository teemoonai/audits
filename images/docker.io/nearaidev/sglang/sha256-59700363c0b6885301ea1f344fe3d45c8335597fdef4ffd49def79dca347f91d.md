### LOW (deployed: ON) — ghost prefix cache: 128-bit keyed digests of every sampled 64-token page of each finished prompt and reply leave the engine process over a unix datagram socket to an in-CVM sidecar; the shared key lives on a tmpfs volume mounted by five containers — sink: egress (in-CVM IPC to glm53-ghost-aggregator) / memory

The priority item for this review, read in full on both sides. The flow, with every step at the bytes:

**Hook.** `mem_cache/common.py:254` calls `observe_finished_req(req)` at the top of `release_kv_cache`, which every finish and abort path reaches (`scheduler.py:3459,5242,5262,5274`; `batch_result_processor.py:124,363`; `schedule_batch.py:2111`; `dynamic_chunk_sizer.py:267`). `ghost_cache.py:444-457`: returns at once unless `SGLANG_GHOST_CACHE=1` (read at import, 410); skips unfinished requests and `FINISH_ABORT` (449); `_get_recorder()` builds a recorder only on TP rank 0 / PP rank 0 (400–408, 416–442) — on `r4` that is one of the two scheduler ranks. Then:

```
# python/sglang/srt/observability/ghost_cache.py:454-455
        prompt = list(req.origin_input_ids)
        recorder.submit(prompt, list(req.output_ids), len(prompt), int(req.cached_tokens or 0))
```

So the **complete prompt and output token ids** of every finished request are copied into a bounded `queue.Queue` (256 requests, 316; beyond that dropped and counted, 350–354) consumed by a daemon thread named `sglang-ghost-cache` (347–348) — a second copy of the plaintext, in the same process that already holds it, in RAM. Not a sink; the structural fact that the next steps rest on.

**What is hashed.** `observe` (248–283) concatenates prompt and output (255) and `_chain` (232–243) cuts the sequence into 64-token pages (a trailing partial page is dropped, 233), packs each page as 64 int64 (236) and computes `blake2b(prev_digest + page_bytes, digest_size=16, key=key)` (241) — a 128-bit keyed digest per page, chained so that page *p*'s digest commits to every token before it. Page boundaries ignore the prompt/output split: the page straddling it mixes both. Pages are *tracked* when the low 32 bits of the digest are divisible by 16 (245–246) — a 1/16 sample by hash value. Every page is hashed; one in sixteen is kept and forwarded.

**The key.** 32 bytes (`KEY_BYTES`, 73). With `SGLANG_GHOST_CACHE_KEY_FILE=/ghost/key`, `load_shared_key` (79–107): if the file is absent, create a temp file `O_EXCL` mode `0600` (86), write `os.urandom(32)`, `fsync`, hard-link into place (first replica wins the race), then read the 32 bytes. The file sits on the `ghost` volume: tmpfs, 1 MiB, `mode=0700` (recipe 1086–1088), mounted by `r1`–`r4` and the aggregator. The engines and the aggregator run as root (no `user:` on either), so **root in any of those five containers reads the key — including the aggregator, the process that receives the digests**: the recipient of every forwarded digest also holds the key that made it, so the separation between "has the digests" and "has the key" does not exist on this host. Nothing else in the recipe mounts the volume, and it is in-memory. Persistence is the volume's lifetime (Not traced).

**What crosses the socket.** `_Recorder._run` (356–388): after accounting, if a socket is configured and the request produced tracked pages, `encode_messages` (122–127) splits them into datagrams of at most 3500 records and `sendto`s each to `/ghost/aggregator.sock` (368), non-blocking; a full or absent socket drops the message and increments `sglang:ghost_forward_dropped_total` (369–370). The wire format (75–76, 109–116): a 4-byte magic `GHC1`, the sample rate, the replica-label length, the record count, the label (`r4`), then per tracked page **one flag byte (1 = prompt page, 0 = generated page) and the 16-byte digest**. No request id, no token ids, no lengths — though the record count per request (about *(prompt + output tokens) / 1024*) and its arrival time are a coarse length-and-timing signal per finished request, per replica.

**The aggregator.** `ghost_aggregator.py` (byte-identical to the v7 image's, which is what the sidecar runs): binds the datagram socket, `chmod 0660` (118–123), starts a Prometheus HTTP server on `:9464` (124), logs one INFO line — socket path, port, sample, max pages (125) — and loops on `sock.recv` (127). `decode_records` (130–140 of `ghost_cache.py`) rejects bad magic or a different sample rate, counted in `sglang:ghost_pool_bad_messages_total` (135). `PoolAccounting.process` (73–96): one `StackDistanceLRU` of digests across replicas (default `--max-pages 4,000,000`; the recipe passes none) plus `seen_by: digest → replica bitmask` (60), **in memory only, "gone on restart"** (docstring 20). Exports: `sglang:ghost_pool_lookup_tokens_total`, `..._reused_tokens_total{within}`, `..._other_replica_only_tokens_total`, `..._messages_total`, `..._bad_messages_total`, `..._tracked_pages` — labels `model_name`, `replica`, `within` (104–112). No per-message log, no file. Engine-side exports (`ghost_cache.py:320-345`): `sglang:ghost_{requests,dropped_requests,prompt_tokens,actual_cached_tokens,lookup_tokens,reused_tokens,reused_age_tokens,forward_dropped}_total` and `ghost_tracked_pages`, labels `model_name`, `within`, `within_s`. All integers of token counts scaled by 16. **Every `logger.*` and `print` in both files:** engine — one INFO at enable (432–441: sample, max pages, "shared"/"per-process", `r4 -> /ghost/aggregator.sock`), `logger.exception("ghost cache: failed to account a request")` (363) and `("ghost cache: hook failed")` (457) with tracebacks and no locals; aggregator — the startup INFO (125), `logging.basicConfig(INFO)` (158), nothing else. No `print` in either.

**Is a digest reversible?** Not without the key: BLAKE2b with a 256-bit random key is a PRF, and a 16-byte output cannot be inverted or tested offline. **With the key** — root in any of the five containers, or anyone who reads the tmpfs — a digest is a **guess-confirmation oracle**: compute the chain over a candidate token sequence and compare. Because the chain commits to everything before the page, confirming page *p* requires the whole prefix up to and including it; a 64-token page cannot be brute-forced in general. What it *does* confirm cheaply is any prefix the holder already knows in full — a fixed system prompt, a template preamble, a document the holder has — so the first-page digests of a replica's traffic become identifiers of *which known prefix* each conversation began with, and chained digests confirm *how far* a known text was reproduced. That is membership testing of known text, not recovery of unknown text. To exercise it the holder needs the digests, which exist only in the rank-0 scheduler's LRU (`max_pages` 1,000,000), transiently in the kernel's socket buffer, and in the aggregator's LRU and `seen_by` dict — none on disk, none in a log, none on `:9464`.

**Why LOW and not INFO.** Content-derived data crosses a process and container boundary to a destination that is neither the user nor the engine, and that destination holds the key. **Why LOW and not higher.** What crosses is a keyed 128-bit digest per sampled page, the key and the digests stay in RAM inside the CVM, the only exports are counters, and the realistic misuse is confirming the presence of text the attacker already possesses. The `ipc`/volume topology is what keeps it inside: the `ghost` volume is not shared with the collector or the proxy.

**Integrity note, not a privacy one.** `0660` on the socket and `cap_drop: [ALL]` on the sidecar: anything with write access to `/ghost` can inject digests; the aggregator parses with fixed-width struct reads, caps a datagram at 1 MiB (127), and refuses mismatched sample rates — a forged message distorts the counters, nothing more.

### Verdict: LEAKS — the base's one leak, carried through seven more patches that add digests but no plaintext

This image is the `47aff791` build plus seven patches in the same recipe directory, and the claim that it is exactly that rests on a chain of hashes — signed commit, workflow pins, `SHA256SUMS`, thirteen patch pins, manifest before/after hashes, a deterministic replay — rather than on the registry bytes the base page compared. I say so, and I cite nothing I did not re-read in the replayed tree.

What the seven patches add, in privacy terms, is one new flow and a lot of plumbing. The flow is the ghost prefix cache: on this replica it is on, in shared mode, and it sends a keyed 128-bit digest of one in sixteen 64-token pages of every finished prompt and reply to a sidecar in the same CVM, where the digests live in RAM and become counters. No token leaves the engine process; the key is a 32-byte random file on a 1 MiB tmpfs that five root-running containers can read; the digests are an oracle for confirming text their holder already has, not a way to recover text they do not. That is a LOW, and it is the only content-derived thing the delta moves across a boundary. The plumbing — a process pool that pickles the complete request and every header to forked workers inside the container, counters of evicted tokens, a profiler that is off, a tool-schema cap, an FP8 row layout, a host-side token count — logs request ids, counts, pids, names and timings, writes a transient trace only when switched on, and sends nothing.

What the delta does not remove is everything the base found. The glm47 parser still logs a model-emitted argument value at WARNING, in a file the pipeline has now rebuilt around four times without touching, and the recipe still ships that line to near.ai unredacted: deployed ON in normal operation, which is why the class is LEAKS. `/configure_logging` is still one unauthenticated POST away from verbatim prompt logging. The watchdog still dumps the in-flight batch's token ids on a hang, and this replica runs twice the batch of the base's TP2x4 recipe. The media fetch still has no allowlist.

One thing the base pages did not record, re-read here after a sibling page's whole-tree sweep: a `logger.debug` in the tool-call path prints up to 2,000 characters of the model's reply when a required tool call cannot be parsed — off at the deployed level, and one `/configure_logging {"log_level": "debug"}` away from on (LOW).

Two things the brief got wrong about the deployment and this page corrects from the file: `r4` runs FP8 KV on `flashmla_kv` with HiCache off, not bf16 with HiCache on. Neither changes a finding's class; both change which hunks are live, and the HiCache INFO of the base page does not apply to this replica.
