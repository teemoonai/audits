# SGLang inference engine (GLM-5.3-Flash, near.ai HiCache W4AFP8 v6 build) — Privacy Audit

> Part of the near.ai inference-path privacy audit. Method: [/notes/method.md](/notes/method.md).

**Image:** `nearaidev/sglang@sha256:9c6ddd4319c4ab00e351d8650459e68b8830e36ffcc029d67fa5e19d0ac3ed17`
**Source:** `PierreLeGuen/sglang-upstream` @ `fc91d2403cc210a86bd5fc715c6609f58c932e5a` + thirteen patch files from three `nearai/cvm-compose-files` recipe directories (the base's eleven, plus two new in `docker/sglang-glm53-hicache-w4afp8` @ `678a6b5e`).
**Role:** the inference engine — the one process legitimately entitled to see message plaintext. Declared behind `nearaidev/vllm-proxy-rs` (`OHTTP_ENABLED=true`) behind nginx; engine port 8000 is not host-published but is reachable on the `external: true` shared Docker network `dstack_default` (recipe `:1473-1476`).

**Deployed state, stated once.** This image is **in scope by the repo's rule** — the attested compose document on `glm-5-3-flash-long` names it for two services — and the drift check derives its targets from that document, not from a container list. But the host's two signed action logs record `compose_down` of both services it is declared for on 2026-10-06 and no `compose_up` of either since; every later up is a TP2 replica or the sidecar on the v7 image. So the honest state is **declared, not running**. Every `deployed:` tag below rates the *declared* flags — the flags a redeploy of these two services would start with — and the verdict line says that nothing runs them. The file's own header says the same (`:6-7`: "kept unchanged on the v6 image … none is deployed by the fleet").

**Citations.** Line numbers are those of the rebuilt v6 installed tree. For files the delta does not touch they are identical to the base page's post-patch numbers (the files are byte-identical; verified by `diff -rq`, and each cited line was re-read). For the two re-patched files (`mem_cache/common.py`, `unified_tree_core.py`) and the three new modules the numbers are the v6 bytes, which no public commit contains, and are given without links. Recipe citations are `LongContext@b4006c232e5d` line numbers.

**Verdict:** The two new patches add no path by which message *text* reaches a log, a file, telemetry or the network. What they do add is the first thing in this image family that is a *function of* the plaintext and leaves the engine process: the ghost prefix cache. At the declared flags (`SGLANG_GHOST_CACHE=1`, shared key, socket) TP rank 0 of each engine hashes every finished request's prompt and output token ids in 64-token pages with a keyed BLAKE2b, keeps the sampled 16-byte digests in an in-process LRU, and sends the sampled digests — with the replica label, the sample rate and a prompt/output flag, nothing else — over `/ghost/aggregator.sock` to a CPU-only sidecar in the same CVM that holds up to four million of them in memory and exports per-replica token *counts* on `:9464`. No token id, no text, no request id, no timestamp crosses. The key is 32 random bytes, created once, mode 0600, on a 1 MiB tmpfs volume mounted by every engine **and by the sidecar**, so the one process that receives the digests can also read the key: for a page whose 64 tokens can be guessed (a shared system prompt, a template header) a key-holder can confirm the guess, and the chain tells it which conversations share a prefix across replicas — which is the feature's purpose. That is a prefix-equality oracle, not text, and I rate it LOW. The KV tier metrics count tokens and seconds and never touch keys or ids (INFO). The PyJWT layer is unreachable from the python tree (INFO).

What makes the class LEAKS is inherited, on byte-identical files, re-read at the v6 bytes:

1. the **glm47 tool-call parser logs a model-emitted argument value verbatim at WARNING** (MEDIUM, declared ON — `function_call/glm47_moe_detector.py` hashes identically in base, v6 and v7);
2. **unauthenticated `/configure_logging`** (CRITICAL) — no `--api-key`/`--admin-api-key` in either declared command;
3. the **watchdog hang dump** (HIGH, ARMED at 1800 s in both);
4. the **request-driven media fetch** (MEDIUM) — no `--allowed-media-domains`.

New from sweeping the whole tree rather than the hunks: a `logger.debug` in the OpenAI chat path writes up to 2,000 characters of model output when a *required* tool call is missing or unparsable — level-gated (default `info`), but the root logger's level is exactly what the unauthenticated `/configure_logging` can raise (LOW, OFF). Also cleared by the sweep: the out-of-memory handlers call `tree_cache.pretty_print()`, and for the cache class this build uses that prints node ids, key lengths and lock counts — not token ids (the legacy `RadixCache` printer would).

### LOW (deployed: ON) — ghost prefix cache: keyed, sampled 128-bit digests of every finished request's prompt and output token pages leave the engine process over a unix datagram socket to a sidecar that holds them in memory beside the key — sink: socket (in-CVM sidecar, memory only)

The priority item, read in full. Nothing here writes text, token ids or request ids to a log, a file, telemetry or the network. What it does is new for this image family: it computes a function of the plaintext and hands the result to another process. Stated exactly:

**What is hashed.** `observe_finished_req` (`ghost_cache.py:444-457`) is called for every request as its KV is released (`common.py:254`), on every rank; it returns unless the request `finished()` and its reason is not `FINISH_ABORT` (`:449`), and unless this is TP rank 0 / PP rank 0 (`:400-407`, `:422`). It then copies `list(req.origin_input_ids)` and `list(req.output_ids)` (`:454-455`) — **the full prompt token ids as the chat template rendered them (system, history, user turn, multimodal pad tokens) and every generated token id including reasoning tokens** — into a `queue.Queue(maxsize=256)` (`:316`, `:350-354`; full → dropped and counted). The daemon thread (`:356`) concatenates prompt then output (`:255`), cuts the sequence into whole 64-token pages (`:52`, `:233-236`; a trailing partial page is not hashed), packs each page as 64 little-endian int64s (`:237-238`) and computes

```
# python/sglang/srt/observability/ghost_cache.py:241
prev = blake2b(prev + page_bytes, digest_size=16, key=key).digest()
```

— a chain: page *p*'s digest covers the previous digest and so every token before it. Key: 32 bytes (`:73`), from the shared file when `SGLANG_GHOST_CACHE_KEY_FILE` is set (`:428`), else `os.urandom(32)` per process (`:224`).

**What is kept in the engine.** Only pages whose digest's low 32 bits are divisible by `SAMPLE` are tracked (`:245-246`; 1 in 16 declared) in a `StackDistanceLRU` of digest → slot and digest → wall-clock-of-last-use (`:165-176`, cap `SGLANG_GHOST_CACHE_MAX_PAGES`, default 1,000,000, `:426`); the rest are discarded after the chain is computed. The prompt and output token lists live in the queue until hashed and are then dropped. Per-request outputs are counters only (`:266-281`).

**What crosses the socket.** When `SGLANG_GHOST_CACHE_SOCKET` is set (`:429`), the tracked records of each request are encoded (`:109-116`) as: magic `GHC1`, the sample rate, the replica label (`SGLANG_GHOST_CACHE_REPLICA`, `r1`/`r2`, else hostname — `:311`), a record count, then per tracked page one flag byte (1 = prompt page, 0 = generated page) and the 16-byte digest (`:76`) — at most 3,500 records per datagram (`:119`). **No token id, no text, no request id, no length, no timestamp, no user identifier.** Sent non-blocking (`:315`, `:368`); an `OSError` (sidecar absent, buffer full) drops the datagram and increments `sglang:ghost_forward_dropped_total` (`:369-370`). The request path never waits on any of this: the hook enqueues and returns.

**What the sidecar keeps and exports.** `ghost_aggregator.py` decodes each datagram (`:130`), rejects a wrong magic, sample or length as "bad" (`:131-136`), and in `PoolAccounting.process` (`:73-96`) touches each digest in one pooled `StackDistanceLRU` (`--max-pages`, declared default **4,000,000** digests, `:155`) and ORs the sender's bit into `seen_by[digest]` (`:91`, pruned to the LRU's live set, `:92-95`). It never writes to disk; `Digests stay in this process's memory and are gone on restart` (`:20`) is accurate to the code. `:9464` serves `sglang:ghost_pool_lookup_tokens_total`, `..._reused_tokens_total{within}`, `..._other_replica_only_tokens_total` (labels `model_name`, `replica`), `..._messages_total`, `..._bad_messages_total`, `..._tracked_pages` (`:105-114`) — token counts scaled by `64 x 16`, nothing per page. Its log output is one INFO line at start (`:125`) and whatever `prometheus_client`'s HTTP server logs (not read — *Not traced*), tagged `model:` (`:1393`) and so shipped to near.ai like the engines'.

**The key.** `load_shared_key` (`:79-106`): if `/ghost/key` is absent, write 32 random bytes to `/ghost/key.<pid>.<tid>.tmp` opened `O_EXCL` mode 0600 (`:86`), `fsync`, `os.link` it to `/ghost/key` (`:93`; `FileExistsError` means another replica won), unlink the temp; then read until the file holds 32 bytes. Created by whichever engine rank 0 starts first; the sidecar never reads it (no reference to the key file in `ghost_aggregator.py`). It lives on the `ghost` tmpfs volume (`:1482-1486`, `mode=0700`, 1 MiB): in CVM RAM, gone with the volume, **kept across engine restarts** while the volume exists — so the digests of conversations before and after a restart are comparable, by design. Who can read it: any process in a container that mounts `ghost` and runs as the owning uid. That is every engine (`:249`) **and the aggregator** (`:1389`), which declares no `user:` and so runs as the image's default (root), `cap_drop: [ALL]` notwithstanding (reading a 0600 file you own needs no capability).

**Is a digest reversible?** Not in general: BLAKE2b with a 256-bit key and a 128-bit output is a MAC, and without the key a digest reveals nothing about the page. **With the key** it is a verification oracle: for any candidate 64-token page (and, because of the chain, any candidate *prefix* of pages) the holder can compute the digest and compare. Low-entropy pages — a fixed system prompt, a chat-template header, a widely shared prefix — are exactly the pages this feature exists to find reused across replicas, and they are guessable by construction. A high-entropy user turn is not. Sampling cuts the exposed set to one page in sixteen, chosen by digest value, i.e. deterministically per content. So the precise statement is: the sidecar holds a *set-membership and prefix-equality oracle* over 64-token pages of recent conversations, for up to four million sampled pages, and the key that makes it an oracle sits on a volume it mounts. It does not hold text and cannot produce text; a key-holder with a guess can confirm the guess.

**Rating.** Memory-only, in-CVM, no file, no log, no exporter carrying anything per page; the engine's own HiCache tier already holds a far richer function of the same conversations (the KV itself) in the same CVM. What is new is that a derivative of plaintext leaves the *engine process* to a process that is not the engine — the boundary this audit draws — and that the recipient also has the key. LOW. What would raise it: logging or persisting digests (neither exists), running the aggregator somewhere other than the engines' CVM (the socket is a unix socket, so it cannot be), or `SAMPLE=1` with a known key (exact page oracle). What would lower it to INFO: an aggregator that does not mount the key (it only needs the socket; a separate volume for `aggregator.sock` would do), or a key held only by the engines.

**Housekeeping noted, not rated:** the engine logs at enable time `forward=r1 -> /ghost/aggregator.sock` (`:432-439`) — a path, not a secret; the `_Recorder` registers its counters on the scheduler process's Prometheus registry, which under `--enable-metrics` is multiprocess mode backed by files in a temp directory (`utils/common.py:2591-2599`) — counters only, as for every other scheduler-side metric.
