### 2. The patch, in full

Pulled from layer `bd12dd7f`:

```

--- a/python/sglang/srt/managers/scheduler.py
+++ b/python/sglang/srt/managers/scheduler.py
@@ -325,6 +325,13 @@ class Scheduler(

         # Parse args

+        self.enable_eagle_prefill_fairness = get_bool_env_var(
+            "SGLANG_EAGLE_PREFILL_FAIRNESS"
+        )
+        if self.enable_eagle_prefill_fairness:
+            logger.warning(
+                "Experimental EAGLE prefill fairness is enabled: force one decode turn between chunked prefill batches."
+            )
         self.nccl_port = port_args.nccl_port
         self.schedule_policy = server_args.schedule_policy
         self.enable_priority_scheduling = server_args.enable_priority_scheduling
@@ -2690,6 +2697,18 @@ class Scheduler(

         if self.dllm_config is not None:
             new_batch = self.get_new_batch_dllm(running_batch)
+        elif (
+            self.enable_eagle_prefill_fairness
+            and self.chunked_req is not None
+            and last_batch is not None
+            and last_batch.forward_mode.is_extend()
+            and not running_batch.is_empty()
+            and not running_batch.is_prefill_only
+        ):
+            # The default scheduler always prefers the next prefill chunk. With
+            # EAGLE disabling mixed chunk, that can starve every active decode
+            # stream for the whole long prompt. Give decodes one bounded turn.
+            new_batch = None

             new_batch = prefill_plan.batch_to_run

Engine stalls on this deployment are a documented, recurring condition, and the watchdog dump is the behaviour that fires when a stall becomes a hang.

**Does the patch change the probability of this firing?** Honest answer: it changes scheduling, so it changes stall dynamics, but the watchdog counts forward passes (`get_counter=lambda: scheduler.forward_ct`), and the patch only ever *substitutes* a decode batch for a prefill batch — it does not create a path where no batch runs at all when work exists. I found no way it could stall `forward_ct` advancement. It is also not a mitigation for the dump: nothing about it reduces what gets printed when the watchdog does fire.

### MEDIUM (deployed: ON) — engine stdout is shipped verbatim off-box, with no redaction anywhere in the pipeline

The amplifier that turns either finding above into egress. It is in the attested compose file, so it is in scope.

The `otelcol-contrib` sidecar mounts the host Docker log directory read-only (compose line 594 — `- /var/lib/docker/containers:/var/lib/docker/containers:ro`) and tails every container's JSON log (compose lines 633–634 — `filelog/docker_containers:` / `include: [/var/lib/docker/containers/*/*-json.log]`). ### INFO (provenance, deployed: ON) — the OCI commit label describes the **base image**, not the tree that is running

Not a plaintext finding, but the one that most affects how this repo should treat the image.

`ai.sglang.build.commit` / `org.opencontainers.image.revision` = `7de33ce8…` are inherited from the upstream base's Dockerfile ARGs (config history, 2026-07-11), and nothing in the label set names the patch's content or provenance — only `nearai.experiment.patch=eagle-prefill-fairness-v1`, a free-text tag pointing at an unpublished build context. An auditor who resolved this digest to its labelled commit and reviewed `sgl-project/sglang @ 7de33ce8` would be reviewing a tree that is **not** what runs: `python/sglang/srt/managers/scheduler.py` differs. In this instance the difference is benign, and I could only establish that by pulling the image layers.

Consequences worth stating plainly:

- `index.json`'s `sources` map is `digest -> {repo, commit}`. There is no shape in it for "upstream commit **plus** an out-of-tree patch". Registering this digest as `sgl-project/sglang @ 7de33ce8` would assert something that is not exactly true.
- The `sglang_revision:7de33ce8` telemetry tag on the r2 service (compose line 486) repeats the same under-description into the observability data.
- The general rule this establishes: for a vendor-namespace image built `FROM` an upstream one, the source commit label is a statement about the **base**, and the delta must be recovered from the registry. It was recoverable here only because the build left the `.patch` file and the `.orig` in separate layers; a `--squash`ed build, or one that cleaned up in the same layer, would have left the modification invisible to this method.

The *positive* half: because BuildKit wrote a provenance statement naming the base by digest, and because the base's layers are reused verbatim, this image's identity is in one important respect **better** established than the lmsysorg engine images in this repo, whose "source" is a self-asserted label and nothing more. There is no signed attestation here (no `nearai/sglang` repo exists to hold one — a 404, which is itself the answer to "is there a near.ai build attestation"), and BuildKit provenance is builder-supplied and marked `reproducible: false` with an empty `builder.id`. But the base-digest link is independently checkable against the registry by anyone, which is exactly what I did.

### INFO (build delta) — the patch itself introduces no logging, persistence or egress of request content

Read against the audit question directly:

- **New state:** one boolean, `self.enable_eagle_prefill_fairness`, from `get_bool_env_var("SGLANG_EAGLE_PREFILL_FAIRNESS")`. No request data.
- **New log statement:** exactly one, a `logger.warning` at scheduler construction with a **constant string** and no interpolation of any request, batch or config value. It fires once per scheduler process at startup, and only when the env var is set. It reaches stdout and therefore the otel pipeline — carrying nothing but that fixed sentence.
- **New control flow:** in `get_next_batch_to_run`, when a chunked prefill is in progress, the previous batch was an extend, and there is non-empty non-prefill-only running work, set `new_batch = None` so the scheduler runs the decode batch this iteration instead of the next prefill chunk. This changes *ordering*, not *content*: no request is dropped, duplicated, redirected or copied. The five guard conditions are all internal scheduler state.
- **No file I/O, no sockets, no serialization, no new configuration surface** — the patch adds no server arg, no HTTP route, no `ConfigureLoggingReq` field. `SGLANG_EAGLE_PREFILL_FAIRNESS` is the only new operator-facing knob and it selects a scheduling policy.

I also considered second-order effects on the paths that *do* touch plaintext, since a scheduler change is not automatically inert for privacy: it does not alter the radix/prefix cache structure or lifetime, does not alter what the request logger receives, does not change `Req` construction or `__repr__`, and does not change what the watchdog dumps. The one interaction worth naming is timing — reordering prefill and decode changes inter-token timing, which is metadata visible to a network observer. That is outside message-content privacy (the method notes metadata as an explicit non-goal) and applies to any scheduling change.

### Verdict: private at the deployed flags — and the delta is verifiably benign

The question this page had to answer was whether a near.ai-namespace engine image, deployed as the candidate arm of a live A/B against an audited upstream image, is doing anything the audited image is not. It is doing exactly one thing differently, and I can name it to the line: a 19-line patch to `scheduler.py` that, when `SGLANG_EAGLE_PREFILL_FAIRNESS=1`, lets an active decode batch take one turn between chunked EAGLE prefills, and logs one constant-string warning at startup. Everything else — all 63 base layers, the launch command, the model, the revision pin, the proxy digest — is identical to the control replica beside it. There is no privacy-relevant flag divergence between the two arms.

That was worth verifying rather than assuming, because the image's own OCI labels would have led an auditor to review an upstream commit whose `scheduler.py` is not the one running. The patch had to be recovered from the registry. It happens to be benign; the method that establishes that should not be optional.

The engine's posture is therefore the base image's posture, which is: private at these flags, with the same unauthenticated `/configure_logging` runtime switch this repo has now found in every audited SGLang build, plus a watchdog hang-dump of full prompt and output token IDs that the base image's page did not report and that applies equally to it. Both terminate in a stdout stream that is shipped verbatim to `telemetry.infra.near.ai` with no redaction.

### Residuals

1. **`/configure_logging` is unauthenticated** and can enable full prompt/output logging and arbitrary-path request dumping at runtime, with no restart and no attestation-visible event. Reachable by any valid API-key holder through the proxy, and directly by any container on `dstack_default`. **The proxy is a residual, not a mitigation** — it has no path allowlist.
2. **The watchdog prompt dump cannot be disabled by configuration.** New finding for this source tree; applies to the sibling `6bb5fee3` image and the r1 replica too.
3. **Container stdout leaves the machine with no redaction stage.**
4. **The image's declared source commit under-describes the running tree.** The delta is an out-of-tree patch from an unpublished build context, recoverable here only because the build left the `.patch` and `.orig` files in separate layers. A squashed or self-cleaning build would have hidden it.
5. **No signed build attestation.** `nearai/sglang` does not exist as a GitHub repository (404), so there is no near.ai attestation to fetch for this digest; the BuildKit SLSA provenance in the registry is builder-supplied, marked `reproducible: false`, with an empty `builder.id`. The base-image digest link it asserts is independently checkable and I checked it; the rest is trust in the builder.
6. **The 63 base layers were verified by digest, not read.** The `sglang.private.*` metrics-exporter plugin hook noted on the sibling pages remains unverifiable without unpacking them.
7. **`--trust-remote-code` is deployed** against a pinned checkpoint revision whose Python is unaudited third-party code (no `auto_map`, so nothing auto-loads, but the flag remains armed if the pin is ever loosened).
