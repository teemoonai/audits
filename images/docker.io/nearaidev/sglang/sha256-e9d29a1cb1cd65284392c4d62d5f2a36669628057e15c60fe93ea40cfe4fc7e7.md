## Verdict

**PRIVATE at the deployed flags** — this image is the audited `a7b7136a` build with two small layers on top, and I could check that claim from bytes: the layer lists nest, the added layers hold eight recipe files and two source files, and both source files are what you get by applying the published patch to the published tree. The patch is 176 lines of scheduler budgeting. I read every hunk. It logs six integers behind a debug variable nobody sets, opens nothing, sends nothing, and reads two integer-shaped fields of each waiting request. The class is therefore the base's corrected class.

What the patch does not remove is everything the base page found, each re-located at these bytes. `/configure_logging` is one unauthenticated POST away from verbatim prompt logging and arbitrary-path pickling, and this recipe's nginx and shared bridge supply no containment. The watchdog dumps the in-flight batch's token ids on a 1800 s hang — on a scheduler whose own comments record earlier versions of this patch tripping it. The media fetch has no allowlist. Engine stdout leaves the CVM unredacted. And two `fc91d24` behaviours the base page did not list — `/dev/shm` staging under `ipc: host`, exception text at ERROR — apply here, the first of them *without* the narrowing that every later build in this family carries, because that narrowing lives in a patch this chain does not include.

**No path at the deployed flags writes prompt text, reply text or token ids to a log, a file, a socket or an exporter in normal operation.** That is the method's PRIVATE condition (§6), with the qualifier this repo attaches to every sglang engine page that meets it — *at the deployed flags, and not "cannot happen"*. Not LEAKS: no sink receives plaintext. Not COMPROMISABLE: an unauthenticated engine route has consistently been recorded as a residual under PRIVATE. Not QUALIFIED PASS, which this repo uses for proxies and management services.

**Deployment.** The recipe that declares this image was brought up once, project-wide, on gpu23 at 2026-09-29T15:56:49Z (entry 118), and 58 minutes later the W4AFP8-LongContext file's TP4 pair took the same eight GPUs at the same memory fraction (entry 120). Under either reading of a log that records no compose project (the recipe page states both), this image has not served on gpu23 since 2026-09-29T16:54:38Z: under the default project it was removed as an orphan at entry 120; under per-model projects its two containers could persist but could not hold GPUs 0-3 against the W4AFP8 engine at `0.80` on the same devices. Its other declared role, the perception check of every later long-context revision, is profile-gated and OFF. The class above is the class of the bytes at the declared flags; the fleet tool's "running" is the attestation's claim about the last file to touch any service, not a container listing.
