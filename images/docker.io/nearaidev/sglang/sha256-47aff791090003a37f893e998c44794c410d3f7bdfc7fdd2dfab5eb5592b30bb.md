# SGLang inference engine (GLM-5.3-Flash, near.ai HiCache W4AFP8 build) — Privacy Audit

> Part of the near.ai inference-path privacy audit. Method: [/notes/method.md](/notes/method.md).

**Image:** `nearaidev/sglang@sha256:47aff791090003a37f893e998c44794c410d3f7bdfc7fdd2dfab5eb5592b30bb`
**Source:** `PierreLeGuen/sglang-upstream` @ `fc91d2403cc210a86bd5fc715c6609f58c932e5a` + eleven patch files from three `nearai/cvm-compose-files` recipe directories.
**Role:** the inference engine — the one process legitimately entitled to see message plaintext. It sits behind `nearaidev/vllm-proxy-rs` (`OHTTP_ENABLED=true`) behind nginx; engine port 8000 is not host-published but is reachable on the `external: true` shared Docker network `dstack_default` in all three recipes.

**Citations.** Line numbers in files the patches modify (`http_server.py`, `tokenizer_manager.py`, `scheduler.py`, `schedule_policy.py`, `schedule_batch.py`, `serving_base.py`, `mem_cache/*`) are **post-patch** — the bytes in the image, which no public commit contains — and are given without links. Line numbers in untouched files are those of `fc91d24` and are linked.

**Verdict:** The patch stack adds no path by which message plaintext reaches a log, a file, telemetry or the network. What makes the class LEAKS is inherited:

1. the **glm47 tool-call parser logs a model-emitted argument value verbatim at WARNING** (MEDIUM, deployed ON) — the file is untouched by any patch;

and the paths that keep the rest short of "cannot happen" are also inherited, re-located at the patched bytes:

2. **unauthenticated `/configure_logging`** (CRITICAL, deployed ON) — no `--api-key`/`--admin-api-key` in any of the seven deployed commands;
3. the **watchdog hang dump** (HIGH, deployed ARMED at 1800 s in all seven);
4. the **request-driven media fetch** (MEDIUM, deployed ON) — no `--allowed-media-domains` in any recipe.

New on this page, from sweeping the whole target rather than the hunks: image-derived feature tensors are staged in `/dev/shm`, and every recipe runs the engine with `ipc: host` (LOW); unhandled request exceptions are logged with their message text (LOW). Both are `fc91d24` behaviour the base page did not record.

New in the patches and checked clean: the **event-loop stall dump** (on by default) prints file, line, function and source line per frame — no locals, no task or request reprs; the **HiCache tier** enabled by all three recipes is pinned host RAM only — no storage backend is configured, a startup one would abort the engine, and attaching one at runtime is refused without an admin key.

The priority item for this review, read in full. `http_server.py:396` (post-patch) calls `install_stall_dump(asyncio.get_running_loop())` in the lifespan of the HTTP/tokenizer process — not in the scheduler ranks. With `SGLANG_EVENT_LOOP_STALL_DUMP_SECS` unset (all recipes) it arms at 30 s and repeats every 60 s.

What it writes, exhaustively (`event_loop_stall_dump.py`, new file, line numbers in the image):

- **Python path** (`_dump`, 98–115): a header line of pid, stall age, threshold, dump number, thread count, loop-thread CPU seconds and a UTC timestamp; then for each thread from `sys._current_frames()` its ident and `threading` name, and `traceback.format_stack(frames[ident], limit=200)` (110). `format_stack` builds `FrameSummary` objects without `capture_locals`; each renders as `File "…", line N, in <function>` plus the source line read from disk. **No local variable, argument value, or object repr is formatted.** The frames are discarded after formatting.
- **C fallback** (`_arm_backstop`, 66; and 115): `faulthandler.dump_traceback_later(…, file=2)` and `faulthandler.dump_traceback(file=2, all_threads=True)` — faulthandler emits file name, line number and function name per frame and nothing else, by design (it runs without the GIL and cannot touch objects).
- A recovery line with the stall duration (86), and an arming line at startup with pid and thread ident (38–42).

It does not enumerate `asyncio` tasks, does not print coroutine objects, and does not touch request state. Each line is written with `os.write(2, …)` truncated to 4,000 bytes (117–126). What a dump discloses is *where* the process is stuck and for how long — operational metadata — and it reaches `telemetry.infra.near.ai` like the rest of stderr. Thread names are fixed strings (`event-loop-stall-watch`, `sglang-mm-shm_0`, executor defaults). The shipped `test_stall_dump.py` is not run in the image.

Residual of the mechanism rather than of this code: it registers `os.register_at_fork` hooks and a faulthandler timer in the process that holds plaintext; a future edit that adds `capture_locals=True` or a task dump would turn this INFO into a HIGH with a one-line diff. Worth re-reading on every rebuild.

### INFO (deployed: ON) — HiCache keeps KV state of finished conversations in pinned host RAM; no disk or network tier exists at the deployed flags, a startup one would abort the engine, and a runtime one is refused without an admin key — sink: none (memory only)

All seven commands pass `--enable-hierarchical-cache` (default `False`, [`server_args.py:2721-2723`](https://github.com/PierreLeGuen/sglang-upstream/blob/fc91d2403cc210a86bd5fc715c6609f58c932e5a/python/sglang/srt/server_args.py#L2721)). KV rows — a function of the prompt and the response — are copied from GPU to a host pool and back for prefix reuse across requests. The question the brief asked: does any tier write to disk, a file-backed path, or a network peer?

- **The tier below host RAM is `--hicache-storage-backend`**, choices `file`, `mooncake`, `hf3fs`, `nixl`, `aibrix`, `eic`, `simm`, `mori`, `shm`, `sim`, `dynamic`; default `None` ([`server_args.py:2772-2791`](https://github.com/PierreLeGuen/sglang-upstream/blob/fc91d2403cc210a86bd5fc715c6609f58c932e5a/python/sglang/srt/server_args.py#L2772)). **No recipe passes it.** With `None`, `init_hicache` skips storage configuration (`unified_radix_cache.py:435`, `:446`, `:524`, post-patch) and `enable_storage` stays `False` (386); the hybrid controller attaches a backend only `if startup_storage_backend is not None` ([`hybrid_cache_controller.py:140`](https://github.com/PierreLeGuen/sglang-upstream/blob/fc91d2403cc210a86bd5fc715c6609f58c932e5a/python/sglang/srt/mem_cache/hybrid_cache/hybrid_cache_controller.py#L140)). `hicache_host_memory_mode` defaults to `cache`; `buffer_only` requires a backend.
- **The patch makes a startup backend a startup failure here.** Every recipe sets `SGLANG_HICACHE_RAM_BUDGET`, and with it set `startup_ram_budget` raises `"RAM budget currently supports in-CVM host RAM only"` if `hicache_storage_backend is not None` (`mem_cache/startup_ram_budget.py:205-206`, new file), and separately `"Compressed DSA currently supports L2 HiCache only"` when the tree and transfer page sizes differ (`unified_radix_cache.py:436-440`). So adding the flag to these recipes does not silently enable a disk tier; it stops the engine.
- **The runtime attach route is refused.** `PUT /hicache/storage-backend` (`http_server.py:1098-1108`, post-patch) returns `_admin_api_key_missing_response()` when `admin_api_key` is unset — which it is — before doing anything; `DELETE` and `GET` likewise (1139, 1163). This is the one place where the engine's missing admin key *closes* a path.
- **The host pool itself is RAM.** With `SGLANG_HICACHE_CUDA_HOST_MEMORY=1` (all recipes) `alloc_with_host_register` calls `_alloc_cuda_host` (`pool_host/common.py:572-579`, post-patch), which is `cudaMallocHost` through `ctypes` and a `torch.frombuffer` view (305–347) — page-locked anonymous memory — and raises unless the allocator is the in-process `HostTensorAllocator` (the `shm`-backed allocator is selected only when the storage backend is `shm`, `common.py:439-444`). The pooled transfers (`pooled_pages.py`, `pooled_l2.py`) move bytes between that buffer, a GPU staging tensor and the device pool; nothing else.
- **`--enable-unified-cache-external-linker`** ("direct L3, with no host cache tier") is absent, default `False`.

So: OFF for disk and network at the deployed flags, and guarded twice against being turned on without a redeploy that changes the measured recipe. What *is* new is retention: 325–650 GiB of pinned RAM per replica (80% of available RAM on `small-models`) holding KV for conversations that have ended, for as long as the entries survive eviction. It stays inside the CVM. It widens what a memory image would contain (crash-diagnostics LOW), and it lengthens the window over which `--enable-cache-report`'s cached-token count in `usage` reflects other callers' earlier prompts — a prefix-probing side channel that exists with any shared prefix cache and that I note, not rate.

### INFO (deployed: ON, one recipe) — the admission-reserve patch is not inert for scheduling when its env var is unset, and is inert for plaintext either way — sink: log (integer counts only, behind an unset debug env)

The Dockerfiles, the workflow summary and two recipe comments say the patch "is inert unless `SGLANG_CHUNKED_PREFILL_ADMISSION_RESERVE > 0`". Read against the code, in this chain's copy of the diff (byte-identical to the plain recipe's):

- **True for the reserve itself.** The budget carve-out is inside `if getattr(self, "waiting_queue_len", 0) > 0 and CHUNKED_PREFILL_ADMISSION_RESERVE > 0:` (`schedule_policy.py:1014`, post-patch), and `_admission_reserve_need` returns `None` when the cap is `<= 0` (`scheduler.py:429-431`).
- **False for three other changes**, which run with the variable unset. `self._has_inflight_chunked = True` sits at `schedule_policy.py:1031`, one indent level *outside* that `if` — it is set whenever a non-dLLM chunked request is continued. Once set, (1) two guards return `AddReqResult.OTHER` instead of letting a *second* request become a new chunked request in the same pass (`schedule_policy.py:1234-1235`, `:1464-1465`); (2) the scheduler's admission loop `continue`s past such a result instead of `break`ing (`scheduler.py:3946-3947`), so it goes on to consider later waiters; (3) the "refund" block (`scheduler.py:3972-3990`) extends the in-flight chunk into any spare budget. These are scheduling-order changes relative to `fc91d24` on five of the seven deployed engines that leave the reserve unset.
- **What it means for this audit:** nothing reaches a sink. The patch's only log statements are two `INFO` lines of integers, both behind `SGLANG_ADMISSION_RESERVE_DEBUG=1` (`schedule_policy.py:1027-1030`, `scheduler.py:3989-3990`), which no recipe sets; neither carries a request id, a prompt length tied to a request, or token ids. The helper reads `r.seqlen` and `len(r.prefix_indices)` and writes one integer attribute on the request object (`_admission_iters_seen`, only when `MIN_ITERS > 0`). `SGLANG_ADMISSION_RESERVE_MIN_WAIT_S`, if set, raises on the first prefill pass with a waiting request (`scheduler.py:448-449`) — an engine crash, and so a route to the crash-diagnostics path, not to a content dump.

The claim matters as a rollback assumption ("unset the variable to get upstream behaviour"): that assumption is not exact. It belongs on the recipe pages as a behaviour note; it does not move this verdict.

### Verdict: LEAKS — the base's one leak, carried through eleven patches that add none of their own

This image is the audited `a7b7136a` build with six small layers on top, and I could check that claim from bytes rather than labels: the layer lists nest, the added layers hold 41 source files and three recipe directories, and all 41 files are what you get by applying the published patches to the published tree. That matters because the attestation, though signed, does not say which of six recipes was built, and the first reading of it picked the wrong one.

What the patches add is a host-RAM cache tier, scheduler changes, a loader fix, an indexer optimisation, two moves of blocking work off the event loop, and a diagnostic. I read every runtime hunk. None logs, stores or sends message content. The diagnostic — on by default, and the item most worth worrying about — prints stack frames and nothing from them. The cache tier is memory only, and the code refuses the configurations that would make it otherwise. The claim that the admission-reserve patch is inert when unset is not exact for scheduling and is exact for privacy.

What the patches do not remove is everything the base page found. The glm47 parser still logs a model-emitted argument value at WARNING on a routine formatting slip, and all three recipes still ship that line off-box unredacted: deployed ON, in normal operation, which is why the class is LEAKS. `/configure_logging` is still one unauthenticated POST away from verbatim prompt logging and arbitrary-path pickling. The watchdog still dumps the in-flight batch's token ids on a hang, at 1800 s, on a scheduler that has changed considerably and whose own comments record earlier versions tripping it. The media fetch still has no allowlist.

And two things the base page did not record, found by reading the patched files whole: image-derived tensors pass through `/dev/shm` while every recipe shares the host IPC namespace, and unhandled request exceptions are logged with their message text. Both are LOW; both predate this image.

### Residuals

1. **The glm47 `{value}` warning** is one line in a file this build pipeline already patches around. It has survived three attested rebuilds.
2. **`/configure_logging` is unauthenticated**; reachability from outside depends on `vllm-proxy-rs@d61357da…`, a different image.
3. **Upstream's HiCache code is now on the request path and has not been line-reviewed** by any page in this repo; this page traced its storage gates and swept its logs.
4. **The attestation does not bind the recipe.** For this digest the labels and the layers agree; the next multi-variant digest needs the same check, and resolving identity from workflow name alone will be wrong again.
5. **The base image** `lmsysorg/sglang@sha256:eb090e39…` and the compiled stack it supplies remain unread, and the HiCache patches add new calls into it (`cudaMallocHost`, `transfer_kv_direct`, a Triton kernel).
6. **The two LOW findings new on this page apply equally to `a7b7136a`**, whose page does not list them.
