# SGLang inference engine (GLM-5.3-Flash, near.ai HiCache W4AFP8 build) — Privacy Audit

> Part of the near.ai inference-path privacy audit. Method: [/notes/method.md](/notes/method.md).

**Image:** `nearaidev/sglang@sha256:47aff791090003a37f893e998c44794c410d3f7bdfc7fdd2dfab5eb5592b30bb`
**Source:** `PierreLeGuen/sglang-upstream` @ `fc91d2403cc210a86bd5fc715c6609f58c932e5a` + eleven patch files from three `nearai/cvm-compose-files` recipe directories.
**Role:** the inference engine — the one process legitimately entitled to see message plaintext. It sits behind `nearaidev/vllm-proxy-rs` (`OHTTP_ENABLED=true`) behind nginx; engine port 8000 is not host-published but is reachable on the `external: true` shared Docker network `dstack_default` in all three recipes.

**Citations.** Line numbers in files the patches modify (`http_server.py`, `tokenizer_manager.py`, `scheduler.py`, `schedule_policy.py`, `schedule_batch.py`, `serving_base.py`, `mem_cache/*`) are **post-patch** — the bytes in the image, which no public commit contains — and are given without links. Line numbers in untouched files are those of `fc91d24` and are linked.

**Verdict:** The patch stack adds no path by which message plaintext reaches a log, a file, telemetry or the network. What makes the class LEAKS is inherited:

1. the **glm47 tool-call parser logs a model-emitted argument value verbatim at WARNING** (MEDIUM, deployed ON) — the file is untouched by any patch;

and the paths that keep the rest short of "cannot happen" are also inherited, re-located at the patched bytes:

2. **unauthenticated `/configure_logging`** (CRITICAL, deployed ON) — no `--api-key`/`--admin-api-key` in any of the seven deployed commands;
3. the **watchdog hang dump** (HIGH, deployed ARMED at 1800 s in all seven);
4. the **request-driven media fetch** (MEDIUM, deployed ON) — no `--allowed-media-domains` in any recipe.

New on this page, from sweeping the whole target rather than the hunks: image-derived feature tensors are staged in `/dev/shm`, and every recipe runs the engine with `ipc: host` (LOW); unhandled request exceptions are logged with their message text (LOW). Both are `fc91d24` behaviour the base page did not record.

New in the patches and checked clean: the **event-loop stall dump** (on by default) prints file, line, function and source line per frame — no locals, no task or request reprs; the **HiCache tier** enabled by all three recipes is pinned host RAM only — no storage backend is configured, a startup one would abort the engine, and attaching one at runtime is refused without an admin key.

The priority item for this review, read in full. `http_server.py:396` (post-patch) calls `install_stall_dump(asyncio.get_running_loop())` in the lifespan of the HTTP/tokenizer process — not in the scheduler ranks. With `SGLANG_EVENT_LOOP_STALL_DUMP_SECS` unset (all recipes) it arms at 30 s and repeats every 60 s.

What it writes, exhaustively (`event_loop_stall_dump.py`, new file, line numbers in the image):

- **Python path** (`_dump`, 98–115): a header line of pid, stall age, threshold, dump number, thread count, loop-thread CPU seconds and a UTC timestamp; then for each thread from `sys._current_frames()` its ident and `threading` name, and `traceback.format_stack(frames[ident], limit=200)` (110). `format_stack` builds `FrameSummary` objects without `capture_locals`; each renders as `File "…", line N, in <function>` plus the source line read from disk. **No local variable, argument value, or object repr is formatted.** The frames are discarded after formatting.
- **C fallback** (`_arm_backstop`, 66; and 115): `faulthandler.dump_traceback_later(…, file=2)` and `faulthandler.dump_traceback(file=2, all_threads=True)` — faulthandler emits file name, line number and function name per frame and nothing else, by design (it runs without the GIL and cannot touch objects).
- A recovery line with the stall duration (86), and an arming line at startup with pid and thread ident (38–42).

It does not enumerate `asyncio` tasks, does not print coroutine objects, and does not touch request state. Each line is written with `os.write(2, …)` truncated to 4,000 bytes (117–126). What a dump discloses is *where* the process is stuck and for how long — operational metadata — and it reaches `telemetry.infra.near.ai` like the rest of stderr. Thread names are fixed strings (`event-loop-stall-watch`, `sglang-mm-shm_0`, executor defaults). The shipped `test_stall_dump.py` is not run in the image.

Residual of the mechanism rather than of this code: it registers `os.register_at_fork` hooks and a faulthandler timer in the process that holds plaintext; a future edit that adds `capture_locals=True` or a task dump would turn this INFO into a HIGH with a one-line diff. Worth re-reading on every rebuild.

### INFO (deployed: ON) — HiCache keeps KV state of finished conversations in pinned host RAM; no disk or network tier exists at the deployed flags, a startup one would abort the engine, and a runtime one is refused without an admin key — sink: none (memory only)

All seven commands pass `--enable-hierarchical-cache` (default `False`, [`server_args.py:2721-2723`](https://github.com/PierreLeGuen/sglang-upstream/blob/fc91d2403cc210a86bd5fc715c6609f58c932e5a/python/sglang/srt/server_args.py#L2721)). KV rows — a function of the prompt and the response — are copied from GPU to a host pool and back for prefix reuse across requests. The question the brief asked: does any tier write to disk, a file-backed path, or a network peer?

- **The tier below host RAM is `--hicache-storage-backend`**, choices `file`, `mooncake`, `hf3fs`, `nixl`, `aibrix`, `eic`, `simm`, `mori`, `shm`, `sim`, `dynamic`; default `None` ([`server_args.py:2772-2791`](https://github.com/PierreLeGuen/sglang-upstream/blob/fc91d2403cc210a86bd5fc715c6609f58c932e5a/python/sglang/srt/server_args.py#L2772)). **No recipe passes it.** With `None`, `init_hicache` skips storage configuration (`unified_radix_cache.py:435`, `:446`, `:524`, post-patch) and `enable_storage` stays `False` (386); the hybrid controller attaches a backend only `if startup_storage_backend is not None` ([`hybrid_cache_controller.py:140`](https://github.com/PierreLeGuen/sglang-upstream/blob/fc91d2403cc210a86bd5fc715c6609f58c932e5a/python/sglang/srt/mem_cache/hybrid_cache/hybrid_cache_controller.py#L140)). `hicache_host_memory_mode` defaults to `cache`; `buffer_only` requires a backend.
- **The patch makes a startup backend a startup failure here.** Every recipe sets `SGLANG_HICACHE_RAM_BUDGET`, and with it set `startup_ram_budget` raises `"RAM budget currently supports in-CVM host RAM only"` if `hicache_storage_backend is not None` (`mem_cache/startup_ram_budget.py:205-206`, new file), and separately `"Compressed DSA currently supports L2 HiCache only"` when the tree and transfer page sizes differ (`unified_radix_cache.py:436-440`). So adding the flag to these recipes does not silently enable a disk tier; it stops the engine.
- **The runtime attach route is refused.** `PUT /hicache/storage-backend` (`http_server.py:1098-1108`, post-patch) returns `_admin_api_key_missing_response()` when `admin_api_key` is unset — which it is — before doing anything; `DELETE` and `GET` likewise (1139, 1163). This is the one place where the engine's missing admin key *closes* a path.
- **The host pool itself is RAM.** With `SGLANG_HICACHE_CUDA_HOST_MEMORY=1` (all recipes) `alloc_with_host_register` calls `_alloc_cuda_host` (`pool_host/common.py:572-579`, post-patch), which is `cudaMallocHost` through `ctypes` and a `torch.frombuffer` view (305–347) — page-locked anonymous memory — and raises unless the allocator is the in-process `HostTensorAllocator` (the `shm`-backed allocator is selected only when the storage backend is `shm`, `common.py:439-444`). The pooled transfers (`pooled_pages.py`, `pooled_l2.py`) move bytes between that buffer, a GPU staging tensor and the device pool; nothing else.
- **`--enable-unified-cache-external-linker`** ("direct L3, with no host cache tier") is absent, default `False`.

So: OFF for disk and network at the deployed flags, and guarded twice against being turned on without a redeploy that changes the measured recipe. What *is* new is retention: 325–650 GiB of pinned RAM per replica (80% of available RAM on `small-models`) holding KV for conversations that have ended, for as long as the entries survive eviction. It stays inside the CVM. It widens what a memory image would contain (crash-diagnostics LOW), and it lengthens the window over which `--enable-cache-report`'s cached-token count in `usage` reflects other callers' earlier prompts — a prefix-probing side channel that exists with any shared prefix cache and that I note, not rate.

### INFO (deployed: ON, one recipe) — the admission-reserve patch is not inert for scheduling when its env var is unset, and is inert for plaintext either way — sink: log (integer counts only, behind an unset debug env)

The Dockerfiles, the workflow summary and two recipe comments say the patch "is inert unless `SGLANG_CHUNKED_PREFILL_ADMISSION_RESERVE > 0`". Read against the code, in this chain's copy of the diff (byte-identical to the plain recipe's):

- **What it means for this audit:** nothing reaches a sink. The patch's only log statements are two `INFO` lines of integers, both behind `SGLANG_ADMISSION_RESERVE_DEBUG=1` (`schedule_policy.py:1027-1030`, `scheduler.py:3989-3990`), which no recipe sets; neither carries a request id, a prompt length tied to a request, or token ids. The claim matters as a rollback assumption ("unset the variable to get upstream behaviour"): that assumption is not exact. It belongs on the recipe pages as a behaviour note; it does not move this verdict.

### Verdict: LEAKS — the base's one leak, carried through eleven patches that add none of their own

This image is the audited `a7b7136a` build with six small layers on top, and I could check that claim from bytes rather than labels: the layer lists nest, the added layers hold 41 source files and three recipe directories, and all 41 files are what you get by applying the published patches to the published tree. That matters because the attestation, though signed, does not say which of six recipes was built, and the first reading of it picked the wrong one.

What the patches add is a host-RAM cache tier, scheduler changes, a loader fix, an indexer optimisation, two moves of blocking work off the event loop, and a diagnostic. I read every runtime hunk. None logs, stores or sends message content. The diagnostic — on by default, and the item most worth worrying about — prints stack frames and nothing from them. The cache tier is memory only, and the code refuses the configurations that would make it otherwise. The claim that the admission-reserve patch is inert when unset is not exact for scheduling and is exact for privacy.

What the patches do not remove is everything the base page found. The glm47 parser still logs a model-emitted argument value at WARNING on a routine formatting slip, and all three recipes still ship that line off-box unredacted: deployed ON, in normal operation, which is why the class is LEAKS. `/configure_logging` is still one unauthenticated POST away from verbatim prompt logging and arbitrary-path pickling. The watchdog still dumps the in-flight batch's token ids on a hang, at 1800 s, on a scheduler that has changed considerably and whose own comments record earlier versions tripping it. The media fetch still has no allowlist.

And two things the base page did not record, found by reading the patched files whole: image-derived tensors pass through `/dev/shm` while every recipe shares the host IPC namespace, and unhandled request exceptions are logged with their message text. Both are LOW; both predate this image.

**2. What a slot holds, and where.** A slot is one row, per KDA layer, of two tensors: `temporal`, shape `(num_heads / TP, head_dim, head_dim)` = (32, 128, 128) at TP2, the recurrent delta-rule memory folded over every token the sequence has seen; and `conv`, shape `(3, 12288)` at TP2, the last three pre-activation q/k/v projections of that layer's input (`configs/mamba_utils.py:294-301`; `mem_cache/memory_pool.py:584`, `:609-611`). The backend reads and writes both in place on every prefill, decode and verify step (`layers/attention/linear/kda_backend.py:807-810`). Both are functions of the prompt and the generated text and nothing else — content-derived exactly as KV is; the `conv` rows are a linear image of the last three positions' hidden states. The flag does not change what a slot holds, only how many rows exist and the width of `temporal`'s elements: about 36 MiB per slot per rank in bfloat16 against about 70 MiB in float32 (`configs/mamba_utils.py:115-125`, 34 layers).

- **GPU.** `MambaPool` allocates `size + 1` rows (166) of each tensor on the rank's device ([`mem_cache/memory_pool.py:584`](https://github.com/PierreLeGuen/sglang-upstream/blob/fc91d2403cc210a86bd5fc715c6609f58c932e5a/python/sglang/srt/mem_cache/memory_pool.py#L584), `:609-611`), and — because EAGLE is on — a per-draft-token scratch of `(max running + 1) x D` further copies of `temporal` in the same dtype (`:741-752`; `kv_cache_configurator.py:1099`, `:1110-1114`), `D` being the largest draft-token count speculative decoding may use — 6 by `--speculative-num-draft-tokens`; whether `--speculative-adaptive` raises it I did not resolve. At `D` = 6 that is 33 x 6 at this revision against 16 x 6 before: roughly 6 GiB of state rows and 6.7 GiB of scratch per rank now, against roughly 5.5 and 6.5 before; the KV pool pays for the difference (`kv_cache_configurator.py:2361-2366`, `:2448-2453`), which is the recipe header's 1.08M to 1.0M tokens. `--enable-unified-memory` is absent and defaults to `False` (`server_args.py:870-878`), so `unified_memory_pool.py` — one of the ten files that read the flag — constructs nothing here (`kv_cache_configurator.py:435`).
- **Host RAM.** Yes, the host tier holds this state too. `build_hybrid_mamba_stack` builds a `MambaPoolHost` beside the KV host pool (`hybrid_pool_assembler.py:896-902`, post-patch), with `temporal` and `conv` buffers in the device tensors' dtypes (`pool_host/mamba.py:76`, `:156-181`, post-patch). They are allocated by the same function as the KV host pool — `ALLOC_MEMORY_FUNCS[device]` is `alloc_with_host_register` (`pool_host/mamba.py:138`; `pool_host/common.py:609-615`), which at `SGLANG_HICACHE_CUDA_HOST_MEMORY=1` returns `_alloc_cuda_host`, i.e. `cudaMallocHost` (`pool_host/common.py:553-579`, `:305-323`, post-patch) — so it is pinned anonymous memory in the engine process, not a file or a shared-memory segment. The RAM budget is split between the KV and state host pools in proportion to their device pools' bytes (`hybrid_pool_assembler.py:173-186`, `:857-861`), so the flags move the split: the recipe header's 5.87M to 5.4M KV tokens in the 325 GiB tier is the state pool taking a larger share, and at half the bytes per slot that share holds proportionally more checkpoints. I did not compute the host slot count; the engine prints only its size in GB.
- **Lifetime.** A slot is not freed when its request finishes. With the overlap scheduler on, this architecture resolves to the `extra_buffer` strategy (`arg_groups/overrides.py:537`, `:549-553`, `:588-594`): each running request owns a working slot plus two ping-pong checkpoint slots (`mem_cache/memory_pool.py:1227`, `:1362`, `:1466-1495`); at finish the most recent checkpoint slot is *donated* to the radix tree as the cached state for that prefix (`mem_cache/unified_cache/components/mamba_component.py:567-580`, post-patch) and, when the tree took it, only the others return to the allocator (`:642-651`; `memory_pool.py:1532-1537`). A later request that matches the prefix copies the checkpoint into its own slot (`mamba_component.py:187-216`). A retained checkpoint is dropped from the GPU only when the allocator is empty and something needs a slot — LRU eviction through `evict_for_alloc(mamba_num=…)` (`mamba_component.py:493-500`, `:322-338`) — and with HiCache its host copy survives that and is evicted separately, again LRU and again only under allocation pressure (`:870-922`). I found no time-based expiry in the component, the host pool or the allocator.
- **Freed is not erased.** `MambaSlotAllocator.free` appends the index to a free list (`mem_cache/allocator/mamba.py:88-91`); the rows are zeroed when the *next* owner is admitted without a cached prefix (`memory_pool.py:1367`; `managers/schedule_batch.py:2927-2929`; `memory_pool.py:962-990`) or overwritten by a copy. The host pool's `free` likewise only queues indices (`pool_host/mamba.py:271-278`).
- **What 165 changes.** The default is not a constant: with the flag unset and speculative decoding on, the engine solves `K = (budget - per_req x (1 + D)) // (per_req x (1 + D / ratio))` with `budget = rest x r / (1 + r)`, `r = --mamba-full-memory-ratio` 0.9, `D` = 6 draft tokens and `ratio` = 5 (`kv_cache_configurator.py:2394-2411`). The 77 in the recipe's old header is that formula's output on this hardware; it is consistent with the source (about 12 GiB of budget at float32) but I cannot derive it without the free-memory figure. Setting 165 more than doubles the number of rows — so, at low load, the number of finished conversations whose state is still resident on each GPU — while the bytes on GPU stay about the same, because each row is half the size. In host RAM the count grows by the dtype halving and by the larger share of the budget together.
- **Disk or network.** None at the deployed flags, and the gates the page established for KV cover this pool because they sit above the pools, not inside the KV one. The state host pool does implement the page-export interface a storage backend would use (`pool_host/mamba.py:225-227`, `:508-537`, `:539`), and the component does build `BACKUP_STORAGE` and `PREFETCH` transfers for `PoolName.MAMBA` (`mamba_component.py:773-795`). In `unified_radix_cache.py` those phases are entered from `write_backup_storage` and `prefetch_from_storage` (`:1706`, `:1858-1868`, post-patch) and from the completion of a prefetch the latter started (`:2062`); both functions return at once unless `enable_storage` is set (`:1691-1693`, `:1790-1791`; also `:1530`). The controller's `write_storage` has two other callers and both are off: the PD-disaggregation decode offload manager, built only when `--disaggregation-mode decode` and `--disaggregation-decode-enable-offload-kvcache` are both set (`managers/scheduler.py:669-674`, post-patch; defaults `"null"` and `False`), and the buffer-mode pipeline, built only for `--hicache-host-memory-mode buffer_only` (`unified_radix_cache.py:473-480`; default `cache`, `server_args.py:2724-2731`), which startup rejects without a backend (`arg_groups/hicache_hook.py:205-210`). `enable_storage` starts `False` (`:386`) and becomes `True` in one place, inside `attach_storage_backend` (`managers/cache_controller.py:520`, `:569`) — the same function that creates the backend object (`:563-567`) and starts the storage threads (`:606`) — which the hybrid controller calls at startup only `if startup_storage_backend is not None` (`hybrid_cache/hybrid_cache_controller.py:139-146`) and which the runtime route refuses without an admin key (`entrypoints/http_server.py:1098-1108`, post-patch). The remaining callers of the page-export methods are those storage threads (`managers/cache_controller.py:1016-1035`, `:1243-1248`), `mem_cache/hicache_storage.py` and the backend modules under `mem_cache/storage/`: backend code, which I did not trace module by module and which has nothing to run in until that attach happens. `--hicache-storage-backend` is still absent at `e3c487c7…`, and with `SGLANG_HICACHE_RAM_BUDGET` set, adding it stops the engine (`mem_cache/startup_ram_budget.py:205-206`). The shared-memory host allocator is selected only for backend `shm` (`pool_host/common.py:439-454`). `--enable-int8-mamba-checkpoint` (a second, int8 checkpoint pool) is absent, defaults to `False` (`server_args.py:2646-2650`) and is rejected together with HiCache (`arg_groups/mamba_hook.py:84-89`).

**3. The running cap — the recipe's arithmetic is right.** `resolve_max_num_reqs` starts from `--max-running-requests` (32) and applies `mamba_cap = max_mamba_cache_size // ratio` (`mem_cache/kv_cache_configurator.py:2189-2192`, `:2198-2213`). `ratio` is `_calculate_mamba_ratio()` (`:2122-2151`): base 3 (`:166`; `SGLANG_OPT_MAMBA_SKIP_DECODE_LOCK` is `False` by default, `environ.py:1299`, and unset in the recipe) plus 2 for the extra-buffer strategy under the overlap scheduler (`:168`, `:2135-2139`) = **5 slots budgeted per running request**. Nothing on this command disables the overlap scheduler: the resolvers in `arg_groups/` that write `disable_overlap_schedule` are for CPU and MPS devices, pipeline parallelism, diffusion models, an embedding sparse head, and the `no_buffer` fallback, none of which applies. So 77 // 5 = **15** and 165 // 5 = 33, which no longer binds: the cap is the flag's **32**. The dtype is not an input to the cap; it is what makes 165 rows fit in about the memory 77 took. The resolved value reaches the scheduler through `get_worker_info()` (`model_executor/model_runner.py:898`; `managers/scheduler.py:1181-1183`) and the request pool is built with exactly that many rows (`kv_cache_configurator.py:1096-1097`).

**What this does to the page's HIGH (ARMED) watchdog finding** — the heading "watchdog hang dump writes the full prompt and output token IDs of the in-flight batch to stdout at ERROR". ### INFO (deployed: ON) — the HiCache host tier holds recurrent linear-attention state as well as KV: checkpoints of finished conversations stay in GPU memory and in pinned host RAM until LRU eviction, freed slots are not zeroed, and the storage gates that keep KV off disk and network sit above this pool too — sink: none (memory only)

This is not caused by the two flags; reading them is what surfaced it. The page's HiCache INFO speaks of KV rows only. On this model the host tier is a three-pool stack — the engine's own startup line says `pools=KV + MAMBA + INDEXER` (`hybrid_pool_assembler.py:1942-1946`, `:1552`, post-patch) — and the second pool is the state described in item 2 above: per cached prefix, the 34 KDA layers' recurrent memory and their last three short-conv inputs. Everything the page says about the KV host pool's allocator, about `--hicache-storage-backend` being absent, about a startup backend aborting the engine and a runtime one being refused, holds for the state pool for the reasons given under "Disk or network" above, each re-read at these bytes rather than inherited.

What is specific to this pool:

- **It is retained on GPU as well as in host RAM.** Donation at finish (`mamba_component.py:567-580`) keeps the checkpoint row in the device pool until the allocator runs dry. On an idle replica that is up to `max_mamba_cache_size` rows of ended conversations per GPU — 165 on TP2x4 now, a startup-solved number elsewhere.
- **Eviction is by pressure only**, device and host separately (`mamba_component.py:322-358`, `:870-922`); a row's bytes outlive its eviction until the slot is reused (`mem_cache/allocator/mamba.py:88-91`; `managers/schedule_batch.py:2927-2929`).
- **The patch stack's changes to this pool are two lines of sizing** — `host_page_count` and `reserve_startup_bytes` in `pool_host/mamba.py` (`:87`, `:114`), which make the pool respect the RAM budget — and a guard in `mamba_component.py:538-547` that declines to publish a checkpoint whose length does not match its key. Neither adds a sink.

**Recipes.** Established here for TP2x4 at `e3c487c7…`. The other two recipes on this page run the same checkpoint with `--enable-hierarchical-cache` and `SGLANG_HICACHE_RAM_BUDGET`, and the budget code raises unless the stack is this KV+Mamba one (`mem_cache/startup_ram_budget.py:193-200`; `hybrid_pool_assembler.py:1964`), so the pool exists there too; I did not re-read their commands for flags that would change the slot strategy, and their slot counts are whatever the startup solve produced.

Rated INFO for the same reason as the page's KV finding: structural retention inside the CVM, no path out at the deployed flags. It widens what a core image or a CUDA core dump would contain and it is state a storage backend, if one were ever attached, would ship alongside KV.
