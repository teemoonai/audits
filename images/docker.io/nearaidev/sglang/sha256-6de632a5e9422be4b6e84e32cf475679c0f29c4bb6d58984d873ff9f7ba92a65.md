### HIGH (deployed: ON, conditional) — the qwen3_coder tool-call parser logs a model-written argument value verbatim at WARNING whenever it does not parse as its declared type — sink: log (egress to near.ai)

Both Qwen services pass `--tool-call-parser qwen3_coder` (`:76`, `:1010`), which selects `Qwen3CoderDetector` (`function_call/function_call_parser.py:105`). The file is untouched upstream code, the same bytes as in the sibling image, where it is not selected.

`function_call/qwen3_coder_detector.py`, `_convert_param_value` (`:101-176`), is called for every parameter of every tool call the model emits, on the non-streaming path (`:221`) and the streaming path (`:361`). It interpolates the value into a WARNING in five branches:

- `:130-133` — declared integer, `int()` fails: `Parsed value '{param_value}' of parameter '{param_name}' is not an integer in tool '{func_name}', degenerating to string.`
- `:144-147` — declared number or float, `float()` fails.
- `:152-154` — declared boolean, value is neither `true` nor `false`.
- `:166-169` — declared object or array, `json.loads` fails.
- `:173-175` — any remaining type, `ast.literal_eval` fails.

No truncation, no level gate beyond WARNING, no flag. Two more lines name identifiers only: an undeclared tool name (`:91`) and an undeclared parameter name (`:111-114`).

**Executed.** I lifted `_get_param_type` and `_convert_param_value` with the real helpers from `function_call/utils.py` and called it with a tool schema of one integer, one array, one boolean and one number parameter:

```
WARNING Parsed value 'my SSN is 078-05-1120' of parameter 'count' is not an integer in tool 'save_note', degenerating to string.
WARNING Parsed value '[the patient said: chest pain since Tuesday' of parameter 'items' cannot be parsed with json.loads in tool 'save_note', will try other methods to parse it.
WARNING Parsed value '[the patient said: chest pain since Tuesday' of parameter 'items' cannot be converted via Python `ast.literal_eval()` in tool 'save_note', degenerating to string.
WARNING Parsed value 'maybe, see diary entry' of parameter 'flag' is not a boolean (`true` of `false`) in tool 'save_note', degenerating to false.
WARNING Parsed value 'about forty' of parameter 'price' is not a float in tool 'save_note', degenerating to string.
```

**Trigger, as a path.** A chat request with `tools`; the model emits `<tool_call><function=NAME><parameter=P>VALUE</parameter>…`; `P` is declared in the tool's schema with a non-string type; `VALUE` does not parse as that type. Nothing constrains the value: `SGLANG_TOOL_STRICT_LEVEL` is `OFF` (`environ.py:812`) and unset in every recipe. The object and array branch is the likely one in practice: a model that writes a Python-style dict or slightly malformed JSON for an object parameter gets the whole value logged before the fallback parses it. The value is model output, and tool arguments routinely restate what the user said.

**Where it goes.** Engine stdout, then the telemetry pipeline (MEDIUM below). This is why the page is LEAKS: reply content reaches a log and leaves the CVM at the deployed flags, with no operator action.

**Scope.** One argument value per occurrence, only on tool-using requests, only on a type mismatch. Patch 15 fixed the same pattern in the glm4 detector (`Failed to parse {fingerprint(value)} as number`) and not here.

## Verdict

**LEAKS**, narrowly, and not because of anything the three patches do.

The image is what it says: upstream v0.5.23 with three small security patches, and I could check that from bytes — the layers nest on upstream's image, and every file the patches change is what the published patches produce. Those patches are the same bytes the sibling page read; they redact credentials and a list of log lines.

The class comes from what is deployed on it. Both Qwen services select the `qwen3_coder` tool parser, and that parser prints a model-written argument value to the log whenever it does not match the declared type. I ran the function and it does. The log leaves the CVM unredacted. That is reply content off-box at the deployed flags, on a trigger that ordinary tool use produces. And the FLUX service is a different program inside the same image; it saves each generated image to its container's disk by default, and the recipes do not turn that off.

Everything else is the sibling's posture at this tree's line numbers: an unauthenticated logging switch, a watchdog that dumps token ids — armed here at the 300 s default — and stdout shipped off-box. The sibling's new machinery (ghost cache, stall dump, preprocessing pool) is absent.

Not PRIVATE: a sink receives model output at the deployed flags without any operator action. Not INCONCLUSIVE: identity and source are established. The two HIGHs each have a one-line remedy in the table above.
