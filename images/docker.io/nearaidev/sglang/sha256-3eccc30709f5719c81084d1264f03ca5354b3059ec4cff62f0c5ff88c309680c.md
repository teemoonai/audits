### INFO (deployed: ON) — HiCache keeps KV and recurrent state of finished conversations in pinned host RAM; no disk or network tier exists at the deployed flags, a startup one would abort the engine, and a runtime one is refused without an admin key — sink: none (memory only)

The priority item for this image, read at these bytes rather than carried from 47aff791. `--enable-hierarchical-cache` (recipe `:488`; default `False`, `server_args.py:2721-2723`): KV rows — a function of the prompt and the response — and, on this model, the KDA layers' recurrent state (the 47aff791 addendum's `pools=KV + MAMBA + INDEXER`, `hybrid_pool_assembler.py:1552` here) are copied from GPU to a host pool and back for prefix reuse across requests. **`write_through`** (`:489`; `server_args.py:2742-2749`) writes every new page to host as it is produced, not only on eviction. The question: does any tier write to disk, a file-backed path, or a network peer?

- **The tier below host RAM is `--hicache-storage-backend`** (choices `file`, `sim`, `mooncake`, `hf3fs`, `nixl`, `aibrix`, `dynamic`, `eic`, `simm`, `mori`, `shm`; default `None`, `server_args.py:2772-2791`). **The recipe does not pass it.** With `None`, `init_hicache` skips storage configuration (`unified_radix_cache.py:435`, `:446`, `:524`, post-patch) and `enable_storage` stays `False` (`:386`); the hybrid controller attaches a backend only `if startup_storage_backend is not None` (`hybrid_cache_controller.py:140`, untouched). `--hicache-host-memory-mode` defaults `cache` (`server_args.py:2724-2731`); `buffer_only` is rejected without a backend (`arg_groups/hicache_hook.py:205-210`).
- **The patch makes a startup backend a startup failure here.** The recipe sets `SGLANG_HICACHE_RAM_BUDGET` (`:518`); with it set, `startup_ram_budget` raises `"RAM budget currently supports in-CVM host RAM only"` if `hicache_storage_backend is not None` (`startup_ram_budget.py:205-206`), and separately `"Compressed DSA currently supports L2 HiCache only"` when the widened tree page differs from the transfer page (`unified_radix_cache.py:436-440`). The budget's failure mode is collective: every rank's record is gathered (`:211`) and `resolve_budget` raises on any error (`:132-136`), so one rank's refusal stops all four.
- **The runtime attach route is refused.** `PUT /hicache/storage-backend` (`http_server.py:1092-1102`, untouched) returns `_admin_api_key_missing_response()` when `admin_api_key` is unset — which it is — before doing anything; `DELETE`/`GET` likewise (`:1133-1134`, `:1157-1158`). And the patched attach path adds its own refusal for this model (`unified_radix_cache.py:2766-2767`, `"Compressed DSA currently supports L2 HiCache only."`). This is the one place where the engine's missing admin key *closes* a path.
- **The host pool itself is RAM.** With `SGLANG_HICACHE_CUDA_HOST_MEMORY=1` (`:519`), `alloc_with_host_register` (`pool_host/common.py:553-579`) routes to `_alloc_cuda_host` (`:305-349`): `cudaMallocHost` through `ctypes` (`:322-323`), a `torch.frombuffer` view over the returned pointer (`:332-333`) — page-locked anonymous memory owned by the CUDA runtime — and it raises unless the allocator is the in-process `HostTensorAllocator` (`:572-579`; the `shm`-backed allocator is selected only when the storage backend is `shm`, `:439-454`). `_alloc_cuda_managed` (`:229-302`, `cudaMallocManaged` + `cudaMemAdvise`) is the alternative behind `SGLANG_HICACHE_CUDA_MANAGED_MEMORY` (`:580-587`), unset; the two are mutually exclusive (`:567-571`). The pooled transfers (`pooled_pages.py`, `pooled_l2.py`) move bytes between that buffer, a GPU staging tensor of `SGLANG_HICACHE_STAGING_PAGES` pages and the device pool (`pooled_pages.py:99-127`: `transfer_kv_direct` at `:110` and `:127`, `_pages_kernel` at `:117`); `PooledL2` asserts `io_backend == "direct"` (`pooled_l2.py:24`) and the recipe passes exactly that (`:490`), with `page_first_direct` (`:491`) as `_buffers` requires.
- **The budget reads and never writes.** `cgroup_headrooms` (`startup_ram_budget.py:38-101`) reads `/proc/self/cgroup`, `/proc/self/mountinfo` and cgroup `memory.max`/`memory.current` (v1 equivalents); `available_ram_bytes` (`:104-109`) takes the minimum with `psutil.virtual_memory().available`; `parse_budget` (`:24-31`) accepts `%`, `GB`, `GiB`; 10 GiB reserved (`:19`); the result is set as `hicache_size` through `get_context().override` (`:213`) and logged as byte counts (`:214-225`, `:227-231`). `host_page_count` rounds pools *down* to the budget (`:163-169`; `pool_host/base.py:166`, `pool_host/mamba.py:87`), `reserve_startup_bytes` (`:158-160`) claims each pool against it and `claim` raises if exceeded (`:126-128`; callers `memory_pool_host.py:225`, `pool_host/base.py:213`, `pool_host/mamba.py:114`).
- **`--enable-unified-cache-external-linker`** absent; and the patched `init_cache_linker` refuses for this model anyway (`unified_radix_cache.py:364-369`).

So: OFF for disk and network at the deployed flags, and guarded three times against being turned on without a redeploy that changes the measured recipe. ## Verdict

**PRIVATE at the deployed flags** — this image is the audited `a7b7136a` build with four small layers on top, and I could check that claim from bytes rather than labels, through an intermediate that has no page: the layer lists nest, the added layers hold two recipe directories and 32 source and test files, and all 32 are what you get by applying the published patches to the published tree in the published order.

What the patches add is a host-RAM cache tier with two CUDA-owned allocators, a startup budget, pooled transfers, a compressed-index sidecar, and the admission-reserve scheduler change. I read every runtime hunk. None logs, stores or sends message content. The cache tier is memory only, and the code refuses — at startup, at runtime, and in the attach path — the configurations that would make it otherwise. The admission patch is inert for plaintext and not quite inert for scheduling.

What the patches do not remove is everything the base page found, each re-located at these bytes — and because this chain stops before the w4afp8 layer, four of the base's hot files are the base's exact bytes here, so the CRITICAL, the DEBUG LOW and the exception LOW sit at the base page's own line numbers. `/configure_logging` is still one unauthenticated POST away from verbatim prompt logging and arbitrary-path pickling. The watchdog still dumps the in-flight batch's token ids on a 1800 s hang. The media fetch still has no allowlist. Image tensors still transit `/dev/shm` under `ipc: host`, and the one later patch that narrowed that is absent here.

**No path at the deployed flags writes prompt text, reply text or token ids to a log, a file, a socket or an exporter in normal operation.** That is the method's PRIVATE condition (§6), with the qualifier this repo attaches to every sglang engine page that meets it — *at the deployed flags, and not "cannot happen"*. Not LEAKS, not COMPROMISABLE, not QUALIFIED PASS, for the reasons the base page gives.

**Deployment.** One recipe declares this image, for one service, brought up once on gpu23 at 2026-09-29T15:56:49Z (entry 118); 58 minutes later the W4AFP8-LongContext file's TP4 pair took the same eight GPUs at the same memory fraction (entry 120). Under either reading of a log that records no compose project (the recipe page states both), this image has not served on gpu23 since 2026-09-29T16:54:38Z. The class above is the class of the bytes at the declared flags.
