### MEDIUM (deployed: OFF, one label value in a model recipe away) — telemetry egress: the filter trusts a label each container declares for itself, so a recipe that labels an engine as a management service sends that engine's stdout to the exporter

`transform/docker_metadata` takes `service.name` from the container's own labels (`:125-126`), and `filter/management_logs` decides on that value alone (`:134`). The collector has no list of container ids, image digests or compose projects; it cannot tell the harness's `compose-manager` from a model-layer container that says it is `compose-manager`.

Reachable path: a model-layer recipe in which an engine or proxy service carries `com.datadoghq.ad.logs: '[{"service":"compose-manager", …}]'` (the recipes already put this label and the matching log option on every service), or carries no such label and is itself named `compose-manager` (`:125` then decides), deployed through the manager's `/compose/up` by a bearer-token holder. From then on every stdout line of that container passes the filter and is exported unredacted. No measurement changes; the recipe hash does, and the manager records the deploy in its action log. Whether that stdout holds message text is decided by the engine's flags, which the same recipe sets.

**OFF at the deployed recipes:** every label value on the three hosts is outside the keep-list (table above), and no file revision either action log has ever brought up names one of the three (40 of 40 read). The condition fails closed for a container with no labels in its log (`service.name` stays `cvm-docker`, `:31-33`) and for a line that does not parse (`on_error: send_quiet`, `:15`; the name is then `cvm-docker` or absent, and both satisfy the drop condition). Container output cannot forge `attrs`: Docker writes the outer json object and the container's bytes sit escaped inside its `log` string.

Given the sibling collector above already exports engine stdout from these hosts, this path adds a second route more than a new exposure — except on `glm-5-3-flash-long`, where it would also be a route to a different gateway (`telemetry-stg`). It is recorded because this pipeline is the one described as management-only (`e390…:3`), and that property holds by convention between two files, not by anything the collector checks.

**Recommended fix:** filter on something the labelled container cannot choose — the compose project (`com.docker.compose.project` = `dstack`) together with the service name, or container names resolved from the Docker API.

### MEDIUM (deployed: ON, capability; unused by the measured configuration) — egress: the node's off-node exporter runs as root with the Docker socket and the whole guest root filesystem

Three grants in the measured block, the same lines in both harnesses, none of which the configured receivers need in full:

- `user: "0:0"` (`:8`) over an image built to run as `10001`.
- `/var/run/docker.sock` (`:21`). The `:ro` flag makes the socket's inode read-only; it does not make the Docker API read-only. A process that can connect can list, inspect, exec into and create containers. The `docker_stats` receiver is configured for stats and inspection only (`config.yaml:55-74`).
- `/:/hostfs:ro` (`:25`): the guest root, which contains the decrypted env file other services mount (`/dstack/.host-shared/.decrypted-env`, `:123`, `:161`), Docker's data root with every volume and every container's rotated logs, and the `work` volume. `hostmetrics` uses it to read `/proc`, `/sys` and mount tables.

At this configuration the binary reads the log files, the metric sources and the Docker stats endpoints, and nothing else was found that reads further. The capability matters for the HIGH above: a replacement image inherits all three, and it is the one harness container whose purpose is sending data out. It is the reason this image is in scope.

**Recommended fix:** mount `/proc`, `/sys` and the specific paths `hostmetrics` needs instead of `/`; put a read-only Docker API proxy in front of the socket; run as a non-root user with group access to the log directory.

### LOW (deployed: ON, content-free at the deployed engine flags) — disk: the log receiver keeps the first 1000 bytes of every container's current json log, the engine's and the proxy's included, in its checkpoint on a persistent volume

`filelog` identifies files by a fingerprint of their first bytes: `DefaultSize = 1000` (`pkg/stanza/fileconsumer/internal/fingerprint/fingerprint.go:20` at contrib `v0.165.0`; `fingerprint_size` is not set in this config). The fingerprint is a field of the per-file `Metadata` (`internal/reader/reader.go:31-32`), and `checkpoint.Save` (`internal/checkpoint/checkpoint.go:24-25`) writes every file's metadata to the storage extension with the raw bytes included (`internal/checkpoint/checkpoint_protobuf.go:43`, `:82-84`: `FirstBytes: rmd.Fingerprint.Bytes()`). With `storage: file_storage` (`config.yaml:5`) that is `/var/lib/otelcol-management/storage` on the named volume (`e390…:27`).

**Correction to the base page, same conclusion:** it described the stored form as the JSON field `first_bytes` (`fingerprint.go:130`). At `v0.165.0` that JSON form is only the read-side fallback for older checkpoints; the write path is the protobuf one cited above. The bytes stored are the same.

The fingerprint is taken **before** any operator or filter runs, for every file the glob matches, so it covers the dropped services too. A json log starts with whatever the container printed first after start or after its 100 MB rotation. Trigger for message content: an engine or proxy that logs request text, and such a line falling at the head of a log file. At the declared flags the engines do not log requests (`f392013b…:273`; `933f971f…:364`), so the bytes are startup and access lines. Bounded: 1000 bytes per container, replaced on rotation, never exported. It is a second copy on a volume that outlives the container whose log it came from.

The exporter's persisted queue (`config.yaml:154-157`) holds only post-filter batches: the three management services' lines and metrics.

### LOW (deployed: OFF, needs an operator-set env value; read at source, not executed) — telemetry egress: the collector expands configuration values recursively, so a ${file:…} reference placed in one of the five operator-settable env values would be resolved by a root process with the guest filesystem mounted

The config takes five values from env names in `allowed_envs` (`config.yaml:93`, `:96`, `:99`, `:102`, `:152`). Collector core `v0.165.0` re-expands a value until it stops changing (`confmap/expand.go:28-40`, `expandValueRecursively`, up to 1000 passes; `findAndExpandURI` `:152-190`), and the contrib distribution registers the `env`, `file`, `http`, `https` and `yaml` providers among others (`manifest.yaml:267-276`). Read together: an env value that is itself `${file:/hostfs/…}` would be replaced by that file's content at startup and exported as a resource attribute on every record, to the fixed destination. A whole-field value can only replace that one field, so it cannot add a pipeline or an exporter.

For messages this matters only if a file on the guest holds message text, which at the declared flags none is known to (an engine json log would, if request logging were on). It needs no image swap and changes no measurement. **Not executed:** whether compose's own interpolation passes such a value through unchanged, and whether the resource processor accepts the result, were not tested. Values set through the manager API are restricted to `A-Za-z0-9+/=_.~-` (compose-manager `README.md:379` at `77abaec8`) and cannot carry the syntax; values in the sealed CVM env are not restricted by anything read here.

**Recommended fix:** none needed in the config if the five values are validated where they are set; otherwise drop the unused confmap providers from the build.

## Verdict: QUALIFIED PASS — the same collector as 3a9ac823, rebuilt; management logs and metrics only at the measured configurations; the configuration is the only thing that makes it so

**What changed since the base page:** the digest (a rebuild), the commit the attestation names, the measured harnesses that name it, and on one of three hosts the gateway it exports to. **What did not:** the config, the Dockerfile, the base image, the build job, the launcher mechanism, `allowed_envs`.

**What it can read:** every container's json log, the Docker API, the guest root filesystem, as root. **What it does to it:** one filter, keyed on a self-declared label, keeps three management services; no redaction. **Where it sends it:** one host per node, fixed in the measured compose. **Can it change after attestation:** yes — the image, and with it the filter and the exporter list, by the launcher at runtime (not at boot); the token and four attribute values by env. The endpoint variable and the command cannot change without a new measurement.

**Why not PRIVATE:** the collector binary is an upstream release tied to its source by a label; the control that keeps engine and proxy stdout on the node is a string comparison against values the model-layer recipes choose; and the same node runs a second collector that exports that stdout anyway.

**Why not COMPROMISABLE on this page:** this image contains no mechanism for changing itself, no route, and no listener. The mechanisms are the launcher's and the manager's, and their pages carry that class.
