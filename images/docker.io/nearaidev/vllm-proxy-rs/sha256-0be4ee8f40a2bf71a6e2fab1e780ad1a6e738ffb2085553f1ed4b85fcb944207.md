### LOW (deployed: ARMED, legacy v1/v2 clients, client-opt-in) — reply fields outside the legacy encrypted set can carry prompt tokens or text in plaintext to the client through the gateway (network egress, in transit past cloud-api)

**Pre-existing in the base tree, not recorded on the base pages; surfaced by this delta's own fix.** For a request sent with `X-Encryption-Version` 1 or 2, the response transform encrypts only the enumerated content fields and **passes every other key of the engine's reply through unchanged** — the SSE transformer's comment says so for choice-level extras such as `matched_stop` ([`src/proxy.rs#L2343`](https://github.com/nearai/inference-proxy/blob/53d79441487089b069de775b63cfe975cd1abb4d/src/proxy.rs#L2343)), and its own test streams a `hidden_states` array through intact. The delta's new v3 refusal names the request options whose output lands in such fields — `return_token_ids`, `return_prompt_text`, `prompt_logprobs` (even `0`) — with the comment "These engine options return text or token IDs outside the encrypted fields" and "Zero prompt logprobs still includes the prompt's sampled tokens" ([`src/encryption.rs#L779-L791`](https://github.com/nearai/inference-proxy/blob/53d79441487089b069de775b63cfe975cd1abb4d/src/encryption.rs#L779-L791)); `docs/e2ee.md` lists `matched_stop`, `stop_reason`, token IDs and hidden states as what v3 removes (lines 94-99). **At the base tree, and at this tree for v1/v2 clients, none of this is refused or stripped**: `grep prompt_logprobs|return_token_ids|return_prompt_text` over `5faff1bb`'s `encryption.rs`, `proxy.rs` and `chat.rs` finds nothing. So a legacy-version client that asks for prompt logprobs or token ids would receive **its own prompt's tokens in plaintext** in a reply whose only wrapping on the plain-TLS path is TLS to cloud-api — the gateway, which under E2EE is meant to see ciphertext and metadata. **Scope:** the client must both use v1/v2 *and* opt into one of these options, and the engine must honour it (not traced); under OHTTP (`OHTTP_ENABLED=true` on every service) the whole inner response is sealed to the client's OHTTP key, so the exposure is to the TLS path only; and the data goes to the client that asked for it, with the gateway as the only other observer. No log, file, metric or third-party destination is involved. **v3 closes it** by refusing the options and allow-listing the reply ([`#L822-L965`](https://github.com/nearai/inference-proxy/blob/53d79441487089b069de775b63cfe975cd1abb4d/src/encryption.rs#L822-L965)); recorded as ARMED because the proxy still accepts v1 and v2 from any client, and as LOW because it is client-chosen, gateway-visible-only and closed by the version the project now documents as the one clients must not downgrade from.

## Verdict

**QUALIFIED PASS** — five commits that tighten the E2EE (reply-key-bound fields, a reply allow-list, constant error bodies), add a size-aware priority that reads the plaintext into three buckets, give the engine a server-chosen request id, and close the unseal-ECDH advisory by upgrade and a verified vendoring, with no content sink at the deployed env; the two client-opt-in egress features remain live-or-latent on these hosts; one legacy-protocol LOW is recorded.

The delta between `5faff1bb` and `53d79441` is, in privacy terms, mostly subtraction. E2EE v3 binds every encrypted request field to the client's reply key and the field's name, so a swapped reply key fails closed; it encrypts the full field set unconditionally; it deletes from every reply any key it has no policy for, so engine extensions carrying token ids or prompt text cannot ride out in plaintext; and for every encrypted request of any version it replaces the engine's error message — previously regex-sanitised and forwarded — with a fixed sentence. The size bonus reads the decrypted prompt's estimated length and writes a three-valued bucket into the forwarded `priority` and one metric label; the request-id change takes a client-chosen identifier away from the engine. The k256 0.14 upgrade and the vendored dstack client close the accepted timing advisory on the ECDH that unseals every request; the vendored files are the published crate's, byte for byte. Every one of the 245 hunks was read, the vendored crate and the new scheduler in full; the whole-tree sweeps were re-run on both trees and show **zero** changed log sites, one new bounded metric and zero new network call sites in `src/`. No file, no metric, no destination and no log line gains a handle on message content.

The verdict is **qualified** rather than PRIVATE for the `4937ad68` page's reasons as they apply here — client-opt-in web search on all seventeen services and fusion on thirteen move message-derived plaintext off-box to destinations the image neither attests nor allow-lists, armed by host-env values this review cannot see; decrypted-envelope strings reach the exported log — plus one observation this delta's own fix surfaced: the proxy still accepts E2EE versions 1 and 2, under which a client's request for prompt logprobs or token ids returns its prompt's tokens in a plaintext reply field past the gateway on the TLS path. That is client-chosen, gateway-visible only, closed in v3, and recorded as LOW. The RUSTSEC qualification of the base page is gone. **Residuals** are otherwise the `4937ad68` page's: the two GLM recipes plumb a Redis channel and the LongContext recipe an engine pool from host env; the deploy-env values stay unverifiable from here.
