# vllm-proxy-rs (E2EE terminator) — Privacy Audit

> Part of the near.ai inference-path privacy audit. Method: [/notes/method.md](/notes/method.md).

- **Image:** `nearaidev/vllm-proxy-rs@sha256:b0c5cd0786b1…` (signed provenance → `nearai/inference-proxy` @ `48d7e349`)
- **Source:** https://github.com/nearai/inference-proxy/tree/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c (public; full tree fetched via commit-pinned tarball)
- **Location:** `proxy-dsv4-flash` / `proxy-dsv4-flash-2` in both hardware-attested composes; the container that holds the model's OHTTP private key and decrypts the user's request before the inference engine sees it
- **Role:** E2EE terminator / OHTTP gateway / auth / signing / usage-metering reverse proxy in front of the SGLang engine
- **Verdict:** core path clean; two client-opt-in egress features (web_context_search, fusion) move message-derived plaintext off-box by design

## Audit prompt

```text
Independent source review of the E2EE-terminating inference proxy for the
teemoon privacy audit repo. Question: can anything exfiltrate the user's
plaintext chat messages? "Private" = plaintext visible only to the user and
the inference engine process; any copy reaching a log, file, DB, cache,
crash dump, telemetry exporter, or non-model network destination is a
finding.

Procedure followed:
1. Resolve image digest -> source commit via the signed GitHub build
   attestation (DSSE payload, predicate.buildDefinition.resolvedDependencies).
2. Fetch the full tree at that exact commit; never review a different ref.
3. Trace the decrypted buffer: OHTTP decapsulation -> loopback -> route
   handler -> field decryption -> upstream engine call.
4. Enumerate every log/trace statement on the request path and its
   arguments; check whether any env var (RUST_LOG, LOG_FORMAT) can raise
   verbosity into body logging.
5. Walk error paths and panic surfaces for request content embedded in
   error values or panic messages.
6. Enumerate every outbound network destination the process can initiate
   and what data each carries (engine, cloud-api, compose-manager, web
   search, fusion endpoints, image-URL preflight, dstack socket).
7. Check the claimed engine path allowlist; verify what actually guards
   engine admin endpoints.
8. Check key material handling: derivation, storage, export, logging.
9. Cross-check the deployed compose env (OHTTP_ENABLED, LOG_FORMAT=json,
   Datadog/otel log collection labels) against code behavior.
10. Diff against the other attested build in this repo (b183677a/372824b4)
    and enumerate the delta.
Every file:line citation verified against the fetched tree. Distinguish
"OFF at deployed config" from "cannot happen". Fail closed if source is
unreadable.
```

### Traced

1. **The decrypted buffer.** OHTTP decapsulation happens in [`src/routes/ohttp.rs#L112-L116`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/routes/ohttp.rs#L112) (standard) and [`#L192-L204`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/routes/ohttp.rs#L192) (chunked); the plaintext BHTTP request is replayed as a loopback HTTP call to the proxy itself ([`#L440`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/routes/ohttp.rs#L440): `http://127.0.0.1:{listen_port}{path}`). The chat handler then optionally applies **field-level** decryption in place ([`src/routes/chat.rs#L45-L52`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/routes/chat.rs#L45-L52)) and forwards the body to the engine. The plaintext lives in process memory for the request lifetime only: signatures are computed over **hashes** (`"{model}:{request_sha256}:{response_sha256}"`, [`src/proxy.rs#L885`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/proxy.rs#L885), [`#L1537`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/proxy.rs#L1537)), and the only cache is the in-memory moka signature cache keyed by chat id, storing the signature JSON — hashes and signatures, never message content ([`src/cache.rs#L32-L37`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/cache.rs#L32-L37)). **No request-path code writes to disk** — the only `std::fs` uses are reading `/etc/.GIT_REV`, reading the TLS cert, and stat-ing it for renewal ([`src/config.rs#L354`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/config.rs#L354), [`src/attestation.rs#L770`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/attestation.rs#L770), [`#L825`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/attestation.rs#L825)). The agent loop retains the conversation in `request_json` across iterations and appends tool results ([`src/agent_loop.rs#L635-L646`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/agent_loop.rs#L635-L646)); it is dropped when the spawned task completes ([`#L14-L17`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/agent_loop.rs#L14-L17)).

### CRITICAL-class capability, client-gated (deployed: configured via env; fires ONLY on per-request opt-in) — `web_context_search` sends model-written queries derived from the decrypted conversation to an external search API

When — and only when — a request's `tools` is exactly `[{"type":"web_context_search"}]` with `stream:true` ([`src/agent_loop.rs#L64-L70`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/agent_loop.rs#L64), gating at [`src/routes/chat.rs#L110-L122`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/routes/chat.rs#L110)), the proxy runs a server-side tool loop: the model — which has just read the user's E2EE-decrypted messages — emits a `query`, and the proxy sends **exactly** `GET {WEB_CONTEXT_SEARCH_URL}?q=<query>&count=20&…` with the API key header, plus `x-request-id` only if the client sent one; org/workspace IDs are explicitly not forwarded ([`src/agent_loop.rs#L1206-L1227`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/agent_loop.rs#L1206)). The query is model-generated prose that routinely paraphrases the user's message, so **message-derived plaintext leaves the CVM to a third party (Brave)** — this is the feature's documented purpose ([`src/agent_loop.rs#L14-L17`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/agent_loop.rs#L14)). Mitigations verified: without the opt-in tool the loop is unreachable and requests fall through to the byte-identical pass-through path; the tool-call arguments and results traveling back to the client are force-encrypted under E2EE regardless of client header ([`src/routes/chat.rs#L124-L137`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/routes/chat.rs#L124)). This is "OFF unless the client asks", not "cannot happen": the deployed env plumbs the URL/key, so a client that opts in gets the egress.

### HIGH, doubly gated (deployed: UNKNOWN — `FUSION_ENABLED=${FUSION_ENABLED}` from host `.env`; fires only on per-request opt-in) — fusion forwards the FULL plaintext conversation to remote endpoints chosen by a runtime-fetched listing

When `FUSION_ENABLED` is true **and** the request carries an `openrouter:fusion`/`nearai:fusion` tool ([`src/routes/chat.rs#L66-L70`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/routes/chat.rs#L66), [`src/fusion.rs#L163`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/fusion.rs#L163)), the proxy clones the request — **including all `messages`** — and POSTs it to panel/judge model endpoints ([`src/fusion.rs#L696-L704`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/fusion.rs#L696); the judge request embeds `original_messages` verbatim, [`#L724`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/fusion.rs#L724)). The code itself flags the boundary: *"SECURITY(V1): E2EE is terminated at this orchestrating proxy. Panel and judge calls forward plaintext over TLS to trusted direct TEE endpoints"* ([`src/fusion.rs#L829-L831`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/fusion.rs#L829)). Two sharp edges: (a) the destinations come from a **runtime-fetched listing** (`FUSION_ENDPOINTS_URL`, default `https://completions.near.ai/endpoints`, [`src/config.rs#L508-L511`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/config.rs#L508), fetched at [`src/fusion.rs#L1303-L1307`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/fusion.rs#L1303)) — whoever controls that listing (or the env var) steers where plaintext conversations go; (b) the per-endpoint attestation probe is an informational **liveness** check, not a verification gate — an unattested endpoint is still used and merely marked `verifiable:false` ([`src/fusion.rs#L1368-L1407`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/fusion.rs#L1368)). Deployed status cannot be determined from the composes; if `${FUSION_ENABLED}` is unset/empty this path is dead code at runtime (`env_bool`, [`src/config.rs#L22`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/config.rs#L22); [`#L558-L563`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/config.rs#L558) additionally requires the bearer token at startup).

### MEDIUM (deployed: ON) — there is NO engine path allowlist; the catch-all forwards any authenticated request to any engine endpoint

Correction to the premise carried by other pages in this repo: at this commit the proxy has **no** path allowlist. The router's `.fallback(catch_all::catch_all)` ([`src/routes/mod.rs#L95`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/routes/mod.rs#L95)) forwards **any** path that survives traversal validation ([`src/routes/catch_all.rs#L52-L96`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/routes/catch_all.rs#L52) — encoding/`..`/backslash checks only, no path list) straight to the engine ([`#L101-L188`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/routes/catch_all.rs#L101)). The only guard is `RequireAuth`: the deployment `TOKEN` or any valid `sk-` cloud key ([`src/auth.rs#L260-L292`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/auth.rs#L260)). Consequence: SGLang's operational endpoints (cache flush, weight updates, server info, profiling) are reachable by **any paying API-key holder**, not just operators. I found no engine endpoint that returns another user's message content on this engine build, but profiling/dump-style endpoints on inference engines have historically exposed request internals — the guard here is "authenticated", not "safe subset". Distinguish clearly: this is *reachable at deployed config*, and the mitigation other audits assumed does not exist in this tree.

### LOW (deployed: ON) — the decrypted inner request's path is logged, and the log pipeline exports it

After decapsulating an OHTTP request, the proxy logs `inner_path` — the path from inside the encrypted envelope — at `info` ([`src/routes/ohttp.rs#L152-L158`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/routes/ohttp.rs#L152), [`#L232-L237`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/routes/ohttp.rs#L232)), and the request-span middleware logs `path` for every request ([`src/request_tracing.rs#L103-L110`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/request_tracing.rs#L103)). For the API as used (POST endpoints, no query strings) this is metadata, not message content — but the value is taken verbatim from the decrypted BHTTP control data ([`src/routes/ohttp.rs#L429-L434`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/routes/ohttp.rs#L429)), so a client that put sensitive data in an inner query string would see it exported to `telemetry.infra.near.ai` via the stdout→otelcol pipeline. Cannot carry message bodies; can carry envelope metadata.

### INFO (deployed: ON) — stdout is telemetry-collected; verified content-free

Given the Datadog label + otelcol filelog pipeline, every proxy log line leaves the enclave. All log statements on the request path were reviewed (finding-by-finding above): arguments are ids, counts, durations, sanitized URLs, and error categories. Usage reporting to cloud-api carries token counts and identity IDs only. The signature cache and signed text contain hashes only. No `TraceLayer`/`tower-http` request-body tracing is wired in.

### Controls that would change the verdict

| Control | Effect |
|---|---|
| Leave `WEB_CONTEXT_SEARCH_URL`/`_API_KEY` unset on deployments serving privacy-sensitive traffic | `web_context_search` requests are rejected with 400 ([`src/routes/chat.rs#L116-L122`](https://github.com/nearai/inference-proxy/blob/48d7e349f6ea76d6ec5a3ca234c5c254967abf9c/src/routes/chat.rs#L116)); the CRITICAL-class egress becomes *cannot happen* |
| Set `FUSION_ENABLED` empty/false (and/or omit `FUSION_INTERNAL_BEARER_TOKEN`) | Fusion path dead at runtime; full-conversation forwarding becomes *cannot happen* |
| Pin/verify the fusion endpoint listing (signed listing, or hard-fail on unattested endpoints instead of `verifiable:false`) | Removes the mutable control point steering plaintext destinations |
| Add an explicit engine path allowlist (or deny-by-default fallback) in front of `catch_all` | Closes authenticated access to engine admin/profiling endpoints |
| Strip query strings from `inner_path`/`path` log fields | Removes decrypted-envelope metadata from the exported telemetry stream |
| Publish the host `.env` values for `FUSION_ENABLED` / `WEB_CONTEXT_SEARCH_URL` alongside the composes | Converts two "unknown at deploy" gates in this audit into verifiable facts |

### Verdict: core path clean; the two ways message-derived plaintext leaves this process are deliberate, client-opt-in features — not leaks — but both are live-or-latent at deployed config

On the path every ordinary chat request takes — OHTTP decapsulation → field decryption → engine → encrypted response — this build does not log, persist, cache, or transmit message plaintext anywhere except to the inference engine. Error paths sanitize engine-echoed conversation content before it can reach the (telemetry-collected) logs, with tests pinning that behavior. Keys are KMS-derived in-enclave and never exported. The delta from the previously audited build is dependency hygiene plus a watchdog that logs only metadata.

**Residuals:** (1) `${FUSION_ENABLED}` and `${WEB_CONTEXT_SEARCH_URL}` values are not visible in the composes — the two egress features' deployed on/off state is asserted by near.ai, not verified here; (2) the signed attestation binds the image to the commit up to trust in GitHub's attestation service and build runner — the `reproducible-build.yml` workflow exists in-tree but an independent rebuild was not performed for this review; (3) `attestation.rs` internals, `encryption.rs` cryptographic correctness, the full dependency closure, and the `vllm/vllm-openai` base-image contents were not traced; (4) panic reachability was spot-checked, not exhaustively proven — a panic message cannot be shown to *never* carry request-derived bytes, only that no such formatting site was found; (5) the engine itself (separate image, separate audit) sees plaintext by design and is out of scope here.
