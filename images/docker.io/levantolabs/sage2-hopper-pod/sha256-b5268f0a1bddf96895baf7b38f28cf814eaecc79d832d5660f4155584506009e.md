Reaching them makes Sage a network client of those services, with whatever credentials it has, which by this file is none of theirs. That traffic between two Docker bridges is dropped is Docker's default, not a line of the recipe, and was not tested in the guest.

**Docker socket and logs.** The two volumes at 2198-2199 are the whole list. There is no `/var/run/docker.sock`, no `/var/lib/docker`, no host path other than the one socket file.

**The dstack socket filter** (`sage-dstack`, 2126-2168; `nginx@sha256:1d13701a…`, no page). It mounts the real `/var/run/dstack.sock` (2132) and a host directory `/var/run/sage-dstack` (2133), has no network, and writes this configuration at start (2140-2160):

```
http {
  access_log /dev/stdout;
  server {
    listen unix:/sock/dstack.sock;
    location = /Info {
      limit_except GET { deny all; }
      proxy_pass http://unix:/var/run/dstack.sock;
    }
    location = /GetQuote {
      limit_except GET { deny all; }
      proxy_pass http://unix:/var/run/dstack.sock;
    }
    location / {
      return 403;
    }
  }
}
```

Read against nginx's documented behaviour:

- `location =` is an exact match on the normalised path (percent-decoded, `.` and `..` resolved, repeated slashes merged). Only a request whose normalised path is exactly `/Info` or `/GetQuote` is proxied. `/GetKey`, `/GetTlsKey`, `/EmitEvent`, `/Sign`, `/Verify`, `/Attest`, `/Version` and any other path fall to `location /` and get 403 (2156-2158). The guest agent's key, signing and event methods are separate single-segment paths (`agent_rpc.proto:41`, `:44`, `:54`, `:60`), so the claim at 2121-2122 holds as written.
- `limit_except GET` admits `GET` and, by nginx's rule, `HEAD`; `POST` and every other method get 403. nginx does not act on `X-HTTP-Method-Override`.
- The query string is not part of the match and, because `proxy_pass` has no URI part, the request line is forwarded as the client sent it. `GET /GetQuote?report_data=<hex>` passes. This matters below.
- A path that normalises to `/GetQuote` in nginx but is written differently (`/x/../GetQuote`, `/%47etQuote`) reaches the agent in its raw form. The agent routes one path segment as the method name (`ra-rpc/src/rocket_helper.rs:225`, `:253`) and dispatches on an exact string match (`prpc-build 0.6.1 src/server.rs:61-64`, `:202-207`), so a raw form that is not literally a method name is "Service not found". I found no spelling that nginx reads as `/GetQuote` and the agent reads as `GetKey`. This was reasoned from source, not executed (see Not traced).

Not fenced: the rate of `GetQuote` calls. The agent serves every quote in the CVM one at a time behind one lock (`guest-agent/src/rpc_service.rs:116-128`).

## The quote question

**What `GetQuote` takes and returns.** Source read: `Dstack-TEE/dstack` @ `43f69f41cc546423f9f73fc48b16f8cf19053cbc`, which is the `v0.5.12` tag in the clone and the submodule pin the [guest OS page](/os/sha256-91fd5d69ccee3e5ea4f2aeb8c9b632c4358c4ecfc29ba1aa6fb1e402af209829.md) records for the 0.5.12 image this CVM boots. It is the deployed tree, not a later one (the clone's head is `33ece2a4`, v0.6.5+58, and was not used).

1. The socket Sage is handed leads to the agent's internal service, mounted at `/` with both a POST and a GET route per method (`guest-agent/src/server.rs:90`; `ra-rpc/src/rocket_helper.rs:236`, `:253-255`).
2. On a GET the request's query string is the payload (`rocket_helper.rs:558-561`), decoded as a query string into the request message (`prpc-build 0.6.1 src/server.rs:261-262`), with byte fields given as hex, an optional `0x` stripped (`prpc 0.6.0 src/serde_helpers.rs:20-21`). The dstack documentation at that commit shows the call: `curl --unix-socket /var/run/dstack.sock http://localhost/GetQuote?report_data=0x1234deadbeef` (`docs/usage.md:80`). Both crates were fetched from crates.io and their SHA-256 matched `Cargo.lock`.
3. `get_quote` takes `RawQuoteArgs { bytes report_data }` (`agent_rpc.proto:47`, `:170-173`), rejects more than 64 bytes, zero-pads shorter input and passes the 64 bytes on unchanged (`rpc_service.rs:429-431`, `pad64` at `:557-564`). There is no prefix, no hash and no content-type tag on this method. (The legacy `TdxQuote` method hashes with a prefix, `:621-639`; it is on the other socket, which Sage does not have.)
4. The 64 bytes go to the TDX driver as the report data (`guest-agent/src/backend.rs:36-37`; `dstack-attest/src/attestation.rs:1025-1027`, `:1046`). The response is the quote, the CVM's event log, the report data and the VM config (`backend.rs:40-45`; `agent_rpc.proto:193-202`).
5. Nothing about the caller enters the quote or the event log. The handler is built from shared state only (`rpc_service.rs:566-573`); the event log is the VM's boot log read back (`attestation.rs:1048`); `GetQuote` emits no event. The agent cannot tell which container is on the other end of the socket, and after the nginx hop the peer is nginx in any case.

So `report_data` is fully caller-controlled, and the nginx filter passes the GET form that carries it.

**How near.ai's model attestation binds its key.** One capture of the gateway's attestation report (`signing_algo` ed25519, taken by the orchestrator) was parsed here. For each of the three `glm-5.3-flash` entries, this CVM's among them (`compose_hash e8416a02…`), the 64 report-data bytes inside the TDX quote are exactly `signing_public_key` (32 bytes) followed by `request_nonce` (32 bytes), with no prefix and no hashing. The gateway's own entry has the same shape (`report_data` = `signing_address` then `request_nonce`), and the compose-manager attestation inside each entry is `actions_hash` then the nonce. The quotes' runtime events are the ten boot events (`app-id`, `compose-hash`, `instance-id`, `os-image-hash`, ...), the same for every quote the CVM issues.

**The consequence, stated without overclaiming.**

- Established: a process in the Sage container can obtain, through the filter, a TDX quote that is valid for this CVM (same measurements, `app_id`, `compose_hash`, `instance_id`, event log) and whose report data is any 64 bytes it chooses, including a public key it generated and a nonce handed to it by a verifier. This is the capability the recipe grants on purpose so that Sage can serve its own attestation report.
- Established: a quote attests the CVM, not a container. The report-data layout near.ai's proxies use for a model's signing key is one this capability can reproduce byte for byte. A verifier that checks the quote's signature, the measurements, the compose hash and "report data = key then my nonce" cannot tell a quote requested by a near.ai proxy from one requested by Sage. Nothing in the quote says which container holds the key.
- Inferred, not exercised: the same holds for the action-log attestation, since `actions_hash` then nonce is also a raw 64-byte value; and `GET /Info` gives Sage the `app_cert` and `tcb_info` that accompany a quote in near.ai's format.
- Not established: that the image does any of this beyond its own attestation endpoint. The image is unread. I also did not read a client verifier here; the statement is about what the quote can carry, and a client that additionally pins a key through some channel Sage cannot reach would tell the two apart.
- What else is needed for it to matter to a user of the nine model hostnames or of `glm-5.3-flash`: their attestation request and their traffic would have to be answered by Sage instead of a near.ai proxy. Sage listens on its own port (8010) and, by the comments, its own hostname and certificate; the model hostnames terminate at near.ai's nginx on other ports. Sending a model's traffic to Sage is a decision of whoever routes it: the gateway operator, or whoever controls the host's port forwards. And the image would have to speak near.ai's attestation and encryption formats, which is a property of unread code. The quote would not stop it; that is the finding.
- What it means today for a reader: an attestation from this CVM proves "some software in this VM holds this key". The software in this VM includes a third-party container that this repository could not read, and whose image is pinned by the action log, not by the measured compose hash.

Closing it does not need Sage to lose its quotes. dstack's own interface file advises a content-type identifier in report data "to avoid Quote Repurposing Attacks" (`agent_rpc.proto:24-27`); a distinct, checked prefix on either side's report data, or a model key that chains to something the filter withholds (`GetKey`, `Sign`), would let a verifier tell the two apart.
