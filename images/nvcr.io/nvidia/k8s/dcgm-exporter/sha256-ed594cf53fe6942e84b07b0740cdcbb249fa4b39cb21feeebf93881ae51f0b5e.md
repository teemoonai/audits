## why this page exists: an upgrade in evidence class

Everywhere else on this fleet, dcgm-exporter is pinned **by tag**. That is why this repo gives it a deliberately weaker sibling page —
[`tag-4.5.2-4.8.1-distroless.md`](/images/nvcr.io/nvidia/k8s/dcgm-exporter/tag-4.5.2-4.8.1-distroless.md) — which covers "the tag string and its deployed configuration, never bytes."

In `prod/dsv4-flash-glm51.yaml` it is pinned **by digest**, so a real byte-identity page is possible for the first time. What changes, precisely:

> **The tag page's central caveat does not apply to this digest.** That caveat was: *the registry can serve different bytes under one tag with no attestation-visible trace.* A digest is a content address. `nvcr.io/nvidia/k8s/dcgm-exporter@sha256:ed594cf5…` can only ever resolve to these bytes; a registry-side re-push cannot move it, and any substitution is a hash mismatch at pull time, not a silent swap. On this node the "its bytes can drift under the attestation" risk is **closed**.

What does *not* change: the privilege. It is still `SYS_ADMIN` + the nvidia runtime over GPUs on which plaintext is computed, and per this repo's [scope rule](/README.md#scope-rule) it is in scope **for that privilege, not because its function is assumed benign**.

One check worth recording, because it retires an open question rather than restating it: at review time the mutable tag and this immutable digest are **the same bytes**. `GET /v2/nvidia/k8s/dcgm-exporter/manifests/4.5.2-4.8.1-distroless` returned `docker-content-digest: sha256:ed594cf53fe6942e84b07b0740cdcbb249fa4b39cb21feeebf93881ae51f0b5e`. So the tag-pinned nodes are, *today*, running exactly what this page reviewed. That is a point-in-time observation with no cryptographic force — it can stop being true tomorrow without notice, which is the entire reason the tag page exists — but it means this digest review is currently informative about those nodes too.

## deployed configuration

The `&dcgm-common` anchor ([`prod/dsv4-flash-glm51.yaml:172-178`](https://github.com/nearai/cvm-compose-files/blob/main/prod/dsv4-flash-glm51.yaml#L172-L178)):

```yaml
x-dcgm-common: &dcgm-common
  image: nvcr.io/nvidia/k8s/dcgm-exporter@sha256:ed594cf53fe6942e84b07b0740cdcbb249fa4b39cb21feeebf93881ae51f0b5e
  runtime: nvidia
  cap_add:
    - SYS_ADMIN
  restart: unless-stopped
  logging: *logging-conf
```

Two services consume it — `dcgm-dsv4-flash` (`:531-540`, GPUs `0,1,2,3`) and `dcgm-glm51` (`:564-573`, GPUs `4,5,6,7`) — each adding only a device reservation and a block of scrape/telemetry labels (`:541-562`, `:574-596`). No command, so the entrypoint runs `dcgm-exporter` with **zero arguments**: every flag below is at its compiled-in default.

What the service block does **not** contain, all verified by absence in the anchor and both service blocks:

| absent | consequence |
|---|---|
| `volumes:` (any) | no `docker.sock`, no `/var/lib/docker/containers` log mount, no host `/proc`, no writable host path |
| `pid: host` | no shared PID namespace — other containers' processes are not visible |
| `SYS_PTRACE` | no `process_vm_readv` into another process's address space |
| `privileged: true` | not full privilege (contrast `&vllm-proxy-common` at `:35-37`, which *is* `privileged: true`) |
| `ports:` | **`:9400` is not published to the host** — reachable only on the compose network |
| `environment:` | no `DCGM_EXPORTER_*` override is set at all |

That last two deserve emphasis because they are *improvements over the tag-pinned deployment* this repo already reviewed. The GLM-5.1 node's compose published `ports: ["9400:9400"]` and set `NVIDIA_VISIBLE_DEVICES=all` explicitly; here there is no port publishing and no environment block. The only network the containers join is `dstack_default` (`:630-632`, `external: true`) — the shared in-CVM network, so the otel collector and the datadog agent can scrape `dcgm-dsv4-flash:9400` / `dcgm-glm51:9400` (`:846-854`, `:866-874`, `metrics_path: /metrics`, `scrape_interval: 15s`) while nothing outside the CVM can.

## what it collects, and whether GPU telemetry can carry inference content

With no `--collectors` argument the exporter reads its default field list — [`app.go:123,126`](https://github.com/NVIDIA/dcgm-exporter/blob/4.5.2-4.8.1/pkg/cmd/app.go#L123-L126), `Value: "/etc/dcgm-exporter/default-counters.csv"` — and that file ships **inside this digest** (history step `[38]`), so its contents are pinned, not assumed. Extracted from the image, the uncommented fields are exactly:

```
DCGM_FI_DEV_SM_CLOCK / MEM_CLOCK                 clock frequencies (MHz)
DCGM_FI_DEV_GPU_TEMP / MEMORY_TEMP               temperatures (C)
DCGM_FI_DEV_POWER_USAGE                          power draw (W)
DCGM_FI_DEV_TOTAL_ENERGY_CONSUMPTION             energy since boot (mJ)
DCGM_FI_DEV_PCIE_REPLAY_COUNTER                  PCIe retries
DCGM_FI_DEV_GPU_UTIL / MEM_COPY_UTIL             utilization (%)
DCGM_FI_DEV_ENC_UTIL / DEC_UTIL                  encoder/decoder utilization (%)
DCGM_FI_DEV_XID_ERRORS                           last XID error code
DCGM_FI_DEV_FB_FREE / FB_USED / FB_RESERVED      framebuffer memory (MiB)
DCGM_FI_DEV_NVLINK_BANDWIDTH_TOTAL               NVLink byte counters
DCGM_FI_DEV_VGPU_LICENSE_STATUS                  license state
DCGM_FI_DEV_*_REMAPPED_ROWS / ROW_REMAP_FAILURE  row-remap counters
DCGM_FI_DRIVER_VERSION                           label
DCGM_FI_PROF_GR_ENGINE_ACTIVE                    ratio, graphics engine active
DCGM_FI_PROF_PIPE_TENSOR_ACTIVE                  ratio, tensor pipe active
DCGM_FI_PROF_DRAM_ACTIVE                         ratio, memory interface active
DCGM_FI_PROF_PCIE_TX_BYTES / RX_BYTES            PCIe byte rate
```

**Can any of this carry inference content? No — not by construction.** Every field is a scalar counter, ratio, or version string sampled from DCGM/NVML. There is no field in this list, and no DCGM field of any kind, that returns the *contents* of GPU memory. `FB_USED` reports how many MiB are occupied; it cannot report what occupies them. This is the same conclusion the tag page reached, now anchored to a pinned field file rather than to the exporter's reputation.

The residual is a **side channel, not a content channel**: `GR_ENGINE_ACTIVE`, `PIPE_TENSOR_ACTIVE`, `POWER_USAGE` and friends do trace the *shape* of the workload over time, and utilization traces are a recognized side-channel class. Two things bound it here. The default sample interval is **30 s** — [`app.go:137,139`](https://github.com/NVIDIA/dcgm-exporter/blob/4.5.2-4.8.1/pkg/cmd/app.go#L137-L139), `Value: 30000` ms, and nothing overrides it — while the scrapers poll every 15 s, so they resample a value that only changes twice a minute. And these are **per-GPU aggregates across every concurrently-batched request** on that GPU pair. Recovering token-level structure from a 30-second-resolution average over a continuously batched multi-tenant engine is not a realistic attack; it is not comparable to a log line containing the prompt. Recorded as an INFO residual, not a finding.

### egress from the exporter: pull-only, and nothing else

The exporter serves and does not send. A sweep of the upstream tree for outbound HTTP construction (`http.Post`, `http.Get`, `http.NewRequest`, raw `Dial(`) across `internal/` and `pkg/` returns **no non-test hits** — there is no push gateway, no analytics SDK, no error-reporting client, no phone-home. Its listener defaults to `:9400` ([`app.go:130,132`](https://github.com/NVIDIA/dcgm-exporter/blob/4.5.2-4.8.1/pkg/cmd/app.go#L130-L132)) and Prometheus/datadog **pull** from it. Combined with the absent `ports:` block, the metrics never leave the compose network except inside whatever the otel/datadog pipelines forward — which is a property of *those* services, reviewed on their own pages, and what they receive from dcgm is the counter list above.

## findings

### MEDIUM (deployed: ON, unconditional) — `/debug/pprof/*` is served unauthenticated on the metrics port

The exporter registers the full Go pprof suite on the **same** listener as `/metrics`, with no flag guarding it — [`server.go:106-116`](https://github.com/NVIDIA/dcgm-exporter/blob/4.5.2-4.8.1/internal/pkg/server/server.go#L106-L116), followed by an unconditional `slog.Info("Profiling endpoints enabled at /debug/pprof/")` at [`server.go:118`](https://github.com/NVIDIA/dcgm-exporter/blob/4.5.2-4.8.1/internal/pkg/server/server.go#L118). That exposes `/debug/pprof/heap`, `/allocs`, `/goroutine`, `/profile`, `/trace` and `/cmdline` — i.e. **heap dumps and full command lines of a `SYS_ADMIN`, root-running process** — to anyone who can open a TCP connection to `:9400`.

- **Is this a plaintext leak? No.** dcgm-exporter never reads inference buffers; its heap holds GPU counters, device metadata and its own Prometheus registry. A heap dump of it does not contain user messages. Rated MEDIUM as an *unauthenticated debug surface on the most privileged sidecar in the compose*, not as a content path.
- **Authentication is available and unused.** `--web-config-file` ([`app.go:231`](https://github.com/NVIDIA/dcgm-exporter/blob/4.5.2-4.8.1/pkg/cmd/app.go#L231)) hands the listener to `prometheus/exporter-toolkit`'s `web.ListenAndServe` ([`server.go:190`](https://github.com/NVIDIA/dcgm-exporter/blob/4.5.2-4.8.1/internal/pkg/server/server.go#L190)), which supports TLS and basic auth. The deployed config passes no arguments, so the config file is empty and the listener is plain HTTP with no auth.
- **Deployed blast radius is bounded, and only by the network.** With no `ports:` mapping, `:9400` is reachable from the `dstack_default` network — i.e. from any other container in this CVM — and not from the host or outside. So the exposure is to in-CVM peers, which are themselves attested. That is a real mitigation; it is not the same as the endpoint being off.
- **Activates on:** nothing. It is already on. Closing it means `--web-config-file`, or an upstream build flag that does not exist in this release.

### INFO (deployed: OFF) — file-based debug dumps exist and are disabled

`--dump-enabled` defaults `false` ([`app.go:305`](https://github.com/NVIDIA/dcgm-exporter/blob/4.5.2-4.8.1/pkg/cmd/app.go#L305)), with `--dump-directory` defaulting to `/tmp/dcgm-exporter-debug` ([`app.go:311-312`](https://github.com/NVIDIA/dcgm-exporter/blob/4.5.2-4.8.1/pkg/cmd/app.go#L311-L312)) and a 24 h retention. Nothing sets `DCGM_EXPORTER_DUMP_ENABLED`. Even if flipped, the dumper writes the exporter's own metric structures ([`internal/pkg/debug/debug.go:46`](https://github.com/NVIDIA/dcgm-exporter/blob/4.5.2-4.8.1/internal/pkg/debug/debug.go#L46), `DumpToFile(data any, …)`) — counters, not content — to the container's own writable layer, which has no volume and does not survive recreation. Noted for completeness: this is an operator-flippable disk-write feature, and it is off.

### INFO (deployed: default) — `--collectors` can be repointed, but not at content

An operator setting `DCGM_EXPORTER_COLLECTORS` could swap the field list for one including fields the default file leaves commented out (ECC totals, NVLink error counters, serial numbers, VBIOS versions, retired pages). None of those are message content; the most sensitive are hardware identifiers. Whether `DCGM_EXPORTER_*` names appear in the node's measured `allowed_envs` is a **manifest question, not answerable from this image or this source tree — INCONCLUSIVE here.** The bound that matters holds regardless: *no* DCGM field returns memory contents, so no `--collectors` value turns this exporter into a content channel.

### INFO — what the `SYS_ADMIN` privilege would actually allow

`CAP_SYS_ADMIN` is granted for a specific, verifiable reason: the DCP profiling metrics (`DCGM_FI_PROF_*`) require it. Upstream says so directly — [`capabilities.go:31-32`](https://github.com/NVIDIA/dcgm-exporter/blob/4.5.2-4.8.1/internal/pkg/capabilities/capabilities.go#L31-L32), *"CAP_SYS_ADMIN is required for profiling metrics (DCP/DCGM_FI_PROF_*)"* — and the code merely *warns* when the capability is missing rather than failing. Three of the deployed default fields are `DCGM_FI_PROF_*`, so the grant is functionally justified rather than gratuitous.

It is still a broad capability on a container running as `root:root`. What it does **not** compose into here: reading another container's plaintext requires either a shared PID namespace plus ptrace, or a host mount to reach memory/log state — and the deployed config has **neither** `pid: host`, **nor** `SYS_PTRACE`, **nor** any `volumes:` entry at all. So there is no traced path from this container to the inference engines' address space. Stated as fail-closed as I can: **`SYS_ADMIN` is a documented container-escape primitive** (mount operations, and kernel-surface reachability that varies by kernel and seccomp profile), and I did **not** trace the runtime's seccomp/AppArmor profile, the nvidia container runtime's device injection, or the guest kernel's attack surface — those live in the [guest-OS review](/os/) and the runtime, not here. The correct reading is *"no configured path, and a privilege that would matter if the container were compromised"* — which is exactly why this repo keeps it in scope.

### INFO — image-baked `NVIDIA_VISIBLE_DEVICES=all` versus the per-service device reservation

The image config bakes `NVIDIA_VISIBLE_DEVICES=all` and `NVIDIA_DISABLE_REQUIRE=true` (history steps `[50]`,`[51]`), while the compose narrows each service to four GPUs through `deploy.resources.reservations.devices.device_ids` (`:534-540`, `:567-573`) and sets no `environment:` block to override the baked value. Which of the two the nvidia container runtime honors is a **runtime-behavior question that the manifests do not answer**, and I did not resolve it. Impact is bounded either way: GPU *visibility* is not GPU-memory *readability*, and the collection path above is the same counters whether it enumerates four devices or eight. Worth flagging because the tag-pinned sibling deployment set `NVIDIA_VISIBLE_DEVICES=all` explicitly and this one appears to have intended not to.

## verdict: telemetry-not-content at deployed config — GPU-privileged, and the bytes are now pinned

At the attested configuration this container collects **aggregate GPU counters and nothing else**, from a field list that ships inside the reviewed digest, and serves them pull-only on a port that is not published to the host. There is no field in DCGM that returns GPU memory contents; there is no outbound HTTP client anywhere in the exporter; there are no volumes, no shared PID namespace and no `SYS_PTRACE`, so nothing connects this container to another container's plaintext. **No plaintext path was found.**

Two things keep that from being unconditional:

1. **MEDIUM — unauthenticated `/debug/pprof/*`**, always on, on the same port as `/metrics`, exposing heap and cmdline of a root, `SYS_ADMIN` process to any in-CVM peer. Not a content leak; a privileged debug surface that authentication (`--web-config-file`) is available to close and does not.
2. **The source→bytes link is still open.** The digest pins *which* bytes run — a genuine upgrade over the tag page — and the attached provenance even names a build commit, but that commit is in NVIDIA's internal GitLab. Behavior described here is read from the public `4.5.2-4.8.1` tree, which no one outside NVIDIA can prove is what was compiled. `reproducible: false`.

**Untraced, explicitly:** the shipped binary itself (not decompiled, not diffed against upstream); the proprietary DCGM/NVML libraries it links, which are closed source and where the actual GPU reads happen; the nvidia container runtime's device injection and the seccomp/AppArmor profile in force, both of which bound what `SYS_ADMIN` reaches; and what the otel/datadog pipelines do with the scraped counters downstream (separate pages).
