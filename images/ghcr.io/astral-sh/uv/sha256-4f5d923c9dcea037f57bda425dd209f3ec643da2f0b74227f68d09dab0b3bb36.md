## Scope

This image is a Python runtime. It has no serving role, decrypts nothing, and sees a request only if the script it runs asks for one. The page therefore reviews the **one in-scope deployment** — the bench recipe's `hicache-host-exporter` — in the terms the [README's scope rule](/README.md) uses for containers that are in scope *by capability*: privileged mounts that give process-memory or log-stream access. Nothing here is a statement about uv or about CPython.

## Process-access analysis: what the container COULD read

The brief's question: with the host PID namespace and the guest root read-only, can this process read the **engine's** memory or request content? Taken file by file. The engines in question are the serving recipe's four sglang replicas and its terminator, all root (no `user:` on the engine blocks per their pages; the sglang image sets no `USER`; the proxy anchor is `user: root`), all dumpable by default, all on the same guest kernel.

| surface | needs | here | readable? |
|---|---|---|---|
| `/proc/<pid>/cmdline`, `status`, `stat`, `cgroup` | world-readable | — | **yes** (the script reads three of them) |
| `/proc/<pid>/environ`, `maps`, `fd/*` links, `stack` | `PTRACE_MODE_READ` on the target | same uid 0, target dumpable, no LSM | **yes** |
| **`/proc/<pid>/mem`** | `PTRACE_MODE_ATTACH` on the target | same uid 0, target dumpable, no LSM | **yes** — see the rule |
| `/hostfs/dev/shm/*` (the `ipc: host` segment the engines and proxy share) | DAC: root | root, `ro` mount | **yes** (read) |
| `/hostfs/var/lib/docker/containers/<id>/<id>-json.log` (every container's stdout/stderr) | DAC: root | root, `ro` mount | **yes** |
| `/hostfs/var/lib/docker/volumes/*/_data` (the serving recipe's `kernel_cache`, `huggingface_cache`, the collectors' persisted queues) | DAC: root | root, `ro` mount | **yes** |
| writes anywhere under `/hostfs` | — | `ro` | **no** |
| docker API: `GET /containers/<id>/json` (includes `Config.Env` — tokens), `/containers/<id>/logs`, `/containers/<id>/archive`, **`POST /containers/<id>/exec`** | connect to the socket | root; the socket file's `:ro` is a mount flag on the bind, which does not govern `connect()` or the bytes written to a connected unix socket | **yes** — the full API of the guest's daemon |

**The rule for `mem` and `environ`.** The kernel grants `/proc/<pid>/environ` (`PTRACE_MODE_READ`) and `/proc/<pid>/mem` (`PTRACE_MODE_ATTACH`) through `ptrace_may_access`: the caller passes if its uid, euid, suid and the gid triple **equal the target's** *or* it holds `CAP_SYS_PTRACE` in the target's user namespace; then the target must be dumpable (or, again, the caller must hold `CAP_SYS_PTRACE`); then the LSMs are asked. Docker's dropping of `CAP_SYS_PTRACE` therefore matters only when the uids differ or the target is non-dumpable. Here the caller is uid 0 and so are the engines; nothing in the recipes or images clears their dumpable flag; and the [guest-OS page](/os/sha256-91fd5d69ccee3e5ea4f2aeb8c9b632c4358c4ecfc29ba1aa6fb1e402af209829.md) finds `CONFIG_SECURITY` unset — no Yama `ptrace_scope`, no AppArmor, no SELinux — so the third gate is absent. **The read-only bind mount stops writes, not reads, and the socket's read-only flag stops neither a `connect()` nor a `POST`.** What the exporter can read of a serving engine is therefore the engine's whole address space — which on this tier holds up to 325 GiB of finished conversations' KV in the HiCache host tier per replica (the serving recipe's page) — plus its environment (`HF_TOKEN`, `PROXY_TOKEN`-class secrets) and open files. It reads none of it. Two things would break the argument, both untraced: a daemon-level user-namespace remap on the guest (then uid 0 in the container is an unprivileged host uid and `CAP_SYS_PTRACE` would be required), or an engine that clears its dumpable flag.

**What would turn capability into a sink.** A changed script — a different `file_sha256`, a new attestation entry and a new page — or an actor already executing inside the container. The script's own attack surface is one HTTP handler that compares the path for equality and nothing else; no body is read, no header is used, no input reaches a file name or a shell. A Python-level bug in `http.server` is the residual (not traced).

## Verdict

**QUALIFIED PASS** — **Can the exporter read a user's plaintext or send it anywhere?** As written, no: it reads four kinds of `/proc` metadata and two container inspects, serves counters to the bridge, makes no outbound connection and logs nothing. **What qualifies it** is that the container is built with the three things that together make reading possible — root, the host PID namespace, the guest root — plus a docker socket whose `:ro` flag is cosmetic for a socket; on a guest with no LSM those are enough to read a same-uid engine's memory and environment, every container's log and the shared `/dev/shm`, and to exec anywhere, with no attestation-visible change under the reading in which the container still exists. The code does not do it; the attested bytes would have to change for it to; and whether the container is there at all is a fact the signed log withholds. Not PRIVATE, because the capability is deployed if the container is; not LEAKS, because no byte of the script touches content; not INCONCLUSIVE, because identity is re-fetched and equal, the block and script are verified line by line in both revisions, and the capability analysis is stated with its untraced premises named. **What would change the class:** to LEAKS — evidence of a changed script, an exec through the socket, or a userns-free guest where the engine's `mem` is read by this container; toward PRIVATE — a recorded `down`, or a reader without `pid: host`, the root mount and the socket.
