### INFO (deployed: ON) — on every boot the guest now calls the host's UpdateSealedEnv RPC before any container starts: an empty payload when the operator env is current, otherwise the operator env re-encrypted to a KMS-derived key; never message content (egress)

**New in this delta, and the only new data flow out of the guest.** `Stage1::setup` begins with `unseal_env_vars` (`dstack-util/src/system_setup.rs:1723-1724`), which decrypts the host-supplied env and then, unconditionally, closes the host's "env update window":
```
        close_env_window(
            || self.vmm.update_sealed_env(sealed.clone()),
            &ENV_WINDOW_RETRY_DELAYS,
        )
        .await?;
```
(`:1715-1719`). `update_sealed_env` (`dstack-util/src/host_api.rs:86-104`) posts `SealedEnv { sealed_env }` to the host API named by `host_api_url` in the host-supplied sys-config (`system_setup.rs:1023-1028`; the vsock channel `notify-host` already used), with a 30 s timeout (`host_api.rs:19`); `close_env_window` retries after 1, 2, 4 and 8 s and then **fails the boot** if the host never confirms (`system_setup.rs:1805-1829`); no `host_api_url` means no call (`host_api.rs:38-43`, `:90-92`). What is in the payload, by path through `decrypt_env` (`:1605-1675`): (a) no env at all - empty (`:1699-1702`); (b) legacy `.encrypted-env` that opens with the current `env_crypt_key` - empty (`:1651`); (c) `.sealed-env` at the current epochs - empty (`:1643`); (d) an env that only opens with keys of an **older** KMS epoch - the decrypted env, re-sealed with HPKE to the X25519 public key of the current `sealed_env_key`, with the epochs bound into the HPKE `info` (`sealed_env.rs:21-46`). So the host receives either nothing or a ciphertext of the **operator's** environment variables (the 18 `allowed_envs` values: tokens, hostnames) that only a holder of this app's KMS-released key can open - the same secret the host already stores encrypted and supplied in the first place. No request, response, container log or memory content can reach this call: its only input is the env file. With a KMS that has no epochs (the 0.5.x KMS in this tree returns `root_epoch: 0` and an empty `sealed_env_key`, `kms/src/main_service.rs:338-340`) only cases (a)-(c) are reachable, because a re-seal with an empty key fails (`sealed_env.rs:31`) and stops the boot. Which case the two hosts are in depends on the deployed KMS and VMM (Not traced); in every case the content class is the same. The purpose is integrity: the window lets the guest hand the host a migrated env once per boot, and closing it before application code runs stops that code from replacing the env the next boot reads.

### INFO (deployed: ON) — everything durable sits on a LUKS2 volume keyed by the KMS; the header validator now admits a second keyslot and one dstack-kms token so the disk key can be migrated across KMS key epochs (disk)

### INFO (deployed: ON, measured) — the firmware now rewrites the boot-loader-owned fields of the kernel setup header before measuring, and the image ships the kernel with the same values; RTMR1 stops depending on the host's QEMU version and the measured bytes are still the loaded bytes (structural)

**New in this delta; the second priority question.** Background from the patch: QEMU acts as boot loader for `-kernel` and, before 10.2, filled in a handful of setup-header fields before serving the kernel over fw_cfg; OVMF measures the served bytes into RTMR1; QEMU 10.2 stopped doing that for confidential guests, so the same kernel measured differently per host QEMU version and a verifier had to take the host's word for that version. The change has two halves. (1) **Firmware:** `NormalizeLinuxSetupHeader`, called from `QemuKernelFetchBlob` only for the blob named `kernel`, on the buffer that is then published as the virtual kernel file (the patch's last hunk), writes `type_of_loader = 0xB0`, sets `CAN_USE_HEAP` in `loadflags`, `heap_end_ptr = 0xFE00` (zero-extended over the two `ext_loader` bytes), `cmd_line_ptr = 0x20000`, and - when fw_cfg reports a non-zero initrd size - `ramdisk_size` and a `ramdisk_image` address computed from that size and fixed constants. It returns without writing for a blob without the `HdrS` magic, a boot protocol older than 2.02, or a kernel not flagged loaded-high; with no initrd it leaves the two ramdisk fields as served. (2) **Image build:** `mkimage.sh:71-72` writes the same values into the shipped `bzImage` before it is hashed. **Checked against the shipped bytes:** the shipped kernel has `type_of_loader b0`, `loadflags 81`, `heap_end_ptr fe00`, `cmd_line_ptr 00020000`, `ramdisk_size 0076fe5f` (= 7,798,367, the shipped initramfs size) and `ramdisk_image 7f868000`, which is what the patch's arithmetic gives for that size (`xloadflags 006b` has the above-4G bit, so the ceiling is `0x80000000 - 0x28000 - 1`); the v0.5.12 kernel has zeros there. **What this changes about what is bound:** `os_image_hash` still covers the four files by the same rule; the kernel term is now the normalized file, which makes it a function of the initramfs size as well. RTMR1's kernel measurement covered, before, whatever header bytes the host's QEMU produced; now six fields are fixed by the measured firmware before measurement. The host loses the ability to vary those fields and, with it, the verifier loses a host-declared input - a strengthening. No measured-versus-executed gap opens in the source as read: the function edits in place the one buffer that is both measured and loaded, and the only host-supplied input to the values is the initrd size, while the initrd content is measured on its own. On the paths where it declines to write, the header is measured as served - the previous behaviour. That the EFI-stub boot path ignores these fields (so their values cannot redirect the initrd or the command line) is the patch's statement and the Linux boot protocol's; it was not verified against the kernel source, and the firmware binary was not disassembled (Not traced). No effect on any plaintext path.

### Verdict: QUALIFIED PASS at measured configuration

At the measured configuration the upstream 0.5.15 production guest has **no active plaintext sink** on the two DeepSeek hosts. The facilities the v0.5.12 page cleared are cleared again here, this time by a file-by-file comparison of the two shipped root filesystems and initramfs archives: outside the two dstack binaries, the kernel image and three version strings, the image is the reviewed one - no login, getty, ssh, capture or debug tooling; no telemetry or log shipper; a RAM-only journal; container stdout under `json-file` on a KMS-keyed LUKS2/ZFS disk; the host-shared channel read-only, `nosuid,nodev,noexec` and byte-bounded; secrets on tmpfs and owner-only; the container-log route unregistered by `public_logs: false`; no gateway. The source delta of the two binaries adds no listener, no route, no content-bearing log line and no new place where container output is stored. What it does add is key-management machinery: KMS key epochs for the data disk and the env, a sealed env format, a launch ticket, and one new call to the host on every boot whose payload is empty or an encrypted copy of the operator's own env. The firmware change fixes host-variable kernel header fields before they are measured. Every host- or operator-flippable switch that changes guest behaviour still lands inside a measurement.

**Why not PRIVATE:** the same three reasons as v0.5.12, each re-verified at these bytes: (1) an **armed crash path** - `CONFIG_COREDUMP=y`, no handler, unlimited core rlimit from both runtime units, default `core_pattern` - persists a crashing engine's memory to the in-enclave data disk with no flip and no attestation trace; encrypted at rest and off the network, but a plaintext copy on disk that in-guest root can read; (2) the kernel ships **no LSM** (`CONFIG_SECURITY` unset), so the substrate offers the measured scripts and the control plane `/proc/kcore`, kprobes/uprobes/BPF and unsigned modules with nothing but uid checks in the way; (3) the prod image carries `curl`, `rsync`, `python3`, busybox `nc`/`telnet`/`wget` - exfiltration primitives whose only gate is the measurement of the scripts that could call them.

**Residuals (outside this image or unverified):** reproducibility is designed for but was not exercised, and the kernel text changed without a recipe change (above); the application keys bind the `app_id` and the KMS, not the compose hash, so a key match is not a code match; the Linux kernel, poky/meta-oe/meta-virtualization sources, sysbox, EDK2, the NVIDIA blobs and the newly pulled crates were not line-audited; the KMS and VMM that these two hosts actually talk to are host-side and their versions are unknown here; the host serial console and logfile remain a standing host-readable channel for service logs.
