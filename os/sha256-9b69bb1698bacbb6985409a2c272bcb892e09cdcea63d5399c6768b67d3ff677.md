# dstack guest OS (private-ml-sdk v0.5.5) — Privacy Audit

> Part of the near.ai inference-path privacy audit. Method: [/notes/method.md](/notes/method.md) · Index: [README.md](README.md)

**Image:** `dstack-nvidia-0.5.5.tar.gz` release asset (sha256 `48e22657c996…`, GitHub release v0.5.5), containing `ovmf.fd`, `bzImage`, `initramfs.cpio.gz`, `rootfs.img.verity`, `metadata.json`.
**Source:** `nearai/private-ml-sdk` @ `25c25025c556` = Yocto layers (`meta-dstack`, `meta-nvidia`, `mk.d`, repro tooling) + pinned submodules: `Dstack-TEE/dstack` @ `7bf1843a8ddf` (guest-agent, dstack-util — upstream dstack), `meta-confidential-compute` @ `6d1355e0`, `meta-virtualization` @ `bce9962c`, `meta-security` @ `bc63d957`, `meta-openembedded` @ `72018ca1`, `meta-rust-bin` @ `53974894`, `poky` @ `cd44e6bd`.
**Role:** tier-1 — the guest kernel + rootfs under every model-node container. Sees all plaintext by construction.
**Verdict:** **PRIVATE at measured configuration** — no active logging/persistence/egress path for plaintext; every host-flippable switch found is inside the measurement.

## Audit prompt

```text
Defensive privacy audit of a confidential-VM guest OS image (authorized). The OS is
tier-1: it CAN observe all container memory/traffic. Determine whether the BUILD
itself logs, persists, or egresses plaintext, or ships anything (debug daemon,
packet capture, telemetry, host channel) that could copy container memory/traffic
off-box.

TARGET: github.com/nearai/private-ml-sdk @ v0.5.5 (25c2502), submodules pinned.
Also the release assets: derive the published os_image_hash from the release
tarball's own contents and state the derivation rule; assess reproducibility.

LOOK FOR (cite file:line + quote):
1. Observation/export surfaces: serial/debug consoles, login/getty/ssh, kdump/
   coredump to persistent store, ptrace/perf/tcpdump in the image, host-shared
   writable mounts, prod-vs-dev image deltas.
2. Logging/telemetry in the image: journald config + forwarding, log shippers,
   any agent; where container stdout goes and whether any of it leaves the box.
3. dstack guest components (init, dstack-util, guest-agent, mesh): do any handle
   request bytes; enumerate every RPC surface and outbound destination; any
   debug/dump path.
4. Reproducibility & measurement: what exactly the os_image_hash covers, how the

5. Post-attestation flips: everything the host/operator supplies UNMEASURED
   (host-shared files, env, cmdline, sys-config) — cross-reference what is
   measured (RTMR0-3, compose-hash, event log).

RULES: distinguish "CAN see plaintext (structural)" from "LOGS/PERSISTS/
EXFILTRATES (finding)"; cite file:line; report untraced areas; INCONCLUSIVE is
acceptable per part.
OUTPUT: hash derivation; deployed guest config; traced vs not; findings tagged
CRITICAL/HIGH/MEDIUM/INFO; controls-that-change-verdict table; verdict; residuals.
```

## Results

### os_image_hash — derived and verified

The measurement rule is in `meta-dstack-nvidia/mkimage.sh:90-91`:
```
sha256sum ovmf.fd bzImage initramfs.cpio.gz metadata.json > sha256sum.txt
sha256sum sha256sum.txt | awk '{print $1}' > digest.txt
```
i.e. **os_image_hash = sha256(sha256sum.txt)** over firmware, kernel, initramfs, and `metadata.json`. The 445 MB rootfs is not hashed directly but **bound transitively**: `mkimage.sh:72` embeds `dstack.rootfs_hash=$ROOT_HASH` (the dm-verity root hash) into the kernel cmdline inside `metadata.json`, and the initramfs enforces it at boot (`meta-dstack/recipes-core/images/dstack-initscript/init:39`: `veritysetup open ${ROOT_DEV} rootfs ${ROOT_DEV} "${ROOT_HASH}"`). I recomputed all four file hashes from the downloaded asset (asset sha256 `48e22657c996…` matched GitHub's digest), reproduced `sha256sum.txt` byte-for-byte, and got **`9b69bb1698bacbb6985409a2c272bcb892e09cdcea63d5399c6768b67d3ff677`** — equal to the shipped `digest.txt` and to `os_image_hash` in live model-node attestation (fetched 2026-07-22, fresh nonce). `metadata.json` confirms `"is_dev": false`, `"git_revision": "25c2502…"`.

**Deployed guest-OS configuration** (from the measured app-compose in live attestation): `public_logs=false`, `public_sysinfo=true`, `kms_enabled=true`, `gateway_enabled=true`, `runner=docker-compose`; `pre_launch_script` is 94 chars (`export ENCRYPTION_KEY=$(cat /dstack/.host-shared/.appkeys.json | jq -r .k256_key)` — in-guest only). RTMR3 event log: `system-preparing, app-id, compose-hash, instance-id, boot-mr-done, mr-kms, os-image-hash, key-provider, storage-fs, system-ready`.

**Traced:** all image recipes (`dstack-rootfs-{base,prod,dev,nvidia}.inc`, `dstack-nvidia-rootfs.bb`, `dstack-initramfs.bb`), initramfs `init`, kernel config fragments (`dstack.cfg`, `dstack-tdx.cfg`), distro conf, all bbappends (systemd, busybox, docker-moby, base-files), every shipped unit/config in `dstack/basefiles/` (journald, docker daemon.json, 4 services), `dstack-util/src/system_setup.rs` (1427 lines: host-shared handling, RTMR3 extension, LUKS, swap, env decryption, gateway/WireGuard), `dstack-util/src/host_api.rs`, guest-agent (`main.rs`, `config.rs`, `http_routes.rs`, `rpc_service.rs`) + full `guest_api.proto`, repro tooling (`repro-build.sh`, `check.sh`, `Dockerfile.repro`, release `reproduce.sh`). **Not traced (explicit):** Linux kernel source (linux-yocto-dev 6.9, "tiny" type — only the config fragments reviewed); poky/meta-openembedded/meta-virtualization recipe *sources* (docker/containerd audited at config level only); OVMF (`dstack-ovmf`, reproducibility patches seen by name only); **NVIDIA proprietary driver + userspace 570.172.08** (sha256-pinned blob, `nvidia_570.172.08.bb:11`, unauditable); chrony/wireguard-tools/busybox upstream source; the KMS/gateway/VMM host-side counterparts (separate components); the deep internals of `validate_luks2_headers`. The rootfs *binary* was not diffed against a rebuild.

### INFO (structural) — the guest kernel can see everything; that is its role
Tier-1 context, not a finding. The question below is what the build *does* with that access.

### INFO — Production image ships no login, no shell, no capture tools; those are dev-image-only
Prod is `dstack-rootfs-prod.inc:2` (`IMAGE_FEATURES += "nologin"`): `disable_login()` (`dstack-rootfs-base.inc:87-135`) deletes every getty including `serial-getty` (`:92`), `agetty`, `/usr/bin/login`, and `debug-shell.service` (`:112`), and blanks `/etc/securetty`. The dev variant alone adds `packagegroup-core-ssh-openssh strace tcpdump gdb gdbserver vim` + `debug-tweaks` (`dstack-rootfs-dev.inc:3-4`) — a sweep of the prod recipe chain found none of these. Because `metadata.json` (with `is_dev` and a different rootfs hash) is inside the digest, the dev image **cannot** present the measured `9b69bb…` hash. The initramfs has **no failure shell**: `init:2` `set -e` + cmdline `panic=1` — verity mismatch = kernel panic, not a prompt; the initramfs even strips the guest-agent binary (`dstack-initramfs.bb`, `postprocess_initramfs`). No kdump/crashkernel in the measured cmdline; no systemd-coredump in `IMAGE_INSTALL`.

### INFO — No telemetry agent, no log shipper, no analytics in the image; journald is RAM-capped and local
`IMAGE_INSTALL` (`dstack-rootfs-base.inc:6-36`) is: base-utils, systemd, iptables, docker, dstack-guest, wireguard-tools, cryptsetup, curl, jq, chrony, zfs, fs tools — nothing that ships logs off-box. `busybox-syslog` is in `BAD_RECOMMENDATIONS` (`dstack.conf:26`). Journald override (`basefiles/journald.conf`): size caps + `ReadKMsg=no` (`:7`); rootfs is read-only squashfs (`dstack-rootfs-base.inc:54`) so the journal lives in volatile `/run` — RAM-only, no forwarding configured.

### INFO — Host-visible serial console carries guest *service* logs, never container stdout
All four dstack units set `StandardOutput=journal+console` (e.g. `basefiles/app-compose.service:13`) and the measured cmdline sets `console=ttyS0` — so boot progress, `docker compose up` status, wg-checker, and guest-agent messages (`RUST_LOG=warn`, fixed in the measured unit file) are readable by the host operator. This is a designed host channel, but it carries **operational text only**: container stdout/stderr is captured by dockerd (json-file), not the console, and no unit on this path handles request bytes. `dstack-util notify-host` similarly sends only event strings (`"boot.progress"`, instance-info JSON) to the host vsock API (`host_api.rs:55-63`).

### INFO (deployed: OFF, and measured) — guest-agent has a container-log egress route, disabled by the measured manifest
`guest-agent/src/http_routes.rs:22-23`: `if config.app_compose.public_logs { routes.extend(routes![get_logs]); }` — `/logs/<container_name>` (`:101`) would stream docker logs on the **external** interface (`dstack.toml`: `[external] address = "0.0.0.0", port = 8090`). The live model-node manifest sets `public_logs=false`, so the route is **not registered**; flipping it changes the app-compose, hence `compose-hash` in RTMR3 — attestation-visible. `public_sysinfo=true` exposes only the dashboard + `/metrics` (CPU/mem/disk/net counters; `guest_api.proto` `SystemInfo` is content-free). The host-facing vsock guest API is metadata-only: `Info, SysInfo, NetworkInfo, ListContainers, Shutdown` (`guest_api.proto:124-130`) — **no log-fetch, no exec, no memory access**.

### INFO — Everything durable sits on a LUKS2 disk keyed by the KMS; secrets stay in RAM
Container stdout persists via `json-file` (100 MB × 10 per container, `docker-daemon.json:2-5`) under `/var/lib/docker`, which is rbind-mounted from the data disk (`dstack-prepare.sh:45`) — created as LUKS2 `aes-xts-plain64` (`system_setup.rs:895-898`) with `disk_crypt_key` from the KMS (released only after quote verification), ZFS on top of the mapper device; swap (file or zvol) also lives on that encrypted device (`system_setup.rs:698-767`). So even if an app container logged plaintext, it would persist only encrypted-at-rest, on-box. The LUKS header is copied to tmpfs and validated before open (`system_setup.rs:908-947`, cipher pinned `:1326,1382`) against host tampering. Decrypted env (`.decrypted-env`) and `.appkeys.json` are written under `/var/volatile/dstack` — tmpfs, RAM-only. Host-shared 9p is mounted **read-only** and copied before use (`system_setup.rs:262`: `mount -t 9p -o trans=virtio,version=9p2000.L,ro …`).

### INFO — Egress inventory of the OS itself: five destinations, none carries content
(1) KMS over RA-TLS — server cert usage pinned to `kms:rpc` and the KMS's own measurement extended as `mr-kms` into RTMR3 (`system_setup.rs:587,604`), so a host-substituted KMS is attestation-visible; (2) dstack-gateway registration over RA-TLS with the gateway's app-id validated against the KMS-issued `gateway_app_id` (`system_setup.rs:298-311,489-514`), then WireGuard with an iptables chain that **drops all UDP not from the registered gateway endpoints**; (3) PCCS (quote collateral, URL host-supplied — metadata only); (4) chrony NTP; (5) docker registry pulls. A URL sweep of guest-agent + dstack-util found no other outbound destination; no analytics/error-reporting SDK exists in the image.

### INFO — Post-attestation flip surface is fully cross-referenced to the measurement
Host-supplied and **unmeasured**: `.sys-config.json` (kms/gateway/pccs/registry URLs, host_api) — each covered above by RA-TLS + RTMR3 cross-checks; encrypted env **values** — but names are filtered against the measured manifest's `allowed_envs` (`system_setup.rs:1087,1109-1120`) and the deployed list (22 names, all app-level: `DD_API_KEY`, `HF token`, AWS, etc.) contains **no guest-OS debug/log switch**; the guest OS has no env-activated content logging at all. Kernel cmdline knob `dstack.storage_encrypted=0` would disable disk encryption (`system_setup.rs:134,797`) — but the cmdline is part of the OVMF-measured boot (RTMR1/2) and of `metadata.json` inside the digest, so a flip breaks the measurement; `storage-fs` is additionally extended into RTMR3 (`system_setup.rs:1037`). `pre_launch_script`/`init_script` run arbitrary root bash **but are inside the measured app-compose**. Kernel config enables BPF/kprobes (`dstack.cfg`) — an in-guest-root observation capability, reachable only through those measured scripts.

### Reproducibility — designed for it; not exercised by this audit
The release is built in a pinned container (`Dockerfile.repro`: `ubuntu:24.04@sha256:3afff29d…` — though `apt install` inside is unpinned, so long-term repro can rot), with all eight source repos commit-pinned, `DM_VERITY_REPRODUCIBLE = "1"`, and a harness that **builds twice and diffs the rootfs** (`repro-build.sh` build-a/build-b + `check.sh`). The release publishes `reproduce.sh` (uploaded 2025-12-11, ~7 weeks post-release; includes a runc `git describe --abbrev=8` determinism patch — evidence a nondeterminism was found and fixed after the fact). **I did not run the multi-hour Yocto rebuild**, so bit-for-bit reproducibility is *verified-by-design, unexercised here*; the assets carry no Sigstore/SLSA attestation. What this audit did verify: the published hash is honestly derived from the shipped bytes, the derivation rule is in the repo, the shipped `git_revision` matches the tag, and the live fleet boots exactly this measurement.

### Controls that would change the verdict

| Control | Effect if flipped | Attestation-visible? |
|---|---|---|
| Deploy the dev image (ssh, tcpdump, strace, debug-tweaks) | Full interactive/capture access | **Yes** — different `os_image_hash` (dev `metadata.json`/rootfs differ) |
| `public_logs: true` in app-compose | Container logs streamed off-box via gateway | **Yes** — `compose-hash` in RTMR3 changes |
| `dstack.storage_encrypted=0` on cmdline | Plaintext-capable container logs persist unencrypted | **Yes** — cmdline measured (RTMR1/2 + digest) |
| Extra kernel cmdline args (debug shell, crashkernel) | Debug surface | **Yes** — cmdline measured |
| Env-var injection outside `allowed_envs` | — | Blocked in code (`parse_env` filter, names measured) |
| Rogue KMS / gateway URLs in sys-config | Key or mesh redirection | KMS: **yes** (`mr-kms` RTMR3); gateway: app-id pinned to KMS-issued value (unverifiable residual if that value were `"any"`) |

### Verdict: PRIVATE at measured configuration
The v0.5.5 production guest image ships **no plaintext sink**: no login/serial shell/ssh/capture tooling (dev-only, different hash), no telemetry or log-shipping agent, journald RAM-capped and local, container stdout confined to a KMS-keyed LUKS2 disk, secrets on tmpfs, dm-verity read-only rootfs with panic-on-failure, and an egress set limited to KMS/gateway/PCCS/NTP/registry with the content-capable path (container `/logs`) compiled in but disabled by the measured manifest. Every operator-flippable switch found lands inside the measurement (image digest, cmdline RTMRs, or compose-hash in RTMR3).

**Residuals (why not unconditional):** (1) **reproducibility asserted, not exercised** — I re-derived the hash from the shipped bytes but did not rebuild; until someone runs `reproduce.sh` to the same digest, source↔binary correspondence rests on the (deterministic-by-design) build, not on independent verification; (2) **kernel + upstream layer source untraced** — config fragments and recipes only; a backdoored pinned submodule would evade this review (commits are upstream-public, lowering but not eliminating risk); (3) **NVIDIA proprietary blobs** (driver 570.172.08, fabricmanager, container toolkit) run inside the enclave sha256-pinned but unauditable; (4) the **host serial console** is a standing host-readable channel for guest service logs — content-free today, but any future unit that echoed request data would leak silently through it; (5) `gateway_app_id == "any"` would disable gateway authentication — the deployed value is KMS-issued and was not verifiable here; (6) OVMF and the RTMR0-2 computation (`dstack-mr`) were not re-derived — the binding of `os_image_hash` to the actually-booted kernel/cmdline is inherited from the dstack measurement design, not re-proven in this audit.
