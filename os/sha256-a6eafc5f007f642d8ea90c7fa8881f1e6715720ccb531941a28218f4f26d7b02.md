### Repo switch, not a version bump - who built this, and what near.ai's build is not

near.ai's [`nearai/private-ml-sdk`](https://github.com/nearai/private-ml-sdk) is **not a GitHub fork** of `Dstack-TEE/meta-dstack` (the API reports `fork: false`, no parent); it is a separate repository (`meta-dstack-nvidia/`, `sync-upstream.sh`, `vllm-proxy/`, `e2e/`) that vendored the dstack Yocto layers and whose last push is **2025-10-20** - the v0.5.5 era. The image on this host is the **upstream project's own release**, built and published by Dstack-TEE (Phala) from `meta-dstack@ce04e924` with `dstack@40eaf35e` (740 commits past the `7bf1843a8ddf` submodule the v0.5.5 page audited). Consequences for trust:

- **Builder.** The bytes were produced by the upstream maintainers' release pipeline (the release notes cite PR #62, "CI: restrict manual guest releases to protected default branch"), not by near.ai's. Whatever review near.ai applied to its own v0.5.5 build does not transfer; what does transfer is that the digest is derived from the shipped bytes by a rule in the repo, and that anyone can attempt the rebuild.
- **Reproducibility claim.** `repro-build/repro-build.sh:54-62` builds twice in a pinned container (`Dockerfile.repro:1`: `ubuntu:24.04@sha256:3afff29d...`) and diffs the rootfs (`check.sh`); `:71-80` emits `reproduce.sh`. The **published** `reproduce.sh` (224 bytes, release asset) checks out `ce04e924` (`:6`), initializes submodules (`:7`) and runs `./repro-build.sh -n` (`:8`) - `-n` is "Don't check reproducibility" (`repro-build.sh:5, :12-14`), i.e. a single build whose digest the reader compares to the release by hand. `Dockerfile.repro:14-29` `apt install`s unpinned packages, so long-term reproducibility can rot; `DM_VERITY_REPRODUCIBLE = "1"` (`dstack-rootfs-base.inc:85`) and the runc `git describe --abbrev=8` determinism fix carried in the `meta-virtualization` submodule (its one commit past the v0.5.5 pin, `52cd8a29`) show the project chases nondeterminism. **I did not run the rebuild.** Source-to-binary correspondence rests on the deterministic-by-design build, not on independent verification.
- **near.ai fork-specific changes are absent.** Whatever near.ai's `meta-dstack-nvidia/` layer changed relative to upstream at v0.5.5 is not in this image; this page did not enumerate those changes (Not traced). Everything below is upstream behaviour.
- **What the switch changed in the guest, materially** (from the local diff of the pinned submodules): the **sysbox** container runtime is now installed and its two root daemons run at boot (new); `nftables` is installed beside `iptables`; the host-shared channel can arrive as a labelled read-only disk as well as 9p; the guest-agent's Unix sockets are systemd socket-activated with mode 0777 and moved under `/var/run/dstack/`; new signing/attestation RPCs (`Sign`, `Verify`, `Attest`, `GetAttestationForAppKey`); the data disk is now a GPT partition labelled `dstack-data` with a cmdline override `dstack.data_device`; the NVIDIA stack moved 570.172.08 -> **595.58.03**; `disable_login` now also strips `systemd-logind`, `loginctl` and polkit; the kernel fragment disables ESP/RxRPC (DirtyFrag mitigations). None of these adds a plaintext sink; the two that add in-guest surface (sysbox, 0777 sockets) are assessed below.

### INFO (deployed: OFF, measured) — gateway_enabled: false removes the WireGuard tunnel and its iptables chain together; nothing on the guest listens for a gateway (egress)

What the dstack gateway is: a host-side reverse proxy that terminates public TLS and forwards into CVMs over WireGuard. With it **on**, the guest registers over RA-TLS with each `sys_config.gateway_urls` entry, validates the gateway's app-id against the KMS-issued `gateway_app_id` (`system_setup.rs:588-590`, validator `:759`), renders the WireGuard config (`:627-642`) and writes `/etc/wireguard/dstack-wg0.conf` (`:660-662`), installs an `INPUT` jump to a `DSTACK_WG` chain that accepts UDP 9182 only from the registered endpoints and **drops everything else** (`:670-692`), and brings the interface up (`:695`). With it **off** - this host - `GatewayContext::setup` returns at the first line:
```
    async fn setup(&self, force: bool) -> Result<()> {
        if !self.shared.app_compose.gateway_enabled() {
            info!("dstack-gateway is not enabled");
            return Ok(());
        }
```
(`system_setup.rs:583-587`). So: no WireGuard key generation, no registration egress, no `dstack-wg0` interface, no UDP listener, and **no `DSTACK_WG` chain** - the chain the v0.5.5 page called "a control" only ever filtered the port the tunnel itself opened; removing both is a net **surface reduction**, not a removed control. `wg-checker.service` still runs but idles: `basefiles/wg-checker.sh:79-83` only acts when `/etc/wireguard/dstack-wg0.conf` exists, which it never does here. The manifest page's open questions are answered: (a) the flag disables registration + tunnel + filter as one unit; (b) the WireGuard/iptables posture is "absent", with the guest's `iptables.service`/`ip6tables.service` enabled but carrying only docker's rules; (c) the guest's outbound path is unchanged (KMS, PCCS, NTP, registry, host vsock) and the CVM's **inbound** path is whatever the host maps to it - `hotplug_off: true`, `host_share_mode: 9p` in `vm_config` say nothing about port mapping, which is a VMM property (Not traced); the compose-manager's `8080:8080` is reachable from outside only if the host forwards it. TLS for this node terminates in-enclave on certbot certificates (manifest page), so no gateway is needed for ingress.

### MEDIUM (deployed: ARMED) — a crashing container process writes a core file containing its memory into its container layer on the in-enclave data disk; no core-dump handler, unlimited core rlimit, default core_pattern (disk)

The one plaintext-persistence path this build leaves open, and one the v0.5.5 page did not assess. The recovered kernel config has **`CONFIG_COREDUMP=y`**. The rootfs ships **no** `systemd-coredump`, no `50-coredump.conf`, no `kdump`/`kexec-tools` (grep of the 3,004-entry listing for `coredump|kdump|kexec-tools|crash` returns nothing; `CONFIG_KEXEC`/`CONFIG_KEXEC_FILE`/`CONFIG_CRASH_DUMP` are not set), and **no sysctl sets `kernel.core_pattern`** (the only sysctl files are `etc/sysctl.d/99-dstack.conf`, `99-sysbox-sysctl.conf`, `usr/lib/sysctl.d/50-default.conf`, `50-pid-max.conf`; none mentions `core_pattern`) - so the kernel default `core` applies: a relative path in the crashing process's cwd. Both container-runtime units lift the core limit: `usr/lib/systemd/system/docker.service:32` and `containerd.service:33` are `LimitCORE=infinity` (extracted from the shipped rootfs), and the shipped `/etc/docker/daemon.json` sets no `default-ulimits`, so containers launched without an explicit `ulimits: core` inherit an unlimited soft core limit from the shim. Net effect: a SIGSEGV/SIGABRT in an engine process (a CUDA-library fault is not exotic) makes the kernel write the process image - prompts, KV-cache host copies, everything mapped - as `core` into the container's writable layer under `/var/lib/docker/overlay2/`, which `basefiles/dstack-prepare.sh:271` rbind-mounts from the LUKS2 data disk. Bounds and mitigations, stated precisely: the file stays **in-enclave and encrypted at rest** (below); it is readable by in-guest root - on this host that means the measured scripts, the `pid: host` + `SYS_PTRACE` + `docker.sock` compose-manager, and the collector that mounts `/:/hostfs:ro` (manifest page, Check 4) - and by nothing outside the CVM; docker's `json-file` capture does not see it; a core of a multi-hundred-GB engine also threatens to fill the data disk. **ARMED, not ON:** nothing in the measured OS triggers it, and nothing in the measured OS stops it. Whether the inner recipes on this fleet set `ulimits: core: 0` was not checked here (recipe pages' question). Inheritance of the shim's rlimit into the container relies on documented moby/runc behaviour, not on the pinned moby source (Not traced).

### Verdict: QUALIFIED PASS at measured configuration

At the measured configuration the upstream 0.5.11 production guest has **no active plaintext sink**: the facilities the v0.5.5 page cleared are cleared again here, this time against the shipped bytes - no login, getty, ssh, capture or debug tooling; no telemetry or log shipper; a RAM-only journal; container stdout under `json-file` on a KMS-keyed LUKS2/ZFS disk; the host-shared channel read-only at both ends with secrets on tmpfs; the container-log route unregistered by `public_logs: false`; and `gateway_enabled: false` removing the tunnel, its registration egress and its filter as one unit rather than stripping a control. Every host- or operator-flippable switch that changes guest behaviour lands inside a measurement.

**Why not PRIVATE:** (1) an **armed crash path** - `CONFIG_COREDUMP=y`, no handler, unlimited core rlimit from both runtime units, default `core_pattern` - persists a crashing engine's memory to the in-enclave data disk with no flip and no attestation trace; encrypted at rest and off the network, but a plaintext copy on disk that in-guest root can read; (2) the kernel ships **no LSM** (`CONFIG_SECURITY` unset), so the substrate offers the measured scripts and the ptrace-capable control plane `/proc/kcore`, kprobes/uprobes/BPF and unsigned modules with nothing but uid checks in the way - the OS does not mitigate the manifest layer's HIGH findings, it hosts them; (3) the prod image carries `curl`, `rsync`, `python3`, busybox `nc`/`telnet` - exfiltration primitives whose only gate is the measurement of the scripts that could call them.

**Residuals (outside this image or unverified):** reproducibility is designed for but was not exercised (`reproduce.sh` builds once, with `-n`); the Linux kernel, poky/meta-oe/meta-virtualization sources (docker 25.0.3 at moby `f417435e`), sysbox, EDK2 and the NVIDIA 595.58.03 blobs were not line-audited; the host serial console and logfile remain a standing host-readable channel for service logs; the KMS-issued `gateway_app_id` is moot with the gateway off; the host VMM's `readonly=on` for the 9p share is host code, backstopped by the guest's own `ro` mount.
